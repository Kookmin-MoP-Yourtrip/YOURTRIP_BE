# 이슈 작성 규칙

이 문서는 클로드 코드가 이 저장소에서 이슈를 작성할 때 참고하는 규칙이다. 템플릿은 [.github/ISSUE_TEMPLATE/issue_template.md](../../.github/ISSUE_TEMPLATE/issue_template.md)를 따른다.

## 제목

`<타입>: <작업 요약>` 형식으로 작성한다.

예: `docs: 개발 로드맵 문서 작성`

**타입:**

- `feat`: 새로운 기능
- `fix`: 버그 수정
- `docs`: 문서화
- `style`: 포맷팅
- `refactor`: 코드 리팩토링
- `perf`: 성능 개선
- `test`: 테스트
- `chore`: 빌드/도구
- `ci`: CI 관련 설정 수정에 대한 커밋

실제 템플릿 본문 구조:

```
## 📌 작업 설명
<!-- 작업에 대해 설명해주세요-->

## ☑️ 작업 상세 내용
<!-- 해야 할 일들에 대해 적어주세요 -->
- [ ] 할 일
```

## 전체 원칙: 간결함

이슈는 **길게 쓰지 않는다.** 작업 설명이 장황해지거나 체크리스트가 지나치게 세분화되면 오히려 파악이 어려워진다. 한 화면 안에서 스크롤 없이 훑어볼 수 있는 분량을 기준으로 삼는다. 이 저장소에는 별도의 `docs/PRD.md`, `docs/ROADMAP.md` 같은 설계 문서가 없으므로, 자세한 배경이나 근거가 필요하면 관련 이슈/PR 번호나 Notion 링크(README 참고)로 대체하고 이슈 본문에 풀어 쓰지 않는다.

## 📌 작업 설명

- 이 작업이 왜 필요한지, 무엇을 할 것인지를 1~3문장으로 합쳐서 적는다(배경 + 요약).
- 범위가 여러 갈래면 `-` bullet으로 나열하되, 항목은 3~4개를 넘기지 않는다. 그 이상 나뉘면 이슈를 분리하는 것을 고려한다.

## ☑️ 작업 상세 내용

- 실행 가능한 작업 단위로 체크리스트(`- [ ]`)를 작성한다.
- 항목은 5~7개 이내로 유지한다. 더 잘게 쪼개고 싶은 유혹이 들면, 하나의 이슈가 너무 큰 작업을 담고 있다는 신호이므로 이슈 자체를 분리하는 것을 우선 검토한다.
