# PR 작성 규칙

이 문서는 클로드 코드가 이 저장소에서 PR을 작성할 때 참고하는 규칙이다. 템플릿은 [.github/PULL_REQUEST_TEMPLATE.md](../../.github/PULL_REQUEST_TEMPLATE.md)를 따른다.

## 제목

`<타입>: <작업 요약>` 형식으로 작성한다.

예: `docs: 개발 로드맵 문서 작성`

**타입:**

- `feat`: 새로운 기능
- `fix`: 버그 수정
- `docs`: 문서화
- `style`: 포맷팅
- `refactor`: 코드 리팩토링
- `perf`: 성능 개선
- `test`: 테스트
- `chore`: 빌드/도구
- `ci`: CI 관련 설정 수정에 대한 커밋

실제 템플릿 본문 구조:

```
## ✅ 작업 내용
<!-- 작업에 대한 설명을 적어주세요 -->

## 📌 관련 이슈
<!-- 관련있는 이슈 번호(#000)을 적어주세요.
해당 pull request merge와 함께 이슈를 닫으려면
closed #Issue_number를 적어주세요 -->
```

## ✅ 작업 내용

- 과정이 아니라 **이 PR로 무엇을 할 수 있게 됐는지(결과)** 를 기준으로 작성한다. "~을 구현함", "~을 리팩토링함" 같은 작업 나열이 아니라 "~할 수 있다", "~이 추가됐다" 같은 완료된 기능/능력 관점으로 서술한다.
- 여러 기능이 섞여 있으면 가독성을 위해 `###` 하위 섹션으로 기능 단위로 나눈다. 하위 섹션 제목은 그 기능을 한 줄로 요약한다.
- **하위 섹션 제목은 명사형으로 끝낸다** — `~분리`, `~추가`, `~실측`, `~수정`처럼 명사(주로 동작명사)로 맺고, `~했다`·`~한다`·`~않는다` 같은 서술어 종결은 쓰지 않는다. 제목은 문장이 아니라 목차처럼 훑어보는 대상이라, 서술형이면 불필요하게 길어지고 여러 섹션을 나열했을 때 리듬이 깨진다.
  - `### 부하테스트로 개선 효과 실측` (O) / ~~`### 부하테스트로 개선 효과를 실측했다`~~ (X)
  - `### FK 컬럼 인덱스 추가` (O) / ~~`### FK 컬럼에 인덱스를 추가했다`~~ (X)
- 제목과 달리 **본문 bullet은 서술형을 그대로 쓴다.** 위의 결과 관점 서술("~할 수 있다", "~이 추가됐다")은 bullet에 적용되는 규칙이다.
- 각 하위 섹션 내용이 한두 문장을 넘어가면 개조식 `-` bullet으로 쪼갠다.

예시:

```markdown
## ✅ 작업 내용

### 코스 fork 기능
- 다른 사용자가 업로드한 코스를 내 코스로 fork해서 커스터마이징할 수 있다
- fork한 코스는 원본과 별개로 관리되며, 원본의 좋아요/조회수에는 영향을 주지 않는다

### AI 코스 추천
- 여행 기간·동행 인원·선호 스타일을 입력하면 Gemini가 생성한 추천 코스를 받을 수 있다
```

## 📌 관련 이슈

- `closes #<이슈 번호>` 형식으로 작성해 PR이 머지되면 연결된 이슈가 자동으로 닫히도록 한다(템플릿의 `closed #Issue_number` 표기와 동일하게 동작한다).
- 관련 이슈가 여러 개면 각각 `closes #<번호>`를 줄바꿈으로 나열한다.

## 📚 추가 리팩토링 가능성 (템플릿 외 추가 섹션)

실제 `.github/PULL_REQUEST_TEMPLATE.md`에는 없는 섹션이지만, 작업 중 발견했으나 이번 PR 범위를 벗어나는 개선점(테스트/CI 강화, 코드 품질 자동화, 아키텍처 개선, 성능 개선, 트러블슈팅, 기술적 의사결정 포인트 등)이 있으면 본문 맨 아래에 이 섹션을 추가해 정리한다. 이는 [CLAUDE.md](../../CLAUDE.md)의 "작업 방식 (포트폴리오 저장소 특성)" 중 개선 제안 규칙과 연결된다.
