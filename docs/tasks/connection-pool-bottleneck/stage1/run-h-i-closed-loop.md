# Run H/I — 닫힌 루프로 도입 전/후 포화점 비교

> Run A~G는 전부 열린 루프(도착률 req/s 기준)였다. 열린 루프는 원리상 **"동시 사용자 몇 명까지 버티는가"**를 줄 수 없어, custom policy 도입 전/후를 VU로 비교한 기록이 하나도 없었다. 이 문서가 그 빈칸을 메운다. [run-g-before-code-max-rate.md](run-g-before-code-max-rate.md)와 같은 세션에서 측정했고, 마찬가지로 **새로운 성능 개선이 아니라 비교 신뢰도를 높이기 위한 순수 측정**이다.

## 읽기 전에 — 이 측정 방식 자체의 근본적인 신뢰 한계

닫힌 루프(VU 기반)는 **서버 응답 품질이 나빠질수록 오히려 제공 부하가 늘어나는 구조적 왜곡**을 갖는다. VU는 응답을 받는 즉시 다음 요청을 보내므로, 서버가 일을 덜 하고(예: 서명을 건너뛰고) 빨리 응답할수록 같은 VU에서 더 많은 요청이 오간다 — 처리량이 늘어난 것처럼 보이지만 실제로는 품질이 나빠진 결과다. 이 역설은 Run A 시점에 [detail-arrival-rate.js](../../../../scripts/k6/detail-arrival-rate.js) 헤더 주석이 이미 예측했었고, 이번 Run H(도입 전 코드)에서 처음 실측으로 확인됐다 — VU 100→200 구간에서 TPS가 오히려 +37.8% 올랐는데, 같은 구간 이미지 손실률은 32.5%→85.2%로 뛰었다(판정 4에서 상세히 다룬다).

**그래서 아래 표·판정을 읽을 때 다음을 먼저 전제해야 한다.**

| | 신뢰 가능 | 신뢰 불가 |
|---|---|---|
| Run H (도입 전) | 이미지 손실 0%인 VU 5~50 구간의 TPS·지연, 각 지표가 *처음* 무너지는 VU 단계 | **VU 100 이상 구간의 TPS·지연 절대값** — 브라운아웃으로 부풀려진 수치. 표에는 남기되 개선율 계산에는 쓰지 않는다 |
| Run I (도입 후) | 전 구간(VU 5~400) — fail-closed 구조라 이 왜곡이 없다 | 해당 없음 |

이 원칙 때문에 바로 아래 "전체 집계"의 **"+54.1% 처리량"도 이 오염을 포함한 값**이다 — 판정 1의 무손실 구간 비교(+91.5%)가 실제 개선폭에 더 가깝다. 표를 그대로 인용하지 말고 반드시 이 절을 함께 참고한다. 그 외의 측정 방법론상 한계(1회 측정, 도입 후 상한 미발견 등)는 문서 말미 "한계" 절에 모아뒀다.

## 측정 환경

Run D~G와 동일한 인프라(App EC2 t3.small, RDS db.t3.micro, ElastiCache cache.t3.micro, k6 EC2). 부하만 닫힌 루프 `detail-ramping.js`로 바꿨다.

| | 값 |
|---|---|
| 부하 모델 | 닫힌 루프(`ramping-vus`), VU 1→5→10→20→50→100→200→**400**, 540초 |
| **Run H** | 도입 전 코드(`72f0ed2`), `CLOUDFRONT_SIGNING_PERMITS=100000`(AbortPolicy 단독) |
| **Run I** | 도입 후 코드(현행 HEAD, 코스당 서명 1회) |

두 arm 사이에는 **jar 교체 → 재기동 → 재시딩**만 있었고, k6 스크립트·시드·인스턴스는 완전히 동일하다. 각 arm의 빌드가 실제로 교체됐다는 것은 `/actuator/prometheus`의 `cloudfront_signing_*` 메트릭 유무(도입 전 8종 노출 / 도입 후 0종)와 응답 URL 형식(`?Expires=&Signature=` canned / `?Policy=` 와일드카드)으로 각각 확인했다.

### 측정 도구를 먼저 고쳤다

기존 `detail-ramping.js`의 체크는 `status is 200` 하나뿐이었다. AbortPolicy는 fail-open이라 **이미지가 몇 장 빠지든 무조건 200을 반환**하므로, 그대로 썼다면 Run H의 브라운아웃이 지표에 전혀 잡히지 않았을 것이다(과거 닫힌 루프 라운드의 "성공률 100%"가 사실은 이 사각지대였다는 사후 정정이 [abortpolicy-gate-verification.md](../stage0/production/abortpolicy-gate-verification.md)에 남아 있다). `detail-arrival-rate.js`와 동일한 이미지 완전성 체크(`partial_responses`)를 이식하고, `MAX_VUS` 파라미터(기본 200, 200 초과 시에만 마지막 스테이지 추가)를 넣어 앞 6단계를 보존한 채 400까지 확장했다.

## 판정

**판정 1 — "품질을 지키면서 감당한 최대 처리량"이 197.9 → 379.0 req/s로 약 1.9배가 됐다.** 이게 이 측정에서 가장 정직한 비교 지표다. 두 arm 모두 **이미지 손실 0%인 구간의 최대 TPS**를 비교한 것이라 사과 대 사과다.

- 도입 전: VU 20에서 **197.9 req/s**가 천장. VU 50에서 처리량이 오히려 -1.3%로 꺾이고 지연은 81→215ms로 2.65배가 된다.
- 도입 후: VU 50에서 **379.0 req/s**까지 오르고, 그 지점의 지연이 99ms로 도입 전의 VU 20(81ms)과 비슷한 수준이다.

**판정 2 — "포화 시작 VU"만 단독으로 보면 오히려 도입 후가 더 낮다. 이 지표는 단독으로 쓰면 안 된다.** 처리량 평탄화(VU 2배당 증가율 10% 미만)만으로 판정하면 도입 전은 VU 20→50에서, **도입 후는 VU 10→20에서** 먼저 평탄해진다.

| | 평탄화 시작 | 그때의 TPS |
|---|---|---|
| 도입 전 | VU 20 → 50 | 197.9 |
| 도입 후 | VU 10 → 20 | 377.2 |

**도입 후가 더 일찍 평탄해지는 이유는 나빠서가 아니라 요청 하나를 훨씬 빨리 처리하기 때문이다** — VU 10에서 이미 373 req/s를 내므로 서버를 채우는 데 더 적은 동시 사용자면 충분하다(Little's Law: 같은 서버 용량을 채우는 데 필요한 동시성은 응답이 빠를수록 작아진다). 따라서 **"포화 VU가 몇이냐"를 개선 지표로 쓰면 개선을 퇴보로 읽게 된다.** 판정 1의 "무손실 최대 처리량"이나 아래 판정 3의 "품질을 유지한 최대 동시 사용자"로 말해야 맞다.

**판정 3 — 품질 기준으로 보면 감당 가능한 동시 사용자가 50명 → 400명 이상(측정 상한까지 한계 미도달)이 됐다.**

| | 이미지 손실 0%를 유지한 마지막 VU 단계 |
|---|---|
| 도입 전 | **VU 50** (VU 100부터 32.5% 유실 시작) |
| 도입 후 | **VU 400** (측정 상한 — 한계를 찾지 못함) |

도입 전은 VU 100에서 32.5%, VU 200에서 85.2%, VU 400에서 **96.3%**의 서명이 거부됐다. VU 400 구간에서는 요청당 이미지 10장 중 평균 0.4장만 서명에 성공했다는 뜻이다. 도입 후는 VU 400에서도 `partial_responses` 메트릭이 **한 번도 발생하지 않았다** — "0으로 수렴"이 아니라 그 실패 경로가 코드에 존재하지 않는다.

**판정 4 — 닫힌 루프의 "빠른 거부 역설"이 실측으로 드러났다. 이 때문에 Run H의 고부하 구간 숫자는 비교에 쓸 수 없다.** Run H는 VU 100→200에서 TPS가 **+37.8%(214.1→295.1)** 증가했다. 표면적으로는 "부하를 늘리니 처리량이 늘었다"지만, 같은 구간에서 이미지 손실률이 **32.5% → 85.2%**로 뛰었다. **처리량이 늘어난 게 아니라 일을 안 하고 응답했기 때문에 늘어난 것이다** — 서명을 건너뛴 응답이 빨리 돌아오고, VU는 응답을 받는 즉시 다음 요청을 쏘므로 제공 부하 자체가 부풀려진다.

이는 [detail-arrival-rate.js](../../../../scripts/k6/detail-arrival-rate.js) 헤더 주석이 Run A 시점에 예측했던 역설이 **실제 수치로 확인된 첫 사례**다. 그래서 이 문서는 사전에 정한 대로 다음 원칙을 지킨다.

- **Run H에서 신뢰하는 것** — 손실 0%인 구간(VU 5~50)의 TPS·지연, 그리고 각 지표가 *처음* 무너지는 VU 단계
- **신뢰하지 않는 것** — VU 100 이상 구간의 TPS·지연 절대값. 표에는 남기되 개선율 계산에 쓰지 않는다

전체 집계의 "+54.1% 처리량"도 이 오염을 포함한다(Run H의 209.82 req/s가 브라운아웃 덕에 부풀려진 값이다). **따라서 실제 개선 폭은 +54.1%보다 크다** — 판정 1의 무손실 기준 +91.5%가 더 정확하다.

**판정 5 — HikariCP 평균 점유시간은 도입 후가 오히려 2.4배 높다(5.13ms → 12.38ms). 악화가 아니라 일을 실제로 했다는 증거다.** 도입 전은 서명이 거부된 요청이 DB 조회 뒤 할 일이 줄어 커넥션을 짧게 쓰고 나갔고, 도입 후는 같은 시간에 1.5배 많은 요청을 온전히 처리했다. `pending` 최대값은 오히려 도입 후가 낮다(95 → 72). 다만 **커넥션 풀(10개)이 이제 다음 병목 후보로 올라왔다**는 신호이기도 하다 — VU 20부터 `pending`이 발생하고 `active`가 10(풀 전량)에 붙는다. 이는 TASK 문서 4단계(풀 크기 재검토)와 연결된다.

**판정 6 — CPU의 사용처가 근본적으로 바뀌었다. 이제 최대 소비처는 서명이 아니라 JWT다.**

| | Run H (도입 전) | Run I (도입 후) |
|---|---|---|
| JFR `presign_or_signing` | **77.55%** | **18.38%** |
| JFR `crypto` 전체 | 83.58% | 60.61% |
| 스레드 분포 | cloudfront-signing 77.96% / http-nio 20.58% | http-nio 97.43% |

도입 전은 **CPU 샘플의 78%를 전용 서명 풀이 차지**했다. 그러고도 이미지의 절반을 못 내보냈다(전체 브라운아웃 48.05%). 도입 후 서명 비중은 18.38%로 약 1/4이 됐고, 남은 `crypto` 60.61% 중 서명을 뺀 **약 42%p가 JWT 검증**이다 — [run-d-signature-once.md](run-d-signature-once.md) 판정 4가 지목한 "JWT가 이제 더 큰 CPU 소비처"라는 관찰이 닫힌 루프에서도 재확인됐다. 두 arm 모두 http-nio의 `presign_or_signing`이 CallerRunsPolicy 회귀 없이 정상이었다(Run H 0.00% — 전용 풀에 격리, Run I 18.80% — 격리 인프라를 제거했으므로 설계대로).

## 한계

- 각 arm 1회 측정이다.
- **도입 후의 포화 상한을 찾지 못했다.** VU 400에서도 이미지 손실이 0%였다. 진짜 한계를 보려면 VU를 더 올려야 하는데, k6 EC2(t3.micro)가 부하 생성 쪽 병목이 될 위험이 있어 이번 범위에서는 400에서 멈췄다.
- **VU 단계별 "이미지 손실률"은 k6의 `partial_responses`와 다른 층위의 지표다.** 전자는 서버측 카운터 기반의 *이미지 단위* 손실률이고, 후자는 *응답 단위*("10장 중 한 장이라도 빠졌는가")다. 둘은 단순 환산되지 않는다(거부가 요청 내에서 몰려 발생하기 때문). 구간별 *응답 단위* 브라운아웃 %를 정확히 보려면 k6를 `--out csv`로 재실행해 타임스탬프별로 매핑해야 한다 — 이번엔 하지 않았다.
- 두 arm 모두 CPU 평균이 전 구간 99% 안팎이라, **이 인스턴스에서는 VU 5(가장 낮은 단계)에서 이미 CPU가 포화**였다. 즉 "CPU 포화가 시작되는 VU"는 이 사다리의 측정 하한 아래에 있어 특정하지 못했다.
- mycourse 상세조회 경로는 Redis를 쓰지 않으므로(`@Cacheable`/`RedisTemplate` 참조 없음) arm 사이 캐시 초기화는 생략했다.
- t3.small 인프라 선택은 "실제 배포 스펙과 동일 유지" 원칙에서 의도적으로 벗어난 것이다.
