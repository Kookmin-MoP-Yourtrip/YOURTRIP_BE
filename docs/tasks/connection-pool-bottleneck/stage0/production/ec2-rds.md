# EC2+RDS 분리 환경 측정 결과 (0단계 재검증)

> [index.md](../local/index.md)의 Phase C가 "로컬 벤치마크는 앱·PostgreSQL·Redis·Prometheus·Grafana·k6를 전부 한 머신에서 같이 돌린 비격리 환경이라, mycourse에 남은 잔여 병목이 진짜 구조적 문제인지 로컬 CPU 경합 노이즈인지 구분할 수 없다"고 결론 내렸다. 이 문서는 그 노이즈를 제거하기 위해 앱(EC2)·RDS·ElastiCache·k6(별도 EC2)를 물리적으로 분리한 환경을 구축하고, **0단계(트랜잭션 분리) 적용 전/후**를 재검증한 기록이다. 인덱스 자체의 EC2+RDS 재검증은 아직 미착수다.

## 개선 제안 — 배포 환경(EC2 + RDS) 분리 부하테스트 (배경)

**무엇을**: 지금까지의 모든 측정은 앱·PostgreSQL·Redis·Prometheus·Grafana·k6 부하생성기를 전부 코어 12개짜리 개발 노트북 한 대에서 동시에 돌린 결과다. "인덱스 추가 결과"의 Phase C에서 확인했듯, 이 비격리 환경 자체가 잔여 병목의 상당 부분(부하 구간에 머신 전체 CPU가 15~22%→50~73%로 치솟고, 그 구간에 JDBC의 PostgreSQL 응답 대기가 10~40배 느려지는 것)을 설명한다. 실제 배포 구성에 가깝게 **앱은 EC2, DB는 RDS로 분리**하고, **k6도 앱과 별도의 EC2 인스턴스**(같은 리전, 가능하면 같은 VPC/AZ)에서 실행하면 이 CPU 경합 자체가 사라져, "인덱스가 진짜로 얼마나 개선했는지"를 노이즈 없이 측정할 수 있을 가능성이 높다.

**왜 지금 이 결론이 나왔는가**: 로컬 벤치마크에서는 인덱스가 쿼리 실행계획(`EXPLAIN ANALYZE`)을 49~236배 개선했는데도 `acquire_seconds`/`pending`/포화 시작 VU는 거의 그대로였다. Phase A/B/C로 원인을 좁혀보니 애플리케이션 코드나 쿼리 계획 문제가 아니라 벤치마크 환경 자체의 CPU 공유 문제로 수렴했다 — 즉 지금 이 리포지토리의 knee 위치(VU~20)와 절대적인 `acquire_seconds` 수치는 **로컬 개발 머신의 한계를 상당 부분 반영한 것**이라, 실제 배포 환경의 진짜 용량과는 다를 수 있다.

**주의할 점 (대화 중 정리한 내용)**:
- k6를 앱과 같은 EC2 인스턴스에 올리면 이번에 겪은 문제(부하생성기와 시스템이 CPU를 나눠 씀)가 그대로 재현된다 — 반드시 별도 인스턴스여야 한다.
- RDS 인스턴스 클래스 선택에 유의해야 한다. 특히 `db.t3.*` 같은 버스터블 계열은 CPU 크레딧이 소진되면 스로틀링이 걸려, "로컬 CPU 경합"이 "RDS CPU 크레딧 고갈"이라는 비슷한 종류의 새 병목으로 바뀔 뿐일 수 있다.
- EC2↔RDS 통신은 로컬호스트가 아니라 네트워크를 타므로(같은 VPC/AZ라도) 왕복시간이라는 새 변수가 생긴다 — 다만 보통 서브ms~수ms 수준이라 이번에 관찰한 10~40배 지연보다는 작고 예측 가능한 편이다.

**검증**: 동일한 `scripts/k6/detail-ramping.js`(VU 1→200, pool 모드)를 별도 EC2 부하생성기에서 재실행하고, `hikaricp_connections_pending`/`acquire_seconds`/포화 시작 VU가 로컬 벤치마크 대비 실제로 개선되는지 비교한다. 개선된다면 로컬에서 관찰된 잔여 병목이 환경 노이즈였다는 게 확정되고, 개선되지 않는다면 20:1 풀 크기 문제(4단계) 자체가 여전히 유효한 진짜 병목이라는 뜻이다.

**비용/시간 트레이드오프**: EC2 인스턴스 2개(앱+부하생성기) + RDS 인스턴스 1개를 새로 띄우고 철거하는 작업이라, 로컬 재측정보다 비용·시간이 든다.

## EC2+RDS 분리 환경 측정 결과 (실측 완료)

위 제안에 따라 PR [#72](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/pull/72)에서 앱(EC2)·RDS·ElastiCache·k6(별도 EC2)를 분리한 일회성 인프라(`terraform/loadtest/`)를 구축했고, 이번 세션에서 그 위에서 **0단계(트랜잭션 분리) 적용 전/후**를 재측정했다. 인덱스(`e7d0850`)는 아직 검증되지 않은 별도 변수이므로 이번 측정에서는 **전/후 모두 인덱스가 없는 코드 상태로 고정**했다 — 인덱스 자체의 효과는 다음 세션에서 이 환경 위에 별도로 재측정할 예정이다.

**코드 기준점**: 로컬에서 이미 검증까지 마친 커밋을 그대로 재사용했다 — `702a492`(0단계 적용 전, 인덱스 없음)와 `aacf823`(0단계 적용 후, 인덱스 없음). 두 커밋 사이 `application.yml` diff는 `open-in-view: false` 한 줄이 전부라, 이 두 코드 상태의 차이는 정확히 "0단계 변경분"만 남는다. 다만 이 두 커밋은 이후 병합된 조회수 중복방지 게이트(PR #69)를 포함하지 않는다 — uploadcourse의 `getDetail`은 이번 측정에서 무조건 `incrementViewCount`를 호출하는 구버전 로직이며(두 상태 모두 동일하게 적용되므로 전/후 비교 자체는 왜곡되지 않는다), mycourse 경로에는 애초에 영향이 없다.

**측정 절차**: `terraform/loadtest`가 이미 `apply`된 상태(App EC2 `t3.micro`, RDS `db.t3.micro`, ElastiCache `cache.t3.micro`, k6 EC2 `t3.micro`, 전부 `ap-northeast-2a` 단일 AZ)에서, 코드 상태를 전환할 때마다 (1) 로컬에서 해당 커밋을 `./gradlew bootJar`로 빌드해 scp로 App EC2에 배포하고 `systemctl restart`, (2) SSM Session Manager 포트포워딩(App EC2 경유)으로 RDS에 터널링해 `seed-benchmark.sql` 재시딩(`DB_DDL_AUTO=create`라 재기동마다 스키마가 DROP&CREATE되므로 매번 필수), (3) 같은 방식으로 ElastiCache에도 터널링해 `redis-cli FLUSHALL`, (4) k6 EC2에서 `scripts/k6/detail-ramping.js`를 uploadcourse→mycourse 순서로 순차 실행했다. mycourse는 시드 유저(`user_id=1`)의 비밀번호가 실해시가 아니라 로그인이 불가능해, `JwtTokenProvider`와 동일한 HS256 서명 규칙을 알고 있는 `jwt.secret` 값으로 로컬에서 직접 JWT를 발급해 사용했다.

**트러블슈팅 — k6 EC2에서 App EC2의 퍼블릭 IP로 연결이 안 됨**: 첫 시도에서 uploadcourse ramping이 8분 내내 100% `dial: i/o timeout`으로 실패했다(0건 성공). 원인을 좁혀보니 k6 EC2에서 App EC2의 **퍼블릭 IP**로는 TCP 연결 자체가 열리지 않고(`curl`/`/dev/tcp` 모두 타임아웃), 같은 서브넷의 **프라이빗 IP**(`10.42.1.202`)로는 즉시 연결됐다 — 보안그룹(`app_ingress_api_from_k6`, k6 SG를 소스로 하는 규칙)은 정상이었고 NACL도 기본값(전체 허용)이라, 같은 서브넷 내에서 퍼블릭 IP로 라운드트립하는 경로 자체가 막혀 있던 것으로 보인다(로컬 개발 머신에서 App EC2 퍼블릭 IP로의 접근은 문제없었다 — 외부에서 들어오는 경로는 정상). 이후 모든 k6 실행은 `BASE_URL=http://10.42.1.202:8080`(프라이빗 IP)으로 전환해 해결했다. 다음에 이 인프라를 재사용할 때는 처음부터 프라이빗 IP를 쓰는 것을 권장한다.

**측정 결과 — mycourse (DB 접근이 필수인 경로, 핵심 비교 대상)**

| | TPS | p95 | `pending` 최대 | `active` 최대 | `acquire_seconds` 최대 | 평균 커넥션 점유시간 | 포화 시작 VU |
|---|---|---|---|---|---|---|---|
| 0단계 적용 전 (702a492) | 88.65/s | 2.01s | 186 | 10 | 5.361s | 47.3ms | VU10~20 |
| 0단계 적용 후 (aacf823) | 73.38/s | 2.10s | 186 | 10 | 5.704s | 53.3ms | VU10~20 |
| 증감 | **-17.2%** | **+4.5%** | **0%(완전 동일)** | 0 | +6.3% | +12.7% | 동일 |

`pending` 최대값이 186→186으로 **완전히 동일**하고, 포화가 시작되는 VU 지점도 전혀 움직이지 않았다. TPS는 오히려 17.2% 떨어졌다(로컬 baseline에서도 -7.5%로 같은 방향이었는데, 이번이 더 뚜렷하다). 로컬 벤치마크의 결론 — "0단계는 mycourse의 20:1 풀 크기 구조적 병목을 풀 수 없다" — 이 CPU 경합 노이즈를 제거한 순수 환경에서도 그대로 재현됐다.

**측정 결과 — uploadcourse (캐시 히트 위주 경로, 참고용)**

| | TPS | p95 | `pending` 최대 | `active` 최대 | `acquire_seconds` 최대 |
|---|---|---|---|---|---|
| 0단계 적용 전 (702a492) | 1,067.83/s | 157.43ms | 187 | 10 | 0.986s |
| 0단계 적용 후 (aacf823) | 1,551.99/s | 99.89ms | **0** | 3 | 0.0058s |
| 증감 | **+45.4%** | **-36.5%** | **-100%** | -7 | **-99.4%(170배↓)** |

`pending`이 187에서 완전히 0으로 사라졌다 — 로컬 벤치마크(181→0)와 정확히 같은 패턴이다. 캐시 히트 경로가 이제 DB 커넥션을 아예 획득하지 않는다는 게 이 환경에서도 재확인됐다.

**환경 자체가 오염되지 않았다는 근거(CloudWatch)**: 측정 구간(38분) 동안 4개 t3 버스터블 리소스의 `CPUCreditBalance`를 확인했다 — App EC2 134.7→104.8, k6 EC2 163.2→159.1(거의 안 씀), RDS 106.1→85.7. 전부 감소하지만 고갈(0 근접)과는 거리가 멀어, 이번 측정이 "로컬 CPU 경합"을 "AWS 크레딧 고갈"이라는 다른 종류의 병목으로 바꿔치기한 것은 아니다. ElastiCache CPU 사용률도 최대 11.5%로 낮았고, App EC2 메모리는 77.6%→87.5%로 OOM 없이 버텼다.

**로컬 대비 비교**: mycourse의 TPS(88.65/s)와 평균 커넥션 점유시간(47.3ms)은 로컬 baseline(86.42/s, 46.8ms)과 거의 일치한다 — 즉 이 두 지표는 애초에 로컬 CPU 경합의 영향을 덜 받았던 것으로 보인다. 반면 `acquire_seconds` 최대값(로컬 2.61s → 이번 5.36s)과 p95(로컬 1.88s → 이번 2.01s)는 이 환경에서 오히려 더 높게 나왔다 — t3.micro(vCPU 2개, 다만 물리 코어는 1개뿐이라 실질 병렬 처리력은 그보다 낮음)가 로컬 개발 머신(12코어)보다 절대 스펙이 낮아 같은 20:1 과잉수요 상황에서 개별 요청의 꼬리 지연이 더 크게 나타난 것으로 보인다. 다만 핵심 결론(포화 시작 VU, `pending` 패턴)에는 영향이 없다.

**결론**: "로컬에서 관찰된 mycourse의 잔여 병목이 환경 노이즈였는가"라는 이번 실험의 원래 질문에 대한 답은 명확하게 **아니오**다 — CPU 경합이 없는 순수 환경에서도 0단계는 mycourse를 개선하지 못했다. TASK 문서의 1단계(Signed Cookie 전환)·4단계(풀 크기 재검토)의 필요성이 다시 한 번 확인됐다. 다음 단계로는 이 환경 위에 인덱스(`e7d0850`)를 추가해 로컬에서 관찰됐던 "인덱스가 쿼리는 빠르게 했지만 풀 포화 지표는 거의 못 바꿨다"는 결과도 노이즈 없이 재검증하는 것을 권장한다.

**한계**:
- 각 run은 로컬 벤치마크와 동일하게 1회씩만 측정했다.
- 이 두 코드 상태는 조회수 중복방지 게이트(PR #69)를 포함하지 않아 현재 `dev` HEAD와는 다르다(위 "코드 기준점" 참고).
- k6 EC2→App EC2 퍼블릭 IP 라운드트립이 안 되는 정확한 근본 원인(라우팅/헤어핀 NAT 관련으로 추정)은 규명하지 못했다 — 프라이빗 IP 우회로 실용적으로 해결했을 뿐이다.
- 측정 세션 도중 로컬 공인 IP가 여러 차례 바뀌어(유동 IP로 추정) 보안그룹에 임시 규칙을 여러 번 추가했다 — 정리 시점에 오래된 규칙(예: 최초 IP `220.116.231.187`)이 남아있을 수 있어, 인프라를 계속 쓸 경우 주기적으로 정리가 필요하다.
