# 현재 캐싱 적용 현황 및 TTL 정책 (2026-08-03 기준)

현재 프로젝트(YourTrip)에서 적용되어 동작 중인 캐시 항목들과 각각의 정책(TTL 등)을 정리한 문서입니다. 백엔드에서 대규모 트래픽 시 데이터베이스 부하를 줄이고, 응답 속도를 향상시키기 위해 적용되었습니다.

## 1. 랭킹 캐시 (`popularCourses`)

* **저장 데이터**: 카테고리별(전체 `ALL` 및 각 테마별 `MOOD`) 조회수 Top 5 코스의 **ID 목록** (`List<Long>`)
* **TTL (만료 시간)**: **30분** (`POPULAR_COURSES_TTL`)
* **갱신 주기 및 특징**: 
  * 백그라운드 스케줄러(`ViewCountSyncScheduler`)가 **10분마다** 랭킹 쿼리를 다시 실행하여 캐시를 강제로 갱신합니다. (따라서 실질적인 갱신 주기는 10분입니다.)
  * TTL을 30분으로 설정한 이유는, 스케줄러에 장애가 발생해 갱신이 멈추더라도 너무 오래된 과거 랭킹 데이터가 영구적으로 노출되는 것을 방지하기 위한 **안전망(마지노선)** 역할입니다.
  * *조회 시 캐시가 없을 경우 (Cold Cache)*: 한 요청이 분산 락(Lock)을 획득해 DB에서 조회 후 캐시를 채우고, 나머지 요청들은 짧은 시간 대기하며 캐시가 채워지길 기다림으로써 콜드 스타트 스탬피드(Thundering Herd) 현상을 방지합니다.

## 2. 코스 목록 아이템 캐시 (`courseListItem`)

* **저장 데이터**: 개별 코스를 목록 화면에 그릴 때 필요한 가벼운 데이터 (제목, 위치, 썸네일 S3 Key, 포크 수, 키워드 목록 등)
* **TTL (만료 시간)**: **2시간** (`COURSE_LIST_ITEM_TTL`)
* **갱신 주기 및 특징**:
  * 코스의 기본 정보는 한 번 업로드되면 사용자가 수정하는 일이 매우 드문 Read-Heavy(읽기 위주) 특성을 가집니다. 이를 고려하여 DB 부하를 최소화하기 위해 넉넉한 2시간으로 설정했습니다.
  * 인기 코스 목록 조회, 내 코스 조회 등 **코스 ID를 기반으로 화면 목록 항목을 조립하는 모든 경로에서 범용적으로 재사용**할 수 있습니다.
  * 검색이나 랭킹 변경 시점에 이 캐시는 즉시 지워지지 않고, 자체 TTL에 의해 만료되거나 새로운 요청 시점에 개별적으로 생성(Cache-Aside)됩니다. (조회수 증가는 목록 응답에 노출되지 않으므로 갱신 대상이 아님)

## 3. 코스 상세 정보 캐시 (`courseDetail`)

* **저장 데이터**: 코스 상세 페이지 표시에 필요한 무거운 데이터 (기본 정보 + 여행 n일차 일정 + 장소 목록 + 장소별 이미지 목록 전체)
* **TTL (만료 시간)**: **2시간** (목록 아이템 캐시의 TTL 재사용)
* **갱신 주기 및 특징**:
  * `RedisConfig` 파일 상에는 초기에 5분으로 정의되어 있었으나, 실제 비즈니스 로직(`UploadCourseServiceImpl`)에서는 상세 데이터 역시 변경 빈도가 극히 낮다는 점을 고려해 **아이템 캐시와 동일한 2시간으로 덮어씌워 사용**하여 최적화되었습니다.
  * 쓰기 시점과 사용자가 상세 조회하는 시점이 일치하여 정상 트래픽에서는 코스별 캐시 만료 시각이 자연스럽게 분산되므로 트래픽 스파이크에 유리합니다.

## 캐싱 최적화 현황 요약
* **자주 바뀌는 데이터 (순위표)**: 10분 주기(최대 30분)로 짧게 유지하여 트렌드를 빠르게 반영.
* **잘 변하지 않는 데이터 (코스 아이템/상세)**: 2시간의 긴 TTL을 적용하여 캐시 적중률(Hit Rate)과 효율을 극대화.
* **검색 API 구조**: 현재 검색 API(`getAllForSearch`)는 DB를 직접 조회하고 있으나, 향후 검색된 ID 목록만 반환하게 수정한 뒤 `courseListItem` 아이템 캐시를 활용하도록 리팩토링하면 동일한 캐시 리소스를 활용하여 DB 부하를 더욱 낮출 수 있습니다.
