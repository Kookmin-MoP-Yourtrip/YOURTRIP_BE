# TASK-4. 상세 조회 캐싱

> [CACHING-ROADMAP.md](README.md) 4번 섹션("상세 조회 캐싱")에 대응하는 작업 기록. 체크리스트 자체는 원문서를 따르되, 이 문서는 **설계 과정에서 오간 논의, 발견한 버그, 성능 측정 결과**를 포트폴리오용으로 남긴다.

## 배경

인기 코스 목록(3번 섹션)이 "top5 조회" 경로의 DB 부하를 없앴다면, 상세 조회는 그보다 무거운 요청이다.
`UploadCourse` 엔티티 조회에 더해 일차·장소·장소사진을 모두 훑고, 장소 이미지 개수만큼 presigned URL을 생성한다([CACHING-ROADMAP.md 배경 ③](README.md)). 이번 작업의 목표는 같은 코스에 대한 반복 조회가 이 무거운 경로를 매번 타지 않게 하는 것이다.

## 설계 결정과 근거


### 1. 캐싱 데이터 범위 — 상세 전용 신규 DTO

`UploadCourseDetailResponse`를 통째로 미러링하는 4개 record(`UploadCourseDetailCacheItem`/`DayScheduleCacheItem`/`PlaceCacheItem`/`PlaceImageCacheItem`)를 새로 만들었다. 3번 섹션의 `CourseListItemCacheItem`(목록용)과 필드가 일부 겹치지만, TTL·무효화 정책이 서로 달라 분리했다(자세한 내용은 아래 "TTL 재검토" 참고 — 실제로는 재검토 후 TTL도 통일됐다). presigned URL이 아니라 **S3 key만** 캐싱해 응답 조립 시점에 매번 새로 발급한다(설계 원칙 1번).

### 2. 콜드 스탬피드 방지 락 — 미적용

랭킹 캐시는 "테마당 키 1개"라 미스 순간 거의 모든 요청이 몰리지만, 상세 캐시는 키가 코스ID별로 흩어져 있어 그 정도로 취약하지 않다. 특정 코스 하나가 폭발적 트래픽을 받는 극단 상황은 이번 범위에서 제외하고, 실측으로 필요성이 확인되면 별도 항목으로 추가하기로 했다.

## 발견한 버그 — GenericJackson2JsonRedisSerializer가 타입 정보를 심지 않는다

4-3(`getDetail`에 캐시 연결) 구현 후 실제로 캐시 히트를 재현해보니 예외가 발생했다.

```
java.lang.IllegalStateException: Cached value is not of required type [UploadCourseDetailCacheItem]:
{uploadCourseId=1, title=..., daySchedules=[...]}
```

`redis-cli GET`으로 저장된 원본 값을 직접 확인한 결과, JSON에 `@class` 타입 힌트가 없었다. `RedisConfig.cacheValueSerializer()`가 커스텀 `ObjectMapper`를 그대로 `GenericJackson2JsonRedisSerializer`에 넘기기만 하고 `activateDefaultTyping`을 호출하지 않기 때문이다. 타입 정보가 없으니 역직렬화 시 원래 레코드 타입이 아니라 `LinkedHashMap`으로 복원되고, `Cache.get(key, Class)`의 `isInstance` 체크가 예외를 던진 것이다.

**영향 범위가 4번 섹션에 국한되지 않았다.** 같은 직렬화 설정을 쓰는 3번 섹션의 아이템 캐시(`readItemCache`)도 동일한 문제를 겪고 있었다 — 다만 그쪽은 예외 대신 `instanceof CourseListItemCacheItem` 체크가 조용히 실패하는 방식이라 **오류 없이 항상 캐시 미스로 동작**했을 가능성이 높다. TASK-3.md의 벤치마크는 DB 쿼리 횟수를 "랭킹 쿼리 로그 라인 수"만으로 측정했기 때문에 이 문제가 드러나지 않았다.

**수정**: 두 캐시 모두 `CacheManager`를 거치지 않고, 캐시별 타입을 명시한 `Jackson2JsonRedisSerializer<T>`로 원시 Redis 커맨드(`GET`/`SET`/`MGET`)를 직접 다루도록 교체했다. 타입을 이미 알고 있으므로 `@class` 힌트 자체가 필요 없어진다. 실제 코스를 업로드해 상세 API와 `/popular` API를 각각 연속 호출해, 2번째 호출부터 관련 DB 쿼리가 전혀 발생하지 않음을 로그로 확인했다.

랭킹 캐시(`popularCourses`, `List<Long>`)는 `cache.get(key, List.class)`로 조회하는데 `List.class` 검사는 어떤 `List`든 통과시키므로 예외가 나지 않았다(이 느슨한 타입 체크 때문에 `Integer`/`Long` 혼동 버그가 있었던 것도 같은 맥락 — TASK-3.md에 이미 기록된 `Number::longValue` 안전 변환으로 방어돼 있음). 이쪽은 이번에 손대지 않았다.

`RedisConfig`의 `courseDetail` 캐시 설정(`RedisCacheManager`에 등록된 항목)은 이제 코드에서 더 이상 참조하지 않아 미사용 상태로 남아있다. `RedisConfig` 자체는 이번 범위에서 수정하지 않기로 했으므로, 삭제할지 default typing을 활성화해 재사용할지는 별도 검토가 필요하다.

## TTL 재검토 — 5분 → 2시간

문서 초안은 상세 캐시 TTL을 5분으로 정해뒀지만, 실무에서 캐시 TTL을 정하는 방식을 조사한 뒤 값을 재조정했다.

**조사 결과 요약**: AWS의 Redis 캐싱 백서와 Redis 공식 블로그, 실제 이커머스 사례를 종합하면 핵심 원칙은 "TTL은 데이터 변경 빈도에 맞춰야 한다"는 것이다. 한 패션 이커머스 사례는 재고(자주 바뀜)에 TTL 60초, 상품 설명(거의 안 바뀜)에 TTL 3600초(1시간)를 적용해 DB 쿼리를 500 QPS→15 QPS로 줄였다. **일반 가이드로는 "1시간부터 시작해 히트율을 보며 조정하라"는 조언이 반복적으로 등장한다.**

## 성능 측정 계획 및 결과

### 측정 환경

- **DB**: PostgreSQL(네이티브 Windows 서비스, `localhost:5434`)
- **Redis**: 네이티브 Windows 서비스(`localhost:6379`, `SPRING_DATA_REDIS_PORT` 환경변수로 앱 실행 시점에 오버라이드) — TASK-3.md에서 확인된 것처럼 Docker Desktop의 네트워크 가상화 오버헤드를 배제하기 위해 네이티브로 통일
- **부하 생성**: Node.js(v24) 내장 `http` 모듈로 작성한 동시성 제어 스크립트(동시성 50, 요청 600건, p50/p95/p99/TPS 산출) — TASK-3.md와 동일한 도구/방법론
- **DB 쿼리 횟수 측정**: `hibernate.SQL: debug` 로그에서 상세 조회 쿼리(`upload_course` JOIN `my_course`) 문자열의 로그 라인 수를 세는 방식(2줄 = 실제 실행 1회)

### 시드 데이터

빈 DB로는 상세 조회 비용(일차·장소·이미지 개수에 비례)이 드러나지 않으므로, `psql`로 직접 벌크 INSERT하는 SQL 스크립트를 작성해 다음 데이터를 생성했다(레포에 커밋하지 않음).

- **일반 코스 3,000건**: 코스당 일정 4개 × 장소 3개(일정당) × 이미지 2개(장소당) = 코스당 이미지 24장
- **히어로 코스 1건**(단일 인기 코스 시나리오용): 일정 7개 × 장소 5개(일정당) × 이미지 3개(장소당) = 이미지 105장 — 실제 여러 날짜에 사진이 풍부한 "인기 상세 페이지"를 흉내낸 값
- 총 130,000여 행(my_course/upload_course/day_schedule/place/place_image 합계)을 `generate_series` 기반 CTE 체인으로 약 2초 만에 생성

`DB_DDL_AUTO=create`라 앱을 재기동할 때마다 스키마가 초기화되므로, Before/After 측정 사이에 재기동이 있을 때마다 이 스크립트를 다시 실행했다(TASK-3.md와 동일한 제약).

### 측정 시나리오

- **시나리오 A — 단일 인기 코스 반복 조회**: 히어로 코스 하나를 동시성 50, 600건 반복 요청. 캐시가 가장 유리한 "핫 키 반복 히트" 상황.
- **시나리오 B — 여러 코스 혼합 조회**: 일반 코스 3,000건 중 무작위 ID를 동시성 50, 600건 요청. 코스 수(3,000)가 요청 수(600)보다 훨씬 많아 자연 재방문율이 낮은(약 9%) "롱테일" 트래픽에 가깝다.

### 결과 — 시나리오 A (단일 인기 코스, 이미지 105장)

|---|---|---|---|
| TPS | 14.5 | 23.4 | **약 1.6배** |
| p50 | 3380.2ms | 2118.6ms | 약 37% 감소 |

### 결과 — 시나리오 B (여러 코스 혼합, 코스당 이미지 24장, 재방문율 ~9%)

| 지표 | Before(캐시 미적용) | After(캐시 적용) | 개선 |
|---|---|---|---|
| TPS | 41.8 | 44.9 | 약 7% |
| p50 | 1176.0ms | 1077.0ms | 약 8% 감소 |
| 상세 조회 DB 쿼리(600건 요청 기준) | 600회 (100%) | 544회 (90.7%) | 자연 재방문율(약 9%)만큼만 감소 |

### 결과 해석 — DB 부하는 확실히 제거됐지만, 응답시간 개선폭은 이미지 개수에 좌우된다

1. **가장 중요한 지표(DB 쿼리 실행 횟수)는 두 시나리오 모두 설계대로 동작했다.** 시나리오 A는 캐시 히트율이 사실상 100%(600건 중 599건 히트)라 DB 쿼리가 1회로 수렴했고, 시나리오 B는 재방문율(약 9%)만큼만 쿼리가 줄었다 — 이는 캐시가 "안 먹힌" 게 아니라, 3,000개 코스 중 무작위로 600건만 뽑으면 애초에 같은 코스가 재방문될 확률 자체가 낮기 때문이다(생일 문제로 기대 재방문 수 ≈ 600²/(2×3,000) ≈ 60건, 실측 56건으로 거의 일치). **캐시의 효과는 "얼마나 인기 있는 코스인가"에 정확히 비례한다**는 걸 실측으로 보여준 결과다.
2. **시나리오 A의 응답시간 개선폭(TPS +61%)이 DB 쿼리 제거 폭(600회→1회)만큼 극적이지 않은 이유**: 캐시 히트 시에도 presigned URL은 캐싱하지 않고 응답 조립 시점에 매번 새로 발급한다(설계 원칙 1번). 히어로 코스는 이미지가 105장이라, 캐시 히트 요청 1건마다 `s3Service.getPresignedUrl()`이 106번(썸네일 1 + 이미지 105) 호출된다. `S3Presigner`는 싱글턴 빈으로 주입되어 있어(요청마다 새로 만들지 않음) 매 호출이 네트워크 없는 로컬 HMAC 서명이지만, 동시성 50 하에서 이 서명 연산 자체가 새로운 병목으로 등장한 것으로 보인다. 이는 **로드맵 설계 원칙 1번이 "presign은 비용이 작다"고 전제했던 것에 대한 실측 반증**이다 — 개별 호출은 저렴해도 "이미지 개수 × 동시 요청 수"로 곱해지면 무시할 수준이 아니게 된다.
3. **캐싱이 낸 실질적 효과와 아직 남은 비용을 구분해서 봐야 한다.** DB 부하 제거는 이 작업의 1차 목표였고 완전히 달성됐다. 반면 presigned URL 발급 비용은 애초에 캐싱의 대상이 아니었다(캐싱하면 URL 만료 문제가 생기므로 설계 원칙 1번에서 의도적으로 제외한 부분) — 즉 이번 측정은 캐싱이 "실패"한 게 아니라, **캐싱만으로는 해결되지 않는 별개의 비용이 있다는 것을 정직하게 드러낸 결과**다.

### 발견한 개선점 (이번 작업 범위 밖 — 코드 수정 없이 기록)

**이미지가 많은 코스의 presigned URL 발급 비용이 상세 조회 응답시간의 새로운 병목이 될 수 있다.** 시나리오 A처럼 이미지가 많은 인기 코스는 캐시 히트 시에도 요청마다 이미지 개수만큼 순차적으로 `getPresignedUrl()`을 호출한다(현재 `buildDaySchedulesFromCache`/`buildDaySchedulesFromEntities` 모두 스트림으로 순차 처리). 개선 아이디어로는 (1) 병렬 스트림이나 별도 스레드풀로 presign 호출을 병렬화, (2) 장소 이미지 표시 개수에 상한을 두어 상세 응답 자체의 이미지 수를 제한하는 방안(예: 장소당 대표 이미지 몇 장만) 등을 검토할 수 있다. 다만 이는 캐싱 범위를 벗어난 별도의 성능 개선 주제이고, 실제 서비스의 평균 이미지 개수 분포를 먼저 파악한 뒤 필요성을 판단하는 것이 합리적이라 이번 범위에서는 코드를 고치지 않고 기록만 남긴다.

## 이번 작업에서 얻은 교훈 (포트폴리오 포인트)

1. **캐시 조회를 실제로 실행해보기 전까지는 직렬화 문제가 드러나지 않는다.** `GenericJackson2JsonRedisSerializer`가 타입 정보를 심지 않는 문제는 코드 리뷰만으로는 알기 어려웠고, 실제로 캐시 히트를 재현했을 때 예외가 터지면서 발견했다. 이 발견 덕분에 3번 섹션에 이미 존재하던 잠재 결함(아이템 캐시가 조용히 항상 미스였을 가능성)까지 함께 찾아 고칠 수 있었다 — **"에러 없이 조용히 실패하는 코드"가 "에러를 던지는 코드"보다 더 위험하다**는 걸 보여주는 사례다.
4. **문서에 적힌 설계값(TTL 5분)도 절대적인 것이 아니라 재검토 대상이다.** 실무 사례를 조사해 "TTL은 데이터 변경 빈도에 맞춰야 한다"는 원칙을 확인하고, 이 프로젝트의 실제 데이터 변경 빈도(사실상 정적)에 맞춰 값을 근거 있게 조정했다.
3. **캐싱의 효과는 트래픽 패턴(인기 코스 vs 롱테일)에 따라 다르게 나타난다.** 단일 시나리오만 측정했다면 "캐싱이 이 정도밖에 효과가 없다"거나 반대로 "캐싱이 만능이다"라는 잘못된 결론에 도달했을 수 있다. 두 시나리오를 나눠 측정한 덕분에 캐시 히트율과 DB 쿼리 감소가 정확히 비례한다는 것, 그리고 캐싱과 무관한 별도 병목(presign 비용)이 존재한다는 것을 함께 확인할 수 있었다.
