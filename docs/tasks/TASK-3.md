# TASK-3. 인기 코스 상위 5개 목록 캐싱

> [redis-caching-strategy.md](../CACHING-ROADMAP.md) 3번 섹션("인기 상위 5개 목록 — 읽기 경로부터 단계적으로")에 대응하는 작업 기록. 체크리스트 자체는 원문서를 따르되, 이 문서는 **설계 과정에서 오간 논의와 그 근거**를 포트폴리오용으로 남긴다.

## 배경

앱 홈 화면 진입 시 두 개의 "top5" 목록이 노출된다.

1. **요즘 뜨는 인기 코스** — 필터 없는 전체 인기 top5
2. **테마별 인기 코스** — `KeywordType`의 `mood` 카테고리 7개 값(힐링/액티비티/맛집탐방/감성/문화·전시/자연/쇼핑) 탭별 인기 top5

원문서 3번 섹션은 "인기 상위 5개 목록" 단수 케이스만 염두에 두고 작성됐지만, 실제 홈 화면은 이 두 목록을 함께 요구한다. 이 작업은 3번 섹션의 체크리스트를 그대로 따르되, 각 단계에 **테마(mood) 차원**을 파라미터로 얹어 하나의 메커니즘으로 두 목록을 모두 처리하도록 확장했다.

기존 문제(원문서 "배경" 절): `UploadCourseRepository.findAllByKeywordsOrderByViewCountDesc`(전체 스캔, 페이징 없음)를 홈 화면에서 그대로 쓰면 트래픽이 몰릴 때 DB가 병목이 된다. 이 작업은 이 경로를 "상위 5개 ID만 뽑는 전용 쿼리 + 캐싱"으로 대체해 DB 부하를 원천 차단하는 것이 목적이다.

## 설계 결정과 근거

### 1. API 구성 — 단일 엔드포인트 + optional `theme` 파라미터

`GET /api/upload-courses/popular?theme={KeywordType}` (theme optional) 하나로 두 목록을 모두 처리한다.

- 검토했던 대안: 엔드포인트를 `/popular`(전체)와 `/popular/themes/{code}`(테마별)로 분리하는 방식. REST 리소스 경로로는 더 명시적이지만, 컨트롤러/캐시 로직이 두 벌로 나뉘는 단점이 있어 채택하지 않았다.
- `theme` 검증 범위는 `mood` 카테고리 값만 허용한다(그 외 20개 KeywordType 값이 오면 400). FE가 실제로 쓰는 테마 탭 용도에 맞춰 의미를 명확히 제한하기 위함이다.

### 2. 캐시 구조 — 랭킹/아이템 이원화

처음에는 테마당 top5 배열을 통째로 캐싱하는 단일 blob 방식을 검토했으나, **다음 문제 때문에 랭킹 캐시와 아이템 캐시를 분리하는 구조로 전환했다.**

- **문제**: 배열을 통째로 캐싱하면 그 안의 코스 하나의 콘텐츠(제목/썸네일 등)만 바뀌어도 그 코스가 속한 테마 리스트 전체를 evict/재계산해야 한다. Redis 값(String/JSON)은 부분 수정이 안 되기 때문이다.
- **해결**: 캐시를 두 단으로 분리한다.
  - **랭킹 캐시** (`popularCourses`, 기존 인프라 재사용): 키는 `theme == null ? "ALL" : theme.name()`, 값은 `List<Long>`(top5 코스ID, 순위 순서). "어떤 테마에서 누가 몇 등인가"라는 **질의 결과 자체**를 캐싱한다.
  - **아이템 캐시** (`courseListItem`, 신규): 키는 `uploadCourseId`, 값은 `CourseListItemCacheItem`(코스 1개의 콘텐츠 — title/location/thumbnailImageS3Key/forkCount/keywords). "이 코스가 어떻게 생겼는가"를 캐싱한다.
- **이점**: 코스 콘텐츠가 바뀌는 이벤트(fork로 인한 forkCount 증가, 향후 코스 수정 API)가 발생하면 **해당 코스ID의 아이템 캐시 하나만 즉시 overwrite**하면 되고 랭킹 캐시는 건드릴 필요가 없다.

### 3. 아이템 캐시는 "인기 목록 전용"이 아니라 범용 콘텐츠 캐시

랭킹 캐시와 아이템 캐시는 캐싱 기준이 근본적으로 다르다는 점을 명확히 했다.

- **랭킹 캐시**는 **쿼리 조건**(테마)을 키로 쓰므로 조합이 늘어나면 키 공간이 폭발할 위험이 있다 — 그래서 신중하게 골라야 한다(검색어/다중 태그 조합 캐싱을 범위에서 제외한 이유와 동일).
- **아이템 캐시**는 **엔티티 ID**를 키로 쓰므로 키 공간의 상한이 "이 서비스에 존재하는 코스 총 개수"로 고정된다. 이 차이 때문에 다음 기준을 따른다.
  1. **선별하지 않는다** — 접근 빈도를 추적해 "인기 있는 것만" 캐싱하는 로직을 만드는 비용이, 서비스 규모상 그냥 다 캐싱하는 것보다 크다.
  2. **비개인화 필드만 담는다** — "내가 좋아요 눌렀는지" 같은 사용자별 필드는 절대 포함하지 않는다(공유 캐시이므로 데이터 누출 위험).
  3. **read-heavy 데이터라 TTL을 넉넉하게 잡는다** — 코스 콘텐츠는 생성 후 거의 안 바뀌므로(현재 수정 API 자체가 없음) 랭킹 캐시(30분)보다 훨씬 길게(예: 2시간) 잡고, 정합성은 TTL이 아니라 write-through로 보장한다.
  4. **메모리 상한은 Redis `maxmemory` 정책에 위임**한다.
- 그래서 DTO/캐시 이름도 `Popular*`가 아니라 `CourseListItem*`로 지어, 인기 목록에 종속되지 않는 범용 캐시임을 이름에서부터 드러냈다. 향후 검색 결과 화면에서도 이 캐시를 그대로 재사용할 수 있다(아래 "발견한 개선점" 참고).

### 4. 랭킹 캐시 TTL(30분)의 실제 역할

TTL 30분이라는 숫자 자체는 정상 운영 중에는 거의 작동하지 않는다는 점을 설계 과정에서 명확히 했다.

- 5~6번 섹션에서 조회수 동기화 스케줄러가 10분마다 랭킹을 재계산해 `put`으로 캐시를 덮어쓰게 되면(refresh-ahead), `put`마다 TTL이 매번 30분 뒤로 재설정되므로 이 값이 실제로 만료를 일으키는 일은 없다.
- 이 TTL이 실질적으로 작동하는 유일한 상황은 **스케줄러가 멈췄을 때**다 — 그때 마지막 `put` 이후 30분이 지나면 캐시가 자연 소멸하고, 다음 요청이 미스를 보며 cache-aside+락 경로가 DB 기준으로 재계산한다.
- 즉 "30분"이라는 정확한 숫자보다 **"스케줄러 주기(10분)보다 충분히 커야 한다"는 관계**가 중요하다 — 스케줄러가 한 번 정도 밀려도(배포 중 순간 지연 등) 곧바로 만료되지 않도록 여유를 둔 값이다.

### 5. 구현 방식 — `@Cacheable` 대신 수동 cache-aside

`RedisConfig`의 기존 주석은 `@Cacheable` 사용을 암시했지만, 콜드 스타트 분산 락(더블 체크 락킹)을 자연스럽게 끼워 넣기 위해 `CacheManager.getCache(...)`를 직접 다루는 수동 cache-aside 방식을 채택했다.

- `@Cacheable(sync=true)`는 같은 JVM 내 동시 요청만 막아주고, 여러 인스턴스에 걸친 콜드 스타트 스탬피드는 못 막는다.
- 랭킹 캐시 미스에는 락을 걸고 아이템 캐시 미스에는 락 없이 단순 배치 조회로 채우는 등 **캐시별로 다른 처리**가 필요한데, 이는 애노테이션보다 명령형 코드로 표현하는 게 명확하다.
- 단, `RedisCacheErrorHandler`는 애노테이션 기반(`CacheInterceptor`) 호출에만 자동 적용되고 수동 `Cache.get/put` 호출에는 적용되지 않는다는 점을 확인했다 — 그래서 이 경로의 모든 Redis 호출(캐시 get/put, 락 SETNX/삭제)은 직접 try-catch로 감싸 fail-open을 구현한다.

### 6. 콜드스타트 분산 락 — 언제, 왜 거는가

- **언제**: 캐시 조회가 미스를 반환했을 때만. 실질적으로는 서버 재기동 직후(콜드스타트)나 스케줄러가 오래 멈춰 TTL이 만료됐을 때뿐이다.
- **왜**: 인기 목록은 홈 화면 진입점이라 캐시가 비어있는 순간 요청이 대량으로 몰릴 수 있다. 락이 없으면 동시 요청 전부가 미스를 보고 각자 DB로 몰려가는 "캐시 스탬피드"가 발생한다 — 캐시로 막으려던 병목이 미스 순간에 그대로 재현되는 셈이다. `SET NX EX`로 딱 하나의 요청만 DB 조회를 대표로 수행하게 하고, 나머지는 짧게 재시도하며 캐시가 채워지길 기다린다.
- TTL(락 만료시간)을 두는 이유는 락을 잡은 요청이 죽었을 때 다른 요청들이 영원히 대기하는 deadlock을 방지하기 위함이다.
- 랭킹 캐시 미스에만 락을 걸고, 아이템 캐시 미스(2단계, 최대 5건 PK IN 조회)에는 락을 걸지 않는다 — 조회 범위가 좁고 비용이 작아 중복 실행돼도 감내 가능하다고 판단했다.

### 7. 분산 락 구현 및 검증 (3-6)

**구현 상세**:
- `RedisTemplate<String, String>`(기존 `redisTemplate` 빈)의 `opsForValue().setIfAbsent(lockKey, lockToken, TTL)`로 `SET NX EX`를 구현. `lockToken`은 요청마다 `UUID.randomUUID()`로 생성.
- **락 해제는 단순 DEL이 아니라 Lua 스크립트로 비교-삭제**한다 — `GET`한 값이 내가 넣은 토큰과 같을 때만 `DEL`. 단순 DEL이면, 내 락 보유 시간이 TTL(5초)을 넘겨 이미 만료되고 다른 요청이 새로 락을 잡은 뒤에 내가 뒤늦게 `DEL`을 호출하면 **남의 락을 실수로 지우는** 문제가 생긴다.
- `tryAcquireRankingLock`은 `Boolean`을 반환하되 `null`은 "Redis 자체가 예외를 던짐"을 의미하도록 구분했다 — 이 경우엔 락 재시도 없이 바로 DB 직접 조회로 폴백한다(Redis가 죽었는데 락을 재시도하는 건 무의미하므로).

**검증 결과 (실측)**:
- 랭킹 캐시를 강제로 비운 뒤 동시 요청 50건(동시성 50)을 발사 → **DB 쿼리는 정확히 1회만 실행**됨(로그 라인 증가분으로 확인). 락이 스탬피드를 정확히 막고 있음을 확인했다.
- 락 해제 후 Redis에 `lock:*` 키가 남아있지 않음을 확인(정상 해제).
- `docker compose stop redis` 상태에서도 요청이 5xx 없이 200으로 degrade하는 것을 확인(fail-open 동작).


## 논의했으나 확정하지 않은 사항 (6번 섹션에서 재논의 예정)

### 코스 삭제 시 캐시 정리

현재 `UploadCourse`를 삭제하는 API 자체가 없다(`deleted` 필드 + `@SQLRestriction`만 존재, 실제 삭제 트리거 없음). 향후 삭제 기능이 생겼을 때를 대비해 두 방향을 논의했다.

- **검토했던 안 1**: 삭제 이벤트 발생 시 랭킹 캐시 8개 키를 전부 evict — 처음 제안했으나, **삭제와 무관한 테마 캐시까지 매번 무효화되어 "삭제 이벤트가 캐시 전체를 반복적으로 스탬피드시키는" 부작용이 있다는 지적을 받고 기각**했다.
- **검토했던 안 2**: 삭제되는 코스의 mood 키워드를 기준으로 랭킹 캐시를 선택적으로 evict(`{"ALL"} ∪ 그 코스의 mood 태그들`만).
- **가장 타당하다고 판단한 안**: 인기 목록은 trending 성격의 데이터이므로, 삭제된 코스가 몇 분간 목록에 남아있다가 다음 스케줄러 refresh나 TTL 만료 때 자연스럽게 사라지는 것을 허용 — 별도 훅을 아예 안 거는 것. 상세 조회는 `@SQLRestriction`으로 404 처리되므로 실질적 피해는 없다.
- 최종 확정은 6번 섹션("캐시 무효화 연결") 진행 시점에 다시 논의한다.

### 서버 기동 시 웜업(pre-warming)

`ApplicationReadyEvent` 리스너로 서버 기동 직후 8개(전체+mood 7개) 랭킹 캐시를 미리 채워두는 방안을 논의했다. 콜드스타트 락을 **대체**하는 게 아니라 **보강**하는 용도로 판단했다 — Redis만 단독 재시작되거나 캐시가 flush되는 경우는 앱이 재기동되지 않으므로 웜업이 재실행되지 않고, 이 경우 여전히 cache-aside+락만이 유일한 방어선이기 때문이다. 체크리스트에 정식으로 추가할지는 6번 섹션에서 최종 결정한다.

### 측정 환경 및 방법 (실제 적용한 방식)

원래 계획은 k6/Apache Bench + Hibernate `generate_statistics`였으나, 실제 로컬 환경에는 두 도구가 설치돼 있지 않아 다음으로 대체했다.

- **부하 생성**: k6/ab 대신 Node.js(이미 설치돼 있음) 내장 `http` 모듈로 작성한 간단한 동시 요청 스크립트 사용(동시성 50, 총 300~600건 요청, p50/p95/p99/TPS 산출).
- **DB 쿼리 횟수 측정**: `generate_statistics` 대신, 이미 켜져 있는 `hibernate.SQL: debug` + `show-sql: true` 로그에서 랭킹 쿼리 특정 문자열의 로그 라인 수를 세는 방식(2줄 = 실제 실행 1회, 이중 로깅 확인됨). 실행 계획/카운트 확인 용도로는 충분히 정확했다.
- **시드 데이터**: `data.sql`이 없어 빈 DB로는 캐시 유무 차이가 안 드러나서, 코스 5,000건(랜덤 view_count, mood 키워드 1개씩)을 벤치마크 전용으로 생성해 사용(레포에 커밋하지 않음). `DB_DDL_AUTO=create`라 앱을 재기동할 때마다 스키마가 초기화되므로, 재기동 후에는 매번 재시딩이 필요했다.

### 결과 — 비교 1: 캐시 적용 전후

**1) Before (캐시 없음, 3-3 상태 재현)** — 캐시 read/write 호출을 임시로 우회해 재현

| 지표 | 값 |
|---|---|
| 총 요청 (무테마 300 + FOOD 300 + 웜업 1) | 601건 |
| DB 쿼리 실행 횟수 | 601회 (요청당 1회 — 캐시 없이 매번 DB 직접 조회 확인) |
| TPS (무테마 / FOOD) | 78.6 / 93.9 |
| p50 (무테마 / FOOD) | 581ms / 520ms |
| p99 (무테마 / FOOD) | 886ms / 578ms |

**2) 캐시 적용 1차 시도 — 예상 밖으로 "더 느려짐"을 발견**

캐시를 붙인 직후 측정했더니 TPS가 오히려 64.3(무테마)으로 **Before보다 낮게 나왔다.** 원인을 추적한 과정:

1. **1차 원인 발견 — 이 개발 환경의 포트 충돌.** 이 기기에는 프로젝트의 `docker-compose.yml` Redis 컨테이너와 별개로, `C:\Program Files\Redis`로 설치된 **네이티브 Windows Redis 서비스**가 이미 6379 포트를 쓰고 있었다. 앱이 `localhost:6379`로 붙을 때 도커 컨테이너가 아니라 이 네이티브 인스턴스로 연결되고 있었던 것 — `docker exec`로 컨테이너를 아무리 확인해도 앱이 실제로 쓰는 Redis와 다른 인스턴스를 보고 있었다. **조치**: `docker-compose.yml`의 Redis 호스트 포트를 `6379` → `6479`로 변경하고 `.env`/`.env.example`의 `REDIS_PORT`도 함께 수정해 충돌을 피했다.
2. **2차 원인 발견 — `List<Long>` 캐시 역직렬화 버그.** 포트 문제를 고치고 실데이터(5,000건)로 다시 재보니 `ClassCastException: Integer cannot be cast to Long`이 발생했다. `GenericJackson2JsonRedisSerializer`가 `List<Long>`을 역직렬화할 때, 제네릭 타입이 소거돼 요소 타입 정보가 없으면 값 범위에 따라 `Integer`로 복원하는 경우가 있었다(작은 ID값이라 `Integer` 범위 안에 들어감). 빈 DB로 검증했을 때는 리스트가 비어있어 이 버그가 전혀 드러나지 않았다 — **실데이터로 벤치마크를 돌려본 덕분에 발견한 버그**다. **조치**: `readRankingCache`에서 캐시 값을 `List<Number>`로 안전하게 받은 뒤 `Number::longValue`로 명시 변환하도록 수정.
3. **3차 원인 발견 — 아이템 캐시의 순차 개별 GET 구조.** 위 두 문제를 고친 뒤에도 캐시 버전이 여전히 느렸다. 구간별 타이밍을 재보니 랭킹 캐시 조회(Redis GET 1회)는 2~3ms인데, 아이템 캐시 조회 구간은 안정화 후에도 35ms 안팎이었다. 아이템 캐시가 **코스 5건을 순차적으로 개별 GET 5번** 호출하는 구조였는데, 왕복(round-trip)마다의 지연이 5번 누적된 것. 이 프로젝트 설계 논의 당시 "최대 5건이라 개별 조회도 비용이 작다"고 판단했던 가정이 실측으로 틀렸음이 증명됐다.
   - Docker Redis(WSL2 경유) vs 네이티브 Redis로 비교해보니, 네이티브가 항목 조회 구간을 35ms → 17ms로 줄여줬다(Docker Desktop의 네트워크 가상화가 왕복마다 오버헤드를 추가한다는 뜻) — 하지만 네이티브로 바꿔도 여전히 "캐시 없음"보다 느렸다. 즉 **Docker 오버헤드는 문제의 일부였을 뿐, 근본 원인은 순차 개별 조회 자체**였다.

     | 지표 | Before (캐시 없음) | 네이티브 Redis + 순차 개별 GET (MGET 적용 전) |
     |---|---|---|
     | TPS (무테마 / FOOD) | 78.6 / 93.9 | 71.3 / 79.0 |
     | p50 (무테마 / FOOD) | 581ms / 520ms | 646ms / 605ms |
     | p99 (무테마 / FOOD) | 886ms / 578ms | 917ms / 745ms |

     가장 빠른 인프라(네이티브 Redis)로 바꿔도 순차 개별 GET 구조 자체 때문에 TPS는 오히려 낮고(-9~-16%) p50/p99는 더 높다(+11~16%) — Docker 오버헤드를 걷어내도 "캐시 적용판이 캐시 없는 판보다 느린" 역전 현상이 그대로 남아있음을 보여준다.
   - **최종 조치**: `RedisConfig`에 값 직렬화(`GenericJackson2JsonRedisSerializer`)를 공유하는 `cacheValueRedisTemplate`(`RedisTemplate<String, Object>`)을 추가로 등록하고, 아이템 캐시 조회를 `opsForValue().multiGet(keys)` 기반 배치 조회로 재구현했다. Spring의 `Cache` 인터페이스는 다중 키 조회를 지원하지 않아 이 부분만 별도 템플릿을 사용한다.

**3) After (캐시 + MGET 배치 적용, 최종)**

| 환경 | TPS (무테마 / FOOD) | p50 (무테마 / FOOD) | p99 (무테마 / FOOD) |
|---|---|---|---|
| Before (캐시 없음) | 78.6 / 93.9 | 581ms / 520ms | 886ms / 578ms |
| 네이티브 Redis + MGET | **97.6 / 113.9** | **470ms / 417ms** | 698ms / 502ms |
| Docker Redis(6479, 실제 배포 설정) + MGET | 76.4 / 82.7 | 616ms / 522ms | 938ms / 852ms |

- **네이티브 Redis 기준으로는 캐시 적용 후 TPS가 약 24~21% 개선**됐고 응답시간도 뚜렷이 줄었다.
- **Docker Redis(실제 이 프로젝트가 쓰는 설정) 기준으로는 TPS/응답시간이 캐시 없음과 비슷한 수준**이었다 — 이 로컬 개발 환경(Docker Desktop/WSL2)의 네트워크 가상화 오버헤드가, 캐시가 절약해주는 DB 왕복 비용과 상쇄되는 수준이기 때문. 이는 이 프로젝트의 캐싱 설계가 잘못됐다기보다 **로컬 1인 벤치마크 환경의 한계**로 해석해야 한다 — 실제 서비스 환경(같은 데이터센터/가용 영역 내 Redis, 다수 사용자의 동시 트래픽으로 DB가 실제로 경합 상태인 상황)에서는 이 오버헤드가 없고, DB 경합 자체가 훨씬 크기 때문에 캐시의 실질 이득은 더 커질 것으로 예상된다.
- **가장 중요한 지표인 DB 쿼리 실행 횟수는 환경과 무관하게 확실히 개선**됐다: Before는 요청 601건에 쿼리 601회(1:1)였던 반면, After(Docker, 최종 설정)는 요청 602건(웜업 2 + 부하테스트 600)에 **쿼리 단 2회** — 사실상 DB 부하가 제거됐다. 이 프로젝트의 원래 목표("트래픽이 집중되는 지점에서 DB가 병목이 되지 않게 한다")는 raw 응답시간보다 이 지표로 판단하는 게 더 정확하다.

### 결과 — 대용량 데이터 + 동일 조건(Postgres/Redis 둘 다 네이티브) 재측정

5,000건 규모에서는 DB 쿼리 자체가 너무 가벼워(정렬 대상이 작아 1ms 미만) 캐시 효과가 raw 응답시간에 뚜렷이 드러나지 않았고, Postgres(네이티브)와 Redis(Docker/WSL2 경유)의 인프라 조건도 달라 "공정한 비교"가 아니었다. 이 두 변수를 통제하기 위해 다음 조건으로 재측정했다.

- **데이터 볼륨을 500,000건으로 증설**(`view_count`에 인덱스가 없어 정렬 시 풀 테이블 스캔이 발생하도록 — 실제로 `\di upload_course*`로 확인한 결과 PK/unique 제약 외 인덱스 없음)
- **Postgres, Redis 모두 네이티브(Docker 미경유)로 통일** — Postgres는 원래도 네이티브 Windows 서비스였고, Redis도 `--spring.data.redis.host/port`를 임시로 `127.0.0.1:6379`(네이티브)로 오버라이드해 동일 조건으로 맞춤

| 지표 | Before (DB만, 캐시 없음) | After (캐시+MGET, 네이티브 Redis) | 개선 배율 |
|---|---|---|---|
| TPS (무테마) | 32.0 | 76.8 | **약 2.4배** |
| TPS (FOOD) | 19.9 | 82.1 | **약 4.1배** |
| p50 (무테마) | 1452.8ms | 613.7ms | 약 2.4배 |
| p50 (FOOD) | 2456.5ms | 567.9ms | 약 4.3배 |
| p99 (무테마) | 2140.1ms | 1091.7ms | - |
| p99 (FOOD) | 2921.3ms | 823.7ms | - |
| DB 쿼리 실행 횟수 (약 600건 요청 기준) | 600회 이상 (요청당 1회) | **2회** (콜드미스 2건뿐) | 사실상 제거 |

이 조건에서는 캐시 적용 전후의 응답 속도 차이가 raw latency로도 명확하게 드러난다. `view_count DESC` 정렬에 인덱스가 없는 상태에서 50만 건을 매번 스캔·정렬해야 하는 DB 직접 조회 경로는 요청이 몰릴수록(동시성 50) 급격히 느려지는 반면(p50 1.4~2.5초), 캐시 경로는 Redis 왕복 2번(랭킹 GET + 아이템 MGET)만으로 응답해 요청이 늘어도 안정적으로 처리된다. 5,000건 테스트에서 raw latency 차이가 흐릿했던 건 "DB가 딱히 안 힘든 조건"과 "Redis만 불리한 인프라 조건(Docker)"이 섞여 있었기 때문이었고, 두 변수를 통제하니 캐싱의 효과가 명확하게 나타났다.

### 이번 측정에서 얻은 교훈 (포트폴리오 포인트)

1. **가정은 반드시 실측으로 검증해야 한다.** "최대 5건이라 개별 GET 반복도 괜찮다"는 설계 당시의 판단이 실측 벤치마크로 명백히 틀렸음이 드러났고, 그 덕분에 MGET 배치 조회로 고칠 수 있었다.
2. **빈 DB로 하는 기능 검증은 한계가 있다.** `List<Long>` 역직렬화 버그는 빈 리스트로는 절대 드러나지 않았고, 실데이터를 넣어 벤치마크를 돌려본 덕분에 발견했다.
3. **로컬 벤치마크 환경 자체의 특성(Docker Desktop/WSL2 네트워크 오버헤드)을 이해하지 못하면 잘못된 결론(예: "캐싱이 도움이 안 된다")에 도달할 수 있다.** 같은 코드를 네이티브/Docker 두 환경에서 비교 측정함으로써 "느려진 게 코드 문제인지 환경 문제인지"를 구분할 수 있었다.
4. **캐싱의 효과는 단일 요청 latency가 아니라 DB 쿼리 볼륨 감소로 판단하는 것이 이 설계의 목표(DB 병목 방지)에 더 부합한다.**
5. **Before/After를 비교할 때는 비교 대상 외의 조건을 모두 동일하게 통제해야 한다.** 처음엔 DB(네이티브)와 Redis(Docker)의 인프라 조건이 서로 달랐고 데이터 볼륨도 작아 캐시 효과가 묻혔다. 데이터 볼륨을 늘리고 두 저장소를 모두 네이티브로 맞춰 조건을 통일하자 캐싱의 효과가 raw 응답시간으로도 명확하게 드러났다 — "공정한 비교"가 성능 측정의 신뢰도를 좌우한다는 걸 보여주는 사례.
6. **읽기 경로를 고쳤다고 쓰기 경로도 자동으로 안전해지는 건 아니다.** MGET으로 읽기의 순차 호출 문제를 고쳤지만, 쓰기(`writeItemCache`)는 같은 문제를 그대로 안고 있었다. 정상 상황에서는 왕복 비용이 작아 안 드러났고, **Redis 장애 상황을 실제로 재현해보고 나서야** 타임아웃이 곱해지는 문제로 발견됐다 — "fail-open 검증"이 단순히 "5xx 안 나는지"만 보는 게 아니라 "얼마나 걸리는지"까지 봐야 하는 이유다.
7. **테스트를 반복하다 보면 환경이 저절로 "따뜻해져서"(warm-up) 정작 지키려던 시나리오(콜드스타트)를 재현하지 못하게 될 수 있다.** 락 없이 붙였을 때는 우연히 늘 "콜드"(리시드 직후 첫 조회)로 측정됐는데, 락을 붙인 뒤 반복 검증하는 과정에서 같은 세션 안에서 재테스트하다 보니 DB가 계속 "웜"한 상태로 측정돼 문제(재시도 창이 너무 짧음)를 놓칠 뻔했다 — 매번 **앱을 완전히 재기동하고 데이터를 새로 시딩한 직후**에 측정해야 진짜 콜드스타트를 재현할 수 있었다.
8. **부하테스트 도구 자체의 한계(타임아웃 설정)가 실제 서버 문제로 오인될 수 있다.** 재시도 예산을 늘린 뒤 "50건 중 16건만 성공"이라는 결과가 나와 새로운 버그로 의심했지만, 실제로는 내가 만든 Node.js 스크립트의 클라이언트 타임아웃(5초)이 늘어난 대기 시간(최대 4초 재시도 + 쿼리 시간)보다 짧아서 생긴 오탐이었다. 타임아웃을 늘려 재측정하니 서버는 정상이었다 — 측정 도구 자체의 설정도 실측 결과 해석의 일부로 검증해야 한다.

### 결과 — 비교 2: 콜드스타트 분산 락 적용 여부

| p99 | 2595.1ms | 1107.2ms (약 2.3배 개선) |
| 락 해제 후 Redis 상태 | - | `lock:*` 키 잔존 없음(정상 해제 확인) |
| Redis 완전 중단 시 | - | 5xx 없이 200으로 degrade (fail-open 확인) |
| Redis 중단 상태에서 코스 존재하는 요청의 응답 시간 | - | 최초 8.29초 → 아이템 캐시 쓰기 배치화 후 **4.25초**로 개선 |

**추가로 발견한 문제 — 아이템 캐시 쓰기도 순차 개별 호출이었다**:

fail-open 검증(Redis 중단 상태 테스트) 중, 코스가 실제로 존재하는 조건(`theme=FOOD`)의 요청이 **8.29초**나 걸리는 것을 발견했다. 로그에서 `RedisCommandTimeoutException: Command timed out after 1 second(s)`가 반복적으로 찍혔는데, 설정한 타임아웃(1초)은 정확히 지켜지고 있었지만 **한 요청 안에서 Redis 호출이 순차적으로 8번**(랭킹 조회 1 + 락 시도 1 + 아이템 MGET 조회 1 + 아이템 저장 5회) 발생해 1초씩 곱해진 것이었다.

3-5에서 읽기(MGET)는 배치로 고쳤지만, **쓰기(`writeItemCache`)는 여전히 캐시 미스 코스 개수만큼 개별 `cache.put()`을 반복하는 구조로 남아있었다** — 정상 상황에서는 왕복 비용(수 ms)이 작아 안 드러났지만, Redis 장애 상황에서는 실패할 때마다 타임아웃(1초)을 꽉 채우고 나서야 다음 시도로 넘어가므로 그 비용이 그대로 곱해졌다.

**왜 MGET 때와 똑같이 못 고쳤나 — MSET은 TTL을 못 건다**:

읽기 쪽은 Redis의 `MGET` 커맨드를 그대로 갖다 쓰면 끝이었다. 그런데 쓰기 쪽엔 대응되는 손쉬운 해법이 없다 — Redis에도 여러 키를 한 번에 쓰는 `MSET`이 있지만, **`MSET`은 값만 저장할 뿐 만료시간(TTL)을 같이 지정할 수 없다.** 아이템 캐시는 반드시 TTL(2시간, `RedisConfig.COURSE_LIST_ITEM_TTL`)이 걸려야 하는 캐시라(안 그러면 삭제된 코스의 콘텐츠가 영원히 안 지워지는 등의 문제로 이어짐), `MSET`을 그대로 쓸 수 없었다.

그래서 "여러 명령을 하나의 커맨드로 합친다"(MGET 방식)가 아니라, **"여러 개별 SET 명령을 하나의 네트워크 왕복 안에 실어 보낸다"(파이프라이닝)**는 다른 방식을 택했다. Redis 입장에서는 여전히 SET을 코스 개수만큼 실행하지만(그래서 TTL도 각 커맨드에 정상적으로 지정 가능), 그 커맨드들을 모아서 한 번에 전송하고 응답도 한 번에 받아오므로 **네트워크 왕복만 1회로 줄어든다.**

**추가로 발견한 문제 — 재시도 창(150ms)이 정작 콜드스타트에서는 너무 짧았다**:

락 자체는 정상 동작했지만(위 표의 "락 적용" 수치는 재검증 과정에서 재현), **락을 새로 복원한 직후 재검증하다가 DB 쿼리가 10회(락 없음과 동일한 패턴)로 나오는 현상**을 발견했다. 원인을 추적한 결과:

- 재시도 창은 `50ms × 3회 = 150ms`로 설계돼 있었는데, 이는 "랭킹 쿼리가 빠르다"는 암묵적 가정 위에 있었다.
- 그런데 앱을 **완전히 재기동하고 데이터를 막 새로 넣은 직후**(진짜 콜드스타트)의 첫 조회는 1.7~2.5초가 걸렸다 — 재시도 창(150ms)의 10배 이상.
- 락을 못 딴 나머지 요청들은 150ms만 기다려보고 승자가 아직 안 끝났으면 "재시도 실패"로 판단해 **자기들도 DB로 직행**해버렸다 — 락이 있어도 승자가 끝나기 한참 전에 나머지가 포기하고 몰려가는, 사실상 락이 무력화되는 상황이었다.
- 같은 세션에서 반복 테스트하면 DB(Postgres 버퍼/OS 페이지 캐시)가 데워져서 쿼리가 빨라지고(500ms대), 그러면 재시도 창 안에 들어와 락이 정상 작동하는 것처럼 보였다 — **정작 락이 지켜야 할 "진짜 콜드스타트" 상황에서만 재현되는 결함**이라 반복 테스트 중엔 놓치기 쉬웠다.
- 완전 재기동 + 재시딩 + 즉시 부하테스트를 2회 반복해 재현성을 확인한 뒤, 재시도 예산을 `50ms × 3회(150ms)` → `200ms × 20회(4초, 락 TTL 5초보다 짧게)`로 늘렸다. 같은 콜드 재현 절차로 재검증한 결과 **콜드스타트에서도 DB 쿼리 1회로 수렴**함을 확인했다.
- 늘어난 재시도 예산 자체가 새로운 병목(Lettuce 커넥션 풀 경합)을 만드는지도 의심해 확인했으나, 실제로는 위 8번 교훈에서 설명한 **부하테스트 스크립트의 타임아웃 설정 문제**였을 뿐 서버 측 문제는 아니었다.

**재시도 예산 재조정 — 4초는 실제 데이터 규모에 비해 과했다**:

4초는 벤치마크용으로 강제로 채운 50만 건(실제 서비스 데이터가 아님) 기준으로 정한 값이었다. 실제 데이터는 그 근처도 아니므로, 존재하지도 않는 극단치에 맞춰 모든 사용자를 최대 4초씩 기다리게 할 이유가 없다는 지적을 받고 **1초(10회 × 100ms)로 절충**했다.

**콜드스타트 지연의 진짜 원인 재확인 — 데이터量보다 "재기동 직후 첫 실행"이 더 크다**:

재시도 예산을 조정한 뒤, 훨씬 작은 규모(3,000건)로도 콜드스타트 재현을 해봤다. 결과: 3,000건에서도 완전 재기동 직후 첫 조회는 **1.6초 넘게 걸렸고**(같은 세션 재실행 시 283ms로 급락), 이는 앞서 "50만 건이라 느리다"고 설명했던 것과 맞지 않았다. 이를 통해 콜드스타트 지연의 더 큰 비중이 **데이터量에 비례하는 비용(스캔+정렬)이 아니라, 서버 재기동 후 이 쿼리 경로를 처음 실행할 때 드는 고정 비용**(Hibernate의 최초 쿼리 파싱/실행계획 생성, JVM이 아직 이 코드를 JIT 컴파일하지 않은 상태, 커넥션 풀의 최초 연결 등)이라는 걸 확인했다 — 이 비용은 테이블 크기와 거의 무관하게 발생한다.

이 발견에 따라 두 가지를 구분해서 대응하기로 했고, `redis-caching-strategy.md`의 3번 섹션에 정식 체크리스트 항목으로 추가했다:
- **3-7 (`view_count` 인덱스 추가)**: 데이터量에 비례하는 비용을 없앤다.
- **3-8 (서버 기동 시 웜업)**: 재기동 직후의 고정 비용을 없앤다 — `ApplicationReadyEvent`로 부팅 시점(아무도 안 기다리는 때)에 이 쿼리 경로를 미리 한 번 실행해 Hibernate/JVM/커넥션 풀을 데워두고 캐시도 미리 채운다.

두 항목 다 3-6의 분산 락을 대체하지 않는다 — Redis만 단독으로 재시작되는 경우(앱은 안 죽음)엔 웜업이 재실행되지 않으므로, 그 경우엔 여전히 3-6의 락이 유일한 방어선이다.

### 3-7. `view_count` 인덱스 추가 — 구현 및 검증

**구현**: `UploadCourse` 엔티티에 `@Table(indexes = @Index(name = "idx_upload_course_view_count", columnList = "view_count"))`를 추가했다. 컬럼 하나짜리 단일 인덱스로 충분하다고 판단한 이유는, PostgreSQL B-tree 인덱스는 양방향(backward) 스캔이 가능해 `ORDER BY view_count DESC`에도 오름차순 인덱스가 그대로 쓰이기 때문이다(별도 DESC 인덱스 불필요 — 아래 `EXPLAIN ANALYZE` 결과의 `Index Scan Backward`가 이를 보여준다).

**운영 반영 방식에 대한 결정**: 이 레포에는 Flyway/Liquibase 같은 마이그레이션 도구가 없고, 스키마는 `spring.jpa.hibernate.ddl-auto`(환경변수 `DB_DDL_AUTO`)에 전적으로 의존한다. 로컬(`.env`)은 `DB_DDL_AUTO=create`라 앱 재기동 시 엔티티 애너테이션만으로 인덱스가 자동 생성·검증되지만, 운영 권장값(`.env.example`)은 `DB_DDL_AUTO=validate`다. Hibernate의 `validate` 모드는 테이블/컬럼 존재 여부만 확인하고 **인덱스 존재 여부는 아예 검증 대상이 아니며 생성도 하지 않는다** — 즉 엔티티 애너테이션만으로는 운영 DB에 인덱스가 생기지 않는다.

이번 작업 범위에서는 실제 운영 DB에 접근해 DDL을 실행하지 않고(마이그레이션 도구를 새로 도입하는 것도 이번 범위 밖으로 판단), 운영 반영에 필요한 DDL만 기록해둔다.

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_upload_course_view_count
    ON upload_course (view_count);
```

- `CONCURRENTLY`를 쓰는 이유: 일반 `CREATE INDEX`는 인덱스를 만드는 동안 테이블에 `ACCESS EXCLUSIVE` 락을 걸어 그 사이 모든 읽기/쓰기가 막힌다. 운영 테이블(트래픽이 있는 상태)에 인덱스를 추가할 때는 이 락을 피하기 위해 `CONCURRENTLY`를 써야 한다.
- `CONCURRENTLY`는 트랜잭션 블록 안에서 실행할 수 없다 — 단독 문장으로, 트랜잭션을 감싸지 않는 도구(`psql` 등)에서 직접 실행해야 한다.

**로컬 검증 결과**:
- `./gradlew bootRun`(`DB_DDL_AUTO=create`) 재기동 후 `pg_indexes`로 확인한 결과, `upload_course` 테이블에 `idx_upload_course_view_count`가 정상 생성됨을 확인했다(부팅 로그에도 `create index idx_upload_course_view_count` 실행 확인).
- `EXPLAIN ANALYZE SELECT upload_course_id FROM upload_course ORDER BY view_count DESC LIMIT 5;` 실행 결과, 실행계획이 `Index Scan Backward using idx_upload_course_view_count`로 이 인덱스를 실제로 사용함을 확인했다. 로컬 DB가 현재 0건이라(`data.sql` 미커밋) `Seq Scan`과의 실측 성능 차이 비교는 이번엔 하지 않았다 — 이미 3-6 벤치마크에서 인덱스 부재로 인한 50만 건 스캔 비용(쿼리당 1.7~2.5초)을 확인해뒀으므로, 이번 검증의 목적은 "인덱스가 실제로 생성되고 옵티마이저가 선택하는지" 확인으로 충분하다고 판단했다.

### 3-8. 서버 기동 시 인기 목록 웜업 — 구현 및 검증

**구현**: `domain/uploadcourse/initializer/PopularCourseCacheWarmer`를 새로 추가했다. `@EventListener(ApplicationReadyEvent.class)`로 부팅 완료 시점에 `null`(전체) + `KeywordType.findByCategory("mood")` 7종, 총 8개 테마를 순회하며 기존 `UploadCourseService.getPopularCourses(theme)`를 그대로 호출한다.

- **새 캐시-쓰기 코드를 만들지 않은 이유**: `getPopularCourses`는 이미 랭킹 캐시 조회 → 미스 시 분산 락 → DB 조회 → `writeRankingCache` → 아이템 캐시 채우기까지 한 메서드 안에 다 갖고 있다. 이걸 그대로 8번 호출하면 랭킹 캐시뿐 아니라 아이템 캐시(코스 제목/썸네일 등)까지 부수적으로 채워지고, 락 획득/해제·fail-open도 전부 기존 코드를 그대로 재사용하게 된다. 원문서 체크리스트 문구("인기 목록 웜업")는 랭킹 캐시만 지칭하는 것으로도 읽히지만, 기존 프로덕션 경로를 그대로 타는 이 방식이 새 코드 없이 더 안전하다고 판단해 아이템 캐시까지 함께 채우는 쪽으로 범위를 넓혔다.
- **`ApplicationReadyEvent`를 택한 이유**: 이 레포의 유일한 부팅 훅 선례(`TestUserInitializer`)는 `ApplicationRunner`를 구현하지만, `ApplicationReadyEvent`는 애플리케이션 컨텍스트가 완전히 준비된 뒤(요청을 받을 준비가 된 시점) 발행되는 이벤트라 "캐시를 미리 데워둔다"는 웜업의 의도와 의미상 더 맞아떨어진다고 판단했다. 두 방식 모두 부팅 마지막 단계에서 실행되어 타이밍상 실질적 차이는 크지 않다.
- **개별 테마를 try-catch로 감싼 이유**: `getPopularCourses` 내부의 Redis 관련 예외는 이미 fail-open 처리돼 있지만, DB 예외까지 전파되면 `ApplicationReadyEvent` 리스너의 예외가 애플리케이션 부팅 자체를 실패시킬 수 있다. 웜업은 순수 최적화이므로 한 테마가 실패해도 나머지 7개와 앱 부팅에는 영향이 없어야 한다. `@SpringBootTest`를 쓰는 `YourtripApplicationTests`(레포에 유일한 컨텍스트 로드 테스트)도 이 경로를 그대로 타게 되므로, 이 방어가 테스트 안정성에도 필요하다.

## 발견한 개선점 (이번 작업 범위 밖 — 코드 수정 없이 기록)

### 검색 결과 API도 `courseListItem` 캐시를 재사용할 수 있다

검색 화면(키워드/태그 필터링 + 정렬)이 호출하는 `UploadCourseServiceImpl.getAllForSearch`는 `findAllByKeywordsOrderByViewCountDesc`/`findAllByKeywordsOrderByCreatedAtDesc` 쿼리로 조건에 맞는 코스를 매번 DB에서 전체 엔티티(+ keywords JOIN FETCH)까지 통째로 조회한다. 이번 3번 섹션은 `/popular` 엔드포인트만 다루므로 이 경로는 캐싱 없이 그대로 남는다.

**개선 아이디어**: "조건에 맞는 ID를 찾는 것"과 "그 ID들의 콘텐츠를 조립하는 것"을 분리하는 이번 섹션의 패턴을 검색 API에도 적용할 수 있다. `LEFT JOIN FETCH`로 풀 엔티티를 한 번에 가져오는 대신 ID만 조회하는 쿼리로 바꾸고, 콘텐츠는 `courseListItem` 캐시에서 배치 조회(`multiGet`)하면 된다. 인기 코스는 어떤 검색 조건에서도 상위권에 자주 등장하므로, 검색 결과에 이미 인기 목록 캐싱으로 채워진 코스가 포함될 확률이 낮지 않다. "조건 매칭" 자체는 조합이 무한해 여전히 캐싱할 수 없지만(문서의 "범위에서 제외한 것"과 동일한 이유), 콘텐츠 조립 부분만큼은 기존 캐시 히트로 DB 부하를 줄일 수 있다.

**왜 지금 하지 않는가**: 검색 API의 리포지토리 쿼리 구조 자체를 바꾸는 작업이라 이번 섹션(`/popular` 전용) 범위를 벗어난다. 검색 API는 페이지네이션도 없는 상태라(별도 범위 제외 항목) 그쪽 개선과 묶어서 검토하는 게 합리적일 수 있다.

## 진행 방식 원칙

이 작업은 체크리스트 항목(3-1~3-6)을 한 번에 끝까지 진행하지 않고, **항목 하나씩 구현 → 보고 → 사용자 확인 → 다음 항목** 순서로 진행한다. 설계·구현 방식 중 애매하거나 중요한 결정 사항(API 구성, theme 검증 범위, 캐시 구조, 삭제/웜업 처리 방향 등)은 임의로 판단하지 않고 매번 먼저 질문해 답변을 받은 뒤에만 진행했다.
