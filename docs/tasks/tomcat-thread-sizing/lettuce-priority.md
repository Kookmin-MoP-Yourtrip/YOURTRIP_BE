# lettuce 이벤트루프에 우선순위를 주면 서버 전체가 빨라지는가

> [#210](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/210)의 설계·사전 등록·결과 기록이다. [lettuce-dispatch-latency.md](lettuce-dispatch-latency.md) 6-8(#207)에서 lettuce 선점의 91~94%가 **lettuce 자신이 직전에 깨운 Tomcat 워커**의 깨어남 선점임을 확인했다. 이 문서는 lettuce 스레드에만 `renice`로 높은 우선순위를 줬을 때 **서버 전체** 성능이 나아지는지, 나빠지는지를 가린다. 1~5절은 측정 전에 썼다.

## 1. 왜 Redis 지연은 판정 지표가 될 수 없는가

부하 시나리오(`popular-cold.js`)에는 think time이 없다. VU 200이 응답을 받자마자 다음 요청을 보내는 **닫힌 루프**라서, 리틀의 법칙에 따라 평균 응답시간이 TPS로 정해진다.

```
평균 응답시간 = VU ÷ TPS          (실측: 6-6의 T200, 200 ÷ 3,404 = 58.8ms ↔ k6 평균 58.5ms)
```

- **TPS가 그대로면 평균 응답시간도 그대로다.** 그 상태에서 Redis 지연이 줄었다면 그 시간은 사라진 게 아니라 다른 곳(주로 워커의 런큐 대기)으로 옮겨간 것이다.
- 실제로 그런 일이 있었다. T200 → T32에서 Redis 지연은 13.75 → 3.11ms로 줄었는데 TPS는 2,781 → 2,735(−1.7%)였다(6-1). 추적 없이 다시 잰 6-6에서는 −6%였다.
- 그래서 판정 지표는 **TPS(= 평균 응답시간)와 요청당 CPU**다. p95는 분포가 어떻게 바뀌었는지를 보는 보조 지표다. lettuce 쪽 지표(선점 수·Redis 지연)는 **메커니즘을 확인하는 데만** 쓴다.

## 2. TPS가 오를 수 있는 유일한 경로 — 요청당 CPU

박스는 CPU 포화 상태다(2 vCPU). 우선순위는 CPU를 **누구에게 먼저 주는가**를 바꿀 뿐 CPU 총량을 늘리지 않는다. 따라서 TPS가 오르려면 **요청 하나에 드는 CPU가 줄어야** 한다. 이 관점에서 이슈의 두 가설은 하나의 갈림길로 모인다 — **lettuce가 CPU를 한 번 잡았을 때 응답을 몇 개나 처리하는가(배정당 명령 수)** 다.

| | 찬성 쪽 | 반대 쪽 |
|---|---|---|
| nice 적용 후 lettuce | 잘 밀려나지 않아 한 번 잡으면 쌓인 응답을 더 많이 처리한다 | 더 일찍·자주 CPU를 받아 응답이 덜 쌓인 상태에서 처리한다 |
| 배정당 명령 수 | 증가 | 감소 |
| 요청당 전환·CPU | 감소 → TPS 상승 | 증가(epoll 호출·전환 증가) → TPS 하락 |

배정당 명령 수는 직접 재는 계측이 없지만 같은 창의 값으로 계산할 수 있다.

```
배정당 명령 수 = (요청당 명령 수 × TPS) ÷ lettuce 배정/초      (6-1의 T200: 5,562 ÷ 3,247 ≈ 1.71)
```

요청당 명령 수는 GET + MGET 2회이고(lettuce-dispatch-latency.md 4-2 ②), `summarize-batch.py`의 `명령/요청` 열로 run마다 확인한다.

## 3. CFS 6.1에서 nice가 선점을 줄일 수 있는 이유 — 가설

커널 6.1 코드에서 끌어낸 추론이고, 측정 전에는 검증되지 않았다.

- CFS는 깨어난 스레드의 vruntime이 지금 도는 스레드보다 **깨어남 기준값(2 vCPU에서 약 2ms)** 이상 작으면 즉시 선점을 일으킨다.
- lettuce는 거의 잠들지 않고 혼자 CPU의 약 12%를 쓴다(6-3). **스레드 하나 단위로는 vruntime이 가장 빨리 쌓인다.** 반면 Redis 응답을 기다리며 잠들었던 워커는 vruntime이 뒤처져 있다. 그래서 lettuce가 깨운 워커가 거의 매번 lettuce를 밀어낸다 — 공정성 규칙이 가장 바쁜 단일 스레드를 불리하게 대하는 셈이다.
- nice −10은 가중치를 1024 → 9548(약 9.3배)로 올려, 같은 실행 시간에 쌓이는 vruntime을 그만큼 줄인다. 이론상 깨어난 워커가 기준값을 넘기 어려워진다.
- **효과의 크기는 이론으로 정해지지 않는다.** 오래 잠들었던 스레드는 깨어날 때 vruntime이 `min_vruntime − 6ms`로 끌어올려지는데(GENTLE_FAIR_SLEEPERS), 그 `min_vruntime`을 lettuce 자신이 끌고 갈 수 있다. 그래서 4절의 P1(선점 감소)을 메커니즘 확인 조건으로 둔다.

## 4. 사전 등록 — 예측과 판정

### 4-1. arm과 비교 단위

| arm | maxThreads | lettuce 이벤트루프 nice |
|---|---|---|
| `T32` | 32 (운영 설정) | 0 |
| `T32+nice10` | 32 | **−10** |
| `T200` | 200 | 0 |
| `T200+nice10` | 200 | −10 |

- **주 판정은 T32 쌍이다** — 운영 설정이기 때문이다. T200 쌍은 lettuce가 더 심하게 눌린 조건에서의 보조 비교다.
- nice 값은 −10 하나로 둔다. 효과가 보이면 그때 단계(−5·−20)를 나눈다.
- 비교는 **같은 회차의 쌍**(nice arm ÷ 기준 arm)으로 한다. 회차는 4회이고, 홀수 회차는 정순·짝수 회차는 역순이라 시간 표류가 한쪽 arm에만 얹히지 않는다.

### 4-2. 예측 (VU 200, nice ÷ 기준, 4회 평균)

| # | 예측 | 출처 | 확신 |
|---|---|---|---|
| P1 | lettuce **비자발 전환(선점)/초가 0.7배 이하**로 준다 — nice가 겨냥한 메커니즘이 실제로 움직였는가 | schedstat | 중 |
| P2 | lettuce **런큐 대기 비율이 내려가고 자발 전환(수면) 비중이 오른다** — lettuce가 포화에서 벗어나 T8처럼 잠들기 시작한다 | schedstat | 중 |

| P4 | **대기가 옮겨간다** — 요청당 tomcat 런큐 대기 증가분이 요청당 Redis 시간 감소분의 **50% 이상**을 상쇄한다 | schedstat, Prometheus | 중 |
| P5 | **배정당 명령 수가 0.8배 이하**로 준다 — 뭉치가 쪼개진다 | 2절 계산식 | 낮음 |

P3이 맞고 P6도 맞으면 "lettuce 지표는 좋아졌지만 서버는 그대로"라는 이슈의 반대 가설 그림이 된다. 이 그림은 1절의 산술(닫힌 루프)에서 나온 예측이라 확신을 "중"으로 뒀다.

### 4-3. 판정 규칙 — 주 판정은 T32 쌍

| 판정 | 조건 |
|---|---|
| **개선** | TPS가 **+5% 이상**이고 4쌍 중 3쌍 이상이 같은 방향이며, p95가 +10%를 넘게 나빠지지 않는다 |
| **악화** | 다음 중 하나라도 4쌍 중 3쌍 이상에서 성립한다: TPS **−5% 이하** / p95 **+10% 이상** / 요청당 CPU **+5% 이상** |
| **효과 없음** | 위 둘 다 아니다. **Redis 지연만 좋아진 경우도 여기에 속한다** |

- **±5%의 근거**: 같은 arm의 회차 간 TPS 차이가 0.1~9%였다(6-6·6-7). 단일 run 차이보다는 좁고, 4쌍 중 3쌍의 방향 일치로 우연을 거른다.
- **P1이 틀리면(선점이 0.7배 이하로 줄지 않으면)**, TPS가 어떻게 나오든 "nice가 선점을 줄여서"라고 설명하지 않는다. 다른 경로(예: 수면 후 깨어남 우대)를 원인 후보로 따로 적는다.
- 결과별 후속: **개선**이면 운영 적용 방식(systemd 권한, 스레드 재생성 시 재적용)을 별도 이슈로 뗀다. **악화·효과 없음**이면 "CFS 기본 동작이 이 워크로드에 맞다"는 근거로 이 문서에 남기고 끝낸다.

## 5. 측정 설계

### 5-1. 두 배치로 나눈다 — 판정과 메커니즘

bpftrace는 추적 창 안 TPS를 평균 −3.6% 떨어뜨렸다(6-8의 G4). 게다가 bpftrace 스레드도 같은 CPU를 다툰다. nice 효과가 5% 안팎이면 추적 부하와 섞여 가릴 수 없다. 그래서 **판정은 추적 없는 배치로**, 선점자 구성은 별도 배치로 본다.

| 배치 | 용도 | 설정 |
|---|---|---|
| **J (판정)** | 4-3 판정, P1~P7 | `ARMS="T32 T32+nice10 T200 T200+nice10" REPS=4 LEVELS="5 20 50 200" SCHEDSTAT=1 SCHEDSTAT_SEC=30 SCHEDLAT=0` |
| **M (메커니즘)** | 선점자 구성이 바뀌었는가(6-8 표 재현) | `ARMS="T32 T32+nice10 T200 T200+nice10" REPS=2 LEVELS="200" WARMUP_SEC=60 SCHEDSTAT_SEC=30 SCHEDLAT=1` (#207과 같은 구성) |

J는 lettuce-dispatch-latency.md 7절의 "추적 없는 대조 run" 후속 과제도 겸한다. 낮은 VU 레벨(5·20·50)은 6-6과 같은 이유로 JIT 예열을 겸한다. 예상 소요는 J 약 2시간 10분, M 약 30분이다.

### 5-2. nice 적용 — [scripts/loadtest/renice-lettuce.sh](../../../scripts/loadtest/renice-lettuce.sh)

- **스레드 단위로 건다.** 리눅스에서 `setpriority(PRIO_PROCESS, tid)`는 스레드 하나에만 적용된다. JVM의 `Thread.setPriority`는 리눅스 기본 설정(`ThreadPriorityPolicy=0`)에서 무시되므로 쓰지 않는다. systemd의 `Nice=`는 프로세스 전체에 걸려 실험 의도와 다르다.
- **대상은 lettuce 이벤트루프 스레드 전부다**(`lettuce-epollEv*`/`lettuce-nioEven*`). 2개가 있고(`max(vCPU, 2)`) 공유 커넥션이라 그중 하나만 일하는데, 어느 쪽이 일할지는 기동 전에 알 수 없다.
- **적용 시점은 arm 예열 직후다.** arm 전환마다 앱이 재기동해 tid가 바뀌고, netty 이벤트루프 스레드는 첫 작업이 들어올 때 생긴다. 예열이 끝난 뒤라야 대상이 존재한다.
- 리눅스에서 새 스레드는 **만든 스레드의 nice를 물려받는다.** 이벤트루프가 예열 뒤에 새로 생기면 Tomcat 워커(nice 0)에게서 0을 물려받을 수 있다. 그래서 적용 직후뿐 아니라 schedstat 창 끝에서도 nice를 기록한다(N1).
- 음수 nice는 `CAP_SYS_NICE`가 필요하다. loadtest에서는 `sudo`로 해결한다.

### 5-4. 실행 계획

1. **loadtest 스택 재생성** — 모듈이 철거돼 있다. AMI는 이미 `kernel-6.1`로 고정돼 있다(#208).
2. JAR 배포 → 시딩 → 빈 랭킹 캐시 함정 확인(4-2 ②: 예열에서 GET 수 = MGET 수).
3. 스크립트 scp(`renice-lettuce.sh` 포함) → nice arm 하나로 **N1 수동 확인**(renice 후 `/proc/<pid>/task/<tid>/stat`의 nice 필드).
4. 배치 J → 배치 M.
5. `summarize-batch.py`(J)·`summarize-sched-latency.py`(M)로 집계해 6절에 결과와 판정을 남긴다.
6. 인프라 철거(`destroy`).

## 6. 결과 (2026-10-14, 커널 6.1.188, VU 200, 쌍 4개)

> **결론 — 운영 설정(T32)에서는 악화다.** nice −10은 겨냥한 메커니즘을 거의 완전히 바꿨다. lettuce 선점은 **×0.01**로 사라졌고 Redis 지연은 **2.14 → 0.45ms**로 줄었다. 그런데 TPS는 **3,533 → 3,277(×0.93, 4쌍 모두 하락)**, 요청당 CPU는 **+15%(4쌍 모두 상승)**, p95는 **70.3 → 74.4ms**였다. 반대 가설이 맞았다. CFS가 lettuce를 밀어내는 기본 동작이 사실은 **응답을 모아서 처리하게 만드는 일괄 처리 장치**였고, 우선순위가 그것을 없애자 lettuce가 응답마다 깨어나며 문맥 전환과 CPU가 두 배로 늘었다. 보조 비교인 T200에서는 사전 등록 규칙상 "개선"(+7.5%)이 나왔지만, 그 결과(3,450)도 nice 없는 T32(3,533)에 못 미쳐 운영 결정은 바뀌지 않는다.

원자료는 `results/lettuce-priority/`(gitignore)에 있다. 집계는 `compare-arm-pairs.py`로 냈고, 판정 규칙은 4-3을 측정 전 값 그대로 코드로 옮긴 것이다.

### 6-1. 판정 (배치 J, 추적 없음)

| arm 평균 (VU 200) | TPS | p95(ms) | 요청당 CPU(vCPU-ms) | k6 평균(ms) | Redis 지연(ms) |
|---|---|---|---|---|---|
| **T32** (운영) | **3,533** | **70.3** | **0.508** | 56.5 | 2.14 |
| T32+nice10 | 3,277 | 74.4 | 0.587 | 60.7 | 0.45 |
| T200 | 3,219 | 99.4 | 0.594 | 62.0 | 11.48 |
| T200+nice10 | 3,450 | 96.7 | 0.550 | 57.8 | 3.17 |

| 쌍 (처치 ÷ 기준) | TPS 쌍별 | 요청당 CPU 쌍별 | p95 쌍별 | **판정(4-3)** |
|---|---|---|---|---|
| **T32+nice10 ÷ T32** | −2.0 / −9.8 / −11.1 / −5.4% | +16.7 / +13.4 / +16.7 / +14.8% | +2.6 / +9.1 / +8.8 / +3.5% | **악화** — TPS −5% 이하 3/4쌍, 요청당 CPU +5% 이상 4/4쌍 |
| T200+nice10 ÷ T200 | −4.7 / +7.2 / +15.9 / +11.7% | +4.8 / −5.7 / −15.0 / −12.3% | +14.0 / −2.3 / −12.7 / −7.9% | 개선 — TPS 평균 +7.5%, 같은 방향 3/4쌍 |

- 닫힌 루프 산술(1절)이 그대로 맞았다. 평균 응답시간은 VU ÷ TPS다(T32: 200 ÷ 3,533 = 56.6ms ↔ k6 56.5ms, T32+nice10: 61.0 ↔ 60.7ms). Redis 지연이 80% 줄어도 TPS가 떨어지면 평균 응답시간은 늘어난다.
- **T200 쌍의 "개선"은 기준 arm이 흔들린 영향이 크다.** T200 기준 arm의 TPS가 회차별로 3,410 / 3,366 / **3,000 / 3,101**로 13% 흔들렸고, 개선 폭이 큰 두 쌍(r3·r4)이 바로 기준이 낮았던 회차다. 사전 등록 규칙을 그대로 적용해 "개선"으로 기록하지만, 보조 비교라 운영 판단에는 쓰지 않는다.

### 6-2. 사전 등록 예측 대조 (T32 쌍)

| # | 예측 | 실측 (처치 ÷ 기준, 4쌍 평균) | 판정 |

| P2 | 대기 비율 하락·수면 비중 상승 | 대기 비율 87.0 → **6.1%**, 자발 비중 7.3 → **99.6%** | 적중 |
| P3 | Redis 지연 ≤ 0.7배 | **×0.21** (2.14 → 0.45ms) | 적중 |
| P4 | 대기 이동이 Redis 감소분의 50% 이상 상쇄 | 요청당 Redis −3.39ms, 요청당 tomcat 런큐 대기 **+6.67ms(상쇄율 197%)** | 적중 — 줄어든 것보다 두 배 많이 옮겨갔다 |
| P5 | 배정당 명령 수 ≤ 0.8배 | **×0.37** (1.65 → 0.61) | 적중 (확신 "낮음"으로 등록) |
| P6 | TPS ±5% 안 | **×0.929** | **기각** — 예상보다 나빴다 |
| P7 | 요청당 CPU +2% 이상 | **+15.3%** | 적중 (확신 "낮음"으로 등록) |

### 6-3. 왜 나빠졌나 — CFS의 선점은 일괄 처리 장치였다

| T32 쌍, 4회 평균 | 기준 | nice −10 | 비 |
|---|---|---|---|
| lettuce 배정/초 | 4,278 | 10,928 | ×2.56 |
| **배정당 명령 수** | **1.65** | **0.61** | ×0.37 |
| **lettuce CPU 점유** | **12.1%** | **25.4%** | ×2.09 |
| 요청당 문맥 전환 | 4.36 | 9.53 | ×2.19 |
| host CPU busy | 92.5% | 99.0% | |

- **기본 동작에서는** lettuce가 일하다 자기가 깨운 워커에게 밀려나고 약 200μs를 기다린다(lettuce-dispatch-latency.md 6-8, T32 선점 후 재대기 203~207μs). 그 사이 Redis 응답과 보낼 명령이 쌓이므로, 다시 CPU를 얻었을 때 **한 번에 1.65개**를 처리한다.
- **nice −10에서는** lettuce가 밀려나지 않고, 처리할 일이 생기는 즉시 깨어난다. 쌓일 틈이 없어 **배정당 0.61개**만 처리하고 다시 잠든다. 1보다 작다는 것은 명령 하나의 쓰기와 응답 읽기가 각각 따로 깨어남을 일으킨다는 뜻이다.
- 깨어남마다 epoll 호출과 문맥 전환 비용이 붙는다. 그래서 같은 일을 하는데 lettuce의 CPU가 **두 배**가 됐고, 요청당 문맥 전환도 두 배가 됐다. 박스는 원래 CPU 포화 상태라(host busy 92.5%) 늘어난 비용이 그대로 처리량 감소(TPS −7%)로 나타났다.
- 워커 쪽에서는 대기가 늘었다. lettuce가 깨어날 때마다 워커를 밀어내므로(가중치가 9.3배다) 요청당 워커 런큐 대기가 **1.55 → 8.22ms**가 됐다. Redis에서 아낀 3.4ms보다 훨씬 크다.

정리하면, #207(lettuce-dispatch-latency.md 6-8)에서 "결함처럼 보였던" lettuce의 선점은 실제로는 **인터럽트 병합(interrupt coalescing)과 같은 역할**을 하고 있었다. 지연을 조금 내주고 처리할 일을 모아, 깨어남 1회당 비용을 여러 명령에 나눠 싣는 것이다. 처리량이 중요한 CPU 포화 상태에서는 CFS 기본 동작이 이 워크로드에 맞다.

### 6-4. T200에서는 왜 반대 방향이었나

T200의 lettuce는 T32보다 훨씬 심하게 굶주린다(in-flight 명령 수가 스레드 상한에 묶여 4배 이상, lettuce-dispatch-latency.md 6-4). nice −10을 줘도 runnable 워커가 많아 선점이 ×0.37까지만 줄었고, **배정당 명령 수는 ×1.01로 그대로**였다. 일괄 처리 효과는 유지한 채 lettuce가 CPU를 조금 더 받은 셈이라(점유 10.5 → 15.2%), 쪼개짐 비용 없이 대기만 줄었다. 즉 **nice의 효과는 lettuce가 얼마나 굶주렸는지에 따라 방향이 바뀐다.** 다만 T200에 nice를 더한 최선의 결과(3,450)도 스레드 상한 32(3,533)보다 낮다. 경합 상대를 줄이는 쪽(#88)이 피해자의 우선순위를 올리는 쪽보다 낫다.

### 6-5. 누가 밀려나는가 — 선점자 구성 (배치 M, bpftrace)

배치 M은 선점자 구성을 보는 메커니즘 확인용이다. 아래는 게이트(G1·G2·G6)를 모두 통과한 2회차 run이다.

| 2회차, 추적 창 30초 | lettuce 선점 | 그중 tomcat | **lettuce가 깨운 워커** | 그 밖(커널 스레드·인터럽트 깨움 등) | **tomcat이 선점당한 횟수** |
|---|---|---|---|---|---|
| T32 | 112,088 | 98.2% | **101,738 (90.8%)** | 1.8% | 8,268 |
| T32+nice10 | **1,646** | 38.1% | **605 (36.8%)** | 61.9% | **235,767** |
| T200 | 92,648 | 98.5% | 86,107 (92.9%) | 1.5% | — |
| T200+nice10 | 46,797 | 98.2% | 45,426 (97.1%) | 1.8% | — |

- **T32에서 nice는 "lettuce가 깨운 워커의 선점"을 101,738건에서 605건으로 없앴다.** 남은 선점 1,646건의 대부분은 인터럽트가 깨운 커널 스레드(`xfsaild`·CloudWatch Agent 등)로, 우선순위와 무관한 배경 잡음이다.
- **밀려나는 쪽이 lettuce에서 워커로 바뀌었다.** tomcat 워커가 선점당한 횟수가 8,268건에서 235,767건으로 28배가 됐고, 워커의 깨어남 후 대기 평균은 707μs에서 3,918μs가 됐다(r1 기준). 6-1의 "요청당 tomcat 런큐 대기 ×5.3"이 여기서 나온다.
- **T200에서는 선점이 절반만 줄고 구성은 그대로다**(lettuce가 깨운 워커 97%). runnable 워커가 많아 nice −10으로도 깨어난 워커가 여전히 기준값을 넘는다. 6-4의 "일괄 처리 효과가 유지됐다"는 해석과 맞는다.

### 6-7. 측정 중 사고와 설계 이탈

- **2회차 중단과 재측정.** 측정 도중 개발 PC가 모바일 핫스팟으로 바뀌어 공인 IP가 달라졌고, `my_ip_cidr`로 묶인 보안그룹이 SSH를 막아 로컬 드라이버가 2회차 T32 arm에서 끊겼다(`Connection reset by peer`). k6 EC2에 SSM 전용 역할을 붙이고 드라이버를 k6 EC2 안에서 돌리도록 바꾼 뒤(`run-batch.sh`의 `REP_START`), **2회차를 4 arm 모두 다시 돌렸다.** 같은 회차의 두 arm이 시간상 붙어 있어야 쌍 비교가 성립하기 때문이다. 처음 2회차에서 끝났던 3 arm의 결과는 재측정으로 덮어써져 판정에 쓰지 않았다. 재개 뒤에도 15분간 로컬 접속이 끊겼지만 측정은 끊기지 않았다.
- **원격 작업 디렉터리.** 5-1의 설정에 없던 `REMOTE_DIR=/home/ec2-user/lt`를 썼다. k6 EC2의 `/tmp`는 tmpfs(459MB)인데, 1초 폴링 스냅샷(232KB)이 64레벨에 약 1.4GB 쌓인다. lettuce-dispatch-latency.md 6-6에서 실제로 레벨이 유실됐던 문제다.
- **배치 M 첫 run의 추적 실패와 재측정.** 배치 M의 첫 run(T32 r1)에서 bpftrace가 READY 전에 오류 메시지 없이 종료했다(`bpftrace exited early`, stderr 비어 있음). 나머지 7개 run은 부착이 3.7~4.2초로 정상이었다. 이 App EC2에서 bpftrace를 처음 띄운 run이라 첫 실행에만 생기는 문제로 보이지만 원인은 확정하지 못했다. 그 run만 배치 끝에 다시 돌렸다(실패분은 `mech/failed-r1/`에 보존). 배치 M은 판정용이 아니라서, 같은 회차 쌍과 시간상 떨어진 점은 선점자 구성 해석에 영향이 작다.
- **원자료 보존 범위.** 1초 폴링 스냅샷(`.prom`, 약 1.5GB)은 k6 EC2 안에서 집계만 하고 내려받지 않았다. 측정이 끝날 무렵 개발 PC가 모바일 핫스팟에 있었기 때문이다. 집계 결과(`compare-vu200.md`·`mech-summary.md`·`g4.md`)와 run별 schedstat·k6 summary·창 정보는 `results/lettuce-priority/`에 남겼다.

## 7. 결론과 후속

- **운영에 lettuce 우선순위를 적용하지 않는다.** 운영 설정(T32)에서 TPS −7%, 요청당 CPU +15%로 악화가 판정됐다. 이슈의 "개선되면 운영 적용 방식을 별도 이슈로 뗀다"는 해당하지 않는다.
- **#207(lettuce-dispatch-latency.md 6-8)의 해석을 보정한다.** "lettuce가 자기가 깨운 워커에게 밀려난다"는 관측은 맞지만, 그것은 결함이 아니라 CPU 포화 상태에서 처리량을 지키는 일괄 처리 장치였다. Redis 지연(lettuce 쪽 지표)만 보고 처방했다면 서버 전체를 나쁘게 만들었을 것이다.
- **Redis 지연을 줄이는 방향은 이미 정해진 쪽이 맞다.** 경합 상대를 줄이는 `maxThreads` 32(#88)가 피해자의 우선순위를 올리는 것보다 낫다(T32 3,533 vs T200+nice10 3,450).
