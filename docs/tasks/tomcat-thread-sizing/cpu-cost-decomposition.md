# 요청당 CPU 26% 감소의 분해 — 전환 횟수인가, 캐시 지역성인가

> [#97](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/97)의 기록이다. [ec2-measurement.md](ec2-measurement.md)가 한계로 남긴 항목을 정조준한다. 계측을 어떻게 만들고 검증했는지는 [measurement-harness.md](measurement-harness.md)에 따로 있다.
>
> **결론** — 전환을 덜 해서가 아니라, **전환 1회당 캐시를 되채우는 비용이 싸져서다.** 요청당 CPU가 0.7293 → 0.4996 vCPU-ms(**−31.5%**)로 줄었는데 그 낭비의 **92.3%가 유저 시간**이고, 요청당 전환 횟수는 5.05 vs 4.72로 **0.33회밖에 차이 나지 않아 전환 횟수의 몫은 1.4%**다.
>
> **근거 둘** — T8 arm에서 전환이 +3.75회 늘자 비용이 **커널에만** 찍혀(sys +0.0354ms, user +0.0058ms) 이 박스의 전환당 커널 비용 **9.4μs**가 나왔다. 같은 인스턴스 캘리브레이션에서는 스레드당 워킹셋을 4KB로 고정하고 개수만 늘렸을 때 **합계가 공유 L2(1MB)에 닿는 지점에서만** 비용이 붙었다.
>
> **확정하지 못한 것** — GC 몫을 귀속하지 못했다(T200에서 10배 변동, §4-3). 그래서 "유저 92.3% 전부가 지역성"이라고 쓰지 않고, GC·JIT을 구조적으로 배제하는 **요청 처리 스레드 그룹의 59%**만 근거로 삼는다.

## 왜 이 분해가 필요한가

[#88](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/88)에서 `maxThreads`를 200 → 32로 줄이자 요청당 CPU가 26% 줄었고([ec2-measurement.md](ec2-measurement.md)), 그 원인을 "스레드 전환과 CPU 캐시 재적재 비용"이라고 **한 덩어리로** 적었다. 둘의 몫을 나누지 못했고, 하네스가 `/proc/stat`의 `ctxt`를 수집하지 않아 사후 소급도 불가능했다.

나누면 얻는 것:

- "스레드를 줄이면 왜 CPU가 덜 드는가"를 추정이 아니라 수치로 말할 수 있다.
- 같은 근거를 HikariCP·`courseImageCleanupExecutor` 사이징에 재사용할 수 있다. **원인이 전환 횟수라면 "블로킹 지점을 줄여라"가 처방이고, 지역성이라면 "동시 실행 스레드 수를 코어 수 가까이 눌러라"가 처방이다.** 처방이 갈리므로 나누는 값이 있다.

## 1. 측정 전 예산 계산 — 기존 데이터만으로 확정되는 것

재측정 없이 [ec2-measurement.md](ec2-measurement.md)의 VU 200 행(2회 평균)에서 산술로 나온다.

### 1-1. 낭비의 크기

| | T200 | T32 | 차 |
|---|---|---|---|
| TPS | 2,517 | 2,921 | |
| `process_cpu_usage` | 0.940 | 0.810 | |
| **요청당 CPU** = cpu × 2 ÷ TPS × 1000 | **0.7469** | **0.5546** | **0.1923 vCPU-ms** |

- 낭비 전력 = 0.1923ms × 2,517/s = **0.484 vCPU** — 2 vCPU 박스의 **24.2%**를 요청 처리가 아닌 곳에 태우고 있었다.
- 2.50GHz 환산으로 **요청 1건당 480,791 사이클**이 사라졌다.

### 1-2. TPS +16%의 분해 (오차 0의 항등식)

`TPS = 가동률 × 2000 ÷ 요청당 CPU` 이므로

```
TPS비 = (0.810 / 0.940) × (0.7469 / 0.5546) = 0.8617 × 1.3468 = 1.1605
실측  = 2921 / 2517                                          = 1.1605
```

**TPS +16.1% = 효율 +34.7% × 가동률 −13.8%.**

> **그래서 "CPU 사용률이 줄었다" 자체는 성과가 아니다.** 0.940 → 0.810의 절반은 일을 덜 해서가 아니라 **워커가 32개뿐이라 I/O 대기 동안 CPU를 다 못 채워서**다. 실제 성과는 사용률이 아니라 **요청당 비용**에 있다. T8에서 사용률이 더 내려가는데도(0.861) TPS가 T32와 같은 것이 그 증거다.

### 1-3. 배제법 — 이 낭비는 "전환 횟수"로 설명될 수 없다

**요청 1건의 블로킹 지점은 정확히 2개다.** [`UploadCourseServiceImpl.getPopularCourses`](../../../src/main/java/backend/yourtrip/domain/uploadcourse/service/UploadCourseServiceImpl.java)의 히트 경로는 `@Transactional` 없이 랭킹 `GET` + 아이템 `MGET`이 전부다 — DB 커넥션 대여 0회(실측 0.0000), 이 경로에 `synchronized` 0건, 인터셉터 0건, JWT 필터는 토큰이 없어 DB에 닿지 않는다. 소켓 read/write와 poller 디스패치를 얹어도 **요청당 자발 전환은 4~6회**가 상한이다.

**(a) 낭비를 직접 전환 비용만으로 설명하려면** 전환 1회를 2μs로 잡아도 요청당 **96회의 추가 전환**이 필요하다(1μs면 192회, 5μs면 38회). 총 전환이 4~6회인 경로에서 물리적으로 불가능하다.

**(b) 반대편 극단에서 눌러도 마찬가지** — "T200의 전환 6회는 전부 낭비이고 T32는 전환이 0회"라는 성립할 수 없는 가정을 해도 6회 × 2μs = 낭비의 **6.2%**, 5μs로 잡아도 **15.6%**다.

→ **직접 전환 비용의 몫은 어떤 가정에서도 낭비의 6~16%가 상한이다.**

<details>
<summary><b>(c) 타임슬라이스 선점은 1% 미만 — 계산 근거</b></summary>

CFS 기본값(2 CPU 기준 `sched_latency` 12ms, `min_granularity` 1.5ms)에 실측 runnable을 대입하면

| runnable | per-cpu | 슬라이스 | 타임슬라이스 전환 | 요청당 |
|---|---|---|---|---|
| 18.6 (T200) | 9.3 | 1.50 ms | 1,333/s | 0.53회 |
| 7.5 (T32) | 3.8 | 3.20 ms | 625/s | 0.25회 |

Δ = 0.28회/req. 5μs를 붙여도 **낭비의 0.73%**다. 슬라이스를 절반으로 잡아 전환율을 두 배로 올려도 1.5%다. 이 파라미터는 측정 시 박스에서 실제로 읽어 §2에 기록했다.
</details>

<details>
<summary><b>용량-반응 — runnable 1개당 15.5~18.1 μs/req</b></summary>

낭비는 `maxThreads` 설정값이 아니라 **실제로 동시에 runnable인 스레드 수**를 따라간다. 겹치지 않는 두 구간이 거의 같은 기울기를 낸다.

| 구간 | Δrunnable | Δ요청당 CPU | 기울기 |
|---|---|---|---|
| T32 → T64 | 7.5 → 10.8 (+3.3) | +0.0512 ms | **15.5 μs/req/스레드** |
| T64 → T200 | 10.8 → 18.6 (+7.8) | +0.1411 ms | **18.1 μs/req/스레드** |

**이 기울기를 회귀선으로 포장하지 않는다.** T16·T8은 runnable이 T32와 같은데(7.5~8.5) 요청당 CPU는 오히려 조금 높다(0.584·0.598 vs 0.555). 위 두 구간을 벗어나면 선형이 아니고, 같은 arm의 run 간 변동이 ±5%라 그 차이는 노이즈와 구분되지 않는다. **선형성은 T32 이상 구간에 한정된 관찰이다.**
</details>

### → 잠정 결론과 그 한계

**26%의 84~94%는 "전환 1회당 비용"에서 나온다.** 다만 이것은 배제법이고, 유저 모드에서 CPU를 더 태우는 다른 후보(**G1 young GC 빈도** — 스레드 200개 = TLAB 200개, JIT, 스핀-후-파킹)를 차감하지 않았다. 차감 없이 "나머지 = 캐시"라고 쓰면 #88이 저지른 것과 같은 종류의 오귀속이다.

### 사전 등록 예측 (측정 전에 못 박았다)

| # | 예측 | 기각되면 |
|---|---|---|
| **P1** | 요청당 전환 횟수는 T200과 T32가 **±2회 이내**로 같다(블로킹 지점 수가 정하므로) | 횟수 가설 부활 → 26%의 배분을 다시 계산 |
| **P2** | 낭비 0.192ms 중 **커널 몫 < 0.05ms(26%)**, **유저 몫 > 0.14ms(74%)** | 전환 경로가 주범 → §1-3 배제법이 틀린 것 |
| **P3** | GC CPU/요청의 arm 간 차이는 **낭비의 15% 미만** | GC가 3번째 버킷 → 별도 이슈로 분리 |
| **P4** | **T8은 T32보다 요청당 전환이 많다**(idle↔wake 왕복 증가) — T8의 요청당 CPU가 더 높은(0.598 vs 0.555) 이유 | T8 초과분은 다른 원인 |
| **P5** | VU 50(음성 대조군)에서는 arm 간 전환 횟수·user/sys 모두 차이 없음 | 부하와 무관한 계통 오차 존재 |

**결론 규칙**: `낭비 = 커널 몫 + GC/JIT 몫 + 스핀 몫 + 잔여`. **잔여를 지역성으로 귀속하되, 잔여가 전체의 50% 미만이면 "지역성이 지배적"이라고 쓰지 않는다.**

## 4. 무엇이 26%를 설명하는가

### 4-1. T8 대조군이 전환 1회 비용을 자기 교정으로 준다

P4가 성립하면서 **"전환이 실제로 늘면 비용이 어디에 찍히는가"**를 같은 실험 안에서 볼 수 있게 됐다.

| T32 → T8 | 변화 |
|---|---|
| 전환/요청 | 4.72 → 8.47 (**+3.75**) |
| **sys/요청** | 0.0869 → 0.1223 (**+0.0354 ms**) |
| user/요청 | 0.4140 → 0.4198 (+0.0058 ms — 거의 불변) |

전환이 늘어난 몫이 **커널 시간에만** 찍혔다. 여기서 이 하드웨어의 **전환 1회당 커널 비용 = 0.0354ms ÷ 3.75회 = 9.4μs**가 나온다(문헌 인용이 아니라 이 박스의 실측이다).

그 값으로 T200↔T32의 전환 차를 환산하면 `0.33회 × 9.4μs = 0.0031ms`, 즉 **낭비의 1.4%**다. 커널 시간 전체(전환 + 시스템콜)로 넓혀도 7.0%다.

### 4-2. 요청 처리 스레드 자신의 CPU가 59%를 설명한다

`tomcat` 스레드 그룹의 CPU는 **정의상 GC와 JIT을 포함하지 않는다.** 세 번의 T200 run에서 588.0 / 606.8 / 578.3 μs/req(±2.5%)로 안정적이다.

```
요청 처리 스레드 자신의 CPU:  455.2 → 591.0 μs/req   (Δ 135.8 μs/req)
```

Δ 135.8μs는 낭비 229.7μs의 **59%**다. 요청당 유저 모드 명령어 수는 arm과 무관하게 같으므로(같은 코드·같은 히트 경로·요청당 Redis 명령 2.0회), 이 증가분은 "일이 늘어난 것"이 아니라 **같은 일이 느려진 것**이다.

### 4-3. GC 몫은 판정하지 못했다 (P3)

`gc` 스레드 그룹의 CPU가 **T200에서 재현되지 않는다.**

| run | 조건 | gc CPU | tomcat CPU |
|---|---|---|---|
| 배치 T200 r1 | 재기동→예열→VU50→VU200 | 80.8 μs/req | 588.0 μs/req |
| 배치 T200 r2 | 〃 (역순 rep) | 94.7 μs/req | 606.8 μs/req |
| 재현 T200 | 〃 동일 조건 재실행 | **29.8 μs/req** | 578.3 μs/req |
| 임시 T200 | 장시간 부하 후 | **9.4 μs/req** | — |
| 배치 T32 r1 / r2 | | 6.0 / 5.7 μs/req | 458.8 / 451.5 μs/req |

T200의 gc CPU는 9.4~94.7 μs/req로 **10배 범위에서 흔들린다.** 요청당 할당량은 전 arm에서 81~88KB로 사실상 같으므로 할당량 차이가 아니고, JVM이 재기동될 때마다 힙이 차가운 상태에서 시작하는 것도 모든 arm이 같다. **스레드 200개에서 G1의 거동(힙 사이징·TLAB·세이프포인트)이 불안정하다**는 것까지는 말할 수 있지만, 몫을 수치로 귀속할 수는 없다. P3은 판정 불가로 남긴다.

## 5. 캘리브레이션 — 전환 1회 비용을 직접/간접으로 갈랐다

앱을 멈춘 같은 박스에서 `N ∈ {2, 8, 32, 200} × S ∈ {0, 4KB, 32KB, 256KB, 1MB}`를 스윕했다(조합마다 JVM 재기동, 전환/일감 0.97~1.00으로 검증). 벤치마크 설계는 [measurement-harness.md §4](measurement-harness.md).

**(a) 직접 비용은 7.2~7.7μs다(N≥8).** 메모리를 안 건드리는 전환(`c1`)이 커널 경로의 순수 비용이다. §4-1에서 실제 워크로드로부터 역산한 **9.4μs**와 일치한다 — 전혀 다른 두 경로가 서로를 검증한다.

> **`c2 − c1`을 "캐시 페널티"로 읽으면 안 된다.** 거기에는 ① 워킹셋을 훑는 일 자체의 비용과 ② 캐시가 식어서 더 든 비용이 섞여 있는데, **이 벤치마크에는 "전환 없이 같은 일만 하는" 기준선이 없어 ①을 뺄 수 없다.** 따라서 그 값은 페널티의 **상한**이다.

**(b) 깨끗한 측정치는 N 축이다.** 같은 S에서 스레드 수만 바꾸면 **①이 상쇄된다** — 훑는 일의 양이 똑같기 때문이다.

| 워킹셋 | N=32 | N=200 | **순수 오염 비용** |
|---|---|---|---|
| 4KB | 6,468 ns | 13,286 ns | **+6,818 ns** |
| 1MB | 107,808 ns | 123,465 ns | **+15,657 ns** |

**사이클로 환산하면 물리적으로 맞는다.** `+6,818ns` = 2.5GHz에서 17,045 사이클이고 4KB는 캐시라인 64개이므로 **라인당 266 사이클** — DRAM 접근 지연(200~300)대다. S=1MB에서는 N=2의 라인당 6.3사이클(**L3 히트**, 2MB는 33MB L3에 들어감)이 N=200에서 17.7사이클(**DRAM**, 200MB는 L3도 초과)로 올라간다. **간접 비용이 N에 따라 커지는 이유가 "캐시 계층을 한 단계 더 내려가서"** 임이 드러난다.

**(c) S=4KB 행이 기전을 직접 보여준다.** 스레드당 워킹셋을 L1d에도 들어가는 4KB로 고정하고 N만 키우면, 간접 비용은 **총 워킹셋이 공유 L2(1MB)에 닿기 전까지 정확히 0이다.**

| N | 총 워킹셋 | L2 1MB 대비 | 간접 비용 |
|---|---|---|---|
| 2 | 8 KB | 0.01× | −884 ns (≈0) |
| 8 | 32 KB | 0.03× | +190 ns (≈0) |
| 32 | 128 KB | 0.12× | −827 ns (≈0) |
| **200** | **800 KB** | **0.78×** | **+5,562 ns** |

스레드당 작업량도, 전환 횟수도(전 행 1.0/일감) 같은데 **N만 200으로 올려 총 워킹셋이 L2 용량에 닿는 순간 비용이 붙는다.** 비용을 정하는 것은 개별 스레드의 워킹셋이 아니라 **번갈아 도는 스레드들의 합계가 공유 캐시를 넘느냐**다. 같은 축이 S=1MB 행에서 단조롭게 재현된다(41,431 → 84,186 → 100,513 → 115,741 ns, N 2→200에서 **2.8배**).

**(d) 앱 실측과 맞아떨어진다.** §4-2의 tomcat 그룹 증가분 135.8μs/req를 요청당 재개 횟수(3.41회)로 나누면 **재개 1회당 약 40μs**다. 위 표에서 워킹셋 256KB(16~19μs)와 1MB(84~116μs) 사이에 들어간다. 앱의 잔여분이 독립 벤치마크의 측정 범위 안에서 설명된다.

<details>
<summary><b>원자료 — 전체 격자 (전환 1회당 CPU / 간접 비용)</b></summary>

**전환 1회당 CPU (ns)**

| threads | S=0 (직접 c1) | 4KB | 32KB | 256KB | 1MB |
|---|---|---|---|---|---|
| 2 | 15,589 | 14,705 | 15,183 | 19,829 | 57,020 |
| 8 | 7,226 | 7,416 | 7,105 | 26,646 | 91,412 |
| 32 | 7,295 | 6,468 | 8,601 | 24,769 | 107,808 |
| 200 | 7,724 | 13,286 | 10,059 | 24,161 | **123,465** |

**간접 비용 = c2 − c1 (ns)**

| threads | 4KB | 32KB | 256KB | 1MB |
|---|---|---|---|---|
| 2 | −884 | −406 | 4,240 | 41,431 |
| 8 | 190 | −121 | 19,420 | 84,186 |
| 32 | −827 | 1,306 | 17,474 | 100,513 |
| 200 | **+5,562** | 2,334 | 16,436 | **115,741** |

N=2의 `c1`만 15.6μs로 높은데, 스레드가 둘뿐이라 CPU가 놀고 idle→wake 왕복 지연이 얹히기 때문이다. 4KB·32KB 열의 수천 ns는 노이즈와 같은 자릿수라(음수가 섞여 나오는 것이 그 증거) 방향으로만 읽어야 한다.
</details>

## 6. #88 재현 여부

| | #88 (8259CL) | 이번 (8175M) |
|---|---|---|
| T200 요청당 CPU | 0.747 | 0.729 (−2.4%) |
| T32 요청당 CPU | 0.555 | 0.500 (−9.9%) |
| 개선폭 | −26% | **−31.5%** |

**T200은 재현되지만 T32는 이번 세션이 뚜렷이 낫다.** CPU 모델이 다르므로(§2) 절대값을 직접 비교하지 않는다는 사전 규칙대로, **arm 간 비율만 읽는다.** 방향과 크기(−26% vs −31.5%)는 일치한다.

같은 arm의 run 간 변동은 최대 ±8.5%(T32 VU200: 3,726 / 3,145)로 #88의 ±5%보다 컸다. 따라서 **T64(3,410)와 T32(3,435)의 0.7% 차이는 노이즈**이며 순위를 가리지 않는다.

## 7. 한계

- **GC 몫을 귀속하지 못했다(P3).** §4-3대로 T200의 `gc` 그룹 CPU가 9.4~94.7μs/req로 10배 흔들린다. 그래서 "유저 시간 92.3% 전부가 지역성"이라고 쓰지 않고, GC·JIT을 구조적으로 배제하는 **tomcat 그룹의 59%**만 근거로 삼았다. 나머지 33%p(유저 92.3% − tomcat 59%)의 귀속은 열려 있다.
- **#88의 절대값을 재현하지 못했다.** CPU 모델이 다르다(8175M vs 8259CL). **세션 간 절대값 비교는 이 저장소에서 반복해서 문제가 되므로**, 다음 측정에서도 CPU 모델을 먼저 기록해야 한다.
- **run 간 변동이 #88보다 컸다**(T32 VU200에서 ±8.5%). T64와 T32의 차이는 노이즈이며 순위를 가리지 않는다.
- **캘리브레이션에 "전환 없이 같은 일만 하는" 기준선이 없다.** 그래서 `c2 − c1`은 캐시 페널티의 **상한**이고, 순수한 오염 비용은 같은 S에서 N만 바꿔 상쇄시킨 값(§5(b))으로만 읽어야 한다. ExpCS 논문은 배열 크기를 촘촘히 스윕해 이 통제를 했는데 이번 스윕은 그 축이 성겼다.
- **캘리브레이션은 합성 워크로드다.** 스레드마다 독립된 배열을 훑을 뿐이라 실제 앱처럼 코드·자료구조를 공유하지 않는다. 절대값을 앱에 그대로 대입할 수 없고, §5(d)의 대조는 자릿수 확인이다.
- **스핀-후-파킹을 직접 배제하지는 못했다.** 자발 전환/요청이 T200 3.38, T32 2.61로 T200이 오히려 많아 스핀 경합이 늘었을 여지가 있다. 다만 그 차이(0.77회)에 실측 전환 비용 9.4μs를 곱해도 0.007ms(낭비의 3%)라 지배적일 수 없다.
- **열린 루프는 재지 않았다.** #88의 한계를 그대로 물려받는다.
