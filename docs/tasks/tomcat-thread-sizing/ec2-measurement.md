# EC2 분리 환경 실측 — Tomcat `maxThreads` 200 / 64 / 32 / 16 / 8 + `shareNativeConnection=false`

> [README.md](README.md)의 설계·판정 기준에 따라 잰 결과다. 같은 JAR·같은 세션에서 6개 arm을 교대로 2회씩(2회차는 역순) 측정했다.
>
> **결론만 먼저**: **`server.tomcat.threads.max`를 200 → 32로 내린다.** VU 200에서 TPS 2,517 → 2,921(**+16%**), p95 122.9 → 82.9ms(**-33%**), load average 15.8 → 5.3. 32·16·8은 TPS·p95가 1.5% 이내로 **평탄**하고 64부터 밀리므로, 평탄 구간의 최댓값(느린 요청 여유분)인 32를 고른다. 저부하(VU 5·20)에서는 arm 간 차이가 노이즈 안이다.
>
> **개선한 것은 Redis 대기가 아니라 CPU 낭비다.** T32는 T200보다 **CPU를 덜 쓰면서**(0.940 → 0.810) 처리량은 더 냈고, **요청 하나당 CPU 비용이 26% 줄었다**(0.747 → 0.555 vCPU-ms). 워커 200개가 vCPU 2개를 번갈아 타며 새어나가던 전환·캐시 비용이 요청 처리로 돌아온 것이 개선의 실체다. **Redis 명령 지연 15.3 → 2.9ms는 부산물**이다 — 대기하던 요청이 Redis 채널 앞줄에서 Tomcat 커넥션 큐(스레드·CPU를 쓰지 않는 대기)로 자리를 옮긴 결과이지, 없앤 비용이 아니다. 그래서 **Redis 지연 하락 자체를 성과로 읽지 않는다.**
>
> **대안 `shareNativeConnection=false`는 최악이었고, 위 판단의 반증이 된다.** 채널을 8개로 늘려 **Redis 지연 지표는 0.84ms로 6개 arm 중 가장 좋았지만**, 풀 8개를 워커 200개가 다투다 `max-wait 1s` 타임아웃으로 **DB 폴백이 233회** 발생했고 요청당 CPU는 **28% 증가**, VU 200 p95는 400ms(T200의 3.3배)였다. Redis 지연만 보면 최선, 실제로는 최악이다.
>
> **이슈의 메커니즘 서술은 한 단계 정정한다.** 근거로 삼았던 "런큐 대기 비율(90.8%)"은 T64·T32·T16에서 89.9 → 88.8 → 86.5%로 **거의 안 움직였는데** Redis 지연만 내려갔다. 비율은 "이벤트루프 뒤에 항상 누가 있다"는 **포화 신호**이지 지연의 크기가 아니었다 — 크기는 maxThreads가 **단일 채널 앞에 밀리는 in-flight 명령 수의 상한**이 되면서 정해진다.

## 개선의 실체 — 요청당 CPU 비용이 26% 줄었다

위 표에서 **T32는 T200보다 CPU를 덜 쓰면서(0.940 → 0.810) 처리량은 더 냈다(2,517 → 2,921).** 이 두 열을 나누면 "요청 하나를 처리하는 데 실제로 쓴 CPU"가 나오고, 그것이 이 개선의 정체를 가장 직접적으로 보여준다.

```
요청당 CPU(vCPU-ms) = process_cpu_usage × vCPU 2 ÷ TPS × 1000
```

| arm | VU 5 | VU 20 | VU 50 | **VU 200** |
|---|---|---|---|---|
| T200 | 0.934 | 0.603 | 0.598 | **0.747** |
| T64 | 0.875 | 0.600 | 0.591 | 0.606 (**-19%**) |
| **T32** | 0.882 | 0.589 | 0.557 | **0.555 (-26%)** |
| T16 | 0.923 | 0.598 | 0.579 | 0.584 (-22%) |
| T8 | 0.940 | 0.609 | 0.594 | 0.598 (-20%) |
| SNC | 1.150 | 0.734 | 0.688 | 0.958 (**+28%**) |

<sub>2회 평균. 괄호는 같은 VU의 T200 대비.</sub>

**같은 요청을 처리하는데 CPU가 26% 덜 든다는 것은, 그 26%가 원래 요청 처리가 아닌 곳으로 새고 있었다는 뜻이다.** 워커 200개가 vCPU 2개를 놓고 번갈아 타면서 발생하는 스레드 전환과 CPU 캐시 재적재 비용이다. 그것을 걷어내자 같은 하드웨어가 더 많은 요청을 처리했다.

**저부하에서는 이 차이가 사라진다** — VU 5·20·50에서 arm 간 격차는 ±3% 이내다. 그 구간은 워커가 6~51개만 쓰여 애초에 경쟁이 없었기 때문이고, 이것이 "원인은 스레드 과다"라는 해석을 뒷받침한다(스레드 수 자체가 비용이라면 저부하에서도 차이가 나야 한다).

따라서 인과 사슬은 이렇게 정리된다.

```
워커 200 → 32
  → 동시에 CPU를 다투는 스레드 감소 (runnable 18.6 → 7.5개, load1 15.8 → 5.3)
  → 요청당 CPU 비용 26% 감소            ← 개선의 실체
  → 같은 2 vCPU로 처리량 +16%
  → (닫힌 루프이므로) 응답 시간 -17%, p95 -33%
```

**Redis 명령 지연 15.3 → 2.9ms는 원인이 아니라 부산물이다.** 대기하던 요청이 Redis 채널 앞줄에서 Tomcat 커넥션 큐로 자리를 옮긴 결과일 뿐이고, 실제로 걷어낸 것은 CPU 낭비다.

**SNC arm이 그 반증이다.** 채널을 8개로 늘려 Redis 지연 지표는 0.84ms까지 낮췄지만, 요청당 CPU는 오히려 **28% 늘었고**(풀 borrow/return + 폴백 비용) 처리량은 26% 떨어졌다. **Redis 지연 지표만 보면 SNC가 6개 arm 중 가장 좋아 보이는데 실제로는 최악**이라는 것이, 그 지표를 성과 지표로 읽으면 안 되는 이유를 보여준다.

> **한계 → [#97](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/97)에서 잇는다**: 컨텍스트 스위칭 횟수를 직접 재지 않았다(`/proc/stat`의 `ctxt`를 하네스가 수집하지 않는다). 요청당 CPU 감소·runnable 스레드 감소·load average 감소가 모두 같은 방향을 가리키지만, **26% 중 스레드 전환 오버헤드와 CPU 캐시 지역성이 각각 얼마인지는 분해하지 못했다.**
>
> 후속 작업이 [cpu-cost-decomposition.md](cpu-cost-decomposition.md)에 있다. 거기서 **위 표만 다시 계산해도 상당 부분이 배제법으로 좁혀진다**는 것이 드러났다 — 이 경로의 블로킹 지점이 정확히 2개(랭킹 `GET` + 아이템 `MGET`)라 요청당 전환은 4~6회가 상한인데, 낭비 0.192 vCPU-ms를 직접 전환 비용만으로 설명하려면 요청당 **96회의 추가 전환**(1회 2μs 가정)이 필요하다. **직접 전환 비용의 몫은 어떤 가정에서도 6~16%가 상한**이고, 나머지는 "같은 명령어 스트림이 더 느리게 도는 것" 즉 지역성이다. 그 박스의 2 vCPU가 **물리 코어 하나의 하이퍼스레드 2개**(L2 1MB 공유)라는 것도 그때 확인했다.
>
> **재측정으로 확정됐다.** 요청당 CPU를 user/sys로 가르니 낭비의 **92.3%가 유저 시간**이었고, 요청당 전환 횟수는 5.05 vs 4.72로 **0.33회밖에 차이 나지 않았다** — 전환 횟수가 설명하는 몫은 **1.4%**다. 같은 박스에서 잰 전환의 커널 경로 비용은 **7.2~7.7μs**이고, 스레드 수만 2→200으로 올렸을 때(일하는 양은 고정) 캐시가 식어 붙는 비용이 **+6.8~15.7μs**로 그와 맞먹거나 크다. 다만 GC 몫은 T200에서 재현되지 않아 귀속하지 못했다.

## 스레드 그룹별 런큐 대기 (VU 200 구간 중반 10초, `schedstat`)

lettuce = netty 이벤트루프 스레드(2개 존재, 공유 커넥션이면 1개만 사용). "(실행+대기)÷벽시계"가 100%에 가까우면 그 스레드는 한순간도 놀지 않은 것이다.

| arm | lettuce 실행 | lettuce 런큐 대기 | **대기 비율** | (실행+대기)÷벽시계 | tomcat 대기 비율 | tomcat runnable 상당(스레드 수) |
|---|---|---|---|---|---|---|
| T200 | 927ms | 9,348ms | **91.0%** | 86.6% | 92.4% | 19.1개 (202) |
| T64 | 1,038ms | 9,174ms | 89.9% | 94.5% | 82.3% | 8.2개 (66) |
| T32 | 1,087ms | 8,781ms | 89.0% | 93.8% | 75.2% | 5.6개 (34) |
| T16 | 1,188ms | 7,404ms | 86.2% | 82.6% | 76.3% | 6.3개 (18) |
| **T8** | 2,001ms | 2,268ms | **53.1%** | **41.2%** | 72.0% | 5.2개 (10) |
| SNC | 1,545ms | 12,797ms | 89.2% | 122% (2스레드 합) | 74.3% | 5.1개 (202) |

<sub>2회 평균. "runnable 상당" = 그룹의 (실행+대기) ÷ 벽시계 — 그 그룹이 평균 몇 개의 스레드만큼 항상 런큐에 있었는가.</sub>

> **"(실행+대기)÷벽시계" 열은 arm 간 비교에 편향이 있다.** 샘플러가 `/proc/<pid>/task/`를 두 번 훑는데 스레드가 많을수록 그 시간이 길어져 분모(벽시계)가 늘어난다 — T200 11,876ms vs T8 10,354ms. 그래서 T200의 86.6%가 실제보다 낮게, T64·T32의 94%가 상대적으로 높게 나온다. **T8의 41.2%는 이 편향(최대 15%p)보다 훨씬 큰 차이**라 "T8에서 비로소 논다"는 판정은 유효하지만, 나머지 arm 간의 수 %p 차이는 읽지 않는 것이 맞다.
>
> **원인을 찾아 고쳤다([#97](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/97)).** 스냅샷이 스레드마다 `cat`과 `grep` 프로세스를 띄우고 있었다(T200이면 스냅샷당 400여 회의 fork, 게다가 t0 조회가 O(N²)). 셸 내장 `read`와 연관 배열로 바꿔 fork를 0으로 만들자 **스냅샷 1회가 740ms → 37ms**(137스레드 기준)로 줄었다. 이후 측정에서는 이 열을 arm 간에 비교해도 된다.

읽는 법:
- **T200의 워커는 평균 19개가 항상 runnable**이고(호스트 `procs_running` 평균 18.6과 일치) lettuce 스레드는 그 사이에서 91%를 기다린다 — [redis-io-bottleneck.md](../cache-effect-measurement/redis-io-bottleneck.md)의 90.8%가 재현됐다.
- maxThreads를 줄여도 **lettuce 대기 비율은 T16까지 86~90%로 거의 그대로**다. 닫힌 루프라 CPU는 어느 arm에서든 포화되고(proc CPU 0.81~0.94), 포화된 CPU 위에서 "이벤트루프 뒤에 항상 누가 있다"는 상태 자체는 안 바뀐다. **그럼에도 Redis 지연이 15.3 → 6.0 → 2.9 → 1.1ms로 내려간 것**은, 스레드가 한 번 CPU를 얻을 때 처리해야 할 밀린 명령의 뭉치(in-flight ≤ maxThreads × 2)가 작아졌기 때문이다.
- **T8에서야 비율이 53%로 떨어진다** — 밀린 명령이 최대 16개라 뭉치를 다 처리하고 잠깐씩 노는 구간(벽시계의 59%)이 생긴다. 이 지점에서 Redis 지연은 바닥값(0.44ms ≈ VU 5의 0.48ms)이지만 TPS는 T32와 같다 — 워커가 적어 I/O 대기 동안 CPU를 다 못 채우는 손실과 경합 제거의 이득이 상쇄된다.
- SNC는 **이벤트루프 2개를 다 쓴다**(각 811/720ms 실행) — 채널이 8개로 분산된 건 맞다. 하지만 두 스레드 모두 89% 대기이고, 문제는 그 앞단(풀 대기)에서 터진다.

## SNC arm — 왜 최악인가

VU 200에서 `lettuce_command_*`는 0.84ms로 6개 arm 중 가장 낮게 **보이지만**, 서버 평균은 105ms로 T200의 1.7배다. 풀에서 커넥션을 빌리는 대기는 채널에 쓰기 **전**이라 이 지표에 잡히지 않는다. 앱 로그가 그 대기의 정체를 보여준다.

```
WARN UploadCourseServiceImpl : 랭킹 캐시 조회 실패, DB로 폴백합니다. cacheKey=ALL   ← 233회 (VU 200 run 1회 동안)
RedisConnectionFailureException: Unable to connect to Redis
  Caused by: ... Could not get a resource from the pool
  Caused by: ... Timeout waiting for idle object, borrowMaxWaitDuration=PT0.999985374S
```

`max-active: 8`을 워커 200개가 다투다 `max-wait: 1000ms`를 넘긴 요청이 `RedisCacheErrorHandler`를 거쳐 DB로 떨어졌고(그래서 이 arm에만 SQL 165건·`hikaricp` 대여가 잡힌다), 나머지는 1초 가까이 풀 앞에서 기다린 뒤에야 0.8ms짜리 명령을 보냈다. **HikariCP 10 : Tomcat 200에서 봤던 20:1 병목이 Redis 풀 8 : Tomcat 200(25:1)으로 재현된 것**이다. VU 20에서도 이미 p95가 T200의 1.9배(21.5 vs 11.4ms)라 저부하에서도 borrow/return 비용이 보인다.

**결론**: 이 옵션은 채택하지 않는다. 토글(`LettuceShareNativeConnectionCustomizer`)은 측정 후 제거했다.

## 혼합 부하 — 워커 부족이 DB 경로에 새 큐잉을 만들지 않는가

`popular-mixed.js`(배경 `/popular` 300 req/s 고정 + 상세 조회 `pool` 모드 VU 20→50→100→200 ramping, 330s)를 arm마다 **재기동·워밍 직후 `FLUSHALL`** 하고 1회씩 돌렸다. 상세 캐시(3,000건)가 비어 있어 초반은 전부 DB 미스이고, 세 arm의 SQL 건수가 9,04x로 같으므로 **DB 부하는 동일**하다.

| arm | 전체 TPS | busy 최대 | 대기 커넥션 최대 | `pending` 최대 | SQL | HikariCP 대여 | CPU | 상세 avg / p95 / p99 (ms) | `/popular` avg / p95 / p99 (ms) | 총 요청 |
|---|---|---|---|---|---|---|---|---|---|---|
| T200 | 2,133 | 200 | 328 | 0 | 9,042 | 3,036 | 0.945 | 39.1 / 96.8 / 127.6 | 38.0 / 96.1 / 146.1 | 704,271 |
| **T32** | 2,210 | 32 | 308 | 0 | 9,039 | 3,033 | 0.886 | 37.5 / **84.8** / 109.3 | 35.2 / 85.8 / 128.1 | 730,736 |
| T16 | 2,246 | 16 | 302 | 0 | 9,051 | 3,033 | 0.899 | 36.9 / 82.4 / 103.6 | 35.0 / 83.8 / 119.5 | 741,152 |

- **`pending` 최대가 세 arm 모두 0**이다 — HikariCP 풀(10)은 어느 arm에서도 포화되지 않았고, 워커 수를 200 → 32 → 16으로 줄여도 DB 경로에 커넥션 대기가 새로 생기지 않았다. 대여 횟수(3,03x)도 같다.
- 상세 조회 p95는 96.8 → 84.8(T32, **-12%**) → 82.4ms로 **오히려 좋아진다.** 워커 앞 대기(대기 커넥션 최대 328 → 308)는 거의 같은데 CPU 낭비가 줄어 처리량이 3.6~5.3% 오른 결과다. 가드 기준("T200 대비 5% 이상 악화되지 않음")을 통과한다.
- 상세 경로 요청 URI가 `uri="/api/upload-courses/{uploadCourseId}"`라 라벨 값에 `}`가 들어간다 — 집계기의 라벨 정규식이 첫 `}`에서 끊겨 이 라인을 통째로 놓치던 버그를 이 run에서 발견해 고쳤다(`/popular`만 있던 본 배치의 값은 영향 없음을 재집계로 확인했다).

## 최종 JAR 확인 — 설정이 yml 경로로 실제 적용되는가

본 배치는 `.env`의 `SERVER_TOMCAT_THREADS_MAX`로 arm을 바꿨으므로, **토글을 제거하고 `application-prod.yml`에 `server.tomcat.threads.max: 32`를 넣은 최종 JAR**을 다시 배포해 `.env` 오버라이드 없이 `tomcat_threads_config_max_threads = 32`가 나오는지 확인하고 VU 200을 3회 돌렸다.

| run | TPS | Redis 지연 | k6 avg / p95 / p99 |
|---|---|---|---|
| r1 (재기동 + 예열 30s 직후) | 2,253 | 3.80ms | 88.4 / 142.1 / 182.2 |
| r2 | 2,976 | 2.87ms | 66.9 / 79.9 / 93.8 |
| r3 | 2,811 | 3.00ms | 70.9 / 84.4 / 105.0 |

r2·r3가 본 배치의 T32(2,921 / 2.9ms / 82.9ms)를 재현한다. **r1이 낮은 것은 JIT 예열 부족**이다 — 본 배치는 arm마다 VU 5→20→50을 거치며 5분 가까이 예열된 뒤 VU 200에 들어갔는데, 이 확인은 재기동 후 30초 예열만 하고 바로 VU 200을 걸었다. 재기동 직후 첫 고부하 run은 버려야 한다는 것을 기록해 둔다.

## 판정

| 기준 | 결과 |
|---|---|
| 1. 주 지표(VU 200 Redis 지연·lettuce 대기) | 지연 15.3 → 2.9ms(T32). 대기 **비율**은 T8까지 안 떨어진다 — 위 정정 참고. **주 지표를 잘못 골랐다**(아래 참고) |
| 2. 부 지표(VU 50·200 TPS, VU 200 p95) | TPS 2,935/2,517 → 3,018/2,921, p95 122.9 → 82.9ms. **32·16·8이 1.5% 이내로 평탄**, 64는 -4%/+10% |
| 3. 가드(저부하 회귀·오류·혼합 부하) | VU 5·20 arm 간 차이 ±3% 이내(노이즈), 5xx·실패 0. 혼합 부하에서 상세 조회 p95 96.8 → 84.8ms, `pending` 0 유지 |
| 4. 선택 규칙(평탄 구간의 최댓값) | **32** |

**사전 등록한 주 지표가 틀렸다는 것도 결과다.** 측정 전에는 "Redis 명령 지연과 런큐 대기 비율"을 주 지표로 못 박았는데, 실측 후 보니 전자는 **부산물**이고 후자는 **거의 움직이지 않았다.** 개선을 가장 잘 설명하는 것은 사전 목록에 없던 **요청당 CPU 비용**이었다. 다만 사전 등록 자체는 값을 했다 — 그 규칙이 없었다면 "Redis 지연이 5배 좋아졌다"를 성과로 발표하고 끝났을 것이고, SNC arm(지연은 최선, 실제로는 최악)에 속았을 것이다. **선택(32)은 사전 등록한 부 지표·가드·선택 규칙만으로도 동일하게 나온다.**

`application-prod.yml`에 `server.tomcat.threads.max: 32`로 반영했고, 최종 JAR로 yml 경로 적용을 확인했다(위 절). `local` 프로필은 기본값 그대로다(개발 머신은 코어 수가 다르다).

## 한계

- **워커를 수 초 붙드는 경로(Gemini 동기 호출, 10MB 업로드)는 재지 않았다.** 32개가 전부 그런 요청에 잠기면 2ms짜리 `/popular`도 뒤에서 기다린다. 이 문제는 maxThreads 축소가 만든 게 아니라 드러낸 것(200개일 때도 200건이면 같다)이지만, 상한이 낮아진 만큼 발생 확률은 높아졌다. 후속 이슈(느린 엔드포인트의 bulkhead/비동기화)로 뺐다.
- **닫힌 루프만 쟀다.** 열린 루프(도착률 고정)에서는 워커 32개가 소화 못 하는 도착률에서 Tomcat 큐가 쌓이는 모양이 다를 수 있다. 다만 처리량 상한은 CPU가 정하고 그 CPU 효율이 T32에서 더 높으므로 방향은 같을 것이다.
- **VU 200 한 지점의 2회 반복이다.** 같은 arm의 run 간 차이가 ±5%라 T32·T16·T8의 순위는 가리지 못했다 — 그래서 "평탄"으로 읽고 선택 규칙으로 정했다.
- **`lettuce_command_*`는 하한값이다**(채널 쓰기 이후만 잰다). SNC arm이 그 한계를 정확히 보여준다.
- 세션 간 변동(±15%, [ec2-measurement.md](../cache-effect-measurement/ec2-measurement.md) 한계)은 이번엔 회피했다 — 전 arm이 한 부팅 세션 안이고 CPU 모델을 기록했다. 다른 세션의 절대값(#87의 VU 5 TPS 2,073 vs 이번 1,722)과는 직접 비교하지 않는다.
