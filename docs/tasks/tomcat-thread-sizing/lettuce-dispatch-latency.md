# lettuce 이벤트루프는 CPU를 더 빨리, 더 자주 얻게 됐는가

> [ec2-measurement.md](ec2-measurement.md)가 남긴 질문을 잰다. `maxThreads`를 200 → 32로 줄인 뒤 Redis 지연은 15.3 → 2.9ms로 내려갔는데, lettuce 스레드의 **런큐 대기 비율은 91.0 → 89.0%로 거의 그대로**였다. 그 문서는 이를 "비율은 포화 신호이지 지연의 크기가 아니다"로 읽고, 지연이 줄어든 이유를 **밀린 명령 뭉치가 작아져서**라고 설명했다.
>
> 이 문서는 그 설명이 빠뜨린 다른 축을 재려고 한다. **경쟁자가 줄었으니 lettuce 스레드가 CPU를 한 번 얻기까지 기다리는 시간이 짧아지고, 그만큼 더 자주 얻게 됐을 것**이라는 가설이다. 1~5절은 측정 전에 쓴 설계·사전 등록이고, 결과는 6절에 있다.
>
> **결론 — 가설은 기각됐다.** T200 → T32에서 runnable Tomcat 워커는 19.6 → 5.3개로 줄었지만, lettuce가 CPU를 한 번 얻기까지의 대기는 **256.9 → 244.8μs(×0.95)**, 배정 빈도는 **×1.07**로 거의 그대로였다. 그런데도 Redis 지연은 13.75 → 3.11ms로 #88을 재현했다. 지연을 줄인 것은 "CPU를 더 빨리 얻어서"가 아니라, **처리 속도가 그대로인 단일 이벤트루프 앞에 쌓이는 명령 수(in-flight)가 스레드 상한만큼 줄어서**다 — 리틀의 법칙으로 산출한 in-flight가 76.5 → 17.0개로 줄었다. lettuce는 거의 잠들지 않아(전환의 99%가 선점) 깨어남 선점의 혜택을 못 받고, 선점 후 재대기가 경쟁자 수와 무관하게 약 240μs로 일정했다. 밀어내는 것은 **lettuce 자신이 방금 깨운 Tomcat 워커**다 — 선점의 91~94%가 그랬고, 깨우기에서 전환까지 p99 20μs였다(#207, 6-8). 그 결과 lettuce가 CPU를 차지한 비율도 **11.7 → 12.6%**로 거의 그대로였다. 가설대로의 현상은 **T8에서야** 나타났다 — 큐가 비어 lettuce가 잠들기 시작하자 전환의 89%가 자발로 뒤집히고 배정당 대기가 111μs(×0.43)로 줄었다.

## 1. 왜 대기 비율로는 이 가설을 볼 수 없는가

`/proc/<pid>/task/<tid>/schedstat`의 세 필드를 실행 R, 대기 W, 배정 횟수 n(pcount)이라 하면

```
대기 비율 = W / (R + W) = (n · w̄) / (n · (r̄ + w̄)) = w̄ / (r̄ + w̄)
          w̄ = 배정 1회당 대기, r̄ = 배정 1회당 실행
```

**배정 횟수 n이 약분된다.** 그래서 w̄가 줄어도 r̄가 같은 비율로 줄면 비율은 움직이지 않는다. lettuce 스레드는 (실행+대기)÷벽시계가 94%로 거의 쉬지 않았으므로 `n ≈ 벽시계 ÷ (r̄ + w̄)`이고, w̄와 r̄가 함께 줄면 **n은 그만큼 늘어난다.** "더 빨리"(w̄↓)와 "더 자주"(n↑)는 이 조건에서 같은 현상의 두 면이다.

즉 대기 비율이 그대로라는 사실은 가설을 반증하지 못한다. 가설을 재려면 w̄와 n을 직접 봐야 한다. 그리고 그 둘은 이미 수집하던 원자료로 계산할 수 있다(#97에서 pcount 수집을 추가했다). 다만 #88 측정은 #97 이전이고 원자료도 남아 있지 않아 **소급 계산은 불가능하다** — 재측정한다.

## 2. 무엇을 재는가

| 지표 | 출처 | 의미 |
|---|---|---|
| **배정당 대기** w̄ = W ÷ n | `sample-schedstat.sh`(확장) | CPU를 **얼마나 빨리** 얻는가 — 평균 |
| **배정/초** = n ÷ 벽시계 | 〃 | **얼마나 자주** 얻는가 |
| 배정당 실행 r̄ = R ÷ n | 〃 | 한 번 얻었을 때 처리한 밀린 일의 크기 — 기존 "뭉치" 설명의 직접 지표 |
| 대기 분포(p50/p90/p99) — **깨어남 / 선점** 별도 | `trace-sched-latency.bt`(bpftrace) | 평균이 가리는 꼬리, 그리고 대기가 어디서 시작됐는가 |

bpftrace는 대기 구간을 시작 원인으로 나눈다.

- **wake**: 잠든 스레드가 깨워진 뒤(`sched_wakeup`) CPU에 오르기까지 — 소켓에 Redis 응답이 도착해 이벤트루프가 깨어난 뒤 실제로 돌기까지다.
- **preempt**: 일하던 도중 runnable인 채로 밀려난 뒤(`sched_switch`, 수면 비트 없음) 다시 오르기까지.

이 구분이 필요한 이유는 처방이 다르기 때문이다. wake 대기가 지배적이면 경쟁자 수가 직접 원인이고, preempt 대기가 지배적이면 타임슬라이스 단위로 밀려나는 것이 원인이다.

## 3. 사전 등록 — 예측과 기각 조건

근거: [ec2-measurement.md](ec2-measurement.md)의 VU 200 schedstat에서 runnable Tomcat 워커가 T200 평균 **19.1개** → T32 **5.6개**(3.4배 감소). CFS는 runnable 스레드끼리 CPU 시간을 나누므로 lettuce가 차례를 기다리는 시간은 앞에 선 경쟁자 수에 비례할 것이다.

| # | 예측 (VU 200, 2회 평균, T200 대비 T32) | 확신 |
|---|---|---|
| P1 | lettuce **배정당 대기 w̄가 절반 이하**로 준다 (비 ≤ 0.5) | 중 |
| P2 | lettuce **배정/초가 1.8배 이상** 는다 | 중 |
| P3 | 배정당 실행 r̄도 함께 준다 (비 ≤ 0.6) — 대기 비율이 그대로였던 이유 | 중 |
| P4 | arm을 T200 → T64 → T32 → T16 → T8로 내릴수록 w̄가 **단조 감소**한다 | 중 |
| P5 | T200에서 lettuce 대기 시간의 **절반 이상이 preempt** 쪽이다 — (실행+대기)÷벽시계 94%라 거의 잠들지 않으므로 | **낮음** |

**기각 조건** — w̄의 T32/T200 비가 **0.8~1.2** 안이면 "CPU를 더 빨리 얻게 됐다"는 가설은 기각한다. 그때는 지연 개선이 전부 r̄(뭉치 크기) 쪽이라는 기존 설명이 유일한 설명으로 남는다.

## 4. 유효성 게이트 — 실패하면 그 숫자는 쓰지 않는다

bpftrace의 필터·선점 판별이 틀리면 에러 없이 조용히 틀린 숫자가 나온다. 그래서 같은 창의 독립된 출처와 대조한다.

| # | 게이트 | 기준 | 잡아내는 것 |
|---|---|---|---|
| G1 | bpftrace `@dispatch` vs schedstat 전환(pcount) — lettuce·tomcat | ±5% | 스레드 이름 필터 오류, 이벤트 유실 |
| G1b | bpftrace 총 대기(wake+preempt) vs schedstat 런큐 대기 — *게이트 후 추가* | ±5% 또는 배정당 3μs 이내 | "시작점 모름" 배정이 놓친 대기, bpftrace 고정 오프셋 |
| G2 | bpftrace `@out_preempt` vs `/proc` 비자발 전환 — *100건 미만은 판정 제외(게이트 후 수정)* | ±10% | `prev_state` 선점 판별 오류(커널 6.1은 선점을 `0x100`으로 보고) |
| G3 | 합성 워크로드(App EC2, 워커 32 vs 8)에서 lettuce w̄ 차이가 ≥ 1.5배로 검출되는가 | 검출 | 계측기의 민감도 — 알려진 차이를 못 잡으면 실측의 "차이 없음"도 믿을 수 없다 |
| G4 | 추적 창 안 TPS vs 같은 레벨의 창 밖 TPS | 하락 < 3% | bpftrace 자체 부하(전환마다 프로브 실행)가 측정 대상을 바꿨는가 |
| G5 | `uname -r`가 6.1.x(CFS)인가 | 기록 | 6.6+(EEVDF)면 스케줄링 규칙이 달라 #88 절대값과 비교하지 않는다 |

G3는 로컬 WSL(4 vCPU, 커널 6.6 EEVDF)에서 schedstat만으로 먼저 돌려 봤다 — 워커 32 → 8에서 가짜 lettuce 스레드의 w̄ **349 → 177μs**, 배정/초 **1,528 → 2,083**, 대기 비율은 **89.8 → 81.8%**. 계측기가 동작한다는 확인일 뿐이고, 커널·vCPU가 달라 근거로는 쓰지 않는다. 판정은 App EC2(6.1, 2 vCPU)에서 다시 한다.

### 4-1. 게이트 결과 (App EC2, 2026-10-14) — 본 측정 전에 기준 2건을 고쳤다

환경: t3.small, 커널 **6.1.188**(CFS — #97의 6.1.177과 같은 계열), bpftrace **v0.17.0**(AL2023 저장소), 앱 미배포 상태에서 합성 워크로드(워커 32 / 8, 창 20초). 원자료는 `results/lettuce-dispatch/gate2/`(gitignore).

| | 워커 32 | 워커 8 | 판정 |
|---|---|---|---|
| G1 배정 횟수 (lettuce / tomcat) | +0.1% / +0.2% | +1.2% / +1.1% | 통과 |
| G1b 총 대기 (lettuce / tomcat) | +0.1% / −0.8% | **+206.9%** / +0.5% | 아래 수정 후 통과 |
| G2 선점 횟수 (lettuce / tomcat) | 77 vs 78 / +0.2% | 41 vs 40 / +1.1% | tomcat 통과, lettuce는 표본 부족 |
| G3 민감도 — lettuce 배정당 대기(schedstat) | 385.0μs | 1.0μs | **검출** |
| G5 커널 | 6.1.188 | | CFS |

**수정 1 — G1b에 절대 허용치(배정당 3μs)를 더했다.** 워커 8에서 lettuce의 실제 대기는 배정당 1μs인데 bpftrace는 3μs로 쟀다. 차이 147ms ÷ 배정 70,046회 = **배정당 +2.1μs의 고정 오프셋**이다. 프로브(`sched_wakeup`·`sched_switch`) 실행 시간이 측정 구간 안에 얹히기 때문이고, schedstat은 커널 내부 시각으로 재서 이 비용이 없다. 대기가 수백 μs인 워커 32에서는 +0.1%로 묻힌다. 이것은 오류라기보다 **계측기의 해상도 하한**이므로 기준을 고치고 해석 규칙을 정했다 — **10μs 미만의 bpftrace 분위수는 해석하지 않고, 평균은 schedstat을 기준으로 삼는다.**

**수정 2 — G2는 schedstat 쪽이 100건 미만이면 판정하지 않는다.** 1차 게이트에서 lettuce가 37 대 33건(4건 차이)으로 +12.1% FAIL이 났지만, 같은 판별 로직이 tomcat에서는 19,387 대 19,452건(−0.3%)으로 맞았다. 판별 오류가 아니라 작은 표본에서 상대 오차가 의미를 잃은 것이다.

**수정 3 — 해상도.** 1차 게이트에서는 lhist가 100μs 간격뿐이라 lettuce의 p50·p90이 한 버킷(0~99μs)에 뭉개졌다. 10μs 간격(2ms까지) lhist를 함께 두고, 분위수가 2ms 미만이면 그쪽을 쓴다.

두 기준 모두 **본 측정 데이터를 보기 전에** 합성 워크로드만 보고 고쳤다. "시작점 모름" 배정(추적 창 경계 등)은 lettuce 배정의 1.3~1.5%였지만, G1b가 보여주듯 놓친 대기 시간은 1% 미만이다.

> 합성 워크로드에서도 1절의 약분 효과가 그대로 보였다 — 워커 32 → 8에서 lettuce의 배정당 실행은 39.5 → 40.4μs로 고정(일의 양이 고정이므로)인데 배정당 대기는 385 → 1μs, 배정/초는 1,488 → 3,438. 다만 합성이라 일의 양이 고정돼 있어서 대기 비율도 크게 움직였다(90.7 → 2.4%). 실제 앱에서는 한 번에 처리할 밀린 명령의 양이 경쟁 수준에 따라 변한다는 것이 #88의 관측이고, 이번 실측이 그것을 가른다.

### 4-2. 본 측정 준비 중 잡은 함정 — 둘 다 에러 없이 틀린 결과를 냈을 것이다

**① 실제 Tomcat 워커의 comm은 `http-nio-8080-e`가 아니라 `http-nio-0.0.0.`이다.** `server.address: 0.0.0.0` 때문에 커넥터 이름이 `http-nio-0.0.0.0-8080`이 되고, 15자 절단 후에는 포트가 아예 남지 않는다. bpftrace 초안의 필터(`http-nio-8080-e`)였다면 실제 앱에서 tomcat을 **한 건도** 잡지 못했다. 그런데도 게이트는 통과했을 것이다 — 합성 워크로드가 그 이름으로 스레드를 직접 만들었기 때문이다. schedstat 그룹과 맞추려고 접두사를 `http-nio-`로 넓혀 둔 것이 이 문제를 미리 막았다. **합성 워크로드 게이트는 "계측기가 내가 정한 이름을 잡는가"만 증명하지, "그 이름이 실제 앱의 이름인가"는 증명하지 못한다** — 앱 배포 직후 `/proc/<pid>/task/*/comm` 분포로 따로 확인했다(`http-nio-0.0.0.` 12개, `lettuce-epollEv` 2개).

**② 시딩 전에 채워진 빈 랭킹 캐시.** 시딩 후 `/popular`이 모든 테마에서 `[]`를 돌려줬다. 랭킹 쿼리(`findPopularCourseIds`)에는 WHERE조차 없으니 DB 문제가 아니라, 시딩 전 빈 DB에서 계산된 빈 목록이 `popularCourses::*` 8개 키에 남아 있던 것이다. 그대로 측정했다면 요청당 Redis 명령이 **GET 1회**(빈 목록이라 MGET 생략)가 되어 #88의 **GET + MGET 2회** 경로와 다른 워크로드를 쟀을 것이다 — TPS·지연 모두 정상처럼 보였을 것이다. 8개 키만 지정해 DEL한 뒤 20초 예열에서 **요청 20,140 = GET 20,140 = MGET 20,140**으로 #88과 같은 경로임을 확인했다.

환경 대조: CPU **Xeon Platinum 8259CL**(#88과 동일), 두 EC2 모두 `unlimited` 크레딧, k6 **v2.3.0**(#88은 v2.0.0 — 부하 생성기 버전 차이는 arm 간 비교에는 무관하나 #88 절대값과 직접 비교하지 않는다).

## 5. 실행 계획

1. **loadtest 스택 재생성** — 착수 시점에 모듈이 이미 철거돼 있었다. 원래는 정지된 App EC2만 켜서 게이트를 돌릴 계획이었으나, 어차피 전체를 새로 만들어야 해서 게이트와 실측을 한 세션으로 합쳤다. AMI 필터는 `kernel-6.1`로 고정했다(아래 "커널 고정" 참고).
2. **JAR 배포 전 게이트** — 앱 서비스를 정지한 채 `sudo dnf install -y bpftrace` → `SchedLatencyDryRun`(로컬에서 컴파일한 .class — App EC2는 headless JRE라 소스 실행 불가, 워커 32 / 8)로 G1·G2·G3·G5 판정, bpftrace JSON 형식 확인. 앱보다 먼저 하는 이유는 진짜 lettuce·tomcat 스레드가 같은 이름이라 섞이기 때문이다.
3. 게이트 통과 시 JAR 배포·시딩(`DB_DDL_AUTO=validate`로 유지) → `ARMS="T200 T64 T32 T16 T8" REPS=2 LEVELS="200" WARMUP_SEC=60 SCHEDSTAT_SEC=30 SCHEDLAT=1`로 배치 실행(2회차 역순).
4. `summarize-sched-latency.py`로 분위수·게이트 표, 이 문서에 결과와 P1~P5 판정을 덧붙인다.
5. 인프라 철거(`destroy`).

### 커널 고정 — 재생성하다 발견한 전제의 흔들림

`terraform/loadtest`의 AMI 필터 `al2023-ami-2023.*-x86_64`에는 같은 릴리스의 **kernel-6.1 / 6.12 / 6.18 AMI가 같은 생성 시각으로 함께 걸린다**(2026-10-12 릴리스 기준 실측). `most_recent = true`로는 셋 중 무엇이 선택될지 정해지지 않고, 6.6 이상은 스케줄러가 CFS가 아니라 **EEVDF**다. 이번 측정은 "스케줄러가 CPU를 얼마나 빨리 넘겨주는가" 자체를 재므로, apply마다 스케줄러가 바뀔 수 있으면 #88(6.1.177, CFS)과 같은 조건이라고 말할 수 없다. 필터를 `al2023-ami-2023.*-kernel-6.1-x86_64`로 고정했다.

같은 필터가 운영(`terraform/prod/asg.tf`)에도 있었고, 거기서는 동점 처리가 실제로 뒤집혀 왔다(#209). 원격 state 이력을 보면 08-26 apply는 6.12, 08-27 apply는 **같은 릴리스(20260817.0)인데** 6.1을 골랐다. 10-14에 plan을 세 번 돌렸을 때는 세 번 모두 6.18이었다. 운영도 6.1로 고정해서 이 문서의 결론이 운영 커널에서도 같은 스케줄러를 전제로 하게 했다. AWS 기본 커널 포인터(`al2023-ami-kernel-default`, 현재 6.18)는 매년 옮겨지므로 따르지 않았다. 6.1은 2027년 말까지 full support다. 커널을 올릴 때는 loadtest와 운영을 함께 옮기고 이 문서의 측정을 다시 한다.

재생성하면서 `terraform.tfvars`(gitignore)의 낡은 값 두 개도 바로잡았다 — `app_instance_type`이 `variables.tf`의 의도(t3.small, "임의로 바꾸지 말 것")와 달리 `t3.micro`로 덮어써져 있었고, `app_git_ref`가 이번 부하 스크립트(`popular-cold.js`)가 없는 커밋을 가리키고 있었다.

### 6-3. 왜 대기가 경쟁자 수와 무관했는가 — 선점 후 재대기가 일정하다

lettuce가 CPU에서 내려온 이유(bpftrace, r1 기준):

| arm | 선점으로 내려옴 | 잠들어 내려옴 | 선점 후 재대기 평균 / p50 / p90 (μs) | 깨어남 후 대기 평균 / p50 / p90 (μs) |
|---|---|---|---|---|
| T200 | 99,647 (99%) | 982 | **244** / 50 / 500 | 1,144 / 90 / 3,300 |
| T32 | 99,770 (97%) | 2,782 | **239** / 60 / 510 | 686 / 30 / 2,400 |
| T16 | 58,338 (70%) | 24,623 | **239** / 90 / 480 | 386 / 40 / 1,280 |
| T8 | 13,044 (11%) | **109,205** | 161 / 30 / 510 | **116** / 20 / 360 |

- T200~T16에서 **선점 후 재대기가 239~244μs로 일정**하다. lettuce는 평균 36μs 일하고 밀려난 뒤 약 240μs를 기다리는 주기를 경쟁자 수와 무관하게 반복한다. 재대기가 "런큐 전체 길이"가 아니라 **바로 앞에 끼어든 소수의 스레드가 한 번 도는 시간**(Tomcat 워커의 배정당 실행이 122~176μs)으로 정해진다고 보면 일관된다.
- lettuce는 처리할 응답이 늘 쌓여 있어 **거의 잠들지 않는다.** CFS는 잠들었다 깬 스레드에게 vruntime 이점을 주어 곧바로 CPU를 얻게 하는데(깨어남 선점), 잠들지 않는 스레드는 그 혜택을 받을 기회가 없다. 반대로 lettuce가 응답을 처리할 때마다 그 응답을 기다리던 워커가 깨어나 lettuce 앞에 선다 — **lettuce는 자기가 깨운 워커에게 밀려난다.** 처음에는 CFS의 동작에서 나온 추론이었고, #207에서 bpftrace로 직접 확인했다 — lettuce 선점의 **약 98%가 Tomcat 워커**, 그중 **약 95%가 lettuce 자신이 마지막으로 깨운 워커**였고, 깨우기에서 전환까지 p99 20μs였다(6-8).
- **T8에서야 가설대로의 현상이 나온다.** 밀린 명령이 최대 16개라 큐가 비는 순간이 생기고, lettuce가 잠들기 시작한다(내려옴의 89%가 수면). 그러면 깨어남 선점이 작동해 깨어난 뒤 대기 p50이 20μs가 되고, 배정당 대기가 111μs(×0.43), 배정 빈도가 ×1.33이 된다. **"경쟁자를 줄이면 CPU를 더 빨리 얻는다"는 직관은 lettuce가 포화에서 벗어날 때만 성립한다.**
- T16의 일시적 증가(배정당 대기 304μs, 배정당 실행 50μs)는 선점과 수면이 섞이는 전이 구간으로 보인다. 2회 모두 같은 방향(285 / 322)이라 노이즈는 아니지만, 원인은 이번 데이터로 가리지 못했다.

#### lettuce가 CPU를 차지하는 비율도 그대로였다

위의 결과를 시간 비율로 다시 보면 결론이 더 직접적으로 드러난다. lettuce 이벤트루프가 벽시계 시간 중 **실제로 CPU 위에서 돈 비율**(schedstat 실행 시간 ÷ 벽시계)이다.

| arm | **CPU 점유** (회차별) | 런큐 대기 | 둘의 합(쉬지 않은 비율) |
|---|---|---|---|
| T200 | **11.7%** (11.7 / 11.6) | 83.4% | 95.0% |
| T64 | 13.3% (12.8 / 13.7) | 85.4% | 98.6% |
| T32 | **12.6%** (12.0 / 13.2) | 85.2% | 97.8% |
| T16 | 13.0% (13.6 / 12.4) | 78.2% | 91.2% |
| T8 | **17.4%** (16.5 / 18.3) | 47.9% | 65.3% |

경쟁 워커가 19.6 → 5.3개로 줄었는데도 lettuce가 CPU를 차지한 비율은 **11.7 → 12.6%로 거의 그대로**다. 선점으로 밀려나고 약 240μs를 기다리는 주기가 경쟁자 수와 무관하게 일정하니, CPU를 얻는 몫도 일정하다. 이 박스에서 lettuce는 스레드 상한을 200 → 16으로 줄여도 **CPU의 약 12~13%만 얻는 상태가 바뀌지 않았고**, 큐가 비어 잠들기 시작하는 T8에서야 17.4%로 오른다. 6-4의 전제 — "단일 이벤트루프의 처리 능력이 arm 간에 같다" — 를 이 표가 직접 받친다.

> 이 비율은 "대기 비율"(W ÷ (R+W), 1절)과 다른 지표다. 대기 비율은 배정 횟수가 약분되어 속도를 못 보여주지만, 점유 비율(R ÷ 벽시계)은 이벤트루프가 단위 시간에 처리할 수 있는 일의 양에 직접 비례한다.

### 6-4. 그렇다면 Redis 지연은 왜 줄었나 — 리틀의 법칙

lettuce가 CPU를 얻는 속도가 같다면 단일 이벤트루프의 **처리 능력도 같다.** 그런데 Redis 지연은 13.75 → 3.11ms로 줄었다. 닫힌 루프에서 평균 대기 명령 수 L = 처리율 λ × 지연 W이고, λ는 요청당 명령 2개 × TPS다.

| arm | λ = 2 × TPS (명령/초) | W = Redis 지연 | **L = λW (in-flight 명령)** | L ÷ 스레드 상한 |
|---|---|---|---|---|
| T200 | 5,562 | 13.75ms | **76.5** | 0.38 |
| T64 | 5,936 | 5.58ms | 33.1 | 0.52 |
| T32 | 5,470 | 3.11ms | **17.0** | 0.53 |
| T16 | 5,790 | 1.09ms | 6.3 | 0.39 |
| T8 | 5,378 | 0.37ms | 2.0 | 0.25 |

처리율 λ가 arm 간에 ±5% 안에서 같으니, 지연 W는 in-flight L에 비례한다. 그리고 L은 스레드 상한의 약 0.25~0.5배로 상한에 묶여 있다. 즉 **지연을 줄인 것은 이벤트루프가 빨라져서가 아니라, 같은 속도의 이벤트루프 앞에 줄 서는 명령이 스레드 상한만큼 줄어서**다. [ec2-measurement.md](ec2-measurement.md)의 "밀린 명령 뭉치가 작아져서"라는 설명이 맞았고, 이번 측정은 그것을 **큐잉의 형태(L = λW)로 정량화**하고 경쟁 측 설명(스케줄링이 빨라짐)을 배제한다.

### 6-7. 원인 A/B — #88 당시 JAR로도 T200 저하는 재현되지 않았다

6-6에서 사라진 T200의 고동시성 저하가 코드 변경 때문인지 가리려고, #88 당시 커밋(`d31c0ce`)으로 빌드한 JAR과 현재 JAR(`f017414`)을 **같은 박스·같은 시드**에서 T200·VU 50/200으로 ABBA(옛 → 새 → 새 → 옛) 비교했다. JAR을 바꿀 때마다 앱을 멈추고 캐시 두 네임스페이스(`popularCourses::*`, `courseListItem::*`)만 이름 지정 DEL해, 다른 버전이 직렬화한 항목을 읽지 않게 했다. 기동한 바이너리는 JAR 해시와 새 버전에만 있는 기동 로그(LLM 어댑터 활성화)로 확인했다. 옛 설정이 요구하는 `GEMINI_API_KEY`는 인기 코스 경로에서 쓰이지 않아 더미값을 넣었다. 원자료는 `results/lettuce-dispatch/ab-jar/`.

| T200, VU 200 | TPS (회차별) | p95 | 요청당 CPU |
|---|---|---|---|
| #88 당시 (2026-08-18, 옛 코드) | **2,517** | 122.9ms | 0.7469 |
| 오늘 옛 JAR `d31c0ce` | **3,033** (3,170 / 2,895) | 104.7ms | 0.6238 |
| 오늘 새 JAR `f017414` | **3,337** (3,413 / 3,262) | 89.2ms | 0.5404 |

- **같은 옛 코드가 8월보다 TPS 20% 높다.** 사라진 저하의 대부분은 코드가 아니라 **환경**(인스턴스 재생성, JDK 패치, 커널 6.1.177 → 6.1.188, k6 v2.0 → v2.3)에서 왔다. 이 데이터로는 그중 무엇인지 가리지 못한다.
- **코드 변경도 일부 기여했다** — 같은 박스에서 새 JAR이 TPS +10%, 요청당 CPU −13%. 두 쌍(old1/new1, old2/new2) 모두 같은 방향이다. 요청당 할당량은 85~88KB로 같아 차이가 메모리 할당 쪽은 아니다.
- **옛 코드의 T200(3,033)조차 #88 당시 T32(2,921)보다 높다.** #88이 `maxThreads` 32로 없앤 "T200의 고동시성 저하"는 8월 코드를 그대로 돌려도 현재 환경에서는 생기지 않는다. 따라서 #88의 TPS +16%·p95 −33%·요청당 CPU −26%(#97 −31.5%)는 **그 시점 환경의 측정**으로만 유효하고, 현재 설정 근거로는 쓸 수 없다.
- 같은 이유로 #97의 "전환 1회당 캐시 재적재 비용이 싸져서"라는 분해도 근거가 약해진다. 그 설명의 원인 조건(스레드 200개가 공유 L2 1MB를 다툼)은 오늘도 같은데 효과가 사라졌기 때문이다. #97은 배제법으로 추론했을 뿐 앱 안의 전환당 비용이나 캐시 미스를 직접 재지 못했다(t3에서 `perf` 하드웨어 이벤트 미지원).

**한계** — 버전당 2회, 같은 JAR의 회차 간 차이 4~9%라 "코드 몫 10%"는 대략적 크기다. VU 50 run은 예열 30초 직후 첫 레벨이라 JIT가 덜 데워져(6-6의 VU 50보다 약 15% 낮다) 판정에 쓰지 않았다.

### 6-8. lettuce를 밀어내는 것은 자기가 깨운 Tomcat 워커다 (#207, 2026-10-14)

6-3의 "lettuce는 자기가 깨운 워커에게 밀려난다"는 CFS 동작에서 끌어낸 추론이었다. 실행 길이가 평균 36μs라 ms 단위인 틱 선점일 수는 없으니 깨어남 선점일 것이라는 데까지는 좁혀졌지만, **누가** 깨어나 밀어내는지는 재지 않았다. 이번에는 lettuce가 선점으로 내려오는 순간마다 세 가지를 센다.

| 무엇을 | 어떻게 | 왜 |
|---|---|---|
| 그 CPU에 올라가는 스레드의 그룹 | `sched_switch`의 `next_comm` → tomcat / gc / jit / VM Thread / 커널 스레드 / bpftrace / 분류 밖 | 이슈의 1차 질문 |
| 그 스레드를 마지막으로 깨운 쪽 | `sched_waking` 컨텍스트의 comm. softirq·hardirq·hrtimer 안의 깨우기는 "인터럽트"로 분리 | `sched_wakeup`은 원격 깨우기면 대상 CPU의 IPI 안에서 발생해 comm이 깨운 쪽이 아닐 수 있다. 인터럽트 안의 깨우기는 그때 CPU에 있던 스레드(lettuce일 수 있다)의 이름으로 잡힌다 |
| 그 스레드가 이 CPU로 마지막에 깨워진 스레드인가 + 깨우기 → 전환 간격 | `sched_wakeup`의 `target_cpu`별 마지막 wakee | `next`는 "자리를 차지한 스레드"이지 "선점을 일으킨 스레드"라는 보장이 없다 — 일치하고 간격이 μs 단위면 그 깨우기가 선점을 일으킨 것이다 |

#### 게이트 — 정답을 아는 합성 조건, 그리고 그것이 잡아낸 결함 셋

외부 출처로 대조할 수 없는 지표라, 합성 워크로드에 **답을 미리 아는 두 모드**를 만들었다.

| 모드 | 워커를 깨우는 쪽 | 기대 | 최종 실측 (워커 32 / 8) |
|---|---|---|---|
| `indep` (G3의 기존 워크로드) | 타이머(`parkNanos` 만료 = hrtimer 인터럽트) | lettuce가 깨운 워커에게 밀려남 ≈ 0 | **0.0% / 0.0%** |
| `wake` | lettuce가 응답 처리마다 `unpark` | 지배적 | **98.4%** (tomcat 선점자의 깨운 쪽 100% lettuce) / 선점 61건뿐(lettuce가 거의 잠듦) |

처음 돌렸을 때는 이 게이트가 **조용히 틀린 숫자 셋**을 잡아냈다. 셋 다 에러 없이 그럴듯한 숫자를 냈다.

1. **인터럽트 깊이가 한 CPU에 고정됐다** — `wake`/32에서 lettuce가 깨운 워커가 lettuce 50% / 인터럽트 50%로 정확히 반반 갈렸다(정답 100%). bpftrace는 프로브를 하나씩 붙이는데, `softirq_entry`만 붙고 `softirq_exit`은 아직인 틈에 들어온 인터럽트가 진입만 세져 깊이가 영구히 +1로 남았다 — 2 vCPU 중 한쪽이 전부 "인터럽트"가 된 것이다. 문맥 전환은 인터럽트 처리 도중에 일어나지 않으므로 `sched_switch`마다 깊이를 0으로 되돌리게 했다.
2. **기존 스크립트의 잠복 버그 — 낡은 깨어남 시각** — `wake`/32에서 tomcat G1b가 +200%였다. 커널 6.1은 이미 CPU 위에 있는 스레드를 깨워도(`unpark`가 허가만 쌓는 경우) `ttwu_runnable` 경로로 `sched_wakeup`을 낸다. 추적 전부터 돌던 스레드는 `@oncpu`가 비어 이를 거르지 못하고, 잠들 때 지우지도 않아 다음 깨어남에서 "실행 + 수면"이 대기로 잡혔다(5~23ms 이상값 약 50건). 기존 게이트는 잠든 스레드만 깨우는 `indep`뿐이라 이 경로를 한 번도 타지 않았다. CPU에서 내려올 때 깨어남 시각을 항상 지우게 했다.
3. **측정 창의 양 끝** — 프로브가 6개에서 11~12개로 늘자 G1·G2·G1b가 함께 **+4~6%**(이전 +0.1~1.2%)로 벌어졌다. 먼저 붙은 프로브가 나머지를 붙이는 동안 세고, `exit()`이 비동기라 프로브를 떼는 동안에도 셌다. 1초 tick 2번째에 결과 맵을 비우고(무장) READY를 찍고, 끝 tick에서 결과를 직접 출력하게 했다 → **G1 −0.1 ~ −1.5%**, 무장 전 2초 동안 쌓인 상태 덕분에 "시작점 모름" 배정이 수백 건에서 **0~1건**으로 줄었다. 끝 tick의 `print()`도 비동기라 맵끼리 1~2건 시차가 생겨 G6(맵 간 정합성)는 "3건 또는 0.1% 이내"로 뒀다.

**창 위치에서 한 번 더 틀렸다.** 합성 포화 조건(워커 32)에서 bpftrace 부착이 25초 걸려, 실측에서 래퍼를 20초 앞당겨 띄웠다. 그런데 실제 앱의 부착은 **3.8~4.1초**였고, 앞당긴 창(레벨 11~41초)이 VU 5 예열 직후 VU 200의 **약 25초 TPS 램프업**과 겹쳐 G4가 −16~27%로 부풀었다(램프업은 bpftrace를 띄우기 전부터 보인다). 앞당김을 0으로 되돌려 창을 #208과 같은 정상 상태 구간에 두고 다시 쟀다 — 아래 표가 그 결과다. 첫 배치(`preempt/`)도 선점자 구성은 ±0.5%p 안에서 같았다.

#### 결과 (VU 200, arm별 2회 평균 — 2회차 역순, 추적 창 30초)

원자료는 `results/lettuce-dispatch/preempt-center/`(정상 상태 창), `preempt/`(램프업과 겹친 창), 게이트는 `gate3/`~`gate5/`(모두 gitignore).

| arm | TPS | lettuce 선점(30초) | **선점자 tomcat** | ← lettuce가 깨움 | ← 인터럽트 | ← tomcat | 커널 스레드 | 그 밖 | tomcat 중 마지막 wakee | 깨우기 → 전환 p99 |
|---|---|---|---|---|---|---|---|---|---|---|
| T200 | 3,049 | 102,724 | **98.7%** | **93.5%** | 2.9% | 2.4% | 0.9% | 0.4% | 98.8% | 20μs |
| T32 | 3,149 | 111,320 | **98.2%** | **90.8%** | 4.7% | 2.8% | 1.5% | 0.4% | 98.6% | 20μs |

<sub>"← lettuce가 깨움" 등은 전체 선점 대비 비율(선점자 tomcat을 깨운 쪽별로 나눈 것). 선점자가 gc·jit·VM Thread·bpftrace·lettuce인 경우는 합쳐 0.2% 미만이라 "그 밖"에 넣었다. 유효성 게이트 G1·G1b·G2·G6는 8개 run 모두 통과.</sub>

- **6-3의 해석을 확정한다.** lettuce 선점의 98% 이상이 Tomcat 워커이고, 전체 선점의 **91~94%가 lettuce 자신이 마지막으로 깨운 워커**다. 그 워커의 99%가 바로 그 CPU로 마지막에 깨워진 스레드이고, 깨우기에서 전환까지 p99 **20μs**다 — 틱이 아니라 **깨우기 자체가 선점을 일으켰다.** lettuce가 응답을 처리해 워커를 깨우면, 오래 잠들어 vruntime 이점을 가진 그 워커가 같은 CPU에서 즉시 lettuce를 밀어낸다.
- **6-3의 "선점 후 재대기가 경쟁자 수와 무관하게 일정"의 메커니즘이 이것이다.** lettuce를 막는 것은 런큐에 줄 선 워커 전체가 아니라 **방금 자기가 깨운 한 워커**다. 그 워커가 한 번 도는 시간(배정당 실행 164~193μs)만큼 기다리는 주기가 스레드 상한과 무관하게 반복된다(선점 후 재대기 bpftrace 평균: T200 230~250μs, T32 203~207μs).
- T32에서 lettuce가 깨운 비율이 조금 낮은 것(93.5 → 90.8%)은 인터럽트가 깨운 워커가 2.9 → 4.7%로 늘어서다. 이번 데이터로는 원인을 가리지 못했다.
- 커널 스레드 선점자(1% 안팎)의 54~78%도 lettuce가 깨웠다. 소켓 쓰기 경로가 깨우는 커널 작업으로 보이지만, 커널 스레드 그룹은 이름을 남기지 않아 확인하지 못했다.
- 배정당 대기(schedstat)는 T200 245.8μs → T32 210.3μs(**×0.86**), 첫 배치는 ×0.99였다. 둘 다 사전 등록 기각 구간(0.8~1.2) 안이라 6-2의 P1 기각과 어긋나지 않는다.

#### 한계

- **추적 부하(G4)** — 창 안/밖 TPS −6.0 / −5.3 / −3.7 / +0.6%(평균 −3.6%, 3% 기준 FAIL 3건). #208(평균 −2.1%)보다 1~2%p 크다 — 인터럽트 계열 프로브(softirq·hardirq·hrtimer)가 네트워크가 바쁜 실제 앱에서 자주 발생하기 때문으로 보인다. 다만 TPS가 최대 27% 달랐던 두 배치(램프업 창 / 정상 상태 창)에서 선점자 구성이 ±0.5%p로 같았으므로, 추적 부하가 **누가 밀어내는가**를 바꾸지는 않았다.
- 깨운 쪽 판별은 `sched_waking` 시점의 실행 컨텍스트에 기댄다. IPI 같은 다른 인터럽트 경로는 깊이에 넣지 않았다 — `indep` 게이트에서 "lettuce가 깨운 워커" 0.0%가 오귀속의 상한을 보여준다.
- **처방 시 주의(#210에서 확인)** — 이 선점은 결함이 아니었다. lettuce에만 nice −10을 주자 선점은 사라졌지만 lettuce가 응답마다 깨어나 배정당 명령 수가 1.65 → 0.61로 쪼개졌고, 운영 설정(T32)의 TPS가 ×0.93, 요청당 CPU가 +15%가 됐다 — [lettuce-priority.md](lettuce-priority.md).
- "마지막 wakee 일치"는 선점 원인의 강한 정황이지 증명은 아니다. 깨우기 → 전환 p99 20μs가 그것을 뒷받침한다.
- VU 200 한 레벨, t3.small(2 vCPU, 커널 6.1.188 CFS)에서만 쟀다. EEVDF(6.6+)는 깨어남 선점 규칙이 달라 결과가 바뀔 수 있다. 운영 ASG도 6.1로 고정했으므로(#209) 이 결과는 운영 커널 계열에도 적용된다. EEVDF로 옮기는 시점에는 다시 재야 한다.

## 7. 후속 과제

- ~~**lettuce를 누가 밀어내는가**~~ — #207에서 확인했다(6-8). lettuce 선점의 약 98%가 Tomcat 워커이고, 그중 약 95%가 lettuce가 직전에 깨운 워커다.
- **추적 없는 대조 run** — `SCHEDLAT=0 SCHEDSTAT=1`로 T200/T32를 다시 재서, bpftrace가 배정당 대기를 바꾸지 않았음을 G4보다 직접적으로 확인한다.
- **`maxThreads` 32의 근거 재수립** — 6-6·6-7로 #88의 근거(TPS +16%)가 현재 환경에서 성립하지 않음이 확인됐다. 현재 코드·환경에서 32는 p95 −14% / TPS −6%의 교환이다. 열린 루프(도착률 고정)로 최대 처리량과 꼬리 지연을 다시 재서 값을 정하거나, 느린 요청 격리(bulkhead) 관점의 근거로 바꿔 적어야 한다.
- **환경 원인 분리** — 옛 코드로도 8월 대비 TPS +20%였다. JDK·커널·k6 버전을 하나씩 고정해 A/B하면 무엇이 T200 저하를 만들었는지 가릴 수 있다(우선순위 낮음 — 지금 운영 결정에는 영향이 없다).
- **run-batch의 원격 결과 정리** — k6 EC2 `/tmp`가 tmpfs(459MB)라 배치가 쌓이면 가득 찬다. 배치 끝의 scp 회수 후 원격 사본을 지우거나 디스크 여유를 사전 점검해야 한다(6-6에서 실제로 3개 레벨 유실).
