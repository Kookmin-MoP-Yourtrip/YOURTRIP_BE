# 힙 상한 A/B 실측 — 천장을 올려도 G1은 대개 움직이지 않는다

> [#101](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/101)의 실측 기록이다. 설계와 사전 등록은 [README.md](README.md), 메모리 지도는 [memory-map.md](memory-map.md)에 있다.
>
> **결론만 먼저** — `-Xmx`를 448 → 768 → 1024로 올려도 **G1이 실제로 커밋하는 힙은 227~230MB에서 움직이지 않았다**(6개 arm-run 중 5개). 예외 1건에서만 424MB로 확장됐고, 그때 eden이 140 → 265MB로 커지며 **young GC가 정확히 절반(2.2 → 1.12회/s)** 이 됐다. 즉 성능을 정하는 것은 `-Xmx`(천장)가 아니라 **committed 힙**이고, 천장은 그 위에 걸린 한도일 뿐이다.
>
> **TPS·p95의 arm 간 차이는 판정하지 못했다.** 같은 설정 2회 반복의 편차가 VU200에서 **16.3%**로, arm 간 차이(4.7%)의 3.5배였다. 사전 등록한 ±2% 기준은 이 측정의 분해능 아래였다.
>
> **확정하지 못한 것** — 성능 차이의 유무. "차이가 없다"가 아니라 **"이 측정으로는 구분할 수 없다"**가 정확한 서술이다. 원인은 §5에 적었다.

## 1. 측정 환경

| 항목 | 값 |
|---|---|
| 세션 | 2026-08-21 15:28~16:18 KST, 한 부팅 세션·같은 JAR |
| App EC2 | `t3.small` (`i-06bc413840b95ca09`), vCPU 2 = **물리 코어 1개 × SMT 2** |
| CPU | **Intel Xeon Platinum 8259CL @ 2.50GHz** — L1d 32KiB / L2 1MiB / L3 35.8MiB를 두 vCPU가 공유 |
| 메모리 | `MemTotal` **1,913 MiB** (1,959,216 kB), Swap 0 |
| OS / 커널 | Amazon Linux 2023.12 / 6.1.177 |
| JDK | Corretto **21.0.12**, GC = **G1** (`-XX:+PrintFlagsFinal`로 직접 확인, [memory-map.md](memory-map.md) §1) |
| JVM 옵션 | `-Xmx{448\|768\|1024}m -Xss512k` — 그 외 `-XX` 플래그 없음 |
| Tomcat | `server.tomcat.threads.max=32` (전 run에서 지표로 검증) |
| CPU 크레딧 | `unlimited` 모드. **`CPUCreditBalance`가 배치 시작 2분 만에 0이 되어 전 구간 0**, `CPUSurplusCreditBalance` 0 → 61.5로 증가 (§5) |
| RDS / Redis | `db.t3.micro` / `cache.t3.micro`, 같은 AZ |
| 시드 | `seed-benchmark.sql` + `seed-popular.sql` — course 6,000 / place 30,000 / place_image 60,000 |
| 부하 | k6 v2.0.0, `popular-cold.js`, `constant-vus`, `THEME_MODE=all`, **`FLUSHALL` 없음**(워밍 히트 경로) |
| 배치 | 3 arm × VU 5/20/50/200 × 90초 × **2회(2회차 역순)**, 예열 60초, schedstat 창 60초 |

**arm 표기**는 `T<maxThreads>H<heapMB>`다. 힙은 `.env`의 `JVM_OPTS` + systemd 드롭인으로 바꿨고(user_data를 건드리면 인스턴스가 교체된다), arm마다 `/proc/<pid>/cmdline`과 `jvm_memory_max_bytes{area="heap"}` 양수 합 **두 갈래로 적용을 검증**했다 — 6회 전부 기대값과 정확히 일치했다(448 → 469762048, 768 → 805306368, 1024 → 1073741824).

### 시작 전에 정리한 것 두 가지

- **시드가 날아가 있었다.** 인스턴스를 켜자 앱이 `DB_DDL_AUTO=create`로 자동 기동해 Hibernate가 스키마를 DROP/CREATE 했고 전 테이블이 0건이었다. `validate`로 내린 뒤 SSM 포트포워딩으로 재적재했다.
- **이전 세션의 JFR 드롭인이 남아 있었다.** `jfr.conf`가 `-XX:StartFlightRecording=...settings=profile`을 걸고 있었다. 프로파일링 오버헤드로 측정을 오염시킬 뿐 아니라, **파일명이 `10-jvm-opts.conf`보다 뒤에 정렬돼 힙 설정을 덮어쓴다.** `.disabled-101`로 이름을 바꿔 비활성화했다(systemd는 `.conf`만 읽는다).

## 3. 결과

### 3-1. 메모리 (VU200)

| run | 힙 상한 | 힙 committed | 논힙(CCS 제외) | direct | JVM 보고 합계 | **RSS** | **힙 밖 잔여** | MemAvail 최소 |
|---|---|---|---|---|---|---|---|---|
| T32H448 r1 | 448 | 227 | 181.9 | 8.4 | 417.3 | 581.3 | **164.0** | 996.2 |
| T32H448 r2 | 448 | 227 | 181.9 | 8.4 | 417.3 | 588.5 | **171.2** | 1004.6 |
| T32H768 r1 | 768 | 227 | 181.8 | 8.4 | 417.2 | 579.5 | **162.3** | 1004.1 |
| T32H768 r2 | 768 | 230 | 183.1 | 8.4 | 421.5 | 580.8 | **159.3** | 1012.5 |
| T32H1024 r1 | 1024 | 227 | 182.0 | 8.4 | 417.4 | 582.8 | **165.4** | 1000.8 |
| **T32H1024 r2** | 1024 | **424** | 191.8 | 8.4 | 624.2 | **790.7** | **166.5** | 801.4 |

<sub>단위 MB. `힙 밖 잔여 = RSS − (힙 committed + 논힙 + direct)` — 스레드 스택·GC 자료구조·컴파일러 아레나·심볼 등 Actuator가 노출하지 않는 영역이다. 항목별 분해는 [memory-map.md](memory-map.md).</sub>

**힙 밖 잔여는 24 run 전체에서 159.0~171.2MB였다.** 힙 상한이 448이든 1024든, committed가 227이든 424든, VU가 5든 200이든 거의 변하지 않는다.

### 3-2. 기전 — eden은 천장이 아니라 committed가 정한다

| run (VU200) | eden committed | 힙 committed | eden/힙 | young GC |
|---|---|---|---|---|
| T32H448 r1 | 141MB | 227MB | 62.1% | 2.31회/s |
| T32H448 r2 | 141MB | 227MB | 62.1% | 2.27회/s |
| T32H768 r1 | 141MB | 227MB | 62.1% | 1.95회/s |
| T32H768 r2 | 143MB | 230MB | 62.2% | 2.20회/s |
| T32H1024 r1 | 140MB | 227MB | 61.7% | 2.03회/s |
| **T32H1024 r2** | **265MB** | **424MB** | 62.5% | **1.12회/s** |

**eden은 예외 없이 committed 힙의 61.7~62.5%다** — `G1MaxNewSizePercent` 기본값 60%에 region 반올림이 붙은 값이고, 상한에 붙어 있다는 뜻이다. 그래서 사슬은 이렇게 닫힌다.

```
-Xmx(천장) ──[ G1의 확장 판단 ]──> committed ──[ ×62% ]──> eden ──[ 할당률 ÷ eden ]──> GC 빈도
                     ↑
            6번 중 5번은 여기서 안 움직였다
```

G1이 힙을 넓히는 조건은 GC 오버헤드가 목표를 넘는 것인데(`GCTimeRatio=12` → 목표 ≈ 7.7%), **실측 GC 점유는 벽시계의 1% 안팎**이라 목표의 1/7도 안 된다. 넓힐 이유가 없다. 한 번 넓어진 r2는 기동 시점의 사이징 변동으로 보이며, 재현되지 않았다.

### 3-3. 성능 (VU200 평균, 2회)

| arm | TPS | p95 | young GC | 요청당 GC | **요청당 CPU** |
|---|---|---|---|---|---|
| T32H448 | 3,605 | 68.6ms | 2.29회/s | 0.0033ms | **0.5161** vCPU-ms |
| T32H768 | 3,434 (−4.7%) | 71.0ms (+3.5%) | 2.07회/s (−9.4%) | 0.0032ms (−3.1%) | **0.5174** (+0.3%) |
| T32H1024 | 3,429 (−4.9%) | 72.3ms (+5.5%) | 1.57회/s (−31.3%) | 0.0024ms (−26.2%) | **0.5027** (−2.6%) |

<sub>1024의 GC 감소는 전적으로 r2(committed 424MB) 한 run에서 나온다. r1만 보면 2.03회/s로 448과 다르지 않다.</sub>

**그런데 이 차이를 신뢰할 수 없다.** 같은 설정 2회 반복의 편차가 이렇다.

| VU | arm 내 반복 편차(TPS) 최대 |
|---|---|
| 5 | 5.1% |
| 20 | 7.8% |
| 50 | **15.9%** |
| 200 | **16.3%** |

**노이즈가 신호의 3.5배다.** 방향성도 레벨마다 뒤집힌다 — 1024는 VU50에서 +5.1%, VU200에서 −4.9%다. 사전 등록한 "2회 모두 같은 방향" 조건도 충족하지 못한다.

**요청당 CPU는 안정적이다**(0.5027~0.5174, ±1.4%). 이 지표는 처리량으로 정규화돼 있어 사용 가능한 CPU의 변동에 둔감하다. **앱이 요청 하나를 처리하는 비용은 arm과 무관하게 같았다**는 뜻이고, TPS 변동이 앱이 아니라 바깥에서 왔음을 시사한다.

## 4. 판정

### 사전 등록 예측

| # | 예측 | 실측 | 판정 |
|---|---|---|---|
| **P1** | heap committed가 arm 간 ±40MB 안 (H1) | 6개 중 5개가 227~230MB, 1개가 424MB | **부분 적중** — 기본은 H1이지만 확장이 배제되지 않는다 |
| **P2** | young GC 빈도가 arm 간 ±25% 안 | 768 −9.4%, 1024 −31.3% | **기각** — 단 1024의 감소는 P1 예외 run 하나에서만 나온다 |
| **P3** | TPS·p95가 ±2% 안 | TPS −4.7% / −4.9%, 노이즈 16.3% | **판정 불가** — 기준이 분해능 아래였다 |
| **P4** | `native_other_mb`가 arm 간 ±20MB 안 | 159.0~171.2MB (**±6MB**) | **적중** |
| **P5** | RSS 증가분 ≤ heap committed 증가분 | committed +197MB일 때 RSS +207.9MB | **조건부 적중** — 초과분 10.9MB는 논힙 +9.8, 잔여 +1.1로 전액 설명된다 |

**H1(G1 자율 사이징이 지배한다)이 주된 그림으로 지지됐다.** 다만 "천장을 올려도 절대 안 늘어난다"는 아니다 — 6번 중 1번은 늘어났고, 늘어났을 때는 GC가 정확히 예측대로 줄었다.

### 채택 기준

| # | 조건 | 결과 |
|---|---|---|
| C1 | 5xx·k6 실패 0, PID 변경 없음, OOM 없음, `VmSwap=0` | **통과** (Swap 자체가 0인 박스) |
| C2 | VU200 2회 모두 여유·`MemAvail` ≥ 350MB | **통과** — 최소 801.4MB |
| C3 | VU200 TPS가 448 대비 −2% 이내 | **판정 불가** (노이즈 16.3%) |
| C4 | VU200 p95가 448 대비 +5% 이내 | 768 +3.5% 통과 / 1024 +5.5% **경계 초과** — 역시 노이즈 안 |
| C5 | 전 run `cpu_xcheck_pct` 절댓값 ≤ 5 | **통과** (최대 1.2) |
| C6 | `heap_max_mb`·`config_max_threads` 일치 | **통과** (24/24) |

**C3·C4를 판정할 수 없으므로 "성능이 나빠지지 않았다"를 실측으로 입증하지 못했다.** 대신 다음 두 가지는 말할 수 있다.

- **요청당 CPU가 arm 간 ±1.4%로 평평했다.** 앱이 요청당 태우는 CPU는 힙 상한에 무관했다.
- **메모리 안전 조건은 여유 있게 통과했다.** 최악의 run(committed 424MB)에서도 RSS 790.7MB, `MemAvailable` 801.4MB로 기준(350MB)의 2.3배였다.

### 채택값

[README.md](README.md) §5에 못 박은 규칙 — **"OS 실측이 300MB를 넘으면 1024 → 768로 내린다"** — 이 발동했다. 앱 정지 상태에서 잰 OS·에이전트 몫이 **321MB**였다.

산정식에 실측을 대입하면 여지는 923MB(64MB 내림 896MB)로 768보다 넉넉하지만, **사전 등록한 규칙을 사후에 완화하지 않는다.** 채택값은 **`-Xmx768m`** 이다.

> **산정식에 오류가 있었다.** 사전 등록한 식은 `… − 스택실측×1.2 − 잔여네이티브실측×1.3 …`로 스레드 스택을 따로 뺐는데, `native_other_mb`의 정의(`RSS − 힙 − 논힙 − direct`)가 이미 스택을 포함한다. 그대로 쓰면 스택을 두 번 빼는 셈이라 스택 항을 제거하고 계산했다. 결과에 미치는 영향은 32MB이고 채택값(768)은 두 계산 모두에서 안전 범위 안이다.

## 5. 한계

- **성능 차이를 판정하지 못했다.** 이것이 이번 측정의 가장 큰 한계다. 원인으로 지목되는 것은 **CPU 크레딧**이다 — `CPUCreditBalance`가 배치 시작 2분 만에 0이 되어 세션 전체가 `unlimited` 모드의 surplus 크레딧 위에서 돌았다(`CPUSurplusCreditBalance` 0 → 61.5). 인스턴스를 정지 상태에서 막 켠 직후라 크레딧이 쌓여 있지 않았다. **다음 측정에서는 기동 후 크레딧이 회복될 때까지 기다리거나, 크레딧에 좌우되지 않는 인스턴스 계열을 쓰는 것을 검토해야 한다.**
- **요청당 CPU는 안정적이었지만 그것이 TPS 동등성을 증명하지는 않는다.** 같은 CPU 비용으로도 사용 가능한 CPU가 다르면 처리량은 달라진다.
- **1024에서 관측된 힙 확장은 1회뿐이다.** 재현 조건(기동 시점의 무엇이 확장을 유발하는가)을 규명하지 못했다. 반대로 말하면 **768·1024에서도 확장이 언제든 일어날 수 있다**는 뜻이고, 그래서 메모리 여유를 확장 시나리오 기준으로 잡아야 한다.
- **과거 세션과 절대값을 비교하지 않았다.** 이번 T32 VU200 TPS는 약 3,600으로 #97(8175M, 3,435)·#88(8259CL, 2,921)과 다르다. CPU 모델이 #88과 같은데도 값이 다른 것은 크레딧 상태 차이로 설명될 수 있다 — **세션 간 절대값 비교를 금지하는 이 저장소의 규칙을 다시 확인해 준 셈이다.**
- **부하는 인기 코스 조회 한 경로뿐이다.** AI 코스 생성처럼 응답이 크고 할당이 많은 경로는 재지 않았다. 힙 상한의 가치가 실제로 드러나는 곳은 오히려 그쪽일 수 있다.
- **1초 폴링 해상도의 최대값이다.** 그 사이의 순간 첨두는 놓친다.
