# 비교 실험 E·F·V·G — Tomcat 워커를 비동기나 가상 스레드로 풀면 AI 지연은 어떻게 되는가

> **상태: 측정 완료(2026-11-05, 분당 40건 5회차)**. 질문·예측·판정 기준은 측정 전에 고정했고, 결과는 [measurement.md 8절](measurement.md#8-비교-실험-efvgh--스레드를-tomcat에서-떼면-ai-지연은-풀리는가)에 있다. 판정 K1~K8이 모두 성립했다(K7·K8은 2026-11-06). r70-V(2026-11-08)는 K9 성립, K10 불성립이다([measurement.md 8-9](measurement.md)). 주실험 설계는 [README.md](README.md), 앞선 비교 실험은 [abort-variant.md](abort-variant.md)다.

## 0. 요약

- **질문**: AI 요청을 Tomcat 워커에서 분리하면 다른 API는 지켜지는가. 그때 AI 요청 자체는 어떻게 되는가
- **왜 예산과 폴백을 끄는가**: 지금 구조는 과부하를 "35초 뒤 폴백 코스"로 흡수해, 문제가 응답 시간에 드러나지 않고 코스 품질로 숨는다. 이 실험은 그 정책들을 끄고 **밀린 일이 응답 지연으로 그대로 드러나는 조건**을 만든다
- **이것은 운영 구성이 아니라 반사실(counterfactual) 조건이다.** 결과를 인용할 때 "예산·폴백·`CallerRunsPolicy`를 끈 실험 조건"임을 함께 밝힌다
- **핵심 예측**: 동기(E)는 서비스 전체 장애, 비동기(F)와 가상 스레드(V)는 다른 API 정상 + AI 응답 대부분 60초 초과, 입장 제한(G)은 다른 API 정상 + 받아들인 AI 요청이 60초 안에 성공
- **모델**: 운영과 같은 `gpt-5.6-luna`다(1-4절). nano로 잰 첫 회차는 기각했다

## 1. 비교 대상

세 arm 모두 같은 코드(`dev`)에서 출발하고 측정 전용 브랜치 `test/ai-async-variant`에서 **JAR 하나**를 빌드한다. **운영 코드에 머지하지 않는다.** arm은 회차 스크립트가 SSM `env/`의 환경변수(`AI_COURSE_ASYNC_ENABLED`, `AI_COURSE_ADMISSION_MAXWORKUNITS`, `AI_COURSE_ADMISSION_MAXREQUESTS`)로 고른다 — 코드가 같으므로 차이가 정말 이 값들뿐임이 보장된다. E는 입장 제한 값을 100000으로 둬 사실상 끈다.

동기 arm(E·G)은 워커가 끝까지 실행한 뒤 완료된 future를 돌려준다. 응답 경로를 F와 맞추기 위해서이며 워커 점유는 운영과 같다.

| | E — 동기 · 제한 없음 | F — 비동기 · 제한 없음 | G — 동기 · 입장 제한 |
|---|---|---|---|
| AI 파이프라인을 쥐는 스레드 | Tomcat 워커 | **전용 풀 32 + 무제한 큐** | Tomcat 워커 |
| 입장 제한 | 끔 | 끔 | 켬(자리 16 · 요청 8) |

E → F는 **쥐는 스레드의 위치 하나만**, E → G는 **입장 제한 하나만** 다르다.

### 1-1. 세 arm에 공통으로 끄는 것 — 예산 하나로는 폴백이 꺼지지 않는다

코드를 따라가 보니 요청을 포기시키는 지점이 세 곳이었다. 예산만 끄면 나머지 둘이 여전히 폴백을 만들어, 지연 대신 품질 저하가 나온다.

| 지점 | 지금 | 실험 조건 | 그대로 두면 |
|---|---|---|---|
| 요청 예산 `ai.course.budget-ms` | 35초 | 1시간 | 35초에 폴백 |
| LLM 슬롯 대기 (`OpenAiLlmClient.acquirePermit`) | 20초에 포기 | 사실상 무제한 | 20초에 `LlmTransportException` → Planner 기본 플랜 · Curator day 비움(폴백) |
| `aiAgentExecutor` 넘침 | 큐 50 + `CallerRunsPolicy` | 무제한 큐 | E에서 워커가 LLM을 직접 실행. 원하는 전제가 아니다 |

**그대로 두는 것**
- LLM HTTP 시도당 20초 상한과 재시도 — 줄 때문이 아니라 실제 전송 실패에 대한 처리다. 그래서 폴백이 0이 되지는 않고, 드물게 남는 폴백은 `ai.curation.slot`으로 함께 기록한다
- 슬롯 5, `aiAgentExecutor` 스레드 20, 네이버 속도 제한 초당 25
- `placeGroundingExecutor`의 `CallerRunsPolicy` — 장소 API 경로까지 바꾸면 변수가 늘어난다. 스레드 덤프로 발동 여부를 함께 본다
- ALB idle timeout 60초 — FE OkHttp `readTimeout`도 60초라 **사용자가 실제로 겪는 상한**이다

### 1-2. F의 전용 풀 크기 — 32

풀 크기가 곧 동시 처리 수라, 값에 따라 다른 실험이 된다. 8로 작게 잡으면 큐가 입장 제한처럼 동작해 "F는 제한 없음"이 거짓이 된다. **E의 워커 수와 같은 32**로 둬야 E와 F의 동시 처리 수가 같고 스레드 위치만 달라진다.

무제한 큐는 "거절 없이 전부 받는다"는 전제 때문이다. 크기를 제한하고 넘칠 때 거절하면 그것이 입장 제한이다.

### 1-3. F에 필요한 구현

| 항목 | 내용 | 빠뜨리면 |
|---|---|---|
| 컨트롤러 반환형 | `CompletableFuture<AICourseCreateResponse>` | — |
| 비동기 타임아웃 | `spring.mvc.async.request-timeout` 1시간 | 기본 30초에 503. 실험 대상이 아닌 제한이 끼어든다 |
| `SecurityContext` 전파 | `DelegatingSecurityContextExecutor` | 전용 풀에서 `getCurrentUserId`가 사용자를 찾지 못한다 |
| ASYNC 디스패치 허용 | `dispatcherTypeMatchers(ASYNC).permitAll()` | Spring Security 6은 재디스패치도 인가 대상이고 `JwtAuthenticationFilter`(`OncePerRequestFilter`)는 재디스패치를 건너뛴다. **이 규칙을 뺀 대조 실행에서 재디스패치를 타는 테스트 3건이 모두 실패했다**(`AiCourseAsyncDispatchTest`, 실제 Tomcat 기동). 토큰 없는 요청은 규칙이 있어도 첫 디스패치에서 막혀 파이프라인을 부르지 않는다 |

입구 판정·인증·검증은 Tomcat 워커에서 끝낸다. 전용 풀에는 통과한 요청만 들어간다.

### 1-3-1. V — 전역 가상 스레드

`SPRING_THREADS_VIRTUAL_ENABLED=true`로 Tomcat이 요청마다 가상 스레드를 쓴다. 구조는 E와 같은 동기이고 입장 제한은 끈다. F와 같은 "스레드 위치만 바꾼다"의 다른 구현이지만 차이가 둘 있다.

- **동시 파이프라인 상한이 없다.** F는 전용 풀 32가 묶지만 V는 도착한 요청이 전부 파이프라인에 들어간다. 슬롯을 나눠 쓰는 요청이 늘어나 **먼저 온 요청도 뒤 요청 때문에 느려진다**
- **피닝 위험이 서버 전체에 있다.** Java 21이고 캐리어가 2개라 `-Djdk.tracePinnedThreads=short`로 건수와 위치를 함께 기록한다. 짧은 피닝은 있을 수 있으므로 배경 API 영향과 함께 읽는다

`aiAgentExecutor`와 `placeGroundingExecutor`는 플랫폼 스레드로 그대로 둔다(Spring Boot 설정은 직접 만든 풀을 바꾸지 않는다). V는 "AI 요청이 Tomcat을 묶지 않게 하는 효과"를 재는 조건이며, 운영 적용 시 필요한 다른 API의 자원별 제한은 만들지 않는다. 그래서 **V 결과로 전역 도입의 안전성까지 주장하지 않는다.**

### 1-4. 모델 — `gpt-5.6-luna`, nano 기각

처음에는 비용을 줄이려 `gpt-5-nano`로 r40-E1을 쟀다(2026-11-05, 결과 `results/ai-bulkhead/r40-E1.nano`). 배경 API 장애(1분 에러율 최대 40.75%, 워커 32/32)는 재현됐지만, 호출이 빨라 AI 요청 196건 중 147건이 60초 안에 201을 받았다. 슬롯이 운영보다 넉넉한 상황이라 운영 모델의 지연을 보여 주지 못하고 A·B·C·D와도 비교할 수 없어, **운영과 같은 luna로 처음부터 다시 잰다.** Planner는 기본 추론, Curator는 `low`로 운영 설정 그대로다.

## 2. 부하와 회차

주실험의 회차 절차(README 5·10절)를 그대로 쓴다 — t3.small 1대, ALB, 배경 API 초당 20건, 웜업 2분 → 기준선 2분 → AI 포아송 도착 5분 → 회복 3분, 3일 코스, TourAPI 생략, 매 회차 인스턴스 교체.

| 순서 | 회차 | 시드 | 목적 |
|---|---|---|---|
| 1 | r40-E1 | 197040 | 동기 + 제한 없음의 장애 |
| 2 | r40-F1 | 197040 | E와 같은 도착에서 비동기가 다른 API를 살리는가 |
| 3 | r40-V1 | 197040 | 같은 도착에서 가상 스레드가 다른 API를 살리는가 |
| 4 | r40-G1 | 197040 | 같은 도착에서 입장 제한의 효과 |

분당 70건(r70-F·V·G)은 이 네 회차의 결과를 본 뒤 정한다.

- E를 70에서 재지 않는 이유: 40에서 장애가 나면 70은 더 크게 무너진다는 것 외에 알려 주는 것이 없다(주실험 5-7과 같은 판단)
- 각 회차는 회복 관측이 끝나면 앱을 내린다(`STOP_APP_AFTER_ROUND=1`). 제한 없는 arm의 잔여 작업이 다음 교체까지 LLM·네이버를 쓰지 않게 하기 위해서다. 그래서 서버 소요는 **"관측 창 안에 끝난 요청" 기준의 하한**이고, 끝나지 못한 요청 수를 함께 적는다

## 3. 측정 전 예측

### 3-1. 계산

- **LLM 처리량**: 슬롯 5 ÷ 호출 약 6~7초 ≈ 분당 43~50회. 3일 코스는 요청당 4회라 **분당 약 11~12건**이 공급이다
- **밀림**: r40은 분당 약 28건씩 쌓여 동시 요청 32에 약 70초에 닿고, 5분 도착 후 약 143건이 남는다
- **응답 시간**: 60초 안에 끝나려면 앞선 요청이 약 11~12건 이하여야 하므로, 도착 **첫 약 25초**의 요청만 성공할 수 있다

### 3-2. 단계별 예측

| | E r40 | F r40 | V r40 | G r40 |
|---|---|---|---|---|
| 배경 API 판정 | **장애** | **정상** | **정상** | **정상** |
| Tomcat busy 최대 | 32/32 | 10 미만 | 의미 없음 | 12 미만 |
| ALB unhealthy | 1 | 0 | 0 | 0 |
| AI 201 | 약 15건 안팎 | **약 10~25건** | **F와 같거나 적음** | 약 45~55건 |
| AI 60초 초과 | 대부분 | **대부분** | **대부분** | 거의 없음 |
| AI 429 | 0 | 0 | 0 | 나머지 전부 |
| 처리 중 AI 요청 최대 | 32 | 32 | **약 140건 이상** | 8 이하 |
| 응답을 못 받았는데 저장된 코스 | 있음 | **많음** | **많음** | 거의 없음 |

- **G의 Tomcat 예측**: 요청 상한 8 + 429 처리 + 배경 몫. #200 r70 실측 최대 11을 근거로 잡았다
- **E의 서버 소요는 F와 직접 비교하지 않는다.** E의 `totalMs`는 워커가 요청을 잡은 뒤부터라 Tomcat 대기열 시간이 빠진다. nano r40-E1에서 서버 기준 60초 초과는 25건인데 클라이언트 기준은 49건이었다. 사용자 지연은 k6 기준으로 본다

**이 예측이 깨지는 경우**
- F나 V의 배경 API가 저하·장애면 "워커만 풀면 다른 API가 지켜진다"가 틀렸다는 뜻이다. CPU·GC·DB 커넥션·피닝 가운데 원인을 지표와 스레드 덤프로 가려 그대로 보고한다
- F의 201이 예측보다 크게 많으면 처리량 계산이 틀린 것이다

### 3-3. 추가 회차 H — 입장 제한 + 비동기

r40-E·F·V·G를 잰 뒤 추가했다(시드 197040). 입장 제한 단독(G)으로 충분해도 워커 8개를 AI 경로에서 떼는 이중 방어가 합리적이라는 판단을 조합 수치로 확인한다. 조건은 F에 입장 제한(자리 16 · 요청 8)을 켠 것이고, 예산·폴백을 끈 실험 조건과 풀 크기 32는 그대로다. 이 JAR은 입장 판정이 풀 안에서 일어나므로 **운영 구현의 검증이 아니라 G와 같은 조건의 비교값**이다.

**측정 전 예측**: 배경 API 정상, ALB unhealthy 0. Tomcat busy는 G의 7/32보다 낮다(F 3/32 수준). 처리량은 슬롯이 정하므로 AI 201은 G의 62건에서 ±15건 안이고 201 p95는 60초 미만, 응답 못 받은 저장 코스는 0에 가깝다.

**판정(K6)**: 배경 **저하·장애 없음**, `UnHealthyHostCount` 0, Tomcat busy 최대 < G, 201이 47~77건, 201 p95 < 60초.

### 3-4. 추가 회차 P — 입장 제한 + 비동기 운영 구현

H는 실험 조건의 비교값이라 운영 구현(`feat/ai-request-async-isolation`)을 따로 잰다. 시드 197040, 분당 40건, `gpt-5.6-luna`.

- **H와 다른 점**: 입장 판정이 Tomcat 워커에 있고, 전용 풀은 요청 상한과 같은 8개이며, 넘친 요청은 풀을 거치지 않는다. 예산 35초·슬롯 대기 20초·`aiAgentExecutor` 큐 50 + `CallerRunsPolicy`는 **운영 설정 그대로**다
- **비교 대상의 한계**: 같은 조건의 동기 회차(운영 G)는 재지 않았다. G·H는 예산을 끈 조건이라 직접 비교가 아니라 방향 확인으로 읽는다. 입장 제한 아래에서는 예산에 걸리는 요청이 드물어 차이는 작을 것으로 본다

**측정 전 예측**: 배경 API 정상, ALB unhealthy 0. Tomcat busy는 H와 비슷하게 낮다(5/32 미만). AI 201은 약 47~77건, 나머지는 즉시 429, 201 p95 35초 미만, 60초 타임아웃·5xx 0건. `executor_*{name="aiRequestExecutor"}` 활성 8 이하, 큐 최대 2 이하, 거절 없음.

**판정(K7)**: 배경 **저하·장애 없음**, `UnHealthyHostCount` 0, Tomcat busy 최대 < 5, 201이 47~77건, 응답 코드는 201·429뿐.

**상태**: 2026-11-05 측정은 네이버 일별 한도 소진으로 무효였고, 2026-11-06 재측정에서 **K7이 성립했다**([measurement.md 8-6·8-7](measurement.md)).

**남은 범위**: 이 회차는 배포 중 진행 요청 처리(#190)를 재지 않는다. 일반 API 고부하나 후속 단계 멈춤도 재지 않아, 비동기가 **평소 성능**을 개선한다는 근거가 아니다.

### 3-5. 추가 회차 r70-H — 부하가 늘어도 입장 제한이 유지되는가

r40-H에 이어 분당 70건(시드 197070, AI 요청 366건)으로 같은 H를 잰다(2026-11-06). 실험 조건(예산·폴백 끔)과 JAR(`app/b4f8749.jar`)은 r40-H와 같다. "비동기로 AI 지연은 해결되지 않는다"는 r40-F가 근거이고, 이 회차는 **높은 부하에서도 입장 제한이 받아들인 요청의 품질과 다른 API를 지키는가**만 본다. r70-F는 재지 않는다.

**측정 전 예측**: 배경 API 정상, ALB unhealthy 0, Tomcat busy 최대 5 미만. 입장 제한이 처리 능력만큼만 받으므로 AI 201은 r40-H(62건)와 비슷한 약 55~65건이고 나머지 약 300건은 즉시 429다(거절률 약 83%). 201 p95는 60초 미만, 60초 타임아웃·5xx 0건.

**판정(K8)**: 배경 **저하·장애 없음**, `UnHealthyHostCount` 0, Tomcat busy 최대 < 5, 201이 47~77건, 응답 코드는 201·429뿐.

### 3-6. 추가 회차 r70-V — 가상 스레드에 상한이 없으면 부하가 늘 때 무엇이 망가지는가

r40-V는 "가상 스레드도 다른 API는 지킨다"를 보였지만 처리 중 요청이 154건까지 쌓였다. 분당 70건(시드 197070, AI 요청 366건)으로 같은 V를 잰다(2026-11-08). 실험 조건(예산·폴백 끔, 슬롯 대기 1시간, `aiAgentExecutor` 무한 큐)과 JAR(`app/b4f8749.jar`)은 r40-V와 같다. **이 회차는 상한 없는 구조가 무엇을 대가로 치르는지를 본다.** 가상 스레드가 대체하는 것은 Tomcat 워커뿐이다. 파이프라인 안쪽(`aiAgentExecutor` 20, `placeGroundingExecutor`)은 그대로 플랫폼 풀이고, LLM 슬롯 5개가 여전히 병목이다.

**r40-V 자원 기준선**(측정 뒤 원자료에서 다시 뽑았다. 당시 집계기에는 없던 항목이다)

| | r40-V 최대 | 한도 |
|---|---|---|
| 처리 중 AI 요청 | 154 | 없음 |
| 힙 Old Gen | 113MB (요청 0일 때 약 80MB) | 768MB |
| GC 정지 | 합 1.3초, 1회 최대 32ms | – |
| DB 커넥션 활성 · 대기 | 3 · 0 | 10 |
| 프로세스 CPU 1분 평균 | 23% | – |
| 플랫폼 스레드 | 64 | – |
| LLM 슬롯 대기 1회 최대 | 70초 | – |

처리 중 요청 1건이 힙 Old Gen을 약 0.2MB 붙잡는다(154건에 약 33MB). 이 비율이면 Old Gen 768MB를 채우는 데 처리 중 요청 약 3,000건이 필요하다. **[정정]** 측정 뒤 회귀로 다시 재니 1건당 약 0.1MB, 직선 외삽으로 약 6,500건이다(measurement.md 8-9). 아래 예측과 판정은 측정 전 그대로 둔다.

**관측 연장**: 도착이 끝난 뒤에도 서버는 사용자가 떠난 요청을 계속 처리한다. 이번에는 앱을 바로 내리지 않고 **처리 중 요청이 0이 될 때까지 최대 60분** 지표를 계속 모은다(`DRAIN_WAIT_SEC=3600`, 0이 되면 일찍 끝냄). 이 동안 쓰는 LLM 호출·네이버 호출·저장된 코스가 "상한 없음"의 비용이다. 피닝 추적은 r40-V에서 적용 여부를 확인하지 못했으므로, 이번에는 기동 로그의 `Picked up JAVA_TOOL_OPTIONS`로 확인하고 없으면 회차를 멈춘다.

**측정 전 예측**

- **다른 API는 이번에도 정상이다.** 늘어나는 것은 슬롯을 기다리는 요청 수인데, 기다리는 요청은 가상 스레드와 큐 항목으로 싸게 쌓이고 CPU·DB를 쓰지 않는다
- 처리 중 요청은 k6 종료 시점에 약 250~320건이다. 도착 366건에서 분당 약 6건만 끝난다(r40-V의 Curator 완료 속도)
- 힙 Old Gen 최대는 약 140~200MB, DB 대기 0, 프로세스 CPU 1분 평균 50% 미만이다. **이 부하에서 자원 압박은 다른 API로 번지지 않는다**
- AI 201은 10건 이하이고, 나머지는 60초 클라이언트 타임아웃과 ALB 504다
- **망가지는 것은 보이지 않는 곳이다.** k6가 끝난 뒤 처리 중 요청이 0이 되기까지 30~60분이 걸리고, 그동안 LLM 호출 600회 이상과 네이버 호출 수천 회를 쓴다. 응답을 못 받았는데 저장된 코스가 250건 이상 생긴다. 사용자는 실패를 봤지만 나중에 "내 코스"에서 그 코스를 발견한다
- 피닝은 관측돼도 소수다. 판정에는 쓰지 않고 기록만 한다

**판정**

- **K9**: 배경 **저하·장애 없음**, `UnHealthyHostCount` 0, 힙 Old Gen 최대 < 384MB(한도의 절반), DB 커넥션 대기 최대 0
- **K10**: k6 종료 시 처리 중 요청 ≥ 200, 그 뒤 0이 되기까지 ≥ 30분(60분 안에 0이 안 돼도 성립), 응답을 못 받았는데 저장된 코스 ≥ 200

K9가 깨지면(다른 API 저하나 자원 압박) 이 부하에서 이미 번진다는 뜻이고, 예측이 틀린 것으로 기록한다.

**외부 사용량**: 366건이 끝까지 처리되면 네이버 지표 약 10,200건(r40-V 실측: 후보 수집 1건당 약 28건, HTTP 약 31회), 카카오 약 7,700건, LLM 요청당 약 0.003달러로 합계 약 1.3달러다. 네이버 작업 상한(지표 일 15,000건) 안이고, 이날은 이 회차만 잰다. 측정 전 AI 요청 1건으로 네이버 성공을 확인한다.

## 4. 관측

주실험의 관측(README 6절)에 둘을 더한다.

|---|---|---|
| 요청 전체 소요 | 앱 로그 `AI_REQUEST_LIFECYCLE queueMs serviceMs totalMs outcome` | k6는 60초에서 끊겨 그 뒤를 볼 수 없다. **서버가 실제로 언제 끝냈는지**는 이 로그만 안다. 기존 `ai.course.request.duration`은 큐 대기를 재지 않고 분포 상한도 35초다 |

## 6. 외부 한도와 비용

폴백을 껐기 때문에 받은 요청을 LLM까지 처리하지만, 슬롯이 호출 수를 묶고 관측 뒤 앱을 내린다. 요청당 사용량은 r40-B1 실측(3일 코스 46건)이다.

| | 요청당 | E | F | V | G | 합계 |
|---|---|---|---|---|---|---|
| 후보 수집까지 간 요청(상한) | – | 124 | 124 | 124 | 58 | **약 430** |
| LLM 호출 | 4회 | 400 | 400 | 400 | 230 | **약 1,430** |
| 네이버 | 25회 | 3,100 | 3,100 | 3,100 | 1,450 | **약 10,750** |
| 카카오 | 약 21회 (상한 45) | 2,600 | 2,600 | 2,600 | 1,200 | **약 9,000 (상한 19,350)** |

- **상한의 근거**: 분당 약 50회 × 도착·회복 8분 = 400회. 동시 32건에서 호출 수 N이면 약 `(N + 96) ÷ 4`건이 후보 수집까지 간다. V는 동시 상한이 없어 Planner가 더 많이 통과할 수 있으므로 표보다 네이버를 더 쓸 수 있다

### 네이버 일별 한도 — 문서와 실제가 다르다

[운영-관심사.md](../ai-course-create/design/운영-관심사.md)는 일 한도가 없다고 정정돼 있지만, #200 사고의 실제 응답은 `일별 사용량 한도가 초과하였습니다.`(429)였다. **일별 한도는 존재한다.** 정확한 값은 확인하지 못했다.

그날(10-08) 지표에서 합산되는 네이버 호출은 소진 시점까지 **약 2.05만 건**이다(운영 구성 회차 약 1.61만 + 로컬 약 0.44만, 누적 카운터는 서버 프로세스별 최댓값으로 셌다). 지표에 없는 점검 요청이 더 있었으므로, 예전 기록의 일 25,000건과 모순되지는 않는다. ~~보수적으로 일 20,000건을 작업 상한으로 본다.~~ **[정정] 지표 기준 일 15,000건을 작업 상한으로 본다.** 2026-11-05에 지표 합계 약 1.64만 건에서 소진됐다(measurement.md 8-6).

- 같은 날 nano r40-E1과 점검이 약 5,000건을 먼저 썼으므로 합계 약 15,750건으로 잡는다. ~~작업 상한 안이다~~ **[정정]** 이 판단은 정정 전 상한 20,000건 기준이었다. 정정된 15,000건 기준으로는 넘고, 실제로 이날 P 회차에서 한도가 소진됐다(measurement.md 8-6). 그 뒤 회차는 다른 날 정정된 상한으로 계획했다
- 측정 일에는 같은 키로 다른 측정을 하지 않는다
- 인프라는 첫날 밤에도 유지한다. 내렸다가 다시 올리는 시간과 시드 작업보다 싸다고 보며, #200 재측정 때도 같게 했다
- 집계기에 네이버 한도 소진 로그를 무효 조건으로 추가했다. 전에는 카카오만 검사해 사고 회차를 사람이 찾아야 했다

## 7. 한계

- 반사실 조건이다. 운영 코드는 예산·폴백·`CallerRunsPolicy`가 있는 상태 그대로이고, 측정 결과는 그 구성의 성능이 아니다
- nano r40-E1을 본 뒤 모델과 F의 판정 기준을 luna 예측으로 되돌렸다. 기준을 부하 결과에 맞춰 느슨하게 한 것이 아니라 설계 초안의 값으로 복귀한 것이고, 이 순서를 그대로 밝혀 둔다
- 회차당 1회다. 앞선 비교 실험과 같이 예측하는 차이가 시간대 변동으로 뒤집힐 크기가 아니라고 본다
- F는 파이프라인을 다시 짜지 않은 서블릿 비동기다. 블로킹 대기 스레드가 전용 풀로 옮겨갈 뿐이고, 논블로킹 재작성이나 202 + 폴링의 결과가 아니다
- V는 Java 21 기준이다. JDK 24 이후의 피닝 개선 효과는 재지 않는다
- G는 동기 구조에 입장 제한을 얹은 것이다. 처음 계획(E·F·V·G)에서는 비동기 + 입장 제한 조합을 재지 않기로 했다. 입장 제한이 있으면 AI가 쥐는 워커가 최대 8개로 묶여 Tomcat 쪽 차이가 작다고 봤기 때문이다. **[보강]** 이후 이 조합을 실험 조건으로 H(3-3절), 운영 구현으로 P(3-4절)에서 따로 쟀다
