# 비교 실험 C — 입장 제한 없이 AbortPolicy와 큐 축소로 장애를 격리하면

> 이슈 [#201](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/201). 주실험 설계는 [README.md](README.md), 결과는 [measurement.md](measurement.md)가 정본이다. 이 문서는 그 위에 얹는 추가 실험의 설계다.
>
> **결과(2026-10-08): 분당 40에서는 격리됐지만 AI 결과의 86%가 LLM 없이 채워졌고, 분당 70에서는 배경 API까지 장애가 나 2절의 격리 예측이 반증됐다.** 수치와 해석은 [measurement.md 7절](measurement.md#7-비교-실험-c--거절-정책만-바꾸면-격리되는가), 반증 원인은 아래 7절.

## 0. 요약

- 주실험에서 개선 전(A)의 서비스 전체 장애 원인이 `CallerRunsPolicy`(Tomcat 워커가 LLM 작업을 직접 실행)임을 확인했다. 그렇다면 **입장 제한 없이 거절 정책만 바꾸고 큐를 줄여도** 장애가 격리되는가
- 이론상으로는 된다. 결과를 기다리는 요청은 실행기 안에 자기 작업이 있어야 하므로, `AbortPolicy`에서는 기다리는 요청 수 ≤ 스레드 + 큐다. 이 합을 워커 수보다 작게 잡으면 워커 고갈이 막힌다
- 대가로 예상하는 것은 **파이프라인 중간 거절**이다. 실행기는 작업마다 따로 받을지 정하므로, Planner를 통과한 요청의 Curator가 새 요청의 Planner에 자리를 뺏겨 거절된다. 요청 하나가 일부 day만 LLM으로, 나머지는 후보 목록으로 채워진 채 200으로 나간다
- 이 실험은 그 두 가지(격리 성공, 중간 거절 발생)를 운영 인프라에서 실측해 입장 제한(B)과 나란히 놓는다

## 1. 비교 대상

| 버전 | 구성 | 출처 |
|---|---|---|
| A | 개선 전. 실행기 4/8/큐 50, `CallerRunsPolicy`, 입장 제한 없음 | 주실험 |
| B | 개선 후. 실행기 20/20/큐 50, `CallerRunsPolicy`, 입장 상한 4 | 주실험 |
| **C** | **B − 입장 제한 + `AbortPolicy` + 큐 4 + 제출 시점 거절 처리** | 이번 |

- **B에서 출발한다.** A와 B 사이에는 커밋이 96개 있다(실행기 크기, 예산, LLM 슬롯 등). C를 B 위에 만들면 **C ↔ B의 차이가 입장 제한(과 그것이 없을 때 필요한 넘침 처리) 하나**가 되어, 마지막 질문("입장 제한이 Abort보다 무엇을 더 주는가")에 깨끗하게 답한다. 대신 A ↔ C 비교에는 96개 커밋이 섞인다 — "CallerRuns를 없애면 장애가 사라진다"는 주실험의 메커니즘 분석(measurement.md 3·4절)으로 갈음한다
- **입장 제한은 설정으로 끈다**(`ai.course.admission.max-concurrent-requests` = 1000). 코드는 그대로 둔다
- C는 측정 전용 브랜치에서 JAR만 빌드한다. 운영 코드에는 머지하지 않는다

### 1-1. 큐 크기 — 4

`AbortPolicy`에서 AI 요청이 결과를 기다리며 쥐는 워커 수의 상한은 **스레드 + 큐**다. B의 스레드는 20(LLM 슬롯 5 × 4)이다.

| 큐 | 상한 | 배경 API 몫(워커 32 기준) |
|---|---|---|
| 50 (B 그대로) | 70 | 보장 없음 |
| 12 | 32 | 0 — 경계 |
| **4** | **24** | **8** |
| 0 | 20 | 12 |

- 배경 API는 초당 20건 × 수 ms라 워커를 1개 미만 쓴다. 8개면 충분하다
- 실행기 밖에서 요청 스레드가 직접 일하는 구간(검증·그라운딩 일부·저장)은 이 상한 밖이라 몇 개를 더 쓴다. 이 몫도 8 안에 들어간다고 본다
- 0(`SynchronousQueue`)이 아니라 4로 둔 이유: "큐를 없앴다"가 아니라 "줄였다"는 일반적인 대안을 재기 위해서다. 0이면 Planner가 끝나고 Curator 3개를 내는 순간의 짧은 경합에도 거절이 나 중간 거절이 과장된다

### 1-2. 제출 시점 거절의 처리

지금 코드는 `supplyAsync`가 제출 자리에서 던지는 `TaskRejectedException`을 다루지 않는다 — 그대로 두면 요청 전체가 500이 되고 이미 낸 day 작업은 좀비가 된다. Abort를 진지하게 적용했다면 넣었을 처리를 넣어, "제대로 적용해도 남는 문제"를 재도록 한다.

| 거절된 작업 | 처리 | 근거 |
|---|---|---|
| Planner | **결정론적 기본 플랜으로 폴백**(LLM 실패와 같은 경로) | 기존 "Planner가 실패해도 코스는 나온다"(7-3)와 같은 처리 — 사용자 결정 |
| Curator(day) | **그 day를 빈 자리로** → 후보 목록으로 채움(LLM 실패와 같은 경로) | 기존 day 실패 처리와 같다 — 사용자 결정 |

거절은 어댑터의 재시도 대상이 아니다. 실행기가 찬 상태에서 같은 실행기에 다시 내면 또 거절될 뿐이다.

## 2. 가설과 예측

| | 예측 (r40) | 예측 (r70) | 근거 |
|---|---|---|---|
| 배경 API | **정상** | **정상** | AI가 쥐는 워커 ≤ 24 + 실행기 밖 구간 |
| Tomcat busy | 24 근처에서 멈춤 | 24 근처에서 멈춤 | 위 상한 |
| CallerRuns | 0 | 0 | 정책이 없다 |
| AI 응답 | 대부분 201 | 대부분 201 | 거절이 폴백으로 흡수돼 실패로 드러나지 않는다 |
| **완전 폴백 코스**(Planner 거절 → 기본 플랜 + Curator 전부 거절) | 많다 | 더 많다 | 혼잡할수록 첫 작업부터 거절 |
| **부분 폴백 코스**(day 일부만 LLM) | **0보다 크다** | **0보다 크다** | 이 실험의 핵심 관측 |
| 받아들인 요청의 LLM 큐레이션 비율 | B보다 낮다 | B보다 낮다 | 처리 가능량을 넘겨 받는다 |

- **반증 조건**: 배경 API가 저하·장애면 "Abort + 큐 축소로 격리된다"는 이론이 틀렸다(실행기 밖 구간의 워커 사용이 예상보다 크다는 뜻). 부분 폴백이 0이면 중간 거절 문제는 이 부하에서는 실제로 드러나지 않는다 — 둘 다 그대로 보고한다
- 응답이 대부분 201이라는 것 자체가 관측 대상이다. C는 혼잡을 **에러가 아니라 품질 저하로** 흡수하므로, 에러율·지연만 보는 모니터링에는 아무것도 보이지 않는다

## 3. 관측

주실험의 관측(6절)을 그대로 쓰고 셋을 더한다.

| 추가 관측 | 방법 |
|---|---|
| 단계별 실행기 거절 수 | 카운터 `ai.agent.rejected{agent=planner\|curator}` |
| 요청별 day 구성 | 파이프라인 끝에서 한 줄 로그: 요청 일수, LLM이 고른 day 수, 폴백 day 수, Planner 폴백 여부 → 집계기가 앱 로그에서 읽어 완전/부분/정상 코스로 분류 |
| 칸 단위 폴백 | 기존 `ai.curation.slot`(누가 채웠나) 증가분 |

집계기(`aggregate-bulkhead.py`)는 위 로그가 있으면 코스 분류를 함께 출력한다. 판정 기준(8절)은 바꾸지 않는다 — 배경 API 판정은 A·B와 같은 기준이다.

## 4. 측정

| 회차 | 시드 | 비교 대상 |
|---|---|---|
| r40-C1 | 197040 | r40-A1(장애), r40-B1(정상) |

- 같은 시드라 A·B와 정확히 같은 도착 시각표를 받는다. 회차 절차(instance refresh, 캐시 삭제, 12분 k6)는 주실험과 같다
- 두 회차를 연달아 잰다. A·B 회차와 날이 달라 LLM 속도가 다를 수 있으므로, 회차마다 B와 같은 시간대 공변량(201 p50, Curator 호출 시간)을 함께 남긴다

## 5. 무효 조건

주실험 9-1을 그대로 쓴다. 단, C에서는 입장 제한이 없어 429가 나오지 않고, 거절이 폴백으로 흡수되므로 AI 응답은 201·504가 대부분이어야 한다. 500이 나오면 1-2의 거절 처리가 빠진 경로가 있다는 뜻이라 **도구 문제가 아니라 구현 결함**으로 보고 측정을 멈춘다.

## 7. 결과와 예측 대조

| 예측 (2절) | r40-C1 | r70-C1 |
|---|---|---|
| 배경 API 정상 | 성립 | **반증** — 장애(p99 10초, 에러율 99.2%) |
| Tomcat busy 24 근처에서 멈춤 | 성립(23) | **반증** — 32/32, 포화 257초 |
| CallerRuns 0 | 성립 | 성립 |
| 대부분 201 | 성립(194/196) | 성립(335/366, 나머지 504) |
| 완전 폴백 많다 | 성립(195건 중 134) | 성립(313건 중 257) |
| 부분 폴백 0보다 크다 | 성립(54) | 성립(52) |
| LLM 큐레이션 비율이 B보다 낮다 | 성립(14% vs 99%) | 성립(6% vs 100%) |

- **1-1절의 상한이 틀렸다.** "기다리는 요청 ≤ 스레드 + 큐"는 실행기 결과를 기다리는 순간의 요청만 센다. 실행기에서 거절된 요청도 폴백한 채 후보 수집·그라운딩을 계속하며 워커를 쥐고, 그 구간은 실행기 자리를 쓰지 않는다. 1-1절에서 "실행기 밖 구간도 8 안에 들어간다고 본다"고 한 가정이 r70에서 깨졌다 — 포화 시점 워커 32개 중 10~18개가 후보 수집 단계였다
- 동시 AI 요청 수는 도착률 × 처리 시간으로 정해지고, 처리 시간은 혼잡할수록 늘어난다(네이버 속도 제한 앞 대기). 실행기 크기로는 도착률을 제한할 수 없으므로 큐나 스레드를 더 줄여도 같은 부하에서 다시 깨진다
- 예상하지 못한 관측: **받아 준 작업도 예산 안에 끝나지 못했다**(미완료 day 130). 실행기 자리 24 > LLM 슬롯 5라 받아 준 작업이 슬롯 앞에서 기다리다 예산을 넘겼다. 입장 총량을 실행기가 아니라 LLM 처리량 기준으로 정해야 한다는 근거가 돼 #200을 고쳤다
