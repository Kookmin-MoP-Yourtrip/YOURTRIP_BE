# STEP-4. `NaverLocalClient` + `TourApiClient` + 후보 공급 순수 함수 — 실행 기록

> [ROADMAP.md](../ROADMAP.md) 4단계의 상세 기록. 설계 근거는 [지식 신호 층과 후보 공급](../design/지식-신호와-후보-공급.md)이
> 소유하고, 이 문서는 **구현하며 내린 결정과 실측**만 담는다.
>
> **동작 변화 없음.** 5단계(`CandidateRetrievalStage`)가 조립에만 집중할 수 있도록 부품을 먼저
> 만들어 검증해 둔다. 클라이언트 빈이 둘 늘지만 파이프라인은 아직 컨트롤러에 연결되지 않는다.
>
> **진행 상황: 4-10 · 4-2 · 4-1 · 4-3 · 4-4 완료.** 다음은 4-8(area 지오코딩).

## 실행 순서

로드맵의 항목 번호는 식별자이지 실행 순서가 아니다. 의존 관계로 재배열하면 이렇다.

```
[네이버 계열 — 키 확보됨]
  4-10 소급 집계  →  4-2 네이버 실호출 확정  →  4-1 NaverLocalClient
                                            →  4-3 스타일 modifier 사전
                                            →  4-4 네이버 category → SlotType
[카카오 — 키 확보됨]
  4-8 area 지오코딩 (KakaoLocalClient 결과 값 반환이 선행)
[TourAPI 계열 — 키 발급 대기]
  4-7 TourApiClient  →  4-9 cat3 → 스타일 태그
                     →  4-5 후보 dedupe·매칭 키
[마무리]
  4-6 단위 테스트 전량 + 스텁 테스트
```

**TourAPI 키(`TOUR_API_KEY`)가 아직 없다.** 개발계정은 자동승인이라 블로커는 아니지만, 발급 전까지
4-7·4-9·4-5에 착수할 수 없어 네이버·카카오 계열을 먼저 끝내도록 배치했다.

## 판정 1 — 4-10의 대상을 OpenAI에서 Gemini 아티팩트로 바꿔야 했다 ★

로드맵 4-10은 *"기존 OpenAI 재측정(`AI-HALLUCINATION-OPENAI.md`) 아티팩트를
유명/무인지 그룹으로 다시 집계한다"* 였다. **그 아티팩트가 존재하지 않았다.**
(그 문서 자체도 이후 산출물 미보존을 이유로 삭제됐다 — 남은 기록은 [STEP-2](STEP-2-llm-port.md)뿐이다.)

STEP-2가 산출물로 기록한 `results/*-openai-{model}-{mode}-relow-*`를 다음 범위에서 찾았고 전부 0건이었다.

| 찾은 곳 | 결과 |
|---|---|
| 113개 브랜치의 **전체 커밋 히스토리** (`git log --all -- 'results/*'`) | 0건 — `results/`가 `.gitignore` 대상이라 애초에 커밋될 수 없다 |
| 모든 ref의 트리에서 `relow`·`openai-`·`luna`·`nano` 이름 검색 | 0건 |
| 5개 worktree의 `results/` 디렉터리 실측 | 0건 (전부 Gemini 시절 파일) |
| `C:\YOURTRIP`·사용자 폴더·Temp 스크래치패드 파일시스템 검색 | 0건 |

남아 있는 `hallucination-baseline-*` 파일은 **전부 `20260811`·`20260812`** 다. OpenAI 재측정이 기록된
커밋은 `9d3737c` (2026-08-13)이므로 그 산출물이라면 `20260813-` 이후여야 한다. **측정을 수행한
워크트리가 삭제되며 함께 사라진 것으로 보인다.**

**대상을 Gemini 아티팩트로 바꿨다.** 4-10의 목적은 *"출발 가설을 코드 짜기 전에 확인하는 가장 싼
검증"* 이지 OpenAI 값의 확정이 아니다. 가설("무인지 지역일수록 파라메트릭이 약하다")은 모델과 무관한
**파라메트릭 지식이라는 소스의 성질**에 대한 주장이므로 before 데이터로도 검증이 성립하고, 실제로
OpenAI 쪽에 문서로 남은 요약값(FAMOUS 5.1% / MINOR 7.8%)도 같은 방향을 보인다.

**집계 결과는 [AI-HALLUCINATION-GEMINI.md](../hallucination/AI-HALLUCINATION-GEMINI.md)의 "지역 티어별 소급 집계"
절에 있다.** 요지만 옮기면:

- **가설 성립** — 당시 복합 환각률 FAMOUS **13.9%** vs MINOR **35.4%** (2.5배). z = 3.74, p ≈ 0.0002,
  95% CI 비중첩, 요청 단위 평균으로도 동일
  (이후 지표 재정립·재채점에서도 방향은 유지된다 — 현행 지어냄률 FAMOUS 4.4% vs MINOR 15.0%, 3.4배)
- 전체값(자동 프록시 19.8% · 세탁 5.71%)이 기존 문서 기록과 소수점까지 재현돼 집계 경로가 검증됐다
- **파싱 실패는 티어와 반대 방향**(FAMOUS 26.7% vs MINOR 6.7%) — 실패가 전부 절단이므로 "할 말이
  많은 지역일수록 잘린다"로 읽힌다. **환각과 파싱 실패의 원인 축이 다르다**
- **티어 안의 분산이 티어 간 격차만큼 크다**(삼척 6.7% ~ 통영 40.4%). "무인지"는 단일 변수가 아니며,
  통영 값은 `NO_RESULT`가 아니라 `S1_4`(띄어쓰기 거짓 음성 밴드)가 만든 것이라 성격도 다르다

**이 사고에서 얻은 운영 교훈 하나를 남긴다.** STEP-2는 *"산출물이 다른 워크트리에만 남아 몇 달 뒤에야
재분석된 전례"* 를 경고하며 판정 40건을 문서로 옮겼는데, **그 대비 덕분에 OpenAI 측정의 결론은
살아남았고 재집계가 불가능해진 것은 원본 분해뿐이다.** 이번 소급 집계도 같은 이유로 표를 전부
문서에 적었다 — `results/`는 언제든 사라질 수 있는 저장소로 취급한다.

## 판정 2 — 네이버 지역검색의 경로가 문서와 다르다: `/v1/search/local.json` → `/search/v1/local` ★

**첫 실호출은 23건 전량 404였다.** `.env.example`과 설계 문서가 적어 둔 경로
`https://naverapihub.apigw.ntruss.com/v1/search/local.json`이 존재하지 않는다.

진단이 한 번 헛돌았다 — 처음에는 "게이트웨이 호스트가 살아 있으니 경로만 틀렸다"고 봤는데,
**존재하지 않는 호스트(`no-such-gateway-xyz.apigw.ntruss.com`)도 똑같은 404 본문을 돌려준다.**
`*.apigw.ntruss.com`이 와일드카드 catch-all이라 **404는 호스트·경로 어느 쪽이 틀렸는지 구분해 주지
않는다.** 이 사실을 확인하고 나서야 후보 조합을 넓게 훑는 쪽으로 방향을 바꿨다.

| 시도 | 결과 |
|---|---|
| `naverapihub` + `/v1/search/local.json`·`/search/local.json`·`/api/v1/...` 등 6종 | 전부 404 |
| `naveropenapi.apigw.ntruss.com` (구 NCP 게이트웨이) | 404 |
| **레거시 `openapi.naver.com/v1/search/local.json` + 레거시 헤더** | **401** — 경로는 살아 있고 인증만 실패 |
| 레거시 경로 + NCP 헤더 | 401 `Not Exist Client ID` |
| **`naverapihub` + `/search/v1/local`** | **200** ✅ |

**이관되며 확장자가 사라지고 세그먼트 순서가 뒤집혔다**(`/v1/search/local.json` → `/search/v1/local`).
레거시 401은 이 키가 developers.naver.com 자격이 아님을 뜻하므로 **되돌아갈 길도 없다.**

**교훈: `.env.example`의 엔드포인트는 0-2에서 키를 발급받을 때 문서를 보고 적은 값이고 실호출로
검증된 적이 없었다.** 로드맵이 4-2를 4-1보다 앞에 둔 이유가 정확히 이것인데, 실제로 걸린 것은
설계가 예상한 두 항목(`mapx` 정밀도·서술어 매칭)이 아니라 **경로 그 자체**였다.

> **부수 확인** — `/search/v1/news`·`/search/v1/blog`는 401 `요청한 API는 이 Application에서
> 활성화되어 있지 않습니다`를 준다. 키는 유효하고 **지역검색만 활성화**돼 있다. V1의 네이버 의존은
> 지역검색 하나뿐이라 문제가 없지만, **9단계에서 블로그를 켜려면 콘솔에서 활성화가 먼저다.**

## 판정 3 — 설계가 "확정 필요"로 남긴 응답 형식은 대체로 맞았고, 셋이 어긋났다

경로를 찾은 뒤 얻은 실응답으로 설계의 가정을 대조했다.

| 설계 가정 | 실측 | |
|---|---|---|
| `mapx`/`mapy`는 WGS84 × 10⁷ 정수 문자열 | `mapx="1292092884"` → 129.2092884(경도), `mapy="358363900"` → 35.8363900(위도) | ✅ |
| `title`에 `<b>` 태그가 섞인다 | `두낫디스터브 <b>경주</b>본점` | ✅ |
| `description`·`telephone`은 대부분 빈 값 | 전 항목 빈 문자열 | ✅ |
| 항목에 고유 ID가 없고 네이버 플레이스 URL도 없다 | `link`는 업소 자체 URL(인스타그램 등)이거나 빈 값 | ✅ |
| `display`는 5가 하드 실링 | 10을 요청해도 5건 | ✅ |
| `sort=comment`가 유효 | `random`과 다른 목록을 준다 | ✅ |
| **`start`가 1로 고정이라 6위 이하를 못 받는다** | **거부가 아니라 무시** — `start=2·6·11·16` 전부 응답 `start:1`에 **동일한 5건** | ⚠️ |
| **`category`는 `대분류>중분류` 계층** | **계층이 없을 수 있다** — `음식점>카페,디저트`·`카페,디저트>베이커리`와 나란히 **`브런치카페`** 단일 토큰 | ⚠️ |
| (설계에 없던 항목) `total` | **전체 매칭 수가 아니라 반환 건수다** — 항상 `display`와 같다(5→5, 3→3, 1→1) | ⚠️ |

어긋난 셋이 각각 다음을 바꾼다.

1. **`start` 무시** — 결론("풀을 넓히는 유일한 축은 쿼리 변주")은 그대로지만 **근거가 '거부'에서
   '무시'로 바뀐다.** 에러가 아니라 같은 5건을 조용히 다시 주므로, 5-8이 페이징으로 풀을 넓히려
   시도하면 **중복을 후보로 세는 조용한 버그**가 된다. 4-1의 클라이언트는 `start`를 파라미터로
   노출하지 않는다.
2. **`category` 계층 없음** — 4-4의 매핑을 "최상위 분류만 본다"로 짜면 `브런치카페`가 매핑 실패로
   빠진다. **구분자가 없으면 문자열 전체를 분류명으로 보는 폴백**이 필요하다.
3. **`total`의 의미 변화** — 9-2의 인기도 `log10(total)`은 **지역검색으로는 만들 수 없다.** 3층을
   켜려면 블로그 API의 `total`이 반드시 필요하다(그 API는 현재 미활성화 — 판정 2).

**`mapx`/`mapy`는 자릿수가 다르다**(경도 10자리 / 위도 9자리)는 것도 적어둔다 — 문자열 길이로
소수점을 끼워 넣으면 위도가 10배로 튄다. 정수로 읽어 `1e7`로 나눈다. 정밀도는 소수점 7자리(≈1cm)라
5-10의 300m 임계값에는 충분하고도 남는다.

## 판정 4 — 서술어 매칭이 작동한다: 스타일 modifier를 설계대로 채택한다 ★

**이것이 4-2에서 설계를 가르는 항목이었다.** 네이버가 `"조용한"` 같은 서술어를 상호명·카테고리에서만
찾는다면 스타일 쿼리는 빈 결과를 주고, 스타일 축을 retrieval에서 포기한 뒤 9단계 4층을 켜는 것이
유일한 길이 된다(설계의 "확정 전 실측이 필요한 지점").

기본 쿼리와 스타일 쿼리의 상위 5건을 비교했다.

| 기본 쿼리 | 스타일 쿼리 | 기본 | 스타일 | 겹침 | **신규** |
|---|---|---|---|---|---|
| 경주 황리단길 카페 | 경주 황리단길 **루프탑** 카페 | 5 | 5 | 2 | **3** |
| 경주 황리단길 카페 | 경주 황리단길 **조용한** 카페 | 5 | 5 | 2 | **3** |
| 강릉 안목해변 카페 | 강릉 안목해변 **야경** 카페 | 5 | 1 | 1 | 0 |
| 공주 맛집 | 공주 **주차** 맛집 | 5 | 4 | 0 | **4** |

**서술어가 결과를 실제로 바꾼다.** 상호명에 `루프탑`·`조용한`이 들어가지 않은 가게들이 새로 올라오므로
매칭 범위가 상호명 밖(리뷰·태그 등)까지 닿는다는 뜻이다. **설계대로 modifier 쿼리를 채택하고, 9단계
착수 조건 중 "네이버가 서술어를 매칭하지 못해 스타일 축을 포기했다"는 항목은 켜지지 않는다.**

`강릉 안목해변 야경 카페`가 1건으로 좁아진 것은 설계가 예상한 **"modifier가 결과를 좁히는 방향"** 의
사례다. 합집합이라 풀이 줄지는 않으므로 fail-open 그대로 두면 된다.

> **남는 한계는 그대로다.** 이 실측이 보인 것은 "서술어가 결과를 바꾼다"이지 "바뀐 결과가 실제로 그
> 속성을 갖는다"가 아니다. SEO 편승 여부는 설계가 말한 대로 8-7 삭제 로그로만 확인된다.

## 판정 5 — 무인지 지역에서 시더가 실제로 후보를 준다 (4-10의 공백을 메운다)

4-10이 확인한 것은 **파라메트릭이 무인지 지역에서 약하다**(당시 복합 환각률 MINOR 35.4%, 현행 지어냄률 15.0%)는 사실이고,
시더를 두는 이유가 그 공백을 메우는 것이다. 그렇다면 **시더 자신이 그 지역에서 비지 않아야** 한다.

| 지역 | MEAL | CAFE | ATTRACTION |
|---|---|---|---|
| 삼척 | 5건 (삼척보스대게 본점) | 5건 (보사노바 커피로스터스 삼척점) | 5건 (환선굴) |
| 공주 | 5건 (정안알밤(하)휴게소) | 5건 (베이커리 밤마을) | 5건 (마곡사) |
| 영주 | 5건 (나드리) | 5건 (태극당) | 5건 (부석사) |

**빈 결과 0/9.** 상위 결과도 그럴듯하다 — 환선굴·마곡사·부석사는 그 지역의 대표 관광지다. 설계가
*"`"{area} 카페"`가 0건인 지역은 카페가 실제로 없는 곳"* 이라며 카카오 커버리지를 뺀 근거가 이 표본에서는
성립한다. **5-9의 "0건일 때만 카카오" 폴백은 지금 붙일 이유가 없다.**

지연은 9회 평균 **109ms**, 최대 134ms, 단건 57ms였다. **카카오와 같은 응답 제한 3초면 여유가 크다** —
4-1은 카카오 설정값을 그대로 복제한다.

## 판정 6 — `NaverLocalClient`가 노출하지 않기로 한 것들

4-1 구현에서 내린 결정은 대부분 **"무엇을 넣을까"가 아니라 "무엇을 막을까"** 였다. 4-2 실측이
드러낸 함정이 전부 *조용히* 틀리는 종류였기 때문이다.

| 막은 것 | 열어두면 생기는 일 |
|---|---|
| `start` 파라미터를 아예 만들지 않음 | 무시되는 파라미터라 페이징을 시도하면 **에러 없이 같은 5건**이 온다. 5-8이 그걸 새 후보로 세면 풀이 부풀고 dedupe가 뒤늦게 지운다 |
| `sort`를 인자가 아니라 상수로 고정 | 호출부가 `accuracy`로 바꾸면 "인기 축 시더"라는 계약이 조용히 깨진다. 이 클라이언트의 존재 이유가 `sort=comment`다 |
| `display`를 5로 clamp | 상한을 모르는 호출부가 20을 넣으면 5건을 받고도 20건을 기대한다 |
| 빈 쿼리에서 호출 자체를 생략 | 일 25,000건 한도를 의미 없는 호출로 깎는다 |

**예외를 던지지 않는 것**도 같은 계열의 결정이다. `NaverLocalResult`를 sealed interface로 두고
`Found`/`Empty`/`Failed`로 갈랐는데, **핵심은 `Empty`와 `Failed`를 가르는 것**이다. 설계가 카카오
커버리지를 후보 소스에서 뺀 근거가 *"`{area} 카페`가 0건인 지역은 카페가 실제로 없는 곳"* 인데,
이 판단은 "0건"과 "못 물어봄"이 구분될 때만 성립한다. 뭉치면 네이버 장애 시간 동안 전국에 카페가
없는 것처럼 보인다 — 5-6이 `no_result`와 `failed`를 반드시 갈라야 한다고 못박은 것과 같은 이유다.

`Failed`의 `Cause`도 처음부터 다섯으로 갈랐다. 특히 **`QUOTA_EXCEEDED`(429)만 성격이 다르다** —
재시도로 풀리지 않고 다음 날을 기다려야 하는 실패다. 하루 약 830~1,400코스에서 켜지는 분기라
(ROADMAP 0-5) 다른 실패와 뭉치면 "장애인가 한도인가"를 로그로 되짚어야 한다.

**좌표 변환은 클라이언트 밖(`NaverPlaceMapper`)에 뒀다.** 여기가 실제로 틀리기 쉬운 곳이고, 떼어내야
외부 호출 없이 테스트할 수 있다 — 3-2에서 `GeoUtils`를 route 타입과 분리한 것과 같은 취급이다.
그 안에서 지킨 규칙 하나: **`mapx`/`mapy`는 자릿수가 다르므로**(경도 10자리 · 위도 9자리) 문자열
길이로 소수점을 끼워 넣으면 위도가 10배로 튄다. 정수로 읽어 `1e7`로 나눈다.

**좌표 파싱 실패는 예외가 아니라 `null`이다.** 1-1이 `Place`의 좌표를 `double`에서 `Double`로 올린
것과 같은 판단이다 — 좌표가 없는 것을 `0.0/0.0`으로 위장하면 아프리카 앞바다에 장소가 생긴다.
좌표 없는 후보는 거리 정렬·dedupe에서만 빠지고 후보로는 살아남는다.

**키가 비어도 기동한다**(`${NAVER_CLIENT_ID:}`). 후보 공급이 fail-open이므로 키 부재가 기동 실패가
되면 안 된다 — `llm.openai.api-key`가 세운 관례다. 이 주장을 문서가 아니라 테스트로 고정했다
(빈 키로 조립해 호출하면 예외가 아니라 `Failed(UNAUTHORIZED)`가 온다).

## 판정 7 — 설계 문서 안의 어휘 불일치를 합집합 enum으로 해소했다

설계는 4-3(키워드→traits 사전)과 4-9(`cat3`→스타일 태그)가 **같은 traits 어휘**를 쓴다고 못박았다.
두 표를 실제로 대조하니 어긋나 있었다 — 4층 traits **26개**에 4-9가 쓰는 `자연`·`역사`·`문화`·
`액티비티`·`실내`가 없다.

**`StyleTag` 하나에 합집합 31개를 담았다.** 어휘를 둘로 나누면 9단계 4층을 켤 때 매핑 테이블을 두 벌
유지해야 하고, "스타일 쿼리가 주장으로 끌어온 후보를 같은 어휘로 사실 검증한다"는 설계의 대칭이
성립하지 않는다.

**`KeywordType` 20개 중 매핑을 채운 것은 13개다.** 설계 표의 10개 + 확장 3개(`NATURE`·`CULTURE`·
`ACTIVITY`)이고, 나머지 7개는 **비운 것이 결정이다.**

| 비운 키워드 | 근거 |
|---|---|
| `duration` 4종 | 스타일 축이 아니다. 처리 방침은 6-5가 따로 정한다 |
| `NORMAL`(평균예산) | `"경주 보통 카페"`는 검색어로 무의미하다 |
| `FOOD`·`SHOPPING` | **이미 슬롯 구성으로 표현된다** — Planner가 MEAL·SHOPPING 슬롯을 늘리는 축이지 수식어가 아니다. `"맛집 카페"` 같은 쿼리는 쿼터만 쓰고 결과를 흐린다 |

**태그 이름과 검색어를 필드로 나눴다.** `QUIET`의 라벨은 "조용함"이지만 쿼리에는 `"조용한"`이,
`PARKING_AVAILABLE`은 `"주차"`가 들어가야 한다(4-2에서 `"공주 주차 맛집"`이 신규 4/4를 줬다).
**감점 전용 태그(`주차난`·`웨이팅`)와 검색어로 무의미한 태그(`보통`)는 `searchTerm`을 비웠다** —
사전이 구조적으로 그것을 고르지 못한다.

> **검색어 표기 대부분은 아직 실측되지 않았다.** 4-2가 확인한 것은 `루프탑`·`조용한`·`야경`·`주차`
> 넷뿐이다. 나머지가 유의미한 결과를 주는지는 5-9에서 확인하고 그때 표기를 조정한다.

## 판정 8 — 동점 처리에 enum 선언 순서를 쓰면 설계 표를 배신한다 ★

설계는 "가점 태그 **상위 1~2개**"라고만 적어 두었는데, 사용자가 `COUPLE + HEALING`을 함께 고르면
후보가 8개가 되므로 "상위"의 정의가 필요하다. 세 단계로 정했다.

1. **피하고 싶다고 표시한 태그를 먼저 걷어낸다.** 어떤 키워드의 감점 태그가 다른 키워드의 가점
   태그일 수 있는데(`FRIENDS`는 `시끌벅적`을 원하고 `COUPLE`은 피한다), 이때는 **피하는 쪽을
   존중한다** — 원하지 않는 곳으로 데려가는 실수가 그저 그런 곳으로 데려가는 실수보다 나쁘다
2. **중복 등장을 우선한다.** 취향이 겹치는 지점이라 신호가 강하다
3. 동점이면 **설계 표 안에서의 순위**로 깬다

**3번을 처음에는 enum 선언 순서로 짰고, 테스트가 그것을 잡았다.** `StyleTag`는 범주별(뷰·접근성·
가격…)로 묶여 있어 **어느 키워드의 선호 순서와도 일치하지 않는다.** 실제로 `COUPLE`은 설계 표에서
야경 → **루프탑**인데 선언 순서로는 야경 → **뷰맛집**이 나왔다.

```
설계 표 COUPLE : 야경  루프탑  통창  조용함  뷰맛집
enum 선언 순서 : 야경  뷰맛집  루프탑  통창   …      ← 범주로 묶인 순서라 표와 무관
```

**태그가 등장한 가장 앞 위치(`bestRank`)를 2차 기준으로 두어 고쳤다.** enum 순서는 그래도 같을 때의
최종 확정에만 쓴다 — 결정론은 유지하되 순위의 근거는 설계 표가 갖는다.

이 결함은 **"설계 표 그대로 옮겼다"고 믿기 쉬운 종류**였다. 매핑 데이터는 정확히 옮겼는데 그것을
읽는 순서가 다른 자료구조의 순서를 따라가 버렸고, 단일 키워드 테스트가 없었다면 통과했을 것이다.

## 판정 9 — "최상위 분류를 매핑한다"는 설계 규칙은 실제 응답과 맞지 않는다 ★

설계는 네이버 `category`의 **최상위 분류**를 `SlotType`으로 매핑하라고 적었다
(`카페,디저트` → CAFE, `음식점` → MEAL). 4-2가 받아온 실제 값이 그 규칙을 반증한다.

```
음식점>카페,디저트      ← 카페인데 최상위는 "음식점"이다   (실측 3건)
카페,디저트>베이커리
브런치카페              ← 구분자가 아예 없다
```

**최상위만 보면 카페가 MEAL로 판정되고**, 5-3의 하드 제약에서 CAFE 슬롯의 정당한 후보가 탈락한다.
설계가 막으려던 것("점심 슬롯에 호프집")과 정반대로, **막지 말아야 할 것을 막는** 실수가 된다.

**규칙을 뒤집어 가장 구체적인 세그먼트부터 훑고 먼저 맞는 것을 택한다.** `음식점>한식>국밥`처럼
뒤쪽이 매핑에 없으면 자연히 앞쪽(`음식점` → MEAL)으로 떨어지므로 **설계가 의도한 동작은 그대로
보존된다** — 규칙을 바꿨지만 잃은 것은 없다.

### 판정을 동등 비교로 하지 않는다

`isCompatibleWith`가 `SlotType` 동등 비교였다면 **전망대·산책로 슬롯의 후보가 전부 탈락한다.**
네이버 분류는 `ATTRACTION`·`VIEWPOINT`·`STROLL`을 구분하지 않고 셋 다 `관광,명소` 아래로 넣기
때문이다. 그래서 네이버 분류가 **실제로 가를 수 있는 단위**(MEAL / CAFE / SIGHT / EXPERIENCE /
SHOPPING)로 묶어 비교한다 — `SlotType.allowedCategoryCodes`가 셋에 `AT4`를 공유시켜 둔 것과 같은 구조다.

### 술집 계열은 매핑이 아니라 표시로 다룬다

설계는 *"MEAL 슬롯 ← FD6 필수. 단 `category_name`이 '술집' 계열이면 감점(점심에 호프집 방지)"* 을
요구한다. **MEAL 매핑 자체는 맞다** — 저녁 슬롯에는 정당한 후보다. 그래서 `isBarLike()`로 판정
재료만 제공하고, 시간대에 따른 감점은 슬롯 배치를 아는 5-3이 한다. **이 클래스는 정책을 갖지 않는다.**

## 판정 10 — 부분 문자열 매칭에서 한 글자 토큰이 무관한 분류를 삼켰다

`찻집`을 잡으려고 토큰에 `차`를 넣었더니 **`교통>주차장`이 CAFE로 판정됐다.** 세차장·기차역도 같은
경로로 걸린다. 테스트가 아니었다면 "카페 슬롯에 주차장이 배치되는" 형태로 뒤늦게 드러났을 결함이다.

**한 글자 토큰을 금지하고** 의도한 뜻은 `찻집`처럼 두 글자 이상으로 적는 것으로 규칙을 세웠다.
회귀 케이스(`주차장`·`세차장`·`기차역`·`자차렌트`)를 테스트에 고정해 두었다.

> 판정 8과 성격이 같다 — **매핑 데이터는 맞는데 그것을 읽는 방식이 틀린** 종류이고, 둘 다 단위
> 테스트가 없었으면 조용히 통과했을 것이다. 이 단계의 순수 함수들이 "결정론이라 테스트가 완전하다"는
> 것은 곧 **이런 결함이 전부 잡힌다는 뜻**이기도 하다.

## 판정 11 — 스텁이 실제와 다른 Content-Type을 쓰는 동안 클라이언트는 전 호출 실패였다 ★★

4-3의 검색어를 실측하려고 프로브를 돌렸더니 **26개 전부 0건**이었다. 원인은 네이버가 아니라
**우리 클라이언트**였다.

```
네이버 지역검색 실패(HTTP_ERROR): query=경주 카페, status=200 OK, body=
```

`200 OK`인데 실패로 분류된다. 응답 헤더를 직접 떠보니 답이 나왔다.

```
content-type: text/plain;charset=UTF-8      ← JSON을 text/plain 으로 내려준다
```

Spring의 기본 Jackson 디코더는 `application/json`만 받으므로 **역직렬화가 거부되고 모든 호출이
실패로 떨어진다.** `NaverConfig`의 디코더에 `text/plain`을 등록해 해소했다.

### 왜 4-1의 테스트 12개는 이걸 못 잡았나

**WireMock 스텁이 `application/json`을 썼기 때문이다.** 스텁 본문은 4-2 실응답에서 그대로 가져왔지만
**헤더는 내가 관례대로 적었고**, 그 한 줄의 차이가 "테스트는 전부 통과하는데 실 API에서는 100%
실패하는" 상태를 만들었다.

> **스텁이 실제와 다르면 그 차이만큼 테스트가 거짓말을 한다.** 그리고 거짓말하는 지점은 대개
> 본문처럼 눈에 띄는 곳이 아니라 **헤더·상태코드처럼 "당연히 이렇겠지" 하고 적은 곳**이다.

스텁을 `text/plain`으로 바꾸고, `application/json`으로 와도 읽히는지도 함께 단언했다(네이버가
헤더를 표준으로 고칠 수 있다).

### 이 결함이 드러난 경위도 남겨둔다

4-1을 끝내고 4-3·4-4까지 진행한 뒤, **"스타일 modifier 검색어가 실제로 결과를 주는지 확인했나"** 라는
질문에서 시작해 프로브를 돌리다 발각됐다. 4-2 프로브는 `bodyToMono(String.class)`로 원문을 받아
직접 파싱했기 때문에 `text/plain`에 영향을 받지 않았다 — **실호출 검증을 했는데도 그 경로가 프로덕션
클라이언트와 달라 결함을 통과시킨 것**이다. 프로브가 프로덕션 조립을 그대로 쓰도록 이번에 바꿨다.

## 판정 12 — 스타일 검색어 26개를 전량 실측했다 (4-3 보강)

4-2는 서술어 매칭이 "작동한다"는 것만 표본 4개로 확인했는데, 4-3에서 검색 가능한 태그를 26개로
늘리며 **나머지 22개는 표기가 추측**이 됐다. 각 태그를 겨냥하는 슬롯으로 던져 셋을 쟀다 — 결과 건수,
기본 쿼리 대비 **신규** 후보 수, 그리고 **상호명 포함률**(총 44회 호출).

**22개는 그대로 쓴다.** 야경 5/5 · 뷰맛집 5/5 · 레트로 5/5 · 역세권 5/5 · 주차 5/5 · 단체 5/5 ·
자연 5/5 · 역사 5/5 · 체험 5/5 처럼 신규를 온전히 끌어온 것이 다수다.

**4개는 죽은 표기라 조정하거나 비웠다.**

| 태그 | 원래 표기 | 결과 | 조치 |
|---|---|---|---|
| `WALKABLE` | `도보` | 0건 (`도보5분`도 0건) | **`역근처`** 로 교체 — 신규 5/5 |
| `UNCROWDED` | `한적한` | 0건 | **`한적`** 으로 교체 — 1건, 표본이 얇다 |
| `PANORAMIC_WINDOW` | `통창` | 0건 (`통유리`·`창가`도 0건) | **비웠다** |
| `LIVELY` | `시끌벅적한` | 0건 (`번화가` 0건, `핫플`은 신규 0) | **비웠다** |

**상호명 포함률이 거의 0이었다는 것이 이 측정에서 가장 중요하다.** 신규 후보의 상호명에 검색어가
들어 있지 않다는 뜻이므로, 네이버가 이름이 아니라 **속성**을 매칭한다는 근거가 된다 — 스타일 축을
retrieval에 두는 설계의 전제가 여기서 확인됐다(4-2는 "결과가 달라진다"까지만 보였다).

**남는 한계 — 표기의 유효성이 슬롯에 따라 다르다.** `뷰맛집`은 카페에서 신규 5/5인데 관광명소에서는
0건이다. 지금은 태그마다 표기 하나만 두므로 그런 조합은 빈 결과로 fail-open 된다(합집합이라 풀이
줄지는 않는다). 슬롯별 표기가 필요한지는 5-9에서 판단한다.

### 3차 — "1건짜리 통과"를 걸러내고, 결과가 나와도 뜻이 다르면 버렸다 ★

2차까지의 판정 기준(`결과 0건 또는 신규 0건`이면 실패)이 **느슨했다.** `한적`은 1건, `한적한`은
0건이었는데 **1 대 0 차이로** 채택됐다. 5건 중 1건이면 사실상 죽은 표기이고, 슬롯당 후보 8~15건을
목표로 하는 설계에서 1건 추가는 쿼리 한 번의 쿼터값을 못 한다.

경주 한 곳에서만 잰 것도 문제였다 — **표기가 나쁜 것과 그 지역에 그런 곳이 적은 것을 구분할 수
없다.** 얇은 표기 3개를 **경주·강릉·부산 3곳 × 표기 변주**로 다시 재고, 기준을 **지역당 평균 신규
2건 이상**으로 올렸다(78회 호출).

| 태그 | 표기별 3개 지역 신규 합계 | 결정 |
|---|---|---|
| `UNCROWDED` | 한적 1 · **한적함 0** · 한적한 1 · 조용한골목 0 · **숨은 6** | `숨은` 채택 |
| `COZY` | 아늑한 1 · 아늑 0 · 아늑함 0 · ~~소품샵 12~~ | **비웠다** |
| `EXPENSIVE` | 고급 7 · 고급스러운 10 · 파인다이닝 13 · **프리미엄 15** | `프리미엄` 채택 |

**`COZY`가 이 측정에서 가장 중요한 판단이다.** `소품샵`은 3개 지역에서 12건을 끌어와 수치로는 가장
좋은 후보였지만 **"아늑함"과 뜻이 다르다.** 채택했다면 사용자가 `SOLO`(혼자)를 골랐을 때 소품샵이
후보로 들어오고, 태그가 가리키는 속성과 실제로 끌어온 후보가 어긋난다. **검색 결과가 나온다는 것과
그 표기가 옳다는 것은 다른 문제다** — 설계가 경계한 "스타일 쿼리는 주장을 끌어오지 사실을 확인하지
않는다"의 우리 쪽 판이다. 수치가 좋아서 채택하고 싶은 유혹이 정확히 여기 있었다.

> **[후속] `소품샵`을 태그로 넣었다가 되돌렸다 — 어휘의 층이 다르다.** 처음 판단은 *"`COZY`의
> 검색어로 쓰지 않는다"* 였고, 그 뒤 *"뜻이 같은 태그를 따로 만들면 어긋남이 없다"* 며
> `LIFESTYLE_SHOP`을 신설해 `SOLO`에 넣었다. **그 판단이 틀렸다.**
>
> **`StyleTag`는 "장소가 어떤 속성을 갖는가"를 담고, 업종은 `SlotType`이 담는다.** `소품샵`은
> 속성이 아니라 업종이므로 애초에 이 어휘에 들어올 자리가 아니었다. 뜻을 맞추는 문제가 아니라
> **층을 섞는 문제**였다.
>
> **실측이 그 이유를 그대로 보여줬다.** 슬롯 교차 검증에서 `"강릉 소품샵 맛집"`이
> `"강릉 소품샵 카페"`와 **완전히 같은 결과**를 돌려줬다(경주도 동일, 부산은 4/5 겹침).
>
> ```
> [강릉 소품샵 카페] 르봉마젤 소품샵, 이로이로스모모, 소돌엔등대 소품샵, 묘묘젤라또&소품샵, 음차차
> [강릉 소품샵 맛집] 르봉마젤 소품샵, 이로이로스모모, 소돌엔등대 소품샵, 묘묘젤라또&소품샵, 음차차
> ```
>
> 스타일 수식어는 `"어떤 성격의 X"`로 X를 좁히는데, `소품샵`은 **X 자리에 오는 업종**이라 슬롯
> 힌트(`맛집`·`카페`)와 경쟁해 그것을 밀어냈다. 그대로 뒀다면 `SOLO` 요청에서 **소품샵이 식사
> 후보로** 들어왔을 것이다. 4-4의 카테고리 제약(5-3)이 사후에 걸러내긴 하지만, 그전에 풀의 자리를
> 차지하고 쿼리 한 번을 낭비한다.
>
> **`StyleTag`는 31개로 되돌렸고 `SOLO`는 `조용한`·`숨은`을 쓴다.** 이 사건이 남긴 규칙 하나:
> **어휘에 무언가를 추가하고 싶을 때 "그것이 속성인가 업종인가"를 먼저 묻는다.** 검색 결과가 좋다는
> 것은 그 질문에 답하지 못한다.
>
> 교차 검증 프로브는 남겨 5-9가 쓰도록 범용화했다 — 아직 열린 대상은 `뷰맛집`이다(카페 5/5,
> 관광명소 0건).

`UNCROWDED`의 `숨은`은 **직역이 아니라 대용어**다. "숨은 카페"는 한적함을 함의하는 관용 표현이라
채택했지만 완전히 같은 뜻은 아니며, 이 타협은 기록해 둔다.

> **`한적함`은 검색어로 재본 적이 없었다.** 라벨(`한적함`)과 검색어(`한적`)를 혼동하기 쉬운데,
> 3차에서 라벨 표기 자체도 던져보니 3개 지역 전부 0건이었다. 라벨을 그대로 검색어로 쓰는 것이
> 자연스러워 보여도 실제로는 통하지 않는다는 사례다.

> 비운 세 태그는 사전에서 자동으로 빠진다 — `SENSIBILITY`는 통창 대신 한옥·레트로를,
> `FRIENDS`는 시끌벅적 대신 단체·야간을, `SOLO`는 아늑함 대신 조용한·숨은을 쓰게 됐다. **검색어를 비우는 것만으로 사전이 조정되는
> 구조**라 `StyleModifierDictionary`는 한 줄도 고치지 않았다.

## 판정 13 — 실패 사유 어휘는 공유하고, 결과 타입은 공유하지 않는다

4-1이 `NaverLocalResult.Cause`로 만든 5개 상수를 4-8(카카오)과 4-7(TourAPI)이 그대로 필요로 했다.

## 판정 18 — `serviceKey` 이중 인코딩이 실호출을 통째로 죽인다 ★★

공공데이터포털은 키를 **Encoding / Decoding 두 형태**로 발급한다. Encoding 키에는 `%2B`·`%3D`가
들어 있는데, 이것을 `UriBuilder.queryParam`에 넣으면 `%`가 다시 `%25`로 인코딩된다. 같은 키로 잰
결과다.

```
raw URI 조립        -> resultCode=0000
UriBuilder 조립     -> 403 SERVICE_KEY_IS_NOT_REGISTERED_ERROR
```

로그만 보면 **"키가 잘못됐다"로 읽혀** 원인을 찾기 어려운 실패다. 판정 11(`text/plain`)과 같은
부류 — 코드는 멀쩡한데 조립이 틀려 전 호출이 죽는다.

막는 방법을 둘로 나눴다.

1. **인코딩 모드를 `NONE`으로 둔다.** 이 API에 보내는 값이 전부 숫자와 ASCII 상수라 안전하다
   (한글 파라미터를 쓰게 되는 날의 판단 근거를 주석에 남겼다)
2. **키를 Encoding 형태로 정규화한다.** 발급 형태와 무관하게 같은 결과가 나오므로
   **".env에 어느 형태를 넣었는가"가 장애 원인에서 지워진다**

> **반대 방향(디코딩해서 넘기고 인코더에 맡기기)은 틀린다.** 디코딩된 키에는 `+`가 들어 있는데
> `+`는 쿼리 문자열에서 합법적인 문자라 인코더가 그대로 통과시키고, **서버는 그것을 공백으로
> 해석한다.** 키 한 글자가 조용히 바뀌어 인증이 깨진다. 더 자연스러워 보이는 쪽이 더 위험했다.

## 판정 19 — 0건일 때 `items`가 빈 문자열로 온다 (판정 11과 같은 부류)

```json
{"response":{"header":{"resultCode":"0000"},"body":{"items":"","totalCount":0}}}
```

`items`가 객체가 아니라 **빈 문자열**이다. 그대로 두면 Jackson이 `MismatchedInputException`을 던지고,
그 예외는 `MALFORMED`로 분류돼 **"관광지가 없는 지역"이 통째로 "호출 실패"로 둔갑한다.**

이것이 왜 나쁜지는 4-1이 이미 적어 두었다 — `Empty`와 `Failed`를 가르는 것이 결과 타입의 핵심인데,
디코더 설정 하나가 그 구분을 무의미하게 만든다. `ACCEPT_EMPTY_STRING_AS_NULL_OBJECT`로 흡수하고,
**4-7 실호출로 받은 실제 0건 응답을 그대로 스텁에 넣어** 회귀 테스트로 고정했다.

> 판정 11에서 배운 대로 **프로덕션 조립 그대로의 클라이언트를 실제 API에 붙이는 테스트**도 함께
> 뒀다(`[4-7h]`·`[4-7i]`). 스텁 12개가 전부 통과하는 동안 실호출이 100% 실패였던 상태를 다시 만들지
> 않기 위해서다.

## 판정 20 — 좌표만으로 dedupe하면 이 표본에서 97%가 오합침이다 ★

설계는 *"좌표만 쓰면 대릉원 안의 천마총이 합쳐지고, 이름만 쓰면 전국의 향교가 합쳐진다"* 고 적었다.
4-5 착수 전에 이것을 **실제로 쟀다**(`TourApiProbeTest`의 `[4-7j]`로 재현 가능).

경주 황리단길·부산 해운대·삼척 죽서루 각 관광지 50건, 쌍 3,675개:

| | 건수 |
|---|---|
| 300m 이내인 쌍 | 38 |
| 그중 이름까지 유사한 쌍 | **1** |
| **이름이 다른 쌍** | **37 (97%)** |

```
 288m  경주 내물왕릉  <->  천마총(대릉원)
  62m  천마총(대릉원)  <->  경주 쌈밥거리
 284m  천마총(대릉원)  <->  금관총
  41m  경주 남산 미륵곡 석조여래좌상  <->  보리사(경주)
```

**좌표 단독 규칙은 이 표본에서 성립하지 않는다.** 설계의 AND 규칙(거리 ≤ 임계값 **AND** 이름 유사)이
실측으로 뒷받침됐다.

**다만 이 측정이 보인 것은 "좌표만으로는 안 된다"이지 "300m가 옳다"가 아니다.** 소스 간 좌표 차이의
실제 분포는 시더와 TourAPI를 함께 돌려야 나오므로, 임계값 자체는 **5-9에서 조정한다.** 상수 하나만
고치면 되도록 `CandidateMatcher`에 모아 뒀다.

> **이름 정규화를 `KakaoLocalClient`에서 끌어올렸다.** 두 벌로 두면 한쪽만 고쳐지는 날이 오는데, 그
> 증상이 특히 나쁘다 — 검증에서는 같은 장소로 보던 것이 dedupe에서는 다른 장소가 되어 **같은 곳이
> 코스에 두 번 들어간다.** 원인을 찾기 매우 어려운 종류의 불일치다.
