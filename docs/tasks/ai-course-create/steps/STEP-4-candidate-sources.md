# STEP-4. `NaverLocalClient` + `TourApiClient` + 후보 공급 순수 함수 — 실행 기록

> [ROADMAP.md](../ROADMAP.md) 4단계의 상세 기록. 설계 근거는 [지식 신호 층과 후보 공급](../design/지식-신호와-후보-공급.md)이
> 소유하고, 이 문서는 **구현하며 내린 결정과 실측**만 담는다.
>
> **동작 변화 없음.** 5단계(`CandidateRetrievalStage`)가 조립에만 집중할 수 있도록 부품을 먼저
> 만들어 검증해 둔다. 클라이언트 빈이 둘 늘지만 파이프라인은 아직 컨트롤러에 연결되지 않는다.
>
> **진행 상황: 4-10 · 4-2 · 4-1 완료.** 다음은 4-3(스타일 modifier 사전).

## 실행 순서

로드맵의 항목 번호는 식별자이지 실행 순서가 아니다. 의존 관계로 재배열하면 이렇다.

```
[네이버 계열 — 키 확보됨]
  4-10 소급 집계  →  4-2 네이버 실호출 확정  →  4-1 NaverLocalClient
                                            →  4-3 스타일 modifier 사전
                                            →  4-4 네이버 category → SlotType
[카카오 — 키 확보됨]
  4-8 area 지오코딩 (KakaoLocalClient 결과 값 반환이 선행)
[TourAPI 계열 — 키 발급 대기]
  4-7 TourApiClient  →  4-9 cat3 → 스타일 태그
                     →  4-5 후보 dedupe·매칭 키
[마무리]
  4-6 단위 테스트 전량 + 스텁 테스트
```

**TourAPI 키(`TOUR_API_KEY`)가 아직 없다.** 개발계정은 자동승인이라 블로커는 아니지만, 발급 전까지
4-7·4-9·4-5에 착수할 수 없어 네이버·카카오 계열을 먼저 끝내도록 배치했다.

## 판정 1 — 4-10의 대상을 OpenAI에서 Gemini 아티팩트로 바꿔야 했다 ★

로드맵 4-10은 *"기존 [AI-HALLUCINATION-OPENAI.md](../hallucination/AI-HALLUCINATION-OPENAI.md) 아티팩트를
유명/무인지 그룹으로 다시 집계한다"* 였다. **그 아티팩트가 존재하지 않았다.**

STEP-2가 산출물로 기록한 `results/*-openai-{model}-{mode}-relow-*`를 다음 범위에서 찾았고 전부 0건이었다.

| 찾은 곳 | 결과 |
|---|---|
| 113개 브랜치의 **전체 커밋 히스토리** (`git log --all -- 'results/*'`) | 0건 — `results/`가 `.gitignore` 대상이라 애초에 커밋될 수 없다 |
| 모든 ref의 트리에서 `relow`·`openai-`·`luna`·`nano` 이름 검색 | 0건 |
| 5개 worktree의 `results/` 디렉터리 실측 | 0건 (전부 Gemini 시절 파일) |
| `C:\YOURTRIP`·사용자 폴더·Temp 스크래치패드 파일시스템 검색 | 0건 |

남아 있는 `hallucination-baseline-*` 파일은 **전부 `20260811`·`20260812`** 다. OpenAI 재측정이 기록된
커밋은 `9d3737c` (2026-08-13)이므로 그 산출물이라면 `20260813-` 이후여야 한다. **측정을 수행한
워크트리가 삭제되며 함께 사라진 것으로 보인다.**

**대상을 Gemini 아티팩트로 바꿨다.** 4-10의 목적은 *"출발 가설을 코드 짜기 전에 확인하는 가장 싼
검증"* 이지 OpenAI 값의 확정이 아니다. 가설("무인지 지역일수록 파라메트릭이 약하다")은 모델과 무관한
**파라메트릭 지식이라는 소스의 성질**에 대한 주장이므로 before 데이터로도 검증이 성립하고, 실제로
OpenAI 쪽에 문서로 남은 요약값(FAMOUS 5.1% / MINOR 7.8%)도 같은 방향을 보인다.

**집계 결과는 [AI-HALLUCINATION-GEMINI.md](../hallucination/AI-HALLUCINATION-GEMINI.md)의 "지역 티어별 소급 집계"
절에 있다.** 요지만 옮기면:

- **가설 성립** — 복합 환각률 FAMOUS **13.9%** vs MINOR **35.4%** (2.5배). z = 3.74, p ≈ 0.0002,
  95% CI 비중첩, 요청 단위 평균으로도 동일
- 전체값(자동 프록시 19.8% · 세탁 5.71%)이 기존 문서 기록과 소수점까지 재현돼 집계 경로가 검증됐다
- **파싱 실패는 티어와 반대 방향**(FAMOUS 26.7% vs MINOR 6.7%) — 실패가 전부 절단이므로 "할 말이
  많은 지역일수록 잘린다"로 읽힌다. **환각과 파싱 실패의 원인 축이 다르다**
- **티어 안의 분산이 티어 간 격차만큼 크다**(삼척 6.7% ~ 통영 40.4%). "무인지"는 단일 변수가 아니며,
  통영 값은 `NO_RESULT`가 아니라 `S1_4`(띄어쓰기 거짓 음성 밴드)가 만든 것이라 성격도 다르다

**이 사고에서 얻은 운영 교훈 하나를 남긴다.** STEP-2는 *"산출물이 다른 워크트리에만 남아 몇 달 뒤에야
재분석된 전례"* 를 경고하며 판정 40건을 문서로 옮겼는데, **그 대비 덕분에 OpenAI 측정의 결론은
살아남았고 재집계가 불가능해진 것은 원본 분해뿐이다.** 이번 소급 집계도 같은 이유로 표를 전부
문서에 적었다 — `results/`는 언제든 사라질 수 있는 저장소로 취급한다.

## 판정 2 — 네이버 지역검색의 경로가 문서와 다르다: `/v1/search/local.json` → `/search/v1/local` ★

**첫 실호출은 23건 전량 404였다.** `.env.example`과 설계 문서가 적어 둔 경로
`https://naverapihub.apigw.ntruss.com/v1/search/local.json`이 존재하지 않는다.

진단이 한 번 헛돌았다 — 처음에는 "게이트웨이 호스트가 살아 있으니 경로만 틀렸다"고 봤는데,
**존재하지 않는 호스트(`no-such-gateway-xyz.apigw.ntruss.com`)도 똑같은 404 본문을 돌려준다.**
`*.apigw.ntruss.com`이 와일드카드 catch-all이라 **404는 호스트·경로 어느 쪽이 틀렸는지 구분해 주지
않는다.** 이 사실을 확인하고 나서야 후보 조합을 넓게 훑는 쪽으로 방향을 바꿨다.

| 시도 | 결과 |
|---|---|
| `naverapihub` + `/v1/search/local.json`·`/search/local.json`·`/api/v1/...` 등 6종 | 전부 404 |
| `naveropenapi.apigw.ntruss.com` (구 NCP 게이트웨이) | 404 |
| **레거시 `openapi.naver.com/v1/search/local.json` + 레거시 헤더** | **401** — 경로는 살아 있고 인증만 실패 |
| 레거시 경로 + NCP 헤더 | 401 `Not Exist Client ID` |
| **`naverapihub` + `/search/v1/local`** | **200** ✅ |

**이관되며 확장자가 사라지고 세그먼트 순서가 뒤집혔다**(`/v1/search/local.json` → `/search/v1/local`).
레거시 401은 이 키가 developers.naver.com 자격이 아님을 뜻하므로 **되돌아갈 길도 없다.**

**교훈: `.env.example`의 엔드포인트는 0-2에서 키를 발급받을 때 문서를 보고 적은 값이고 실호출로
검증된 적이 없었다.** 로드맵이 4-2를 4-1보다 앞에 둔 이유가 정확히 이것인데, 실제로 걸린 것은
설계가 예상한 두 항목(`mapx` 정밀도·서술어 매칭)이 아니라 **경로 그 자체**였다.

> **부수 확인** — `/search/v1/news`·`/search/v1/blog`는 401 `요청한 API는 이 Application에서
> 활성화되어 있지 않습니다`를 준다. 키는 유효하고 **지역검색만 활성화**돼 있다. V1의 네이버 의존은
> 지역검색 하나뿐이라 문제가 없지만, **9단계에서 블로그를 켜려면 콘솔에서 활성화가 먼저다.**

## 판정 3 — 설계가 "확정 필요"로 남긴 응답 형식은 대체로 맞았고, 셋이 어긋났다

경로를 찾은 뒤 얻은 실응답으로 설계의 가정을 대조했다.

| 설계 가정 | 실측 | |
|---|---|---|
| `mapx`/`mapy`는 WGS84 × 10⁷ 정수 문자열 | `mapx="1292092884"` → 129.2092884(경도), `mapy="358363900"` → 35.8363900(위도) | ✅ |
| `title`에 `<b>` 태그가 섞인다 | `두낫디스터브 <b>경주</b>본점` | ✅ |
| `description`·`telephone`은 대부분 빈 값 | 전 항목 빈 문자열 | ✅ |
| 항목에 고유 ID가 없고 네이버 플레이스 URL도 없다 | `link`는 업소 자체 URL(인스타그램 등)이거나 빈 값 | ✅ |
| `display`는 5가 하드 실링 | 10을 요청해도 5건 | ✅ |
| `sort=comment`가 유효 | `random`과 다른 목록을 준다 | ✅ |
| **`start`가 1로 고정이라 6위 이하를 못 받는다** | **거부가 아니라 무시** — `start=2·6·11·16` 전부 응답 `start:1`에 **동일한 5건** | ⚠️ |
| **`category`는 `대분류>중분류` 계층** | **계층이 없을 수 있다** — `음식점>카페,디저트`·`카페,디저트>베이커리`와 나란히 **`브런치카페`** 단일 토큰 | ⚠️ |
| (설계에 없던 항목) `total` | **전체 매칭 수가 아니라 반환 건수다** — 항상 `display`와 같다(5→5, 3→3, 1→1) | ⚠️ |

어긋난 셋이 각각 다음을 바꾼다.

1. **`start` 무시** — 결론("풀을 넓히는 유일한 축은 쿼리 변주")은 그대로지만 **근거가 '거부'에서
   '무시'로 바뀐다.** 에러가 아니라 같은 5건을 조용히 다시 주므로, 5-8이 페이징으로 풀을 넓히려
   시도하면 **중복을 후보로 세는 조용한 버그**가 된다. 4-1의 클라이언트는 `start`를 파라미터로
   노출하지 않는다.
2. **`category` 계층 없음** — 4-4의 매핑을 "최상위 분류만 본다"로 짜면 `브런치카페`가 매핑 실패로
   빠진다. **구분자가 없으면 문자열 전체를 분류명으로 보는 폴백**이 필요하다.
3. **`total`의 의미 변화** — 9-2의 인기도 `log10(total)`은 **지역검색으로는 만들 수 없다.** 3층을
   켜려면 블로그 API의 `total`이 반드시 필요하다(그 API는 현재 미활성화 — 판정 2).

**`mapx`/`mapy`는 자릿수가 다르다**(경도 10자리 / 위도 9자리)는 것도 적어둔다 — 문자열 길이로
소수점을 끼워 넣으면 위도가 10배로 튄다. 정수로 읽어 `1e7`로 나눈다. 정밀도는 소수점 7자리(≈1cm)라
5-10의 300m 임계값에는 충분하고도 남는다.

## 판정 4 — 서술어 매칭이 작동한다: 스타일 modifier를 설계대로 채택한다 ★

**이것이 4-2에서 설계를 가르는 항목이었다.** 네이버가 `"조용한"` 같은 서술어를 상호명·카테고리에서만
찾는다면 스타일 쿼리는 빈 결과를 주고, 스타일 축을 retrieval에서 포기한 뒤 9단계 4층을 켜는 것이
유일한 길이 된다(설계의 "확정 전 실측이 필요한 지점").

기본 쿼리와 스타일 쿼리의 상위 5건을 비교했다.

| 기본 쿼리 | 스타일 쿼리 | 기본 | 스타일 | 겹침 | **신규** |
|---|---|---|---|---|---|
| 경주 황리단길 카페 | 경주 황리단길 **루프탑** 카페 | 5 | 5 | 2 | **3** |
| 경주 황리단길 카페 | 경주 황리단길 **조용한** 카페 | 5 | 5 | 2 | **3** |
| 강릉 안목해변 카페 | 강릉 안목해변 **야경** 카페 | 5 | 1 | 1 | 0 |
| 공주 맛집 | 공주 **주차** 맛집 | 5 | 4 | 0 | **4** |

**서술어가 결과를 실제로 바꾼다.** 상호명에 `루프탑`·`조용한`이 들어가지 않은 가게들이 새로 올라오므로
매칭 범위가 상호명 밖(리뷰·태그 등)까지 닿는다는 뜻이다. **설계대로 modifier 쿼리를 채택하고, 9단계
착수 조건 중 "네이버가 서술어를 매칭하지 못해 스타일 축을 포기했다"는 항목은 켜지지 않는다.**

`강릉 안목해변 야경 카페`가 1건으로 좁아진 것은 설계가 예상한 **"modifier가 결과를 좁히는 방향"** 의
사례다. 합집합이라 풀이 줄지는 않으므로 fail-open 그대로 두면 된다.

> **남는 한계는 그대로다.** 이 실측이 보인 것은 "서술어가 결과를 바꾼다"이지 "바뀐 결과가 실제로 그
> 속성을 갖는다"가 아니다. SEO 편승 여부는 설계가 말한 대로 8-7 삭제 로그로만 확인된다.

## 판정 5 — 무인지 지역에서 시더가 실제로 후보를 준다 (4-10의 공백을 메운다)

4-10이 확인한 것은 **파라메트릭이 무인지 지역에서 약하다**(복합 환각률 MINOR 35.4%)는 사실이고,
시더를 두는 이유가 그 공백을 메우는 것이다. 그렇다면 **시더 자신이 그 지역에서 비지 않아야** 한다.

| 지역 | MEAL | CAFE | ATTRACTION |
|---|---|---|---|
| 삼척 | 5건 (삼척보스대게 본점) | 5건 (보사노바 커피로스터스 삼척점) | 5건 (환선굴) |
| 공주 | 5건 (정안알밤(하)휴게소) | 5건 (베이커리 밤마을) | 5건 (마곡사) |
| 영주 | 5건 (나드리) | 5건 (태극당) | 5건 (부석사) |

**빈 결과 0/9.** 상위 결과도 그럴듯하다 — 환선굴·마곡사·부석사는 그 지역의 대표 관광지다. 설계가
*"`"{area} 카페"`가 0건인 지역은 카페가 실제로 없는 곳"* 이라며 카카오 커버리지를 뺀 근거가 이 표본에서는
성립한다. **5-9의 "0건일 때만 카카오" 폴백은 지금 붙일 이유가 없다.**

지연은 9회 평균 **109ms**, 최대 134ms, 단건 57ms였다. **카카오와 같은 응답 제한 3초면 여유가 크다** —
4-1은 카카오 설정값을 그대로 복제한다.

## 판정 6 — `NaverLocalClient`가 노출하지 않기로 한 것들

4-1 구현에서 내린 결정은 대부분 **"무엇을 넣을까"가 아니라 "무엇을 막을까"** 였다. 4-2 실측이
드러낸 함정이 전부 *조용히* 틀리는 종류였기 때문이다.

| 막은 것 | 열어두면 생기는 일 |
|---|---|
| `start` 파라미터를 아예 만들지 않음 | 무시되는 파라미터라 페이징을 시도하면 **에러 없이 같은 5건**이 온다. 5-8이 그걸 새 후보로 세면 풀이 부풀고 dedupe가 뒤늦게 지운다 |
| `sort`를 인자가 아니라 상수로 고정 | 호출부가 `accuracy`로 바꾸면 "인기 축 시더"라는 계약이 조용히 깨진다. 이 클라이언트의 존재 이유가 `sort=comment`다 |
| `display`를 5로 clamp | 상한을 모르는 호출부가 20을 넣으면 5건을 받고도 20건을 기대한다 |
| 빈 쿼리에서 호출 자체를 생략 | 일 25,000건 한도를 의미 없는 호출로 깎는다 |

**예외를 던지지 않는 것**도 같은 계열의 결정이다. `NaverLocalResult`를 sealed interface로 두고
`Found`/`Empty`/`Failed`로 갈랐는데, **핵심은 `Empty`와 `Failed`를 가르는 것**이다. 설계가 카카오
커버리지를 후보 소스에서 뺀 근거가 *"`{area} 카페`가 0건인 지역은 카페가 실제로 없는 곳"* 인데,
이 판단은 "0건"과 "못 물어봄"이 구분될 때만 성립한다. 뭉치면 네이버 장애 시간 동안 전국에 카페가
없는 것처럼 보인다 — 5-6이 `no_result`와 `failed`를 반드시 갈라야 한다고 못박은 것과 같은 이유다.

`Failed`의 `Cause`도 처음부터 다섯으로 갈랐다. 특히 **`QUOTA_EXCEEDED`(429)만 성격이 다르다** —
재시도로 풀리지 않고 다음 날을 기다려야 하는 실패다. 하루 약 830~1,400코스에서 켜지는 분기라
(ROADMAP 0-5) 다른 실패와 뭉치면 "장애인가 한도인가"를 로그로 되짚어야 한다.

**좌표 변환은 클라이언트 밖(`NaverPlaceMapper`)에 뒀다.** 여기가 실제로 틀리기 쉬운 곳이고, 떼어내야
외부 호출 없이 테스트할 수 있다 — 3-2에서 `GeoUtils`를 route 타입과 분리한 것과 같은 취급이다.
그 안에서 지킨 규칙 하나: **`mapx`/`mapy`는 자릿수가 다르므로**(경도 10자리 · 위도 9자리) 문자열
길이로 소수점을 끼워 넣으면 위도가 10배로 튄다. 정수로 읽어 `1e7`로 나눈다.

**좌표 파싱 실패는 예외가 아니라 `null`이다.** 1-1이 `Place`의 좌표를 `double`에서 `Double`로 올린
것과 같은 판단이다 — 좌표가 없는 것을 `0.0/0.0`으로 위장하면 아프리카 앞바다에 장소가 생긴다.
좌표 없는 후보는 거리 정렬·dedupe에서만 빠지고 후보로는 살아남는다.

**키가 비어도 기동한다**(`${NAVER_CLIENT_ID:}`). 후보 공급이 fail-open이므로 키 부재가 기동 실패가
되면 안 된다 — `llm.openai.api-key`가 세운 관례다. 이 주장을 문서가 아니라 테스트로 고정했다
(빈 키로 조립해 호출하면 예외가 아니라 `Failed(UNAUTHORIZED)`가 온다).

## 남은 항목의 실행 계획

**로드맵은 "무엇을 어떤 순서로"만 담는다.** 항목별로 무엇을 어떻게 만들지는 여기가 소유한다.
착수하며 바뀌면 로드맵 항목 자체를 고치고, 바뀐 경위는 위 판정에 남긴다.

### 4-3. 키워드 → 스타일 modifier 사전 (순수 함수)

`global/ai/candidate/` 신설. **LLM을 쓰지 않는다** — 결정론으로 되는 일에 LLM을 먼저 쓰지 않는다는
설계 원칙 1이 그대로 적용된다.

- `StyleTag` enum — 설계의 닫힌 태그 집합. **각 태그는 한국어 검색어 표기를 함께 갖는다**
  (`야경`·`루프탑`·`조용한`). 4-2에서 서술어 매칭이 작동하는 것이 확인됐으므로 이 표기가 그대로
  modifier 쿼리에 실린다
- `StyleModifierDictionary.modifiersFor(List<KeywordType>)` → 가점 태그 **상위 1~2개**
- 매핑은 설계 표 그대로: `COUPLE`→야경·루프탑, `FAMILY`→주차가능·아이동반, `HEALING`→조용함·뷰맛집,
  `SENSIBILITY`→한옥·레트로·통창, `SOLO`→아늑함·조용함, `WALK`→역세권·도보접근, `CAR`→주차가능,
  `FRIENDS`→시끌벅적·단체가능, `COST_EFFECTIVE`→저렴, `PREMIUM`→고가·뷰맛집

> **결정해야 할 것 — 설계 표에 없는 키워드가 11개다.** `KeywordType`은 21개인데 설계의
> 키워드→traits 표에는 10개만 있다. 빠진 것은 mood 5개(`ACTIVITY`·`FOOD`·`CULTURE`·`NATURE`·`SHOPPING`),
> duration 4개, `NORMAL`이다. **duration·`NORMAL`은 비운다**(6-5가 duration 방침을 따로 정한다).
> **mood 5개는 4-9의 `cat3` 표가 이미 `자연`·`문화`·`액티비티`를 쓰고 있으므로 그 어휘를 `StyleTag`에
> 포함시켜 채운다** — 설계는 "4-3과 4-9는 같은 traits 어휘"라고 못박았는데 두 표의 어휘가 실제로는
> 어긋나 있다. 합집합 enum 하나로 해소하고 판정으로 남긴다.

### 4-4. 네이버 `category` → `SlotType` 매핑 (순수 함수)

- `NaverCategoryMapper.toSlotType(String category)` → `Optional<SlotType>`
- 최상위 분류 기준: `음식점`→MEAL, `카페,디저트`→CAFE, `관광,명소`·`문화,예술`→ATTRACTION,
  `쇼핑,유통`→SHOPPING
- **구분자 없는 단일 토큰 폴백이 필요하다**(판정 3) — `브런치카페`처럼 `>`가 없는 값이 실제로 온다.
  구분자가 없으면 문자열 전체를 분류명으로 보고 다시 찾는다
- **매핑에 없으면 통과시키되 표시한다**(감점, 하드 드롭 아님). `Optional.empty()`가 그 표시다

### 4-8. area 지오코딩 (카카오)

**`KakaoLocalClient`를 먼저 손봐야 한다** — 지금 `findBestPlace`는 호출 실패에 `BusinessException`을
던져 **무결과와 실패를 구분할 수 없다.** 캐스케이드는 이 둘을 정반대로 다뤄야 한다.

- 결과 값을 돌려주는 메서드를 **추가**한다(`Found`/`NoResult`/`Failed`). 기존 `findBestPlace`는
  시그니처·예외 계약을 그대로 둬 `MyCourseServiceImpl`의 동작이 변하지 않게 하고, 새 메서드 위에
  얇게 재구현해 검색·게이트 로직이 두 벌이 되지 않게 한다
- `AreaGeocoder` — 캐스케이드 `"{location} {anchor}"` → `"{location} {area}"` → `location`.
  **`NoResult`면 다음 단계, `Failed`면 즉시 중단**(같은 API가 죽었는데 다른 쿼리로 재시도할 이유가 없다).
  전부 실패하면 그 day의 TourAPI를 건너뛴다는 신호를 돌려준다
- 반환에 `GeocodeOutcome`(`HIT`/`FALLBACK_AREA`/`FALLBACK_LOCATION`/`FAILED`)을 실어둔다

> **메트릭과 캐시는 여기서 붙이지 않는다.** 로드맵 4-8이 `ai.geocode{result=...}`를 적었지만 5-6이
> *"이 저장소 최초의 커스텀 Micrometer 메트릭이라 `MeterRegistry` 주입 패턴을 여기서 세운다"* 고
> 명시한다 — 4-8이 먼저 붙이면 그 문장이 거짓이 되고 패턴이 두 곳에서 따로 선다. `GeocodeOutcome`을
> 값으로 들고 있으면 5단계가 메트릭으로 옮기기만 하면 된다. 캐시(TTL 30일)도 10단계 소관이다.

### 4-7. `TourApiClient` — **키 발급이 선행 조건**

- 4-2와 같은 방식으로 `@Tag("benchmark")` 프로브를 먼저 돌려 확정한다.
  **최우선은 분류체계(`cat1~3` vs 신 체계)** — 4-9가 통째로 이걸 전제한다. 그 외 오퍼레이션명,
  `arrange` 거리순 동작, 좌표 형식, 상권형 명소 등록 여부
- **4-2의 교훈을 그대로 적용한다** — `.env.example`에 적힌 경로는 검증된 적 없는 값이다.
  실호출 전에 경로를 신뢰하지 않고, 404가 나오면 호스트·경로 중 어느 쪽인지부터 가른다
- `global/tour/` — `TourApiConfig`(static 팩토리 포함) + `TourApiClient` + dto.
  `serviceKey`는 쿼리 파라미터이고 **Encoding/Decoding 발급 구분에 주의**한다
- `locationBasedList2(x, y, radius=20000, contentTypeId=12|14|28, arrange=거리순, numOfRows=50)`.
  반경은 튜닝값이 아니라 **최대 고정 울타리**이고 실질 필터는 거리순 + cap이다
- 반환은 4-1과 같은 결과 타입(fail-open). 격자 좌표 계산은 순수 함수로 만들되 **캐시는 10단계**

### 4-9. `cat3` → 스타일 태그 매핑 (순수 함수) — 4-7 의존

- `TourCategoryMapper.styleTagsOf(String cat3)` → `Set<StyleTag>`. 어휘는 4-3과 같은 enum
- **필터가 아니라 표시다** — 후보에 `styleTags`를 달아 Curator 입력과 목록 정렬에 쓴다
- 코드표는 4-7 실호출로 확정하고, **실제 코드 목록에 존재하는 값만 넣는다**

### 4-5. 후보 dedupe·매칭 키 (순수 함수) — 4-7 표본 의존

- MEAL/CAFE/SHOPPING은 provider가 하나라 **쿼리 간 중복만** 잡는다(정규화 상호명 + 주소)
- **관광 슬롯은 좌표와 이름을 둘 다 본다** — 좌표만 쓰면 대릉원 안의 천마총이 합쳐지고,
  이름만 쓰면 전국의 "향교"가 합쳐진다
- 거리 계산은 **`GeoUtils.haversineKm` 재사용**. 3-2에서 route 타입을 모르는 원시 함수로 만들어 둔
  것이 정확히 이 용처다
- 이름 정규화는 `KakaoLocalClient.normalize`와 **같은 규칙**을 써야 한다. private이므로 공용 유틸로
  끌어올리고 카카오 쪽이 그것을 쓰게 바꾼다 — 두 벌이면 drift가 생긴다
- **임계값(설계 초안 300m)은 4-7 표본으로 정하고 5-9에서 조정한다.** 미리 못 박지 않는다

### 4-6. 단위 테스트

`route` 패키지 관례를 따른다 — 한 파일 = 한 관심사, 클래스 `@DisplayName`에 ROADMAP 번호,
Spring 컨텍스트·Mockito 없이 순수 JUnit 5 + AssertJ.

- 순수 함수 전량 + `NaverPlaceMapper`(4-1에서 분리해 둔 변환 함수)
- `TourApiClientTest` — WireMock, `NaverLocalClientTest`와 동일 패턴
- `AreaGeocoderTest` — **"무결과는 다음 단계, 실패는 중단"** 을 각각 단언. 4-8의 핵심 계약이다
- `NaverLocalClientTest`는 4-1에서 이미 작성했다(12개)
