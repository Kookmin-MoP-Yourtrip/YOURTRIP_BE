# 보류한 설계와 미해결 과제

> [멀티 에이전트 파이프라인 설계](../멀티-에이전트-파이프라인.md)에서 분리된 문서다. **CriticAgent · CandidateRefiner**(V1 범위 밖)와 **남는 한계와 후속 과제**를 담는다.
>
> 셋을 함께 두는 이유는 성격이 같기 때문이다 — **"지금 만들지 않기로 한 것과, 그 판단을 뒤집을 조건"**이다. 앞의 둘은 설계까지 마쳤으나 V1에서 제외됐고(근거는 [운영 관심사](../design/운영-관심사.md)의 "Critic·Refiner를 V1에서 제외한 이유"), 남는 한계는 이 설계로도 답하지 못하는 것과 착수 전 확인이 필요한 항목이다.
>
> **같은 자격의 보류 항목이 하나 더 있다 — `PlaceSignalStage`(3층 인기도 + 4층 속성 추출).** 설계는 [지식 신호 층](../design/지식-신호와-후보-공급.md)에 그대로 있고, 제외 근거는 같은 문서 "PlaceSignal을 V1에서 제외한 이유", 착수 조건은 [도입 순서](../멀티-에이전트-파이프라인.md#도입-순서) 9단계에 있다. 여기로 옮기지 않은 이유는 지식 신호 층이 4층 어휘(traits 태그 집합·키워드 사전)를 스타일 modifier 쿼리(후보 공급)와 공유하고 있어 갈라놓으면 두 문서를 번갈아 읽어야 하기 때문이다.
>
> 재검토 조건이 충족되면 이 문서에서 `design/`으로 승격시킨다.

## CriticAgent — 블라인드 리뷰로 확증편향을 완화한다

> **V1 범위 밖.** 설계는 남기되 지금은 만들지 않는다 — 근거는 "Critic·Refiner를 V1에서
> 제외한 이유". 아래 내용은 나중에 재검토할 때 참고할 설계다.
>
> **재검토 순서 제약**: 아래 장치 1·2는 `traits`(4층 산출물)를 전제한다. 4층이 V1에서 빠졌으므로
> **Critic은 4층이 켜진 뒤에만 재검토가 성립한다** — 4층 없이 Critic을 켜면 "Critic·Refiner를 V1에서 제외한 이유"가 경고한 "Curator와
> 같은 파라메트릭 지식으로 재추측하는 것"이 전 슬롯에서 일어난다.

같은 모델이 자기가 뽑은 결과를 자기 지식으로 채점하면 확증편향이 그대로 남는다(원칙 2).
새 데이터 없이 독립성을 확보하는 세 가지 장치를 둔다.

1. **블라인드 리뷰** — Critic에게 Curator의 선정 근거를 **주지 않는다.** 최종 코스(장소명 + 카테고리
   + 시각 + `traits`)만 보고 판단하게 한다. 근거를 미리 보여주면 그 프레이밍에 끌려간다.
2. **외부 근거 제공** — `traits`를 함께 넘긴다. **Critic이 처음으로 파라메트릭 지식 밖의 근거를 갖는다.**
3. **모델 분리 + 결정론** — Critic만 다른 모델(설정 한 줄)로 돌리고, `temperature 0` + `seed` 고정으로
   채점을 재현 가능하게 만든다. 재현 가능해야 A/B 비교가 성립한다.

`IssueType`에 `DUPLICATE`·`TIME_OVERLAP`·`MISSING_MEAL`·`WRONG_CATEGORY`가 **없는 것이 핵심**이다.
전부 앞 단계가 구조적으로 보장한다.

```java
public enum IssueType { KEYWORD_MISMATCH, CONCEPT_MISMATCH, LOW_APPEAL }
```

> **미확정**: 위 세 가지 장치는 "무엇을 검사하는지"만 정의할 뿐, **각 `IssueType`을 언제 부여하는지에
> 대한 구체적 판단 기준(rubric)은 아직 없다.** `prompts/critic.md` 작성 시점에 반드시 명문화해야
> 한다 — 그렇지 않으면 "적절히 판단해라"는 느슨한 지시만 남아 재현성도, 설명 가능성도 없어진다.
> 이번 설계 단계에서는 확정하지 않는다.

## CandidateRefiner를 LLM이 아니라 결정론으로 두는 이유

> **V1 범위 밖.** Critic이 없으면 이 단계를 트리거할 입력 자체가 없다 — Critic과 함께 제외한다.

Critic이 지목한 `(day, placeIndex)`의 장소를 **같은 슬롯 후보 풀의 차순위로 교체**하고
RouteOptimizer를 재실행한다. LLM을 쓰지 않는다.

1. 후보 풀은 이미 Curator(LLM)가 취향을 반영해 만들었고 인기도·컨셉 점수로 정렬까지 됐다.
   차순위 교체도 여전히 근거 있는 선택이다.
2. LLM 호출 1회와 실패 모드 1개가 통째로 사라진다.
3. 교체 후 동선·시간을 반드시 재계산해야 하는데, LLM에게 맡기면 지그재그 동선이 다시 생긴다.
4. 순수 함수라 단위 테스트가 완전히 결정론적이다.

## 남는 한계와 후속 과제

### 이 설계로도 답하지 못하는 것

**"왜 이 장소가 좋은가"에 대한 신뢰할 만한 평가.** V1의 품질 신호는 **시딩(리뷰 수 순위)과 LLM
파라메트릭 지식**뿐이다. 초안은 여기에 속성(`traits`)을 더해 "어떤 곳인가"까지는 답하려 했으나
PlaceSignal을 V1에서 빼면서(후보 공급) 그마저 없어졌다. **협찬 편향을 우회한 대가로 평가 정보를 통째로
버리는 것이니, 이건 해결이 아니라 트레이드오프다** — 그리고 이 개정으로 트레이드오프의 폭이 조금
더 넓어졌다. 대신 얻은 것은 지연 −3~5초, LLM 호출 −1, 네이버 쿼터 상한 2~3배, 실패 모드 −1이다.

**관광 슬롯의 품질 신호는 "시더 5건 + TourAPI 분류"뿐이다.** 시더를 전 슬롯으로 넓히고 TourAPI를
붙였지만, 인기도는 여전히 쿼리당 5건의 상대 순위이고 TourAPI 자체에는 인기도가 없다. 유명 지역에서는
파라메트릭이 채우고 무인지 지역에서는 시드가 채우는 구조인데, **그게 실제로 충분한지는 사용자 삭제
로그(`seeded`/`official` 태그별)로만 확인할 수 있다.** 부족하다면 손댈 순서는 시더 쿼리 변주(호출 1회씩)
→ 3층 인기도(9단계) 순이다.

**스타일 modifier 쿼리는 "주장"을 끌어오지 "사실"을 확인하지 않는다.** SEO로 `야경` 키워드를 심어둔
가게가 실제로 야경이 좋은 가게와 같은 자격으로 풀에 들어온다. 초안의 4층이 그 검증 자리였는데
V1에서 빠졌으므로, 남은 방어선은 Curator의 파라메트릭 대조와 사용자 삭제 로그다(후보 공급). 위험이
실측되면 4층을 켠다 — 위험을 모르는 채 검증 비용을 선불하지 않는다.

**(재검토 시) 속성 추출 단계 자체가 새로운 LLM 왜곡 지점이다.** 닫힌 태그 집합과 "원문에 없으면
비워라"는 스키마 강제로 완화하지만 제거되지는 않는다. 4층을 켤 때 이 한계도 같이 돌아온다.

### 가장 유망한 후속 — 사용자 피드백 루프

**생성된 코스에서 사용자가 삭제한 장소와 남긴 장소가 곧 정답 라벨이다.**
`DELETE .../places/{placeId}` API가 이미 있고, `upload_course`의 fork 수·좋아요까지 합치면
**우리 서비스만의 컨셉 적합도 데이터셋**이 된다.

- "연인 키워드로 생성된 코스에서 자주 삭제되는 장소" = 컨셉 미스매치의 실측 신호
- 외부 API가 아니라 **우리가 축적한 고유 자산**이고, 협찬 편향이 없다
- `place` 테이블에는 이미 실제 장소가 좌표·URL과 함께 쌓이고 있다

지금은 데이터가 없어 쓸 수 없지만, **삭제 이벤트 기록은 지금부터 시작할 가치가 있다** — 나중에
소급할 수 없는 데이터다. 별도의 작은 작업으로 분리하는 것을 제안한다.

설계에는 확장 지점만 남긴다: `CandidateRetrievalStage`(후보 공급)가 후보 소스를 `CandidateSource`
인터페이스 목록으로 갖게 만들어(V1: `NaverLocalSeedSource`, `TourApiSource`), 나중에
`InternalPlaceRepositorySource`를 **세 번째 소스**로 꽂을 수 있게 한다 — "연인 키워드 코스에서
살아남은 장소"가 `SEEDED`와 같은 자격으로 풀에 들어오는 것이다. 초안이 `CuratorAgent` 안에
두려던 `PlaceSuggestionSource` 확장 지점이 이 개정으로 별도 단계로 승격된 셈이고, 데이터가 적을 땐
외부 소스만, 쌓이면 내부 소스를 섞는 점진적 전환이 그대로 가능하다.

### 품질을 정량 측정하는 방법

지금은 "좋아졌다"를 증명할 방법이 없다. 두 가지를 후속으로 제안한다.

1. **환각률 프록시** — `ai.grounding.match{result=name_mismatch}` 비율의 before/after 비교.
   지금 당장 측정 가능하고, 이 작업의 **1차 정량 지표**로 삼는다.
   → **before 값은 구현 착수 전에 이미 측정했다: [AI-HALLUCINATION-GEMINI.md](../hallucination/AI-HALLUCINATION-GEMINI.md).**
   그 문서에 측정 하네스·방법론·자동 프록시의 한계(거짓 양성/거짓 음성)와 after 측정 재현 절차가
   정리돼 있으므로, 파이프라인 도입 후 **동일한 입력 세트와 동일한 `score()` 로직으로** 재측정한다.

   **단, 이번 작업은 벤더 교체(Gemini → OpenAI, LLM 포트 설계)를 동반하므로 측정점이 둘이 아니라 셋이다.**
   2점만 재면 개선폭을 모델과 구조 중 어느 쪽에도 귀속시킬 수 없다.

   | 측정점 | 시점 | 분리되는 변수 |
   |---|---|---|
   | Gemini 단일 호출 | 완료 (환각률 25.6%) | — |
   | **OpenAI 단일 호출** | 도입 순서 2단계 직후 | 모델 교체 효과 |
   | OpenAI 파이프라인 | 도입 순서 8단계 직후 | 파이프라인 구조 효과 |

   세 측정점이 비교 가능하려면 **입력 세트(지역 10곳 × 스타일 3조합, 3일 고정)와 판정 `score()`
   로직이 동일해야 한다.** 1단계에서 카카오 매칭 로직을 바꾸므로(점수 하한선 대신 **이름 일치
   게이트**), 하네스의 판정 기준은 변경 전 `score()` 값으로 고정한 채 재측정한다 — 그러지 않으면
   "필터를 바꿔서 환각률이 내려간" 자기충족적 결과가 나온다.
2. **골든 데이터셋** — 입력 20세트에 대해 생성 결과를 사람이 채점하거나 LLM-as-judge로 평가.
   파이프라인이 안정된 뒤 착수하는 것이 맞다. **이 인프라가 생기는 것이 V1에서 제외한
   `CriticAgent`를 재검토하는 조건 중 하나다** — Critic이 실제로 품질을 개선하는지 측정할
   방법이 없는 채로는 만들어도 그 값어치를 확인할 수 없다.

### 보류 — TourAPI 축제·행사(`contentTypeId=15`)의 여행 날짜 매칭

TourAPI에는 다른 어느 소스도 못 하는 것이 하나 있다 — `searchFestival2(eventStartDate, eventEndDate)`에
요청의 여행 기간을 넣으면 **그 날짜에 실제로 열리는 축제·행사**가 나온다. ACTIVITY 슬롯 후보로 넣을 수
있고, 코스당 1회 호출·순수 추가(additive)·fail-open이라 비용도 작다.

**그럼에도 V1에서 뺀다.** ① 축제를 제대로 살리려면 Planner가 그 존재를 알고 슬롯 구성을 조정해야
자연스러운데(축제가 있는 날 ACTIVITY 슬롯을 늘리는 식) 그건 Planner 계약 변경이다 ② "축제 후보가
실제로 채택되고 유지되는가"는 미측정이다 — 관광지 후보(TourAPI 12·14·28)가 채택되는지부터 삭제 로그로
보고 나서 붙이는 것이 순서다. **재검토 조건**: 8단계 이후 삭제 로그에서 TourAPI 유래 후보의 채택률이
확인되고, 여행 날짜에 축제가 겹치는 요청 비율이 유의미할 때.

### 착수 전 확인 필요

- ~~**네이버 검색 API 키 발급**~~ — 발급 완료(ROADMAP 0-2). 초안은 3·4층(`NaverBlogClient`)의 선행
  조건으로 적었으나 V1에서는 **지역검색(시더)이 유일한 네이버 용처**다. 블로그 검색 쿼터·다중 키워드
  매칭 방식은 9단계(3·4층)를 켤 때 확인한다
- **네이버 지역검색 API 실호출 확정** (후보 공급 층 시더의 선행 조건, **V1 네이버 의존의 전부**) — ① 블로그
  검색처럼 API HUB로 이관됐는지, 이관 후에도 `sort=comment`·`display≤5`·`start=1` 제약이 동일한지
  ② `mapx`/`mapy`가 실제로 WGS84×10⁷ 정수로 오는지 — **이제 이 좌표를 SEEDED의 실좌표로 쓰므로**
  (초안과 달리 "안 쓰는" 값이 아니다) 정밀도(소수 몇 자리까지 유효한지, 카카오 좌표와 얼마나
  어긋나는지)까지 표본으로 확인한다. `PlaceUrlEnricher`의 300m 임계값도 이 실측으로 정한다
  ③ `category` 문자열의 실제 형태·최상위 분류 목록 — `SlotType` 매핑 사전(지식 신호 층의 2층)의 재료
  ④ `title`의 `<b>` 태그 실제 형태 ⑤ **서술어 매칭 범위** — `"황리단길 카페"` vs `"황리단길 루프탑
  카페"`·`"황리단길 조용한 카페"`의 건수·겹침·`total`. 상호명·카테고리만 매칭하면 후보 공급 스타일 modifier
  확장이 fail-open으로 조용히 무력화되므로, 이 결과가 스타일 축을 retrieval에 둘지 Curator에만 맡길지를
  가른다 ⑥ 일일 쿼터가 검색 API 전체 합산인지 엔드포인트별인지(V1은 지역검색만 쓰므로 당장은
  덜 중요하지만 9단계 때 상한 계산에 직결)
- **TourAPI 운영계정 승인** — 개발계정은 일 1,000건이다. 격자 캐시로 초기엔 버티지만 운영 전에 공공데이터포털
  활용사례 등록으로 증량 승인을 받아야 하고 며칠 걸린다. 4단계 착수와 함께 신청
- **TourAPI 실호출 확정** (후보 공급 "ATTRACTION 계열 슬롯"의 선행 조건) — ① 게이트웨이 이관 후 오퍼레이션명
  (`locationBasedList2`·`categoryCode2`) ② `arrange` 값에 거리순이 실제로 있는지, 최대 반경(20km) ③ `mapx`/`mapy`
  형식(WGS84 십진 문자열) ④ 분류체계 — `cat1~3`과 이관 후 추가된 새 체계 중 어느 쪽을 쓸지, 코드표 ⑤ 응답
  필드(`title`·`addr1`·`firstimage`·`contentid`·`modifiedtime`) ⑥ 하네스 지역 세트(유명/무인지)로 **시더↔TourAPI
  겹침·오매칭 표본** — 300m·이름 유사도 임계값의 근거 ⑦ 상권형 명소(황리단길·감천문화마을류) 등록 여부
  ⑧ 무인지 시군구의 항목 수·품질 표본
- **네이버 `"{area} 관광명소"` sort=comment 품질** — 관광 슬롯 시더 쿼리가 실제로 유의미한 5건을 주는지.
  `searchHint` 표현(관광명소/명소/가볼만한곳)은 이 실측으로 정한다
- **`placeUrl` null 허용 여부 FE 확인** — `PlaceUrlEnricher`가 이름 불일치·좌표 불일치 시 URL을
  비우는데(후보 공급), FE가 `placeUrl == null`을 "링크 없음"으로 처리하는지 확인한다. 현재 Swagger 명세는
  이미 nullable이지만 실제 FE 동작은 별개다
- **네이버 시더의 빈 결과 빈도** — `ai.candidate.retrieval{result=empty}`가 특정 지역·슬롯에서
  자주 찍히면 "네이버 0건/실패 시에만 카카오 키워드 검색"을 폴백으로 붙인다(후보 공급 "카카오
  커버리지 검색을 후보 소스에서 뺀 이유"). 배포 후 실측 항목이며 미리 넣지 않는다
- **지역 티어별 환각률 소급 집계** — [AI-HALLUCINATION-OPENAI.md](../hallucination/AI-HALLUCINATION-OPENAI.md)
  아티팩트를 유명 지역 / 안 알려진 지역(순천·영주·공주·통영·삼척) 그룹으로 나눠 다시 집계한다.
  이 개정의 출발 가설("무인지 지역일수록 파라메트릭이 약하다")을 코드 한 줄 짜기 전에 기존
  데이터로 확인할 수 있는, 가장 싼 검증이다
- **Spring AI의 구조화 출력이 스키마를 디코딩 레벨에서 강제하는지** (LLM 포트 설계) — 프롬프트 지시 기반 JSON
  모드로 떨어진다면 파싱 실패율 near-zero 전제가 깨지고, OpenAI 공식 SDK로 폴백해야 한다
- **OpenAI 모델 ID와 단가** — LLM 포트 설계의 agent별 `model` 배정(Planner·Curator = luna, 확정)을 바탕으로
  비용 분석 표를 OpenAI 기준으로 재계산하는 근거가 된다. PlaceProfile(nano) 배정은 9단계 재검토 시
- **OpenAI RPM/TPM 티어** — 호출이 4배가 되면 낮은 티어에서는 동시 사용자 2~3명만으로도 429가 난다.
  `llm.max-concurrent-calls` 초기값을 결정하는 근거가 된다
- 카카오 Local API 일일 쿼터 (요청당 ~20~30회 기준 상한 계산 — SUGGESTED 검증 + URL 보강)
- **(9단계 재검토 시) 실제 요청 중 `mood` 키워드 포함 비율** — 비용 분석의 PlaceProfile 조건부 확장(ATTRACTION
  포함 여부)이 얼마나 자주 켜질지를 결정한다. V1에는 PlaceProfile이 없으므로 당장은 무관하다
- **사용자 삭제 로그 기록을 8단계 스위치와 함께 켠다** — `source`·`modifier` 태그 포함(관측 설계). 이
  데이터가 9단계(3·4층)·TourAPI 축제·Planner `styleTags` 세 후속 결정의 공통 근거이고, 소급할 수 없다
