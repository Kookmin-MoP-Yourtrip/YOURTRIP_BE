# TASK-AI-HALLUCINATION-OPENAI. OpenAI 단일 호출 환각률 재측정 (luna vs nano)

> [TASK-AI-HALLUCINATION-GEMINI.md](TASK-AI-HALLUCINATION-GEMINI.md)가 잰 **before 값(Gemini 25.6%)** 의 짝이 되는 측정이다. [ROADMAP.md](ROADMAP.md) 2단계에서 LLM 벤더가 Gemini → OpenAI로 바뀌었으므로, 파이프라인 도입 후 값을 before와 그냥 비교하면 **"모델 교체"와 "파이프라인 도입" 두 변수가 섞여** 개선폭을 어느 쪽에도 귀속시킬 수 없다. 이 문서는 **파이프라인 없이 모델만 바꾼 중간 측정점**을 남긴다.
>
> 동시에 0단계가 넘긴 숙제 하나를 닫는다 — `gpt-5.6-luna`의 한국어 지역 지식을 확인하지 못한 채 Curator에 배정했으므로(ROADMAP 0-4), **luna와 nano를 같은 조건으로 재서 Curator 모델을 데이터로 확정**한다.
>
> 측정 과정에서 드러난 구현 이슈(모델이 거부하는 옵션, 숨은 재시도 계층 등)는 이 문서의 범위가 아니다 — [steps/STEP-2-llm-port.md](steps/STEP-2-llm-port.md)에 있다.

## 배경 — 왜 다시 재는가

before 측정이 잰 것은 `gemini-2.5-flash`다. 그런데 2단계에서 벤더가 OpenAI로 확정되면서, 8단계 이후의 값은 **모델도 다르고 구조도 다른** 상태가 된다. 중간에 한 점을 찍어야 두 효과가 갈라진다.

```
Gemini 단일 호출 ──[모델 교체]──▶ OpenAI 단일 호출 ──[파이프라인]──▶ OpenAI 파이프라인
    25.6%                            이 문서                          8단계에서 측정
```

여기에 **모델 선택 자체가 결과를 얼마나 좌우하는지**를 같이 본다. 설계는 비용을 아끼려고 Curator에 저가 모델(`gpt-5-nano`)을 쓸 여지를 열어뒀는데, 그 선택이 환각률에 어떤 대가를 치르는지가 확인되지 않은 상태였다.

## 측정 방법

**before 측정과 완전히 같은 자를 쓴다.** 값이 비교 가능하려면 이게 전제다.

- 입력 세트 — 지역 10곳(유명 5 + 비유명 5) × 여행 스타일 3조합 = 30요청, 여행 일수 3일 고정
- 판정 로직 — `KakaoLocalClient.score()`를 리플렉션으로 원본 그대로 호출, 점수 밴드 경계도 동일
- 수동 검증 — 밴드별 층화 추출(밴드당 10건, 시드 42), 4분류(`CORRECT`/`LAUNDERED`/`WRONG_MATCH`/`UNVERIFIABLE`)
- 하네스 — `src/test/java/backend/yourtrip/global/benchmark/AiHallucinationBaselineTest.java`

**프롬프트도 95줄 원문 그대로다.** 하네스가 문자열을 복사하지 않고 `GeminiService.buildPrompt()`를 직접 호출해 drift를 원천 차단했다.

### 측정 축 — 4조합 120요청

before 대비 바뀌는 변수가 셋이라(모델 / 출력 강제 방식 / 파이프라인 구조), 이 중 앞의 둘을 각각 켜고 꺼 4조합을 돌렸다.

| 축 | 값 |
|---|---|
| 모델 | `gpt-5.6-luna` / `gpt-5-nano` |
| 출력 강제 | 프롬프트지시(스키마 미전송) / `response_format.json_schema` |

```bash
BASELINE_MODEL=luna BASELINE_SCHEMA_MODE=prompt BASELINE_REASONING_EFFORT=low \
  ./gradlew benchmarkTest --tests '*AiHallucinationBaselineTest*' --rerun
```

**3점 비교의 중간점은 `luna / 프롬프트지시` 조합이다** — before가 스키마를 전송하지 않는 JSON 모드였으므로, 그것과 짝이 맞는 쪽이 "모델 교체"만 분리한다.

### 모델 선택에 딸려 들어간 변수 두 개

**분리할 수 없는 차이가 있고, 이건 한계로 기록해야 한다.**

| 항목 | Gemini | OpenAI |
|---|---|---|
| temperature | 0.3 | **1(고정)** — 두 모델 모두 커스텀 값을 400으로 거부한다 |
| 추론 강도 | thinking 기본 활성 | `low`(두 모델의 공통 최저값) |

우리가 고를 수 있는 변수가 아니라 **모델 선택에 딸려오는 성질**이다. 온도가 높을수록 환각이 느는 경향을 감안하면 OpenAI 쪽에 불리한 조건이므로, 아래 수치는 **보수적인 값**이다. 상세는 [steps/STEP-2-llm-port.md](steps/STEP-2-llm-port.md) 판정 6.

## 발견

**1. 모델 교체만으로 복합 환각률이 25.6% → 7.5%로 떨어진다.** 파이프라인은 아직 하나도 도입되지 않은 상태다. 즉 이 작업의 1차 지표 개선분 중 상당 부분이 **모델 선택에서 이미 나온다.**

**2. `gpt-5-nano`는 Curator로 쓸 수 없다.** 같은 조건에서 복합 환각률 89.4%로 luna의 **12배**이고, 진짜 환각률로는 **38.6배**, Gemini와 비교해도 **7.3배** 나쁘다. 장소 448개 중 약 187개가 존재하지 않는 이름이다. "OpenAI로 바꿨으니 좋아졌다"가 모델과 무관하게 성립하지 않는다는 뜻이다.

**3. nano의 실패는 로컬 상호 지식에 국한된다.** 유명 관광지(`S8_10` 밴드)는 9/10 정답으로 luna와 차이가 없다. 무너지는 곳은 **가게 이름을 회상해야 하는 지점**이고, 그때 nano는 이름 대신 **설명구를 채워 넣는다.**

```
맛집 강릉횟집 · 삼척항 맛집 · 흑돼지거리 맛집 · 삼청동길 카페 · 오대의리 맛집 삼척점
```

상호가 아니라 "지역 + 맛집/카페"다. Curator가 하는 일이 정확히 "슬롯당 실제 상호명 3개 회상"이므로 **가장 나쁜 지점에서 무너진다.**

**4. 구조화 출력은 환각률을 낮추지 않는다 — 낮출 수도 없다.** 스키마를 켠 판이 오히려 소폭 높았다(luna 6.4→7.8%, nano 47.8→50.7%, 자동 프록시 기준). **스키마는 형식을 강제하지 내용을 강제하지 않는다** — "존재하는 상호명을 대라"는 JSON 스키마로 쓸 수 있는 규칙이 아니다. 환각을 없애는 것은 카카오 그라운딩(3~5단계)이지 구조화 출력이 아니라는 역할 분담이 데이터로 확인됐다.

**5. before의 JSON 파싱 실패 16.7%는 모델 성질이었다.** 120요청 전체에서 응답 절단이 **0건**이다. 로드맵 목표 1은 "구조화 출력을 켜면 파싱 실패가 사라진다"고 적었으나, 실제로 해결한 것은 **모델 교체**다. 구조화 출력이 없앤 것은 스키마 밖 필드 1건뿐이었다.

**6. 자동 프록시(매칭 실패율)는 실제보다 부풀려져 있다.** luna의 `NO_RESULT` 표본 10건 중 3건이 **실존하는데 카카오가 못 찾은** 경우였다(통영 분소식당, 제주 민트 레스토랑, 통영 연대도몽돌해변). before 문서가 한계로 명시한 *"카카오 미등록 실존 업소는 원리적으로 환각과 구분할 수 없다"*가 실제로 관측된 것이다.

## 핵심 결과

| 측정점 | 복합 지표 | 진짜 환각률 | 자동 프록시 | JSON 실패율 |
|---|---|---|---|---|
| Gemini 2.5-flash (before) | **25.6%** | 5.7% | 19.8% | 16.7% |
| **OpenAI `gpt-5.6-luna`** | **7.5%** | **1.08%** | 6.4% | **0.0%** |
| OpenAI `gpt-5-nano` | **89.4%** | **41.7%** | 47.8% | 3.3% |

**두 지표를 함께 보는 이유**는 재는 대상이 다르기 때문이다.

- **복합 지표** = 자동 프록시 + 세탁된 환각. *"사용자에게 잘못된 장소가 노출되는 비율"*에 가깝고, before와 비교 가능한 유일한 값이다
- **진짜 환각률** = 세탁된 환각만. *"LLM이 실제로 지어낸 이름"*의 비율이다. 카카오 커버리지 문제가 섞이지 않아 **모델 간 비교에는 이쪽이 정확하다**

배수로 보면 어느 쪽을 보느냐에 따라 결론의 세기가 달라진다.

| 비교 | 복합 지표 | 진짜 환각률 |
|---|---|---|
| nano ÷ luna | 12.0배 | **38.6배** |
| nano ÷ Gemini | 3.5배 | **7.3배** |
| Gemini ÷ luna | 3.4배 | **5.3배** |

**복합 지표는 모델 간 차이를 희석시킨다** — 매칭 실패율에 카카오 커버리지 문제가 섞여 있는데, 그건 모델 탓이 아니기 때문이다.

### 밴드별 구성

| 밴드 | 의미 | Gemini | luna | nano |
|---|---|---|---|---|
| `NO_RESULT` | 검색 결과 0건 | 11.6% | **2.2%** | **40.8%** |
| `S0` | 전부 불일치 | — | 0.0% | 0.4% |
| `S1_4` | 이름 불일치, 주소만 | 8.2% | 4.2% | 6.5% |
| `S5_7` | 이름 불일치 + 주소·카테고리 | 14.1% | 9.0% | 18.1% |
| `S8_10` | **이름 일치(+5) 포함** | 66.1% | **84.6%** | 34.2% |

**차이는 밴드 배분과 밴드 내 품질 양쪽에서 난다.** ① nano는 전체 장소의 **40.8%가 `NO_RESULT`에 떨어진다**(luna 2.2%) ② 그 밴드 안에서도 실존 비율이 낮다(luna 3/10 실존, nano 1/10). 두 효과가 곱해져 이 밴드 하나가 nano 진짜 환각률의 **32.7%p**를 만든다.

지역 tier별 경향은 before와 같다 — luna 기준 유명 5.1% / 비유명 7.8%로, **덜 알려진 지역이 여전히 더 나쁘다.**

### 진짜 환각률의 산출

before의 "세탁된 환각률"과 같은 식이다.

```
진짜 환각률 = Σ_전체밴드 (밴드별 LAUNDERED 비율 × 밴드별 전체 비중)
```

| 밴드 | luna | nano |
|---|---|---|
| `NO_RESULT` | 3/10 × 2.2% = 0.66%p | 8/10 × 40.8% = **32.68%p** |
| `S0` | — | 2/2 × 0.4% = 0.45%p |
| `S1_4` | 1/10 × 4.2% = 0.42%p | 2/10 × 6.5% = 1.29%p |
| `S5_7` | 0/10 × 9.0% = 0 | 4/10 × 18.1% = **7.23%p** |
| `S8_10` | 0/10 × 84.6% = 0 | 0/10 × 34.2% = 0 |
| **합** | **1.08%** | **41.65%** |

장소 수로 환산하면 luna는 454개 중 약 5개, nano는 448개 중 약 187개가 지어낸 이름이다.

**`S8_10`이 두 모델 모두 0이라는 점이 중요하다.** 이름 일치(+5)가 강제되는 밴드에서는 nano도 지어내지 않는다 — 발견 3(로컬 상호 지식에 국한된 실패)과 같은 이야기다. nano의 환각은 이름이 전혀 안 맞는 밴드(`NO_RESULT`·`S0`)와 주소·카테고리만으로 점수를 얻는 밴드(`S5_7`)에 몰려 있고, 이 셋이 합쳐 41.7% 중 **40.4%p**를 차지한다.

### `S8_10`에서 세탁이 0인 것은 구조 때문이다

표본이 밴드당 10건뿐이라 그것만으로는 근거가 얇다. 그런데 `score()`의 가점은 **이름 `+5` / 주소 `+3` / 카테고리 `+2`** 셋뿐이므로 가능한 점수는 `0·2·3·5·7·8·10`이고, **8점 이상은 반드시 이름 일치를 포함한다**(`8 = 5+3`, `10 = 5+3+2`). 지어낸 이름이 "카카오 상호명과 부분 일치 + 지역 일치"를 동시에 만족하기는 어렵다.

대신 이 밴드에는 **다른 종류의 거짓 양성**이 있다 — 짧은 이름이 긴 상호에 포함돼 버리는 경우다(`환선굴 → 환선굴휴게실가든`, `성산일출봉 → 성산바다풍경 제주성산일출봉점`). 이건 `WRONG_MATCH`라 환각에 포함하지 않는다.

반대로 **`S5_7`은 `5 = 주소3 + 카테고리2`로 이름이 하나도 안 맞아도 도달**한다. ROADMAP 1-2가 이 밴드를 위험 구간으로 지목한 진단이 여기서도 유효하고, **nano에서 정확히 이 지점이 터졌다**(4/10 세탁).

## 이 측정의 한계

- **표본이 밴드당 10건이다.** before는 밴드당 30건(3배치 병합)이었으므로 신뢰구간이 그때보다 넓다. 특히 비중이 큰 밴드에서 `0/10`은 산술적으로 상당한 폭을 남긴다 — 위의 구조적 논거가 그 폭을 좁혀주지만 표본을 대신하지는 않는다
- **`UNVERIFIABLE`을 정답으로 간주한 하한값이다**(before의 전제 ③과 동일). 환각으로 보는 상한은 luna 9.3% / nano 96.0%다. **다만 `UNVERIFIABLE` 대부분은 이후 검토에서 `LAUNDERED`로 재판정했다** — `카페 드 바다`·`삼한본색`처럼 그럴듯한 조어라 검색으로 부재를 확증하기 어려웠을 뿐, 지역 맛집·관광 목록 어디에도 없다는 점에서 미실존으로 보는 것이 타당하다고 판단했다. 재판정 후 남은 `UNVERIFIABLE`은 luna 4건 / nano 3건이고, 이들은 지칭 대상이 부분적으로 실존한다(예: 카페베네 체인, 영주댐, 초당순두부마을)
- **판정자가 사람이 아니라 Claude Code 세션이다.** 웹 검색으로 확인하고 근거를 `note` 칸에 남겼으나, before 측정(사람 판정)과 판정자가 다르다
- LLM 응답은 비결정적이라 수 %p 차이는 반복 측정이 필요하다는 before의 한계를 그대로 승계한다
- 카카오에 미등록된 실존 업소는 원리적으로 환각과 구분할 수 없다 — 발견 6이 그 실례다

## 결정

**1. Curator 모델은 `gpt-5.6-luna`로 확정한다.** 0단계가 2-6에 넘긴 숙제를 닫는다. 비용을 아끼려고 nano로 내리는 선택은 이 작업의 1차 목표를 정면으로 훼손한다.

**2. `PlaceProfileAgent`의 nano 배정은 유지하되 9단계에서 재확인한다.** nano가 실패한 것은 *지식 회상*이고 PlaceProfile이 하는 일은 *주어진 블로그 텍스트에서 속성 추출*이라 과제 성격이 다르다. 다만 닫힌 태그 집합 준수율을 별도로 봐야 한다.

**3. 구조화 출력은 환각 대책이 아니라 비용·형식 대책으로 위치를 옮긴다.** 실익 두 가지가 실측으로 확인됐다 — 출력 바이트 **약 48% 감소**(pretty-print 제거, 설계 문서 §11이 지목한 Curator 출력 비용에 직결)와 **스키마 밖 필드 차단**.
