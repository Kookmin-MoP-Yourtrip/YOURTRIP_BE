# BASELINE 산출물 재분석 — 점수 밴드 분포와 파싱 실패 원인

> [AI-HALLUCINATION-GEMINI.md](AI-HALLUCINATION-GEMINI.md)의 환각률 측정이 남긴 **원본 산출물(`results/*.csv`)을 집계한 기록**이다. [ROADMAP.md](../ROADMAP.md) 1-2("카카오 점수 하한선 도입, 임계값은 BASELINE 측정의 점수 밴드 분포를 근거로 정한다")를 실행하려면 그 분포가 필요한데, 산출물이 `.gitignore` 대상이라 레포에 남지 않는다. 이 문서가 그 대체물이다.
>
> 결론부터: **점수 하한선은 이 데이터에서 역효과다.** 로드맵이 전제한 "점수가 높을수록 정확하다"가 성립하지 않는다. 그리고 부수적으로, 로드맵이 미해결로 남긴 항목 두 개(파싱 실패 산출물 소실, 실패 원인 추정)가 **둘 다 정정 대상**임이 드러났다.
>
> 작성 시점: 2026-08-13. 대상 산출물은 2026-08-11 ~ 08-12 측정분.

## 왜 이 문서가 필요한가

측정 하네스 `AiHallucinationBaselineTest`는 결과를 레포 루트 `results/`에 쓴다. 그런데 [.gitignore:51](../../../../.gitignore)이 이 디렉터리를 부하 테스트 산출물과 같은 규칙으로 제외한다.

```
# 부하 테스트 원본 산출물(k6 summary JSON, JFR 덤프 등). 과거 TASK-3/4/CLOUDFRONT와
# 동일하게 레포에는 커밋하지 않는다 — 핵심 수치는 docs/tasks/TASK-*.md에 정리해 남긴다.
results/
```

의도 자체는 타당하다(원본 CSV·JSON은 레포에 넣을 것이 아니다). 문제는 **"핵심 수치를 문서에 정리해 남긴다"의 뒷부분이 실행되지 않았다**는 것이다. BASELINE 문서에는 최종 요약 수치만 있고 밴드별 분포표가 없어, 1-2의 임계값을 정할 근거가 사라진 상태였다.

산출물은 다른 워크트리(`claude/multi-agent-travel-course-fc4b56`)의 작업 디렉터리에만 남아 있었다. 브랜치를 지우거나 워크트리를 정리했다면 영구 소실이었다. **이 문서는 그 집계 결과를 커밋되는 형태로 고정한 것이다.**

## 판정 1 — 점수 하한선은 이 데이터에서 역효과다 ★

`KakaoLocalClient.score()`는 이름 일치 +5 / 주소 일치 +3 / 카테고리 +2로 최대 10점을 매긴다. 가능한 값은 `{0, 2, 3, 5, 7, 8, 10}` 이산 집합이고, 실제 관측값은 `{-1, 3, 5, 7, 8, 10}`뿐이었다(`-1`은 검색 결과 0건).

|---|---|---|---|
| `NO_RESULT` | -1 | 45 | 11.6% |
| `S0` | 0 | 0 | 0.0% |
| `S1_4` | 3 | 32 | 8.2% |
| `S5_7` | 5 | 50 | 12.9% |
| | 7 | 5 | 1.3% |

| | 10 | 157 | 40.4% |

`KAKAO_ERROR`(카카오 API 오류)는 0건이었다.

### 밴드별 수동 검증 verdict (표본 104건)

| 밴드 | CORRECT | LAUNDERED | WRONG_MATCH | UNVERIFIABLE | 표본 |
|---|---|---|---|---|---|
| `NO_RESULT` | 12 (40%) | **12 (40%)** | – | 6 (20%) | 30 |
| `S1_4` | **18 (100%)** | – | – | – | 18 |
| `S5_7` | 17 (65%) | 2 (8%) | **6 (23%)** | 1 (4%) | 26 |
| `S8_10` | 28 (93%) | – | 2 (7%) | – | 30 |

**정확도가 점수에 대해 단조가 아니다.** `S1_4`(3점)는 표본 전부가 정답인데 `S5_7`(5·7점)은 31%가 불량이다. 즉 하한선을 `≥5`로 잡으면 **100% 정답인 밴드를 버리고 31% 불량인 밴드를 남기는** 필터가 된다.

원인은 점수 구성에 있다. 검색 키워드가 `"지역명 + 장소명"`이라 **주소 +3이 거의 자동으로 붙고**, 음식점·카페면 카테고리 +2도 거의 자동이다. 따라서 5점은 두 가지 서로 다른 상태를 뭉갠 값이다 — "이름만 맞음(5)" 또는 "주소+카테고리만 맞음(3+2)". 실제 표본에서는 후자가 많았고, 그건 **이름이 하나도 안 맞았다**는 뜻이다.

## 판정 2 — `S1_4`의 정체는 환각이 아니라 표기 차이다

`S1_4` 18건이 전부 정답인 이유는 단순하다. **주소는 맞았고 이름도 사실상 맞았는데, `contains` 비교가 공백·중점 때문에 거짓 음성을 냈다.**

```
동궁과 월지             → 동궁과월지
주문진 수산시장          → 주문진수산시장
허균·허난설헌 기념공원    → 허균허난설헌기념공원
SEA LIFE 부산 아쿠아리움  → 씨라이프 부산아쿠아리움
순천 드라마 촬영장        → 순천드라마촬영장
통영 케이블카            → 통영케이블카
```

즉 하네스가 `S1_4`를 "환각 의심 구간"(`SUSPECT_BANDS`)으로 분류한 것은 **오분류**다.

### 정규화 효과 (실측)

공백·`·`·`.`·`,`·`-`·`_`·괄호·`/`·`&`·`|`를 제거하고 소문자화한 뒤 양방향 `contains`를 다시 적용했다.

| 지표 | 값 |
|---|---|
| 검색 결과가 있는 장소 | 344건 |
| 정규화로 이름 매칭이 새로 성립 | **32건 (9.3%)** |
| — 그중 `S1_4` | 15건 (해당 밴드의 47%) |
| — 그중 `S5_7` | 17건 (해당 밴드의 42%) |
| 정규화 후에도 이름 불일치 | 49건 (검색 성공의 14.2%) |

정규화 후 밴드별 이름 매칭률:

| 밴드 | 이름 일치 | 이름 불일치 |
|---|---|---|
| `S1_4` | 15 (46.9%) | 17 (53.1%) |

남은 49건에는 정답과 오답이 섞여 있다 — `해운대 해변 → 해운대해수욕장`, `송정3대국밥 → 송정삼대국밥`(정답)과 `해운대 시장 → 개미집 국제시장본점직영점`(오답)이 함께 있다. `contains`로는 여기까지가 한계다.

## 판정 3 — 파싱 실패의 원인은 trailing comma가 아니라 응답 절단이다

로드맵은 두 가지를 적어뒀는데 **둘 다 정정이 필요하다.**

| 로드맵 서술 | 실제 |
|---|---|
| "파싱 실패율 28.6%의 산출물이 남아 있지 않다"(미해결 항목) | **남아 있다.** `merged3-requests.csv`와 `raw-*/` |
| "프롬프트의 JSON 예시에 trailing comma가 들어 있는 것이 유력한 원인"(목표 1) | **이 데이터로는 뒷받침되지 않는다** |

### 28.6%의 출처를 특정했다

배치별로 나눠 보면 이 수치가 어디서 나왔는지 재현된다.

| 배치 | 총 요청 | 호출 실패(429) | 파싱 실패 | 파싱 실패 / 호출 성공 |
|---|---|---|---|---|
| `20260811-174326` | 30 | 16 | 4 | **28.6%** (4/14) |
| `20260812-153453` | 8 | 4 | 0 | 0.0% |
| `20260812-184600` | 13 | 0 | 1 | 7.7% |
| **`merged3` (최종 전체 세트)** | **30** | **0** | **5** | **16.7%** |

**28.6%는 호출이 14건만 성공한 초기 배치의 값이다.** 전체 30요청을 커버하는 최종 병합본 기준으로는 **16.7%(5/30)** 다. 표본이 작아 두 값 모두 신뢰구간이 넓다.

### 실패 5건 전부 "응답이 잘림"이다

`parseError` 컬럼의 실제 메시지:

```
#1  경주 A : Unexpected end-of-input within/between Object entries
#3  경주 C : Unexpected end-of-input within/between Object entries
#10 서울 A : Unexpected end-of-input: was expecting closing quote for a string value
#12 서울 C : Unexpected end-of-input: expected close marker for Object
#30 삼척 C : Unexpected end-of-input in field name
```

**전부 `Unexpected end-of-input`이다.** trailing comma는 `Unexpected character ('}')` 계열의 다른 오류를 낸다 — 이 목록에는 하나도 없다.

원본 응답이 남은 것은 #30 하나뿐인데(raw 덤프가 나중에 추가됐다), 결정적이다.

```json
{
  "title": "삼척 친구들과 즐기는 프리미엄 액티비티 미식 여행",
  "daySchedules": [
    {
      "day": 1,
      "places": [
        { "placeName": "해변정",         "startTime": "11:30" },
        { "placeName": "삼척해변",       "startTime": "13:00" },
        { "placeName": "삼척해상케이블카", "startTime": "14:30" },
        {
          "placeName          ← 여기서 끝. 386바이트
```

정상 응답 16개는 전부 1,401 ~ 1,658바이트이고 완전한 JSON이다. #30만 **386바이트에서 키 이름 중간에 잘렸다.**

### 2단계 설계에 미치는 영향

로드맵 목표 1은 "스키마를 디코딩 레벨에서 강제하면(구조화 출력) 이 실패 자체가 사라진다"고 적었다. **절단이 원인이라면 구조화 출력만으로는 사라지지 않는다** — `response_format: json_schema`는 생성되는 토큰의 문법을 강제할 뿐, 응답이 중간에 끊기는 것을 막지 못한다. 끊기면 여전히 불완전한 JSON이 온다.

따라서 2단계에서 **출력 토큰 여유와 종료 사유(`finish_reason`) 확인이 함께 필요하다.** 현재 `GeminiService`의 `maxOutputTokens`는 4096인데 정상 응답이 ~1.6KB인 것을 보면 토큰 상한에 닿은 것으로 보기는 어렵고, 386바이트에서 끊긴 것은 상한이 아닌 다른 원인(스트림 중단 등)을 시사한다. 원인 규명은 2단계 재측정 때 `finish_reason`을 함께 기록해 판단한다.

## 판정 4 — 환각률 25.6%는 `NO_RESULT`를 두 번 센 값으로 재현된다

BASELINE 문서의 수치를 원본에서 재계산했다. **매칭 실패율과 지역 tier별 수치는 정확히 재현된다.**

| 지표 | BASELINE 문서 | 재계산 | 일치 |
|---|---|---|---|
| 유명 지역 환각 의심 | 11.4% | 20/175 = 11.4% | ✅ |
| 비유명 지역 환각 의심 | 26.6% | 57/214 = 26.6% | ✅ |
| 자동 프록시(매칭 실패율) | — | 77/389 = 19.8% | — |

`LAUNDERED`(진짜 환각)를 밴드 비중으로 가중하면:

| 밴드 | LAUNDERED 비율 | 전체 비중 | 기여 |
|---|---|---|---|
| `NO_RESULT` | 12/30 = 40.0% | 11.6% | 4.63%p |
| `S1_4` | 0/18 = 0.0% | 8.2% | 0.00%p |
| `S5_7` | 2/26 = 7.7% | 14.1% | 1.09%p |
| `S8_10` | 0/30 = 0.0% | 66.1% | 0.00%p |
| **합** | | | **5.7%** |

그리고 `19.8% + 5.7% = 25.5%` — BASELINE 문서의 **25.6%와 일치한다.** 즉 25.6%는 "매칭 실패율 + 전 밴드 LAUNDERED 가중합"으로 구성된 값이다.

**여기에 두 가지 문제가 있다.**

1. **`NO_RESULT`가 이중 계산된다.** 45건 전부가 이미 매칭 실패율(19.8%)에 들어가 있는데, 그 40%가 세탁된 환각으로 한 번 더 더해진다(4.63%p). 하네스 주석이 규정한 "세탁된 환각"은 원래 *매칭에 성공한* 밴드 안에 숨은 환각이므로, `S5_7`·`S8_10`만 대상이어야 한다.
2. **`S1_4`(8.2%p)가 매칭 실패율에 포함돼 있다.** 판정 2에서 확인했듯 이 밴드는 표본 100%가 정답이다.

이 둘을 걷어낸 값:

| 해석 | 값 |
|---|---|
| 매칭 실패율 (하네스 정의 그대로) | 19.8% |
| 매칭 실패율 (`S1_4` 제외 = `NO_RESULT`만) | 11.6% |
| 진짜 환각(`LAUNDERED`) 직접 가중 추정 | **5.7%** |
| BASELINE 문서의 "진짜 환각률(추정)" | 25.6% |

추정의 폭도 넓다. 표본이 104건(전체의 26.7%)이라 `UNVERIFIABLE`을 어느 쪽으로 보느냐, 표본 오차가 얼마나 되느냐에 따라 값이 움직인다.

| 조건 | 값 |
|---|---|
| `UNVERIFIABLE` = 정답 (하한) | **5.7%** |
| `UNVERIFIABLE` = 환각 (상한) | **8.6%** |

지배항인 `NO_RESULT`의 `12/30 = 40.0%`에 Wilson 95% 신뢰구간을 씌우면 `[24.6%, 57.7%]`이고, 이 항의 기여만 2.84~6.67%p로 흔들린다. **현실적인 범위는 대략 4~10%** 다.

**주의 — 이 재계산을 확정으로 다루지 않는다.** 밴드별 표본이 18~30건으로 작고, 원 측정자가 25.6%를 어떤 정의로 산출했는지 문서에 명시돼 있지 않아 위 구성은 재현에 의한 추정이다. 다만 세 수치가 소수점까지 맞아떨어지므로 구성 자체는 거의 확실하다.

### 결정 — 25.6%를 유지하고 정의만 명시한다

**값을 고치지 않는다.** 이 지표의 목적은 "절대적으로 정확한 환각률"이 아니라 **파이프라인 도입 전후를 같은 자로 재는 것**이다. 25.6%를 5.7%로 바꾸면 2단계·8단계 재측정도 전부 같은 정의로 다시 계산해야 하는데, 그 비용에 비해 얻는 것은 before 값 하나의 정확도뿐이다. **비교 가능성이 정확성보다 이 지표의 목적에 부합한다.**

대신 산출 절차를 [AI-HALLUCINATION-GEMINI.md](AI-HALLUCINATION-GEMINI.md)의 "25.6%의 정의"와 [ROADMAP.md](../ROADMAP.md) 성공 기준에 고정했다. 앞으로 이 값을 인용할 때 **"매칭 실패율을 포함한 복합 지표"** 라는 것을 함께 밝힌다 — 그래야 "AI가 코스의 4분의 1을 지어낸다"로 잘못 읽히지 않는다.

이 지표를 **재정의해야 하는 시점은 골든 데이터셋이 생길 때**다(로드맵 "범위에서 제외한 것" 참고). 사람 채점이나 LLM-as-judge 평가 인프라가 갖춰지면 프록시 지표 자체가 필요 없어진다.

## 재현 방법

원본 CSV가 있는 상태에서 위 집계를 다시 만들려면:

```bash
./gradlew benchmarkTest --tests '*AiHallucinationBaselineTest*' --rerun
```

집계 규칙(원본 CSV의 컬럼 기준):

- **밴드 분포** — `merged3-places.csv`의 `scoreBand` 빈도. 밴드 경계는 하네스 `bandOf(int)`와 동일 (`-2`=KAKAO_ERROR, `-1`=NO_RESULT, `0`=S0, `1~4`=S1_4, `5~7`=S5_7, `8~10`=S8_10)
- **verdict 교차표** — `manual-verification-*.csv` 3개를 합쳐 `scoreBand` × `verdict`. `#`로 시작하는 주석 행 제외
- **정규화 효과** — `aiPlaceName`과 `matchedPlaceName`에 `[\s·・.,\-_()\[\]/&|]+` 제거 + 소문자화를 적용한 뒤 양방향 `contains`. 정규화 전에는 불일치인데 후에는 일치하는 행을 센다
- **파싱 실패** — `merged3-requests.csv`의 `parseError`에 `JSON_PARSE` 포함 여부. 분모를 전체로 할지 호출 성공분으로 할지에 따라 값이 크게 달라지므로 반드시 명시할 것
- **LAUNDERED 가중 추정** — `Σ (밴드별 LAUNDERED 비율 × 밴드별 전체 비중)`

## 이 분석이 바꾼 것

| 대상 | 변경 |
|---|---|
| ROADMAP 1-2 | "`score()`에 총점 하한선 도입" → **"이름 정규화 + 이름 일치 필수 게이트"** |
| ROADMAP 목표 1 | "trailing comma가 유력한 원인" → **응답 절단이 관측된 원인** |
| ROADMAP 미해결 항목 | "파싱 실패율 산출물이 남아 있지 않다" → **남아 있고, 이 문서에 집계됐다** |
