# 지식 신호 층과 후보 공급

> [멀티 에이전트 파이프라인 설계](../멀티-에이전트-파이프라인.md)에서 분리된 문서다. **지식 신호 층**과 **후보 공급(`CandidateRetrievalStage`)**을 담는다.
>
> **이 둘을 한 파일에 두는 이유는 결합이 가장 강하기 때문이다.** 후보 공급은 지식 신호 층의 traits 사전·`popularityWeight`·인기도 논리를 계속 끌어다 쓰고, 지식 신호 층의 2′층(네이버 지역검색)은 후보 공급이 생기면서 추가된 층이다. 앞으로도 함께 바뀔 확률이 가장 높은 묶음이다.
>
> 다른 문서에서 이 문서를 가리킬 때는 절 이름(지식 신호 층 / 후보 공급)으로 참조한다.

---

## 지식 신호 4층

| 층 | 출처 | 답하는 질문 | 답하지 못하는 것 | V1 |
|---|---|---|---|---|
| 1 | **LLM 파라메트릭 지식** | 무엇이 이 컨셉에 어울리는가 | 실존하는가 (환각) · **이 지역에 무엇이 있는가** (무인지 지역) | ✓ Curator |
| 2 | **카카오 Local API** | 실제로 있는가, 어디인가, **무슨 업종인가** (파라메트릭 제안의 검증) | 좋은 곳인가 · **후보를 고르는 데는 안 쓴다** (인기도 정렬이 없어 목록이 임의 슬라이스) | ✓ SUGGESTED 검증·URL 보강 |
| 2′ | **네이버 지역검색 `sort=comment`** | **이 권역에서 리뷰가 많은 곳은 어디인가** (인기 후보 시드) · 어디인가(좌표·주소·카테고리) | 5건/쿼리 · 어떤 곳인가 | ✓ **후보 공급 — 전 슬롯의 인기 축** |
| 2″ | **한국관광공사 TourAPI** | **이 권역에 어떤 관광지가 있고 어떤 성격인가** (`cat3` 세분류) · 어디인가(좌표·주소) | **인기도** (정렬 없음) · 상업 POI | ✓ **후보 공급 — 관광 슬롯의 커버리지·분류 축** |
| 3 | **네이버 블로그 `total`** | **사람들이 실제로 가는가, 아직 영업하는가** | 어떤 곳인가 | **✗ 제외** (조건부) |
| 4 | **네이버 블로그 스니펫 → 속성 추출** | **어떤 물리적 특징이 있는가** | 왜 좋은가 | **✗ 제외** (조건부) |

**2′·2″층은 검증이 아니라 후보 공급에 쓴다.** 초안의 외부 신호는 전부 Curator 출력을 *사후*에
검증·랭킹하는 것이었는데, 네이버 지역검색을 Curator *앞*에서 호출하면 "리뷰가 많은 곳"을 실존
후보 목록으로 미리 확보할 수 있다 — 카카오에는 인기도 정렬이 없어 후보 소스로 쓰면 밀집 지역에서
임의 슬라이스가 되는데, 네이버는 그 문제가 없다. 관광지 슬롯에는 TourAPI가 **커버리지와 분류**를
보태고(무인지 지역까지 균질, 세분류로 스타일 표시), 인기도는 여전히 네이버 시더가 맡는다. 그래서
**후보를 고르는 소스는 네이버와 TourAPI 둘이고, 카카오는 후보를 고르는 데 관여하지 않는다**
(파라메트릭 제안의 실존 검증, 최종 장소의 URL 보강, `anchor` 지오코딩만). 상세와 카카오를 후보
소스에서 뺀 근거는 후보 공급 절에 있다.

> **[V1 제외] 3층·4층 = `PlaceSignalStage`는 V1에서 만들지 않는다.** 아래 두 절의 설계는
> 그대로 남긴다 — Critic·Refiner를 CriticAgent 설계·CandidateRefiner 설계에 남긴 것과 같은 취급이다. 제외 근거는 후보 공급
> "PlaceSignal을 V1에서 제외한 이유"에, 착수 조건은 [도입 순서 9단계](../멀티-에이전트-파이프라인.md#13-도입-순서)에
> 있다. 요지는 하나다: **초안에서 3·4층은 "컨셉을 판별할 유일한 외부 근거"이자 "품질 신호가 없다는
> 근본 원인 6번의 유일한 답"이었는데, 후보 공급 층이 인기도를 시딩으로 앞에서, 스타일을 modifier
> 쿼리로 앞에서 반영하면서 그 "유일한"이 사라졌다.** 아래 서술 중 "이 층에 필요한 건 딱 그
> 변별력이다" 같은 문장은 초안 시점의 근거이며, 그 논리는 시딩(2′층)으로 옮겨가 살아 있다.

**3층과 4층은 같은 API 호출 하나에서 나온다.** `display=5`로 조회하면 응답 한 번에
`total`(인기도) + `postdate`(최신성) + `title`·`description` 5건(속성 추출 재료)이 전부 들어 있다.
**네이버 호출은 장소당 1회다.** (V1 제외로 이 호출은 지금 0회다.)

각 층에서 **의도적으로 하지 않기로 한 것**이 설계의 절반이다.

### 2층 — 카카오: 좌표뿐 아니라 업종 정합성까지 쓴다

현재 코드는 `category_group_code`를 **가점 +2**로만 쓴다(`FD6/CE7/AT4`면 가산). 이걸
**슬롯별 기대 카테고리 하드 제약**으로 승격시킨다.

```
MEAL       슬롯 ← FD6 필수. 단 category_name 이 "술집" 계열이면 감점 (점심에 호프집 방지)
CAFE       슬롯 ← CE7 필수
ATTRACTION 슬롯 ← AT4 / CT1(문화시설) 허용, FD6·CE7 배제
```

컨셉까지는 아니지만 **최소한의 정합성**이고, 비용이 사실상 0이다. 원칙 1의 연장으로, LLM이나
후속 검토 단계가 볼 필요가 없는 항목이 하나 더 구조적으로 사라진다.

**같은 제약을 2′층(네이버 지역검색) 응답에도 건다.** SEEDED 후보는 카카오를 거치지 않으므로
`category_group_code`가 없다. 대신 네이버 `category` 문자열(`"카페,디저트>카페"`, `"음식점>한식>국밥"`,
`"관광,명소>유적지"`)의 **최상위 분류를 `SlotType`으로 매핑**하는 결정론 사전을 둔다 — `음식점` → MEAL,
`카페,디저트` → CAFE, `관광,명소`·`문화,예술` → ATTRACTION/EXPERIENCE. 카카오 코드와 분류 체계는 다르지만
"점심 슬롯에 술집" 같은 큰 어긋남을 막는 데는 충분하고, 시드 쿼리 자체가 슬롯 `searchHint`로
던져지므로 불일치 자체가 드물다. 매핑에 없는 분류는 **통과시키되 표시**한다(감점, 하드 드롭 아님).

### 3층 — 네이버 `total`: 후기를 "읽지 않고" 인기도만 잰다 `[V1 제외]`

```
GET https://naverapihub.apigw.ntruss.com/v1/search/blog.json
    ?query={카카오 공식 상호명} {지역}&display=5&sort=date
  헤더: X-NCP-APIGW-API-KEY-ID / X-NCP-APIGW-API-KEY
  → { "total": 12847, "items": [ { title, description, postdate }, … ] }
```

> **[정정]** 초안은 엔드포인트를 ~~`https://openapi.naver.com`~~, 인증을
> ~~`X-Naver-Client-Id`/`X-Naver-Client-Secret`~~으로 적었으나, 검색 API가
> **NAVER API HUB(네이버 클라우드 플랫폼)** 로 이관되며 둘 다 바뀌었다(비용 분석 정정 참고).
> **[정정 — 4-2 실측]** 위 경로는 **틀렸다.** 지역검색을 실호출해 확정한 결과 API HUB의 경로는
> `/v1/search/{api}.json`이 아니라 **`/search/v1/{api}`** 다(확장자 제거 + 세그먼트 순서 반전).
> 블로그도 같은 규칙이면 **`/search/v1/blog`** 이고, 실제로 그 경로는 401 *"요청한 API는 이
> Application에서 활성화되어 있지 않습니다"* 를 돌려준다 — **경로는 맞고 활성화가 안 돼 있다**는
> 뜻이므로 9단계 착수 시 NCP 콘솔에서 블로그 API를 먼저 켜야 한다. 더 중요한 제약이 하나 더
> 나왔다: **지역검색의 `total`은 전체 매칭 수가 아니라 반환 건수여서 항상 `display`와 같다.**
> 3층의 `popularity = log10(total)`을 지역검색으로는 만들 수 없고, 블로그 API의 `total`이
> 그 의미를 갖는지도 9단계 착수 시 함께 확인해야 한다. 상세는 [STEP-4](../steps/STEP-4-candidate-sources.md) 판정 2·3
>
> **경로(`/v1/search/blog.json`)와 응답 필드가 그대로 유지되는지는 아직 확인하지 못했다** —
> 이 설계의 3·4층은 `total`·`postdate`·`title`·`description`에 의존하므로, 도입 순서 4단계 착수 시
> 실호출로 먼저 확정한다.

```java
popularity = log10(max(total, 1));                    // 0건→0, 100건→2, 1만건→4, 100만건→6
recentlyMentioned = 최신 postdate 가 12개월 이내;      // 폐업 감지
```

**로그 스케일이 필수인 이유**: `total`은 1건에서 수백만 건까지 **자릿수 단위로 벌어진다.**
선형으로 쓰면 유명 관광지 하나가 다른 모든 신호를 압도한다.

**협찬 편향이 상당 부분 무력화된다.** 협찬 포스팅이 많다는 건 최소한 "사람들이 가는 곳"이라는
신호이기도 하다. 절대적 품질은 못 재도 **무명 vs 유명을 가르는 데는 충분히 유효**하고, 이 층에
필요한 건 딱 그 변별력이다.

**검색 쿼리는 카카오 공식 상호명으로 던진다.** LLM이 추측한 이름이 아니라 카카오 검증을 통과한
`doc.place_name()`을 쓴다 — 표기 흔들림이 없어 `total`이 정확해지고, 동명 업소 문제도 지역명을
붙여 해소한다("황남밀면"은 전국에 여러 곳이다). **이것이 네이버를 카카오 이후에 배치하는 이유다.**

**슬롯 타입별 가중치** — 이 신호를 어디에 투입할 것인가:

| 슬롯 | 가중치 | 근거 |
|---|---|---|
| `MEAL`, `CAFE` | **1.0 (핵심 용처)** | 진짜 맛집과 동네 가게가 자릿수로 갈린다. 변별력 최대 |
| `SHOPPING`, `EXPERIENCE` | 0.6 | 중간 |
| `ATTRACTION`, `VIEWPOINT`, `STROLL` | **0.2** | 대릉원·첨성대 둘 다 수십만 건이라 구분이 안 된다. 관광지 선택은 Planner의 권역 설계가 대부분 정한다 |

### 4층 — 네이버 스니펫: 평가가 아니라 **속성**을 추출한다 `[V1 제외]`

컨셉·분위기를 판별할 유일한 외부 근거다. 다만 **무엇을 요약시키느냐**가 성패를 가른다.

요약 프롬프트가 "이 장소가 좋은가 / 어떤 분위기인가"를 물으면 협찬 문구를 그대로 받아 적는다.
대신 **원문에 사실로 적힌 물리적 속성만** 뽑는다.

| 뽑는다 (사실) | 버린다 (평가) |
|---|---|
| 야경, 루프탑, 한옥, 통창 | 분위기 최고, 강추 |
| 웨이팅 있음, 주차 어려움 | 재방문 의사 100% |
| OO역 도보 5분, 좌석 20석 | 인생 맛집 |
| 반려동물 동반, 아이 의자 | 감성 뿜뿜 |

**협찬 글에도 이런 사실은 정확하게 적혀 있다.** 광고비가 "루프탑이 있다"를 바꾸지는 못한다.
편향은 평가어에 실리지 속성에는 잘 실리지 않는다.

부수적으로 얻는 것이 하나 더 있다 — **접근성 정보**다. "황리단길 도보 5분", "주차장 협소" 같은
문구는 블로그에 흔한데 카카오 좌표만으로는 절대 나오지 않는다. `travelMode: WALK`(뚜벅이)일 때
직접적으로 유용하다.

**블로그 `title`이 `description`보다 신호가 강할 수 있다.** SEO 목적으로 특징을 압축해 넣기
때문이다 — "경주 황리단길 야경 예쁜 루프탑 카페 OO" 같은 제목이 실제로 많다. 100자 스니펫보다
밀도가 높다.

**`traits`는 닫힌 태그 집합에서만 고르게 강제한다.** 자유 텍스트로 두면 요약 단계 자체가 새로운
환각 지점이 되고 테스트도 불가능해진다.

| 범주 | 태그 |
|---|---|
| 뷰/분위기 | `야경` `뷰맛집` `루프탑` `통창` `한옥` `레트로` `넓음` `아늑함` `조용함` `시끌벅적` |
| 접근성 | `역세권` `도보접근` `주차가능` `주차난` |
| 혼잡 | `웨이팅` `예약필수` `한적함` |
| 동반 | `반려동물동반` `아이동반` `단체가능` |
| 가격 | `저렴` `보통` `고가` |
| 시간 | `아침영업` `야간영업` `브레이크타임` |

**키워드 → traits 매핑은 결정론적 사전으로 처리한다.** 여기에 LLM을 또 쓸 이유가 없고(원칙 1),
사전은 순수 함수라 완전히 테스트 가능하다.

| 사용자 키워드 | 가점 traits | 감점 traits |
|---|---|---|
| `COUPLE`(연인) | 야경, 루프탑, 통창, 조용함, 뷰맛집 | 시끌벅적 |
| `FAMILY`(가족) | 주차가능, 아이동반, 넓음, 단체가능 | 웨이팅, 주차난 |
| `FRIENDS`(친구) | 시끌벅적, 단체가능, 야간영업 | – |
| `SOLO`(혼자) | 아늑함, 조용함, 한적함 | 단체가능 |
| `WALK`(뚜벅이) | 역세권, 도보접근 | – |
| `CAR`(자차) | 주차가능 | 주차난 |
| `HEALING`(힐링) | 조용함, 한적함, 뷰맛집 | 웨이팅, 시끌벅적 |
| `SENSIBILITY`(감성) | 통창, 한옥, 레트로, 루프탑 | – |
| `COST_EFFECTIVE`(가성비) | 저렴 | 고가 |
| `PREMIUM` | 고가, 뷰맛집 | 저렴 |

### 최종 랭킹 점수 `[V1 제외 — 3·4층과 함께]`

```java
rankScore = kakaoMatchScore                                  // 실존·이름·주소 일치도
          + popularity × slot.popularityWeight                // 3층
          + conceptScore × CONCEPT_WEIGHT                     // 4층 (traits ↔ 키워드 사전 매칭)
          - closedSuspicionPenalty;                           // 폐업 의심
```

**모든 보조 신호는 감점이지 하드 드롭이 아니다.** 블로그 언급 0건이 곧 폐업은 아니고(최근 오픈한
신규 매장일 수 있다), traits가 비어 있는 게 곧 부적합은 아니다. 후순위로 밀되 같은 슬롯에 다른
후보가 없으면 여전히 쓴다. **보조 신호를 필수 조건으로 승격시키지 않는다**가 원칙이다.

## CandidateRetrievalStage — 후보 풀 구성

**문제를 정확히 자르면 이렇다.** 초안 구조에서 GroundingStage는 정밀도(가짜 상호명 차단)만 풀고,
재현율("이 지역에 좋은 곳이 있는데 후보에 못 올라옴")은 아무도 안 푼다. 그래서 후보를 외부에서
공급한다. 풀은 세 출처로 구성되며, 슬롯 타입에 따라 쓰는 출처가 다르다.

| 소스 | 태그 | 확보하는 것 | 맹점 (다른 출처가 보완) | 적용 슬롯 |
|---|---|---|---|---|
| **네이버 지역검색 `sort=comment`** — `"{area} {searchHint}"` 기본 1회 + 스타일 modifier 1~2회, 각 상위 5건 | `SEEDED` | 리뷰 수 기준 **검증된 인기 장소**(인기 축), 슬롯당 8~15건. 좌표·주소·카테고리를 응답에서 승계 | 5건/쿼리 하드 실링(페이징 불가), 리뷰 많은 곳 편중(신규·숨은 명소 누락) | **전 슬롯** |
| **한국관광공사 TourAPI** — `locationBasedList2(anchor 좌표, r=20km, contentTypeId=12·14·28, 거리순)` | `LISTED` | 권역의 **관광지 커버리지와 분류**(`cat3` → 스타일 태그). 무인지 지역까지 균질. 좌표·주소를 응답에서 승계 | **인기도 없음**(정렬이 제목·수정일·거리순뿐), 상업 POI(카페거리·시장류) 미등록, 데이터 최신성 | **ATTRACTION · VIEWPOINT · STROLL · EXPERIENCE** |
| **Curator 파라메트릭 제안** | `SUGGESTED` | 로컬 검색 랭킹 밖의 **전국구 유명 장소** 회수(본점·명소) | 무인지 지역에서 환각 → 그라운딩 검증 필수 | 전 슬롯 |

**슬롯 타입별로 쓰는 출처가 다르다.** 상업 POI(식당·카페·쇼핑)와 관광지는 데이터의 모양이 달라
같은 소스로 덮을 수 없기 때문이다.

| 슬롯 | 커버리지·분류 축 | 인기 축 | 회수 |
|---|---|---|---|
| MEAL · CAFE · SHOPPING | 네이버 시더 (시드 호출이 겸함) | 네이버 시더 | 파라메트릭 |
| ATTRACTION · VIEWPOINT · STROLL · EXPERIENCE | **TourAPI** | 네이버 시더 | 파라메트릭 |

**출처들이 서로의 맹점을 상쇄한다.** 시더가 없으면 무인지 지역에서 파라메트릭이 모르는 좋은 곳이
후보에 못 오르고, TourAPI가 없으면 관광지 후보가 파라메트릭에만 기대며, 파라메트릭이 없으면 유명
장소가 로컬 검색 랭킹에 밀려 빠진다. 그리고 **어느 소스가 죽어도 나머지로 코스가 성립하고, 전부
죽으면 정확히 초안 구조(회상 + 그라운딩)로 degrade된다** — 새 hard fail 지점이 늘지 않는다(부분 실패 전략).

**provider별 역할은 한 줄로 정리된다.** 후보를 *고르는* 곳과 후보를 *검증·보강하는* 곳이 다르다.

| provider | 역할 | 후보 선택에 관여? |
|---|---|---|
| **네이버 지역검색** | 후보 공급 — 전 슬롯의 인기 축 (시드 + 스타일 modifier). 좌표·주소·카테고리 승계 | 예 |
| **TourAPI** | 후보 공급 — 관광 슬롯의 커버리지·분류 축. 좌표·주소·`cat3` 승계 | 예 |
| **카카오 Local** | `SUGGESTED` 실존 검증 · 배치 장소 URL 보강 · `anchor` 지오코딩 | 아니오 |
| **LLM 파라메트릭** | `SUGGESTED` 제안 (목록 밖 유명 장소 회수) | 예 |

카카오가 후보 소스에서 빠진 근거는 아래 "카카오 커버리지 검색을 후보 소스에서 뺀 이유"에, TourAPI를
관광 슬롯에 채택한 근거는 "ATTRACTION 계열 슬롯 — TourAPI 커버리지"에 있다.

**시더가 필요한 이유 — 카카오에는 인기도 정렬이 없다.** 카카오 Local API의 `sort`는 `accuracy`와
`distance` 둘뿐이고 응답에 평점·리뷰 수 필드도 없다(배경의 근본 원인 6번과 같은 사실). 황리단길 반경에
카페가 수백 개일 때 상위 10개는 "가까운 순" 또는 "비공개 기준의 정확도순"으로 잘리고, 진짜 좋은
곳이 풀에 아예 안 들어올 확률이 밀집 지역일수록 오른다. **사후 랭킹이 아무리 좋아도 풀에
없는 장소는 못 올린다.** 그래서 풀에 요구되는 건 "완벽한 정렬"이 아니라 **"인기 있는 곳의 포함"**
(seeding)이다 — 이 구분이 중요한 이유는 풀 전체를 네이버로 랭킹하면 쿼터가 폭발하지만(기각한 대안 "풀 전체
사전 랭킹" 참고) 상위 몇 개를 심는 건 슬롯당 호출 1회면 되기 때문이다. 그리고 **시드 순위 자체가
인기도 순위**이므로, 시딩이 들어온 뒤에는 인기도를 사후에 다시 잴 이유가 사라진다(아래 "PlaceSignal을
V1에서 제외한 이유").

**시더는 전 슬롯에 적용한다.** 이 절의 이전 판은 시더를 MEAL/CAFE에만 두었다 — 밀집·임의 슬라이스
문제가 식당·카페에서 나고, 관광지는 지식 신호 층에서 인기도 가중치 0.2("대릉원·첨성대 둘 다
수십만 건이라 구분이 안 된다")를 받은 슬롯이니 시더 비용을 쓸 이유가 없다는 근거였다. 이 근거는
**랭킹**에 대한 것이었고, 시딩은 **포함**의 문제라 다르다. 유명 지역에서는 맞다 — 대릉원과 첨성대는
파라메트릭도 알고 순위를 가를 필요도 없다. 그러나 무인지 지역에서는 TourAPI 관광지 목록의 대부분이
작은 사찰·마을 유적이고 파라메트릭도 모르는 이름이라, "그중 사람들이 실제로 가는 5곳"이라는 시드가
없으면 Curator는 무명 목록에서 감으로 고르게 된다. **시더는 폴백이 아니라 관광 슬롯에서도 정규
축이다.** 유명 지역에서 파라메트릭과 겹쳐 잉여가 되는 대가는 슬롯당 1회·`(area, slot)` 캐시라 거의 없다.
쿼리는 슬롯의 `searchHint`(`"관광명소"`·`"전망대"`·`"산책로"`·`"체험"`)를 그대로 쓰고, 스타일 modifier
규칙도 동일하다.

**SEEDED는 네이버 응답을 그대로 그라운딩 데이터로 쓴다 — 카카오로 다시 바꾸지 않는다.** 초안은
"네이버 상호명 → 카카오 검색으로 공식화"였는데, 이건 후보가 전부 파라메트릭이라 실존·좌표를 얻을 곳이
카카오뿐이던 시점의 잔재다. 지역검색 응답에는 이미 `mapx`/`mapy`(WGS84)·`roadAddress`·`category`가
있다. 손에 쥔 정보를 버리고 상호명으로 다시 사러 가는 셈이므로, **그라운딩의 역할을 "카카오 검색"이
아니라 "실존 확인 + 좌표 확보"로 재정의**하고, 그 역할을 SEEDED는 네이버 응답이, LISTED는 TourAPI
응답이, SUGGESTED만 카카오 검색이 채운다. 대차대조표는 이렇다:

| 카카오 재검색을 안 하면 잃는 것 | 무게 |
|---|---|
| `kakaoId` 기반 dedupe | 가볍다 — MEAL/CAFE는 provider가 네이버 하나라 기본/modifier 쿼리 간 중복만 정규화 상호명 + 도로명주소로 잡으면 되고, 관광 슬롯의 시더↔TourAPI 매칭은 아래 "시더 ↔ TourAPI 병합"의 규칙(좌표 + 이름)으로 처리한다. `Place` 엔티티는 kakaoId를 저장하지도 않는다 |
| `category_group_code` 하드 제약 | 가볍다 — 네이버 `category` 최상위 분류 매핑으로 대체(지식 신호 층의 2층) |
| 카카오 플레이스 URL | **가볍지 않다.** FE가 `placeUrl`로 카카오 플레이스에 진입하므로 최종 장소에는 필요하다. 그래서 **배치된 장소 중 URL이 빈 것만** `PlaceUrlEnricher`가 따로 채운다(아래) — 후보 45개가 아니라 ~10~15개에만 호출 |
| 좌표 체계 | 없음 — 둘 다 WGS84, 10⁷ 나눗셈 한 번 |

**네이버 지역검색 응답의 실무적 제약** (남는 한계의 착수 전 실호출로 확정)
- `title`에 검색어 매칭 `<b>` 태그가 섞여 온다 → 상호명으로 쓰기 전 **태그 스트립 필수**
- `mapx`/`mapy`는 WGS84 × 10⁷ 정수 문자열(카텍에서 변경 공지) → 나누어 그대로 좌표로 쓴다.
  공지 기반이라 실응답이 다를 수 있으니 4단계 실호출 때 확정한다
- 항목에 고유 ID가 없다 → dedupe 키는 상호명+주소. 네이버 플레이스 URL도 조립할 수 없어 SEEDED는
  URL이 비어 있고, 이것이 `PlaceUrlEnricher`가 필요한 이유다
- `description`·`telephone`은 대부분 빈 값 (V1에서는 쓸 곳이 없다)
- `start`가 1로 고정이라 **6위 이하는 어떤 방법으로도 못 받는다.** 풀을 넓히는 유일한 축은 쿼리
  변주(각 5건 → dedupe)이고 변주 1개당 쿼터 1회다. 그 변주 예산을 업종 세분화(`"브런치"`·
  `"디저트"`)가 아니라 **스타일 modifier**(아래)에 쓴다 — 스타일 축이 풀에 없으면 뒤에서 아무리
  선별해도 못 살리는 반면, 업종 세분화는 슬롯 `searchHint`가 이미 상당 부분 감당하기 때문이다

**`SEEDED`/`LISTED` 위조 방어 — LLM 출력을 신뢰하지 않는다.** 선별 과제라도 LLM 출력인 이상 "목록에서
골랐다"고 주장하며 목록에 없는 상호명을 내놓을 수 있다. 그래서 목록 후보는 상호명이
아니라 **`listIndex`(목록 인덱스)로 참조**하게 하고, 코드가 세 가지를 검증한다 — ① `listIndex`가
범위 안인가 ② 그 인덱스의 목록 항목 상호명과 응답 `placeName`이 일치하는가(모델이 인덱스는 맞게
쓰고 이름을 바꿔 쓰는 경우) ③ 슬롯 타입이 목록의 슬롯 타입과 같은가. **하나라도 어긋나면 그
후보를 `SUGGESTED`로 강등해 기존 그라운딩 검증 경로로 보낸다** — 버리지 않고 강등하는 이유는
이름이 실존할 수도 있기 때문이고, 강등 건수를 메트릭으로 세면 Curator 프롬프트가 목록을 얼마나
잘 따르는지의 지표가 된다(관측 설계). "재검증 생략"의 전제는 목록 항목의 좌표·주소·카테고리(SEEDED는
네이버, LISTED는 TourAPI 응답)를 **코드가** 승계하는 것이지 LLM이 옮겨 적는 것이 아니다 — 좌표·ID·URL은
응답 스키마에 아예 없다.

**Curator의 출력 순서가 최종 순위다.** 후보 3개를 **선호 순서로** 내게 하고, RouteOptimizer는 슬롯당
그라운딩을 통과한 1순위를 배치한다(탈락하면 2순위). 사후 재정렬 층(PlaceSignal)이 없으므로 이
순서가 곧 "어느 후보가 코스에 들어가는가"를 정한다 — 프롬프트에 **"SEEDED를 우선하고, SUGGESTED는
확신할 때만 앞에 둔다"**를 명시해 무명·폐업 장소가 1순위로 오는 것을 LLM 층에서 막는다. 이 규칙이
초안에서 3층 인기도 감점이 하던 일을 0원에 대신한다.

**튜닝해야 하는 반경 파라미터를 두지 않는다.** 좌표 + 작은 반경으로 검색하는 방식은 Planner의 `area`
("황리단길·대릉원 일대" vs "경주 시내")에 따라 적정 반경이 자릿수로 달라 튜닝 불가능한 파라미터가
하나 생긴다. 네이버 지역검색은 **텍스트 기반 `"{area} {searchHint}"`**라 검색 엔진이 지역명을 스스로
해석하고 반경이라는 개념 자체가 없다. TourAPI는 좌표를 받지만 **반경을 최대(20km)로 고정하고 거리순
정렬 + 상위 N건 cap**으로 쓴다 — 이때 반경은 품질을 가르는 절단선이 아니라 넓은 울타리이고, 실질
필터는 "가까운 순"이라 정할 숫자가 없다(아래 "area → 좌표"). 두 방식 모두 "반경을 몇 km로 할 것인가"를
묻지 않는다는 점에서 같다.

**카카오 커버리지 검색을 후보 소스에서 뺀 이유.** 이 절의 이전 판은 네이버 시더 옆에 카카오 키워드
검색(`LISTED`, 전 슬롯 ~10건)을 "커버리지" 소스로 두었다. 그 근거를 하나씩 다시 저울질하면 대부분
소멸해 있었다.

| 카카오 커버리지의 원래 근거 | 다시 보면 |
|---|---|
| 네이버는 쿼리당 5건 하드 실링이라 풀이 좁다 | 스타일 modifier 쿼리로 슬롯당 **8~15건**이 확보된다. Curator는 3개를 고를 뿐이라 충분하다 |
| 무인지·저리뷰 지역에서 시더가 빌 수 있다 | 네이버 플레이스의 국내 업소 커버리지는 카카오와 대등하거나 낫다. `"{area} 카페"`가 0건인 지역은 카페가 실제로 없는 곳이다 |
| 숨은 명소·신규 매장 보완 | 카카오 `accuracy`/`distance` 정렬은 "숨은 좋은 곳"이 아니라 **임의 슬라이스**다. 처음부터 품질을 담는 소스가 아니었다 |
| 좌표·업종·URL 즉시 확정 | SEEDED도 네이버 좌표·카테고리를 승계하므로 차이 없음. URL은 어차피 `PlaceUrlEnricher`가 배치 장소만 채운다 |

**남는 건 "네이버가 죽었을 때의 이중화"뿐인데, 그건 fail-open 원칙이 이미 처리한다** — 후보 공급이
비면 Curator가 파라메트릭(`SUGGESTED`)만 내고 그라운딩이 검증하는 초안 구조로 degrade하고, 코스는
성립한다. 장애 시간 동안 품질이 초안 수준으로 내려가는 것과, 평시에 항상 잡음 소스 하나를 더 합치고
provider 간 dedupe·소스 클래스·실패 분기를 유지하는 것 — 후자가 비싸다. 빼면 **provider별 역할이
한 줄로 정리되고**(위 표), 같은 슬롯 타입 안에서 provider가 하나이므로 cross-provider dedupe가
사라지며, Curator 입력 토큰도 준다.

실측 항목 하나는 남긴다: `ai.candidate.retrieval{result=empty}`가 특정 지역·슬롯에서 실제로 자주
찍히면 그때 "네이버 0건 또는 실패일 때만 카카오"를 폴백으로 붙인다. 트리거가 "0건/실패"라 튜닝
파라미터가 아니고, 카카오 클라이언트는 검증·URL용으로 어차피 있으니 분기 하나면 된다. 지금 미리
넣지는 않는다.

**스타일 modifier 쿼리 확장 — 풀 자체가 스타일을 알아야 한다.** 풀을 위처럼만 구성하면
후보 공급 쿼리가 `"{area} {searchHint}"`로 **스타일 무관**이라, 사용자 키워드는 Curator 선별에서만
작동한다. 그런데 선별은 **풀 안에서만** 움직인다 — 황리단길 카페 300개 중 스타일 무관 쿼리로 5개가
들어왔는데 그 안에 루프탑·야경 카페가 하나도 없으면, `연인·감성` 요청에서 Curator는 평범한 5개 중
"그나마 나은 3개"를 고르는 수밖에 없다. 인기도에 대해 위에서 쓴 논리("풀에 없는 장소는 사후 선별이
못 올린다")가 스타일에도 그대로 적용되는 것이다. **풀이 천장이고 선별은 천장 아래에서만 움직인다.**
스타일 영향력이 실질적으로 `SUGGESTED`(파라메트릭) 하나에 의존하게 되는데, 그건 무인지 지역에서
약해지는 바로 그 경로다.

그래서 **후보 공급 쿼리에 스타일 수식어를 넣는다.** 네이버 지역검색은 텍스트 기반이라
`"황리단길 루프탑 카페"`, `"황리단길 조용한 카페"` 같은 쿼리가 자연스럽다. 핵심은 **새
어휘를 만들지 않고 지식 신호 층의 traits 닫힌 태그 집합과 키워드→traits 사전을 그대로 재사용**하는 것이다:

```
사용자 키워드 ──(지식 신호 층 키워드→traits 사전, 결정론)──► 가점 traits 상위 1~2개 ──► modifier
  COUPLE       → 야경, 루프탑          → "황리단길 야경 카페", "황리단길 루프탑 카페"
  HEALING      → 조용함, 뷰맛집        → "황리단길 조용한 카페", "황리단길 뷰맛집"
  SENSIBILITY  → 한옥, 레트로          → "황리단길 한옥 카페"
  FAMILY       → 주차가능, 아이동반    → "황리단길 주차 식당", "황리단길 아이동반 식당"
```

풀 = **기본 쿼리 결과 ∪ 스타일 쿼리 결과**(대체가 아니라 합집합). 스타일 쿼리에서 온 후보에는
`matchedModifier: "야경"`을 달아 Curator에게 힌트로 넘기되, 프롬프트에 **"검색이 그렇게 주장했다는
힌트일 뿐 검증된 속성이 아니다"**를 명시한다. 사전은 이미 순수 함수·테스트 대상이라 새로 검증할
것도 없고(원칙 1), LLM 호출은 한 번도 늘지 않는다.

**정직하게 남는 한계 — 스타일 쿼리는 "주장"을 끌어오는 것이지 "사실"을 확인하는 게 아니다.**
`"황리단길 야경 카페"`로 검색되는 가게는 실제로 야경이 좋은 곳과 SEO로 그 키워드를 심어둔 곳이
섞여 있다. 초안의 4층(블로그 스니펫에서 `야경`이 사실로 적혔는지 추출)이 정확히 이 검증을 맡을
자리였고, 그래서 이 확장을 처음 설계할 때는 "retrieval(재현율) ↔ 4층(정밀도)의 대칭"으로 정당화했다.
**4층을 V1에서 빼면서 그 검증은 사라졌다.** 남은 방어선은 두 겹이다 — ① Curator가 `matchedModifier`를
힌트로만 보고 파라메트릭 지식과 대조한다(유명 지역에서는 실제로 작동하고, 무인지 지역에서는
약하다) ② `ai.candidate.adopted{modifier}` + 사용자 삭제 로그로 **스타일 쿼리 유래 장소의 삭제율**을
잰다. 이 삭제율이 기본 쿼리 유래보다 유의미하게 높으면, 그것이 SEO 편승이 실제 문제라는 증거이고
4층을 켜는 조건이 된다(도입 순서 9단계). **위험을 모르는 채로 검증 비용을 선불하는 대신, 위험이 실측되면
검증을 사후 투입한다** — 이 순서가 이 절 전체의 태도다.

- **적용 범위**: 시더와 같이 전 슬롯. 네이버 지역검색이 `"조용한"` 같은 서술어를 실제로
  매칭하는지는 아래 실측 항목이다. 관광 슬롯의 스타일은 여기에 더해 TourAPI `cat3` → 스타일 태그
  매핑(아래 "`cat3` → 스타일 태그")이 코드 기반으로 보완한다
- **fail-open**: 스타일 쿼리가 0건이면 기본 쿼리 결과만으로 진행. modifier가 결과를 좁히는 방향
  (`가성비`)이라 빈 결과가 흔할 수 있는데, 합집합이므로 풀이 줄어드는 일은 없다
- **캐시 키**는 `(area, slotType, modifier)`. 히트율은 기본 쿼리보다 낮지만 같은 스타일 조합의
  사용자끼리는 여전히 공유된다
- **호출**: 슬롯당 기본 1 + 스타일 1~2 → 네이버 지역검색 코스당 ~9~12회 → **~18~30회**(전 슬롯). 위
  "쿼리 변주는 스타일 modifier에 쓴다"가 정확히 이 예산이다

**확정 전 실측이 필요한 지점 — 네이버 지역검색이 서술어를 어디에 매칭하는가.** 상호명·카테고리만
매칭하면 스타일 쿼리가 거의 빈 결과를 돌려주고(그러면 이 확장은 fail-open으로 조용히 무력화된다),
네이버 플레이스의 리뷰·태그까지 반영하면 강력한 채널이 된다. 4단계 `NaverLocalClient` 실호출 확정
때 `"황리단길 카페"` vs `"황리단길 루프탑 카페"`의 결과 건수·겹침·`total`을 같이 잰다(남는 한계). 결과가
나쁘면 대안은 아래 "추후 개선"의 Planner 태그가 아니라 — 그건 쿼리 어휘 문제이지 채널 문제가
아니므로 — 스타일 축을 retrieval에서 포기하고 Curator 선별(파라메트릭 + `SUGGESTED`)에만 맡기는
것이며, 그 경우에도 이 절의 나머지(시더·커버리지·위조 방어)는 그대로 유효하다. 그때는 4층을
되살리는 것이 스타일 축을 되찾는 유일한 길이 되므로 도입 순서 9단계 착수 조건에 이 경우를 포함한다.

> **추후 개선 — Planner가 day별 스타일 태그를 직접 낸다.** 위 사전 방식은 결정론적이고 테스트
> 가능하지만 **문맥을 모른다** — 사용자 키워드가 `힐링`이면 3일 내내 같은 `조용함·뷰맛집` modifier를
> 던지는데, Planner는 이미 day 1을 "한옥 골목 산책과 야경", day 2를 "바다 뷰 드라이브"로 갈라놓았다.
> 사전은 day 1에 `한옥·야경`, day 2에 `뷰맛집·주차가능`을 던져야 한다는 것을 알 수 없다.
> Planner의 `dayPlans[]`에 **traits 닫힌 태그 집합에서만 고른 `styleTags`(스키마 `enum` 배열, 최대
> 3개)**를 추가하면 그 문맥이 modifier로 흐른다 — Planner는 셋 중 유일하게 추론 투자를 정당화한
> 에이전트(LLM 포트 설계)라 이 판단을 맡길 자리로도 맞고, 태그가 닫힌 집합이라 지식 신호 층 traits 어휘와의 일관성도
> 유지된다(4층을 나중에 켜도 같은 어휘로 검증할 수 있다).
> **그럼에도 V1은 사전으로 가는 이유**: ① 원칙 1 — 결정론으로 되는 일에 LLM을 먼저 쓰지 않는다
> ② Planner 스키마가 커지면 Planner 실패 시 폴백(부분 실패 전략의 결정론적 기본 플랜)에도 `styleTags` 기본값이
> 필요해져 실패 표면이 하나 는다 ③ 사전이 문맥을 못 잡아 부족한지는 **실측으로만 알 수 있다** —
> `ai.candidate.adopted{source}`에서 스타일 쿼리 유래 후보의 채택률이 day별로 크게 갈리면(예: 바다
> 권역 day에서 `조용함` 쿼리 후보가 전혀 채택되지 않음) 그때 켤 근거가 생긴다. 켤 때의 형태는
> "사전을 Planner 태그로 대체"가 아니라 **"사전 태그 ∪ Planner 태그"**의 합집합이다 — Planner가
> 태그를 비우거나 실패해도 사전이 바닥을 깐다.

**호출 수와 지연.** 코스당 네이버 지역검색 ~18~30회(3일 × 슬롯타입 3~4종 × (기본 1 + 스타일 1~2)),
TourAPI ≤9회(고유 anchor ≤3 × contentTypeId 3 — 격자 캐시로 대부분 히트), 카카오 지오코딩 ≤3회.
기본 쿼리 캐시 키는 `(area, slotType)`, 스타일 쿼리는 `(area, slotType, modifier)`, TourAPI는
`(~1km 격자, contentTypeId)`라 인기 권역은 사용자 간 공유되므로 **장소 단위 캐시(코스마다 조합이
다름)보다 히트율이 훨씬 높다.** 카카오는 사후 검증이 후보 45개 전량 → **SUGGESTED만**(코스당
~5~15개, 무인지 지역일수록 적다)으로 **줄고**, URL이 빈 배치 장소의 보강 ~10~15회와 지오코딩이 붙어 총
~20~33회 — 초안(~45회)보다 적다(지연 예산·비용 분석 갱신). 네이버 블로그 호출은 PlaceSignal 제외로 **0회**다.
지연은 Planner 직후 병렬 1라운드(+0.4~0.8s)가 추가되지만 그라운딩 라운드가 얇아지고 PlaceSignal
(네이버 조회 + LLM 배치 2~4초)이 통째로 빠져 **초안보다 3~5초 짧다**.

**`PlaceUrlEnricher` — URL이 빈 장소에만, 틀리느니 비운다.** FE가 `placeUrl`로 카카오 플레이스에 진입하므로
최종 장소에는 카카오 URL이 필요하다. **`SUGGESTED`는 그라운딩에서 이미 받았다** — 카카오 키워드 검색
응답에 `place_url`이 필드로 들어 있으므로, 실존 검증에 성공한 순간 좌표·주소와 함께 URL도 승계한다.
같은 장소를 두 번 부르지 않기 위해서다. 남는 것은 카카오를 거치지 않은 `SEEDED`(네이버 승계)와
`LISTED`(TourAPI 승계)이고, RouteOptimizer가 배치를 확정한 뒤 **그중 URL이 빈 장소에만**
`"{상호명} {지역}"`으로 카카오 키워드 검색 1회씩을 던진다(~10~15회).
**수락 조건은 두 개다** — 기존 이름 일치 게이트(1단계에서 점수 하한선을 대체했다 — 로드맵 1-2) **그리고** 카카오 좌표와 후보
좌표(네이버 또는 TourAPI)의 거리 ≤ 300m. 둘 다 통과할 때만 URL을 붙이고, 아니면 `null`로 둔다. 후자 조건이 있는 이유는
같은 상호명의 다른 지점(전국구 프랜차이즈·동명 업소)에 URL을 붙이는 실수를 막기 위해서다 —
좌표를 두 소스에서 갖게 된 덕에 공짜로 생긴 교차 검증이다. **엉뚱한 장소 URL은 URL 없음보다
나쁘다.** 배경이 "환각을 실존하는 엉뚱한 장소로 세탁한다"고 비판한 그 실수를 URL 필드에서 반복하지
않는다. fail-open — 카카오 장애 시 URL만 비고 코스는 성립한다.

**Curator 입력 토큰 증가는 감수한다.** 후보 목록 슬롯당 8~25개(MEAL/CAFE 8~15, 관광 슬롯은 병합 후
cap 20~25) × 3~4슬롯 × (이름+태그+거리) ≈ day당 +900~1,500토큰. 비용 분석 정정에서 "금액을 지배하는 것은 Curator의 **출력**(62%)"이라고 실측했으므로
입력 증가의 금액 영향은 작고, 선별 과제는 회상 과제보다 출력이 안정적이라 의미 재시도가 줄어들
여지도 있다.

**정직하게 남는 한계 — 시더의 협찬 편향.** 리뷰 수 정렬은 마케팅이 몰린 가게를 상위에 올린다.
다만 지식 신호 층이 `total`에 대해 정리한 논리가 그대로 적용된다 — "협찬이 많다는 건 최소한 사람들이 가는
곳이라는 신호이고, 이 층에 필요한 건 무명 vs 유명의 변별력뿐이다." 시더가 뽑은 후보도 Curator의
컨셉 선별을 통과해야 하므로, 편향은 "풀에 들어오는 것"까지만 영향을 주고 "선택되는 것"은 별도
관문이 있다. (초안에서는 4층 traits가 관문 하나를 더 놓았으나 V1에서 제외했다 — 아래.)

**TourAPI 쪽 한계도 적어둔다.** 시더↔TourAPI 매칭 임계값(300m·이름 유사도)과 `arrange` 거리순의 실제
동작, `cat3` vs 신 분류체계, 상권형 명소(황리단길·감천문화마을류)의 등록 여부는 전부 4단계 실호출로
확인해야 하는 가정이다. 개발계정은 일 1,000건이라 운영 전에 활용사례 등록으로 증량 승인을 받아야
하고, 승인에 며칠이 걸린다. 그리고 관광 슬롯의 품질 신호는 이제 "시더 5건 + TourAPI 분류"인데, 그게
실제로 충분한지는 사용자 삭제 로그(`seeded`/`official` 태그별)로만 확인할 수 있다.

### ATTRACTION 계열 슬롯 — TourAPI 커버리지

식당·카페에서 풀었던 문제는 "후보가 수백 개인데 품질 무순으로 잘린다"(밀집 → 시딩으로 해결)였다.
관광지는 정반대다.

| | MEAL / CAFE | ATTRACTION 계열 |
|---|---|---|
| 상업 POI 검색(카카오 `AT4`류) | 수백 건 | **희소하고 잡음** — 관광지·전망대·공원·놀이시설이 섞이고, 무인지 지역은 몇 건 안 나옴 |
| 파라메트릭 | 무인지 지역에서 약함 | 유명 관광지엔 가장 강함, **무인지 지역의 작은 명소는 모름** |
| 스타일 | 텍스트 modifier가 자연스러움 | 자연/역사/체험 같은 성격은 텍스트보다 **분류 코드**가 정확함 |

즉 관광 슬롯의 공백은 정렬이 아니라 **커버리지와 분류**이고, 그 둘이 한국관광공사 TourAPI의
강점이다 — 전국을 행정단위로 균질하게 덮고(약 26만 건), `contentTypeId`(12 관광지 / 14 문화시설 /
28 레포츠)와 `cat1~cat3` 세분류(자연관광지·역사관광지·휴양관광지·체험관광지·건축/조형물 등)를 갖는다.
무료이고 저장 제약이 없어 이 서비스의 영구 저장 구조와도 맞는다(구글·TripAdvisor를 결격 처리한
이유가 저장 약관이었다 — 기각한 대안).

TourAPI가 못 하는 것도 분명하다. **인기도 정렬이 없다**(`arrange`는 제목·수정일·생성일·거리순).
그래서 시더를 관광 슬롯까지 확장해 인기 축을 붙인다(위 "시더는 전 슬롯에 적용한다"). 또 상업형
명소(카페거리·시장·포토스팟)는 등록이 불완전할 수 있는데, 그건 시더가 잡는다 — 네이버 단독 후보로
풀에 남는다. 공공 데이터라 폐업·이전 반영이 느리지만 관광지는 폐업이 드물어 감수하고, `modifiedtime`이
오래된 항목은 표시만 한다(감점, 하드 드롭 아님).

적용 슬롯은 **ATTRACTION·VIEWPOINT·STROLL·EXPERIENCE**(12·14·28)다. SHOPPING은 상업 POI라 시더만 쓴다.
축제·행사(`contentTypeId=15`, 여행 날짜 매칭)는 이 API만 할 수 있는 일이지만 V1에서는 뺀다 —
근거와 재검토 조건은 남는 한계에 있다.

### area → 좌표: Planner `anchor`와 지오코딩

TourAPI는 텍스트 지역명을 받지 않는다. 지역으로 받는 방식은 둘 — `areaBasedList2`(시도·시군구 코드)와
`locationBasedList2`(좌표 + 반경). **후자를 쓴다.** 전자는 Planner의 `area`를 시도·시군구 코드로 바꾸는
코드표와 이름 매칭("경북"/"경상북도" 별칭, 통합시 등)이 필요하고, 시군구 목록을 통째로 받은 뒤 day별
권역으로 다시 걸러야 하며(그 필터는 결국 중심점 거리다), 속초·양양처럼 시군구 경계에 걸친 권역을
못 다룬다. 좌표 기반은 이 셋이 전부 사라진다 — day별 권역 필터가 조회 자체에 내장된다.

좌표를 얻으려면 권역의 중심점이 필요한데, `"황리단길·대릉원 일대"` 같은 자연어를 그대로 지오코딩하면
가운뎃점·"일대"가 붙은 구라 결과가 흔들린다. 그래서 **Planner 응답에 `anchor` 필드를 추가한다** —
그 권역 안의 구체적 랜드마크 이름 하나("대릉원"). Planner는 어차피 랜드마크 단위로 사고하고, `"{location}
{anchor}"`를 카카오 키워드 검색에 넣으면 거의 항상 정확히 맞는다. `area`는 사람이 읽는 라벨이자
네이버 쿼리 접두사로 그대로 둔다 — **`area`를 시군구로 바꾸는 안은 반대다.** `area`의 역할은 한 도시를
day 단위 권역으로 쪼개는 것(황리단길 / 보문단지 / 감포는 전부 "경주시")이라 locality를 잃는다.

```
① 지오코딩   카카오 키워드 검색 "{location} {anchor}" → 대표 장소 좌표 (x, y)     캐시 키 = anchor 텍스트
② TourAPI    locationBasedList2(x, y, radius=20000, contentTypeId=12|14|28, 거리순, numOfRows=50)
             → 권역에 가까운 순서의 관광지 목록. 캐시 키 = (~1km 격자 좌표, contentTypeId), TTL 7일
③ 후보마다   anchor로부터의 distanceKm 를 실어 Curator 입력으로
```

3일 내내 같은 도시면 anchor가 달라도 격자가 겹쳐 캐시 히트가 잦고, 시군구가 갈리는 여행은 자연히
다른 좌표로 조회된다. 실패는 캐스케이드다: `anchor` 지오코딩이 **무결과면** `area` 텍스트 → `location` 순으로 넘어가고, **호출 자체가 실패하면 캐스케이드를 중단한다**(같은 API가 죽었는데 다른 쿼리로 재시도할 이유가 없다). 전부
실패하면 TourAPI를 건너뛰고 시더 + 파라메트릭으로 진행한다. Planner가 없는 랜드마크를 지어내도
카카오가 못 찾으면 다음 단계로 넘어가니 환각이 파이프라인에 박히지 않는다. Planner 실패 시 결정론적
기본 플랜은 `anchor = location`이다.

### `cat3` → 스타일 태그 결정론 매핑

`cat3`는 TourAPI가 모든 항목에 붙이는 3단계 분류의 소분류다(대분류 `A01 자연`/`A02 인문`/`A03 레포츠`
→ 중분류 `A0101 자연관광지`·`A0201 역사관광지`·`A0203 체험관광지`… → 소분류 폭포·계곡·해수욕장·고택·
사찰·테마공원·전망대·박물관…). 관광지가 "무엇인지"를 코드가 이미 말해주므로, 검색어에 기대지 않고
**지식 신호 층의 traits 닫힌 태그 집합으로 옮기는 결정론 사전**을 둔다.

| `cat3` 예시 | → 스타일 태그 | 어울리는 키워드 |
|---|---|---|
| 폭포·계곡·자연휴양림·수목원·호수 | `자연` `조용함` `한적함` | 힐링, SOLO |
| 해수욕장·해안절경·섬·전망대 | `뷰맛집` (전망대는 +`야경`) | 연인, 감성 |
| 고택·민속마을·사찰·고궁 | `한옥` `역사` `조용함` | 감성, 힐링 |
| 테마공원·전통체험·농어촌체험 | `아이동반` `액티비티` | 가족, 친구 |
| 이색거리·시장 | `시끌벅적` `도보접근` | 친구, 뚜벅이 |
| 박물관·미술관·공연장 | `문화` `실내` | 감성 (우천 대안) |

쓰임새는 필터가 아니라 **표시**다 — 풀을 자르지 않고 후보마다 `styleTags`를 달아 Curator 입력에 넣고,
사용자 키워드와 맞으면 목록 정렬에서 앞으로 온다(아래). 합집합·감점 원칙 그대로다. 야경처럼 코드에
없는 속성은 여전히 시더의 modifier 쿼리가 맡으니 둘은 보완 관계다. 4층을 나중에 켜면 같은 어휘로
검증한다. 분류체계는 `cat1~3`과 게이트웨이 이관 후 추가된 새 체계가 공존하는 것으로 알려져 있어,
어느 쪽을 쓸지와 코드표는 4단계 실호출(`categoryCode2`)로 확정한다.

### 시더 ↔ TourAPI 병합과 Curator 입력 목록

관광 슬롯에서는 두 소스가 같은 장소를 자주 가리킨다(대릉원은 양쪽에 다 있다). **중복은 제거가 아니라
병합**이다 — 한쪽을 버리면 정보를 잃는다. TourAPI는 분류·정비된 좌표를, 네이버는 "사람들이 간다"는
신호를 갖고 있으니, 매칭되면 하나의 후보로 합치고 표식을 둘 다 붙인다.

```
후보 레코드 (병합 후)
  name           : TourAPI 정식 명칭 우선
  coord / addr   : TourAPI 값 우선, 없으면 네이버
  official       : true (TourAPI 등록)  → styleTags, distanceKm
  seedRank       : 1..5 또는 null      (네이버 sort=comment 순위)
  matchedModifier: 스타일 쿼리에서 왔으면 그 태그
```

**매칭 규칙은 좌표와 이름을 둘 다 본다** — 하나만 쓰면 틀린다. 좌표만 보면 대릉원 안의 천마총이
대릉원과 합쳐지고, 이름만 보면 전국에 수십 개인 "향교"가 서로 합쳐진다. 거리 ≤ 300m **그리고**
정규화 이름 유사(괄호·지역 접두사·공백 제거 후 포함 관계 또는 토큰 겹침). 관광지는 좌표가 입구냐
중심이냐로 수백 m 어긋날 수 있어 식당보다 넓게 잡고, 값은 4단계 실호출 표본으로 확정한다. 매칭 안 되는
항목은 양쪽 다 풀에 남는다 — 네이버 단독(카페거리·포토스팟)은 `SEEDED`, TourAPI 단독(작은 사찰·계곡)은
`LISTED`. 이 비대칭이 두 소스를 같이 쓰는 이유다.

**Curator에게 넘기는 목록은 순서 자체가 신호다.** LLM은 목록 앞쪽을 더 자주 고르는 위치 편향이 있다.
이걸 억누르지 않고 쓴다 — 우리가 우선 보이길 원하는 순서로 정렬해서 주면 점수 계산 없이도 인기도가
선별에 반영된다. 정렬은 가중치 합이 아니라 **사전식**이라 튜닝값이 없다.

| 순서 | 그룹 | 그룹 안 정렬 |
|---|---|---|
| ① | seed에 든 후보 (병합됐든 네이버 단독이든) | seedRank 오름차순 |
| ② | seed에는 없지만 `styleTags`가 사용자 키워드와 맞는 TourAPI 후보 | distanceKm 오름차순 |
| ③ | 나머지 TourAPI 후보 | distanceKm 오름차순 |
| | 여기까지 **20~25건에서 자른다** (Curator 입력 토큰 상한) | |

cap에 걸려 잘리는 건 항상 ③의 먼 곳이라, 토큰 상한 때문에 중요한 후보가 누락되는 일이 없다. 각 항목은
`[seed 2위] 대릉원 · 역사/한옥/조용함 · 0.4km` 같은 한 줄로 들어간다.

**Curator의 선별 규칙** — 프롬프트에 우선순위 순으로 적는다. 원칙 1을 지킨다: "무엇이 테마에 맞는가"는
LLM이, "무엇이 인기 있고 어디 있는가"는 데이터가.

1. **테마·키워드 적합이 1순위.** day 테마와 사용자 키워드에 맞는 것을 고른다. LLM만 할 수 있는 판단이다.
2. **적합한 후보가 여럿이면 seed 표식이 있는 쪽을 앞에 둔다.** 외부 인기 신호이고, 무인지 지역에서는
   파라메트릭이 모르는 것을 대신 알려준다. 단 테마와 충돌하면(힐링 요청에 시끌벅적한 야시장이 seed
   1위) 뒤로 보내도 된다 — **표식은 근거이지 명령이 아니다.**
3. **`distanceKm`이 작은 쪽을 선호한다.** day 권역 안에 머무르게 하기 위해서다. 동선은 RouteOptimizer가
   계산하니 정밀할 필요는 없다.
4. **목록 밖 제안(`SUGGESTED`)은 확신할 때만, 목록에 같은 곳이 없을 때만.** 유명 지역의 전국구 명소
   회수용이지 무인지 지역에서 이름을 지어내는 통로가 아니다.
5. **3개를 선호 순서로 낸다.** 1순위가 그라운딩을 통과하면 배치되고, 탈락하면 2순위. 이 순서가 최종이다.

인기도 신호가 쓰이는 곳과 안 쓰이는 곳을 분명히 해둔다 — PlaceSignal을 뺀 결정과 모순되지 않기 위해서다.

| 쓰인다 | 안 쓰인다 |
|---|---|
| **풀 포함** — 시드에 든 후보는 무조건 풀에 들어간다 (가장 큰 효과) | 점수 계산 (`rankScore` 같은 것 없음) |
| **목록 순서** — seed 그룹이 앞에 온다 | Curator 선택 뒤의 재정렬 |
| **Curator 입력 표식** — `[seed n위]`를 보고 규칙 2를 적용 | 하드 필터 (seed 없는 후보도 테마에 맞으면 얼마든지 선택) |

인기도는 **선별 전에 후보를 고르고 줄 세우는 데** 쓰이고, 선별 후엔 아무것도 안 한다. `seedRank`는
거친 신호라는 것도 적어둔다 — 쿼리 하나에서 5건의 상대 순위일 뿐이고, 스타일 쿼리에서 온 3위와 기본
쿼리의 3위는 같은 등급이 아니다. 그래서 순위 숫자를 점수로 쓰지 않고 표식과 정렬로만 쓰는 게 오히려
안전하다.

### PlaceSignal(3층·4층)을 V1에서 제외한 이유

초안의 파이프라인은 Grounding 뒤에 **`PlaceSignalStage`**를 두었다 — 카카오 생존 후보 전량에 네이버
블로그를 조회해 3층(인기도·폐업 감지)과 4층(LLM 속성 추출 → 컨셉 사전 매칭)으로 슬롯 내 후보를
재정렬하는 층이다. 이 층의 존재 근거는 지식 신호 층에 명시돼 있었다: "품질 신호가 없다"는 배경의 근본 원인 6번의
유일한 답이자, **"컨셉·분위기를 판별할 유일한 외부 근거"**. 후보 공급 층을 설계하고 나서 이 근거를
다시 저울질했더니 셋 다 얇아져 있었다.

**1. "유일한"이 사라졌다.** 인기도는 시더(2′층)가 **풀 진입 시점에** 리뷰 수 상위로 이미 반영하고,
스타일은 modifier 쿼리(풀)와 Curator 선별(3개 선택)에서 **두 번** 반영된다. 3·4층은 같은 3개
후보를 사후에 한 번 더 정렬하는 세 번째 패스인데, 세 번째 패스의 한계 효용은 앞의 두 번이 잘 될수록
줄어든다. 초안에서 이 층이 유일했던 이유는 후보가 전부 파라메트릭이라 앞에서 아무 신호도 붙일 수
없었기 때문이고, 그 전제가 바뀌었다.

**2. 소스별로 따져보면 3층의 고유 가치가 거의 남지 않는다.**

| 후보 출처 | 3층(블로그 인기도·폐업)의 가치 |
|---|---|
| `SEEDED` | **중복** — 리뷰 수 상위로 들어왔고 시드 순위가 곧 인기도다 |
| `LISTED` (당시엔 카카오 커버리지 후보, 지금은 TourAPI 후보) | 고유하나 **폴백 경로**였다 — 시더가 비었을 때만 주역. 이후 카카오 커버리지는 후보 소스에서 빠졌고(위 "카카오 커버리지 검색을 후보 소스에서 뺀 이유"), 지금의 `LISTED`(TourAPI 관광지)에도 3층 가치는 같다 — 관광지 인기도는 시더가 이미 맡는다 |
| `SUGGESTED` | 폐업 감지는 고유하나, **그라운딩 검색이 실존 확인을 겸한다** — 카카오·네이버 플레이스에 살아 있으면 영업 신호다. 무명 장소 감점은 Curator 프롬프트("SEEDED 우선, SUGGESTED는 확신할 때만")가 0원에 대신한다 |

**3. 4층은 효과가 실측된 바 없는데 비용은 확정적이다.** LLM 배치 1회(금액 19%, STEP-0 실측), 지연
2~4초(에이전트 외 단일 항목 중 최대), 네이버 블로그 ~35회, 실패 모드 1개. 반면 이득 쪽은 전부
가정이다 — 100자 스니펫에 물리 속성이 실제로 등장하는 비율, 닫힌 태그 30개 × 사전 매칭이 실제
선호를 설명하는 정도, 어느 것도 재보지 않았다. 지연 예산이 Critic을 뺀 근거 4번("효과를 측정할 인프라가
없다")이 4층에도 정확히 적용되는데, 초안은 4층에만 예외를 뒀던 셈이다.

**4. 스타일 쿼리의 SEO 편승 검증이라는 새 역할도, 위험 크기를 모르는 채 선불하는 것이다.**
위 "정직하게 남는 한계"에 적었듯 4층은 modifier 쿼리가 끌어온 "주장"을 "사실"로 확인할 자리였다.
논리로는 성립하지만, 그 위험이 실제로 얼마나 큰지는 삭제 로그로 재봐야 안다. 위험이 실측되면 켠다.

**결정: `PlaceSignalStage`는 V1에서 제외한다.** 3층·4층 설계는 지식 신호 층에 그대로 두고, `NaverBlogClient`·
`PopularityScorer`·`PlaceProfileAgent`는 만들지 않는다. 도입 순서 9단계가 "플래그"에서 "조건부"로 바뀌며,
착수 조건은 그곳에 실측 지표로 적었다. **불확실한 이득에 확정적 비용을 선불하지 않는다** — Critic을
뺀 근거와 같은 문장이고, 이 설계 전체가 같은 태도로 일관된다.

이 결정의 대가도 적어둔다. **품질 신호는 이제 MEAL/CAFE의 시딩에만 있다.** ATTRACTION은 Planner
권역 설계 + 파라메트릭에 맡기는데, 이건 지식 신호 층이 원래부터 "관광지 선택은 Planner가 대부분 정한다(가중치
0.2)"고 인정한 지점이라 새로 생기는 공백은 아니다. 다만 그게 실제로 충분한지는 사용자 삭제 로그(남는 한계)로
확인해야 하고, 그 확인이 3·4층을 다시 켜는 조건이 된다.
