# 결정론적 단계 — LLM에게 시키지 않는 것들

> [멀티 에이전트 파이프라인 설계](../멀티-에이전트-파이프라인.md)에서 분리된 문서다. **`SlotType` 설계**와 **RouteOptimizer 설계**를 담는다.
>
> 둘 다 **원칙 1("LLM에게 결정론으로 풀 수 있는 일을 시키지 않는다")의 구현체**다. 체류시간·가중치·업종 제약을 enum이 소유하고, 동선과 시각은 완전탐색으로 계산한다. 로드맵 3단계에서 구현·벤치마크가 끝난 안정 구역이라 변경 주기도 가장 낮다.
>
> 실행 기록은 [STEP-3-route-optimizer.md](../steps/STEP-3-route-optimizer.md)에 있다 — 설계가 비워둔 계수 세 개를 정하는 과정에서 단위를 맞춰야 했고, 식사 윈도우 배정의 첫 구현이 벌점의 목적과 정반대로 동작한 사건이 기록돼 있다.

## 왜 `SlotType` enum이 체류시간·가중치를 소유하는가

```java
public enum SlotType {
    ATTRACTION(90, "관광명소", 0.2, Set.of("AT4", "CT1")),
    MEAL      (75, "맛집",     1.0, Set.of("FD6")),
    CAFE      (60, "카페",     1.0, Set.of("CE7")),
    EXPERIENCE(120, "체험",    0.6, Set.of("AT4", "CT1")),
    VIEWPOINT (45, "전망대",   0.2, Set.of("AT4")),
    SHOPPING  (60, "쇼핑",     0.6, Set.of("MT1", "CS2")),
    STROLL    (60, "산책로",   0.2, Set.of("AT4"));

    private final int defaultStayMinutes;
    private final String searchHint;        // 후보 공급 검색어 "{area} {searchHint}" (후보 공급) + Curator 실패 시 폴백용
    private final double popularityWeight;
    private final Set<String> allowedCategoryCodes;
}
```

LLM이 내보내는 필드가 하나 줄면 스키마 위반 가능성도 하나 줄고, 튜닝이 코드 리뷰 대상이 된다.
트레이드오프는 "경복궁은 2시간, 작은 카페는 30분" 같은 장소별 차등을 못 준다는 것인데,
카카오 `category_name`으로 사후 보정하면 충분하다(2차 개선 항목).

## RouteOptimizer — 완전탐색을 선택한 이유

**`n ≤ 7`이면 브루트포스.** `7! = 5,040` 순열 × 6회 거리계산 ≈ **1ms 미만**. 3일이면 3ms. 무료다.
3단계 벤치마크가 이 추정을 확인했다 — **1일 589µs / 3일 코스 1.77ms**로, 오히려 추정이 보수적이었다.

nearest-neighbor + 2-opt를 쓰지 **않는** 이유:
- 최적해가 공짜인데 근사할 이유가 없다
- 구현이 더 길고(NN + 2-opt swap 루프 + 수렴 조건), 최적성 보장이 없어 테스트로 "옳음"을 증명하기 어렵다
- **더 복잡한데 더 나쁘다.** 알고리즘 선택은 문제 규모의 함수라는 것이 이 결정의 요지다

방어선은 **임계값 가드 하나다** — `n ≥ 8`이면 탐색하지 않고 입력 순서를 유지한 채 시각만 계산한다.
**NN + 2-opt 폴백은 구현하지 않았다**: Planner가 슬롯을 5~7개로 clamp하므로 이 경로에 도달할 방법이
현재 없고, 도달하지 않는 코드는 검증되지 않은 채 썩다가 나중에 그걸 믿고 임계값을 올렸을 때 문제가
된다. 임계값 7의 근거는 `@Tag("benchmark")` / `./gradlew benchmarkTest`로 `n=6,7,8,9`를 실측해 남겼다
(STEP-3 "로드맵에 없던 결정" 2 · 벤치마크 실측).

**튜닝 상수는 설정이 아니라 코드 상수로 둔다.** `@ConfigurationProperties`로 빼면 순수 함수가 설정
객체를 주입받게 되고 테스트마다 설정 인스턴스를 만들어야 한다. 위 `SlotType` 절이 말한 "튜닝이 코드
리뷰 대상이 된다"는 목적에도 코드 상수가 더 맞는다 (STEP-3 "로드맵에 없던 결정" 3).

**순수 TSP가 아니다 — 시간창 제약을 비용 함수에 넣는다.**

```
cost(순열) = Σ 이동거리(km) × DISTANCE_WEIGHT
           + Σ_{MEAL} 시간창위반분 × MEAL_PENALTY_PER_MIN
           + max(0, 종료시각 − dayEndTime)분 × OVERRUN_PENALTY_PER_MIN

DISTANCE_WEIGHT = 4.0    MEAL_PENALTY_PER_MIN = 2.0    OVERRUN_PENALTY_PER_MIN = 3.0
점심 윈도우 11:30~13:30,  저녁 윈도우 17:30~19:30
```

**계수보다 단위가 먼저다.** `km × 계수`와 `분 × 계수`는 같은 저울에 올릴 수 없으므로,
`DISTANCE_WEIGHT`를 **"km당 분"**(4.0 = 60분 ÷ 15km/h)으로 정의해 세 항을 전부 분으로 환산했다.
그러고 나면 나머지 둘은 의미로 읽힌다 — 식사 2.0은 "30분 늦은 점심 ≈ 15km 우회", 초과 3.0은 그보다
비싸다 (STEP-3 판정 1).

초소형 TSPTW(Time Window) 인스턴스이고 `n ≤ 7`에서 완전탐색은 **정확해**를 준다. 결과적으로
"day당 식사를 적절한 시간대에"가 LLM 판단이 아니라 **알고리즘 불변식**이 된다(원칙 1).

**시간 모델**

```
t[0] = dayStartTime                                     (Planner 제공, 기본 09:30)
t[i] = t[i-1] + stayMinutes(type[i-1]) + travelMinutes(p[i-1], p[i])
travelMinutes = ceil(distanceKm / 유효속도 × 60) + 고정오버헤드
```

| travelMode | 유효속도 | 고정 오버헤드 | 근거 |
|---|---|---|---|
| `WALK`(뚜벅이) | 12 km/h | 10분 | 도보+대중교통 혼합, 환승·대기 |
| `CAR`(자차) | 25 km/h | 5분 | 도심 평균 주행 + 주차 |
| 미지정 | 15 km/h | 8분 | 중간값 |

**haversine은 직선거리라 실제 도로 거리보다 짧다**(도심 우회계수 통상 1.2~1.4). 우회계수 파라미터를
따로 두는 대신 **유효속도를 낮춰 흡수**했다 — 파라미터 하나를 아끼고, 두 값이 서로 상쇄되는 튜닝
혼란을 피한다.

- **출력 정규화**: `startTime`은 5분 단위 올림. `09:37`은 사용자가 보는 필드라 어색하다.
  **올림은 출력 직전 한 번만 한다** — 계산 중에 적용하면 장소마다 최대 4분씩 밀려 넘치지 않는 코스가
  넘친 것으로 판정되고, 표시용 반올림이 장소를 지운다 (STEP-3 판정 4).
- **하루 초과**: 종료가 `dayEndTime`(**기본 23:59**, `RouteRequest.DEFAULT_DAY_END`) 초과 시
  ① 체류시간 0.8배 축소 재계산 ② 그래도 초과면 후순위 슬롯 드롭 ③ day당 최소 3개 아래로는 드롭 중단.
  축소·드롭 후에는 도착 시각이 전부 앞당겨져 이전 최적 순열이 더 이상 최적이 아니므로 **다시 탐색한다.**
- **기본값에서는 이 절차가 발동하지 않는다.** 09:30 시작 기준 하루 예산이 869분이라 장소 7개(체류
  525분 + 이동 약 120분)를 넣어도 224분이 남는다. 그럼에도 구현한 것은 `dayEndTime`이 `RouteRequest`의
  필드라 **Planner가 더 이른 종료 시각을 넘기면 즉시 살아나기** 때문이다 — 죽은 코드가 아니라 호출자가
  켜는 안전장치다 (STEP-3 판정 5).
- **드롭 서열**: `SHOPPING → STROLL → VIEWPOINT → CAFE → EXPERIENCE → ATTRACTION`. **MEAL은 목록에 없다**
  (= 드롭 대상이 아니라 "day당 최소 한 끼"가 자명해진다). 산책로·전망대·쇼핑은 대체 가능하고 체류가
  짧지만 관광명소와 체험은 그날의 목적 자체라는 것이 서열의 근거이며, "체류가 긴 체험을 빼야 초과가
  빨리 풀린다"는 반대 논리는 의도적으로 버렸다 — 목표는 시간을 맞추는 것이 아니라 **가치를 최대한
  남기고** 시간을 맞추는 것이다.
- **서열에 `popularityWeight`를 쓰면 안 된다.** 그건 중요도가 아니라 **블로그 신호의 신뢰도**여서,
  오독하면 관광명소(0.2)가 카페(1.0)보다 먼저 버려진다 — "대릉원을 빼고 카페를 남긴다". 그래서 별도
  `DROP_ORDER`를 두고 회귀 테스트로 고정했다 (STEP-3 판정 7).
- **거리 계산은 haversine**(반경 6371.0088km). 한국 도시 규모(<50km)에서 유클리드 근사와의 차이는
  0.1% 미만이지만, haversine은 20줄이고 CPU 비용이 무의미하다. **최적화가 필요 없는 곳을
  최적화하지 않고, 근사 오차라는 변수를 아예 없앤다.**
