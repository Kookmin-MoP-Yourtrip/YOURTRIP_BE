# LLM 호출 경로 성능·안정성 로드맵

> **한 문장 정의** — AI 코스 생성의 병목인 LLM 동시 호출 슬롯을 **측정으로 드러내고**, 그 용량을 **근거 있게 정하고**, 넘치는 부하가 코스 품질과 서버 전체로 **번지지 않게 격리**하는 작업이다.
>
> 이 문서는 단계 순서·진행 상태·판단 근거를 관리하는 **정본**이다. 단계별 상세 기록은 [steps/](steps/)에 둔다. AI 코스 생성 기능 자체의 설계·구현 이력은 [ai-course-create/ROADMAP.md](../ai-course-create/ROADMAP.md)에 있다.

## 출발점 — 무엇이 문제였나

### 지연이 예산에 붙어 있다

| 기준 | 값 | 출처 |
|---|---|---|
| 설계 추정 | 단계 상단 합 ≈ 11.7초, p95 17~24초 | `PipelineStage` javadoc, [운영-관심사.md](../ai-course-create/design/운영-관심사.md) |
| 실측 (30요청) | **p50 22.3초 · p95 29.4초 · max 30.1초**, 30초 초과 1건(3.3%) | [STEP-8 판정](../ai-course-create/steps/STEP-8-switch.md) |
| 요청 예산 | `ai.course.budget-ms: 30000` | `application.yml` |

30초는 HTTP 타임아웃이 아니라 **서버가 스스로 기다림을 끊는 마감**이다. 마감에 걸리면 에러가 아니라 기본 플랜·폴백으로 채운 **품질이 떨어진 200**이 나가고, 장소가 0개일 때만 504(`AI_COURSE_TIMEOUT`)가 된다. 그래서 지연이 예산에 붙어 있다는 것은 "일부 요청의 품질이 조용히 깎이고 있다"는 뜻이다.

### 시간 제한의 층위

| 층 | 값 | 비고 |
|---|---|---|
| Android 클라이언트 (OkHttp `readTimeout`) | 60초 | FE `RetrofitClient` — "ai 코스 생성 api 고려" 주석 |
| ALB `idle_timeout` | 60초 | `terraform/prod/variables.tf` |
| 서버 요청 예산 (`CourseDeadline`) | 30초 → **35초**(6단계) | 모든 스테이지가 남은 예산만큼만 기다린다. 현재 값은 아래 "시간 제한 불변식" |
| LLM 슬롯 대기 / HTTP 시도 1회 | 각 20초 (`llm.timeout-ms`) | **호출 1건 상한이 아니다** — 전송 재시도 3회 × 의미 재시도 2회가 곱해져 이론상 약 144초 |
| Tomcat 워커 (운영) | 32개 | 동기 컨트롤러라 AI 요청 하나가 워커 하나를 22~30초 점유 |

불변식: **서버 예산 < 클라이언트 60초 = ALB 60초.** 예산을 늘릴 수 있는 현실적 상한은 50초 안팎이다. 6단계에서 예산을 35초로 바꾸고, 배포 쪽 관계까지 포함해 아래 "시간 제한 불변식"으로 정리했다.

### 시간 제한 불변식 (6단계, 현재 값 기준 정본)

AI 코스 생성의 시간 제한은 **서로 다른 저장소·파일에 흩어져 있다**(BE yml, FE Java, terraform). 어느 하나를 바꿔도 다른 쪽에서 경고가 나지 않으므로, 값을 바꿀 때는 이 표를 먼저 본다. 근거와 측정은 [STEP-6](steps/STEP-6-budget.md).

| 값 | 현재 | 정의 위치 |
|---|---|---|
| 서버 예산 | 35초 | `ai.course.budget-ms` (`application.yml`) |
| 후처리 (예산 뒤 경로 계산·저장) | 실측 0.3초 미만 | – (STEP-6 측정 최대 282ms) |
| 클라이언트 | 60초 (읽기 공백 기준) | FE `RetrofitClient` OkHttp `readTimeout` |
| ALB 유휴 연결 | 60초 | `alb_idle_timeout` (`terraform/prod/variables.tf`) |
| ALB 연결 정리 (배포·scale-in) | 30초 | `target_group_deregistration_delay` (같은 파일) |
| Spring graceful shutdown | 30초 (미설정, 기본값) | `spring.lifecycle.timeout-per-shutdown-phase` |

| 불변식 | 현재 | 깨지면 |
|---|---|---|
| **① 예산 + 후처리 < 클라이언트 = ALB 유휴 연결** | ✅ 35.3 < 60 = 60 | 서버는 코스를 만들어 저장했는데 사용자는 오류를 받는다. 다시 누르면 같은 코스가 두 개 생기고 OpenAI 비용도 두 번 든다. 클라이언트와 ALB 중 짧은 쪽이 실제 상한이라 둘은 같이 움직인다 |
| **② 예산 + 후처리 ≤ ALB 연결 정리 ≤ graceful shutdown** | ❌ **35.3 > 30** ([#190](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/190)) | 배포 중 진행되던 AI 요청이 잘릴 수 있다. 실질 상한은 ALB 연결 정리다 — ALB 가 먼저 요청을 비운 뒤 인스턴스가 종료되므로, graceful shutdown 은 앱만 내려갈 때(`systemctl restart` 등)의 안전망이다 |

- 예산을 올릴 수 있는 현실적 상한은 ①로 50초 안팎이다. ②는 연결 정리 시간을 같이 늘려야 하고, 그만큼 배포·scale-in 이 인스턴스당 길어진다
- ALB 유휴 연결은 별도로 **Tomcat keep-alive(65초)보다 짧아야** 한다(`alb_idle_timeout` 설명) — ①을 위해 ALB 값을 올릴 때 이 제약도 함께 본다
- 서블릿 비동기로 바꾸면 **비동기 요청 타임아웃**(설정하지 않으면 Tomcat 기본 30초)이 ①의 서버 쪽에 한 층 더 생긴다

### 병목 가설 — LLM 동시 호출 슬롯

`llm.max-concurrent-calls: 2`는 OpenAI 티어를 모르는 상태에서 429를 피하려고 고른 **보수적 초기값**이고, 실측 근거가 한 번도 없었다([#108](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/108)). 0단계에서 조직 한도(Tier 1, 500K TPM / 500 RPM)와 호출당 토큰(평균 약 4,100)을 확인한 결과, 서버당 상한은 4~8이고 2는 그 절반 이하다.

- 세마포어가 **서버 전체 공용**이라 3일 코스의 Curator 3개가 두 번에 나뉘어 돌고, 동시 요청끼리도 같은 슬롯을 다툰다
- 세마포어는 **인스턴스마다** 2개인데 OpenAI 한도는 계정 단위다 — ASG max 2면 실제 동시 호출은 최대 4개
- `aiAgentExecutor`(core 4, 큐 50)는 큐가 차기 전까지 4개 스레드로만 돈다

**1단계 E2E에서 확인됐다** — 경주 3일 1회 생성에서 세 번째 Curator가 슬롯을 **8.1초** 기다렸고, Curator 단계 13.3초가 사실상 두 라운드의 직렬 합이었다([STEP-1](steps/STEP-1-permit-wait.md)). 세 호출이 동시에 나갔다면 단계는 가장 느린 호출(≈8.3초) 근처까지 줄 여지가 있다.

### 병목이 서버 전체로 번지는 경로

LLM이 먼저 포화된다(서버당 제대로 처리 가능한 양 ≈ 분당 5~6건, Tomcat 32개가 다 차는 지점 ≈ 분당 77건 — 둘 다 추정치). 그 사이 구간에서 넘친 요청은 Tomcat 워커를 쥔 채 슬롯을 기다리다 예산을 다 쓰고 **30초 뒤 품질이 떨어진 결과**를 낸다. 32개가 차면 피드·목록 같은 수 ms짜리 API까지 커넥션 큐에서 기다린다.

워커는 `future.get()`에서 잠들어 CPU를 쓰지 않으므로 이것은 CPU가 아니라 **자리(스레드 개수) 문제**다. `maxThreads`를 다시 올리는 것은 답이 아니다 — 빠른 API 쪽 스레드까지 늘어 #88에서 걷어낸 CPU 경합이 되살아난다.

## 단계별 계획

### 0. OpenAI 티어 확인 ✅

- OpenAI 콘솔 Limits에서 `gpt-5.6-luna`의 RPM/TPM을 확인한다
- **4단계의 상한**이 여기서 나온다: 동시 호출 상한 ≈ 계정 한도 ÷ 최대 인스턴스 수(2)
- 계정 화면이라 사람이 확인한다

**확인 결과** (2026-10-02, 조직 Settings → Limits)

| 항목 | 값 |
|---|---|
| Usage tier | **Tier 1** (누적 결제 $5 이상, 결제액에 따라 자동 상향) |
| `gpt-5.6-luna` TPM | **500,000** |
| `gpt-5.6-luna` RPM | **500** |
| Batch 대기열 | 5,000,000 TPD — Batch API를 쓰지 않아 해당 없음 |

**동시 호출 수로 환산.** 동시 호출 ≈ 분당 호출 × 호출 1건 시간(초) ÷ 60 (리틀의 법칙). 호출 시간은 [STEP-1](steps/STEP-1-permit-wait.md) E2E 실측(Planner 7.4초, Curator 최대 8.3초)을 따라 약 8초로 잡았다.

- **RPM 기준**: 500 × 8 ÷ 60 ≈ **66개** 동시 — 3일 코스(LLM 4회)로 분당 약 125코스라 걸림돌이 아니다
- **TPM 기준** (먼저 걸리는 쪽): 호출당 토큰 수가 필요해 `ai.llm.tokens` 지표를 추가하고 실측했다([STEP-0](steps/STEP-0-token-usage.md), #174)

**호출당 토큰 실측** (경주 3일 1건): 코스 1건 **16,418토큰**. Planner 2,245, Curator 평균 4,724(입력 3,894 · 출력 830)이고, Curator 입력의 약 29%가 캐시 적중이었다.

| 기준 | 호출당 토큰 | 동시 호출 | **서버 1대 (÷2)** |
|---|---|---|---|
| 실사용 (입력 + 실제 출력) | 4,105 | 16.2 | **8.1** |
| 보수적 (입력 + 출력 상한 `max_completion_tokens`) | 6,918 | 9.6 | **4.8** |

**결론.** 서버 한 대당 동시 호출 상한은 **보수적으로 4, 실사용 기준으로 8**이다. 지금의 2는 한도의 절반 이하만 쓰고 있고, 4단계에서 **2 → 3 → 4**로 올려 보는 범위는 보수적 기준으로도 한도 안이다.

**프로젝트 한도 확인 ✅** (Project Settings → Limits → Rate limits) — `gpt-5.6-luna` **500,000 TPM / 500 RPM**으로 조직 한도와 같다(오버라이드 없음). 공유 한도 그룹(Shared limits)에는 `gpt-5.6-luna` 자신만 있다. 즉 **Planner와 Curator가 한 한도 풀을 나눠 쓰고**, `gpt-5-nano`(PlaceProfile, 현재 미사용)는 이 풀과 무관하다.

**미확인**

- **TPM의 `max_completion_tokens` 반영 여부** — 반영된다면 보수적 기준이 맞고, 출력 상한(Curator 4,096)을 ~~실제 출력(최대 876)에 맞게~~ 낮추는 것만으로 한도 여유가 커진다 → **4-3에서 해소**: 공식 문서 기준 반영으로 보고 Curator 상한을 **2,048** 로 낮췄다. "최대 876"은 표본 3건이었고 누적 596건 최대 1,490 · 전후 측정 최대 1,540 이다. `ai.llm.truncated{reason=length}`가 0을 넘으면 상한을 다시 본다([STEP-4-3](steps/STEP-4-3-curator-output-cap.md))
- **표본 1건** — Curator 입력은 후보 목록 길이에 따라 다르다. 2단계 기준선 측정에서 분포로 보완한다

### 1. 슬롯 대기 지표 추가 ✅

### 2. 기준선 측정

1단계 E2E는 표본 1건이라 분포를 말할 수 없다. 두 조건으로 잰다.

1. **단일 요청 분포** — STEP-8의 30요청 세트를 새 지표가 있는 상태로 다시 돌린다. Curator 대기가 매번 5~8초인지, 지역·일수에 따라 다른지 본다
2. **동시 요청 시나리오** — 2~3명이 동시에 요청한다. 서버 전체 슬롯 경합, `timeout` 발생, `waiting` 누적, `tomcat_threads_busy`, 빠른 API의 p95를 함께 본다. `CallerRunsPolicy`도 이 조건에서만 드러난다

- 결과물: **설계 추정치와 실측을 단계별로 나란히 놓은 표** — 3단계 이후 무엇을 고칠지는 이 표가 정한다
- #108의 "개선 전" 측정을 겸한다. OpenAI 비용이 30~40요청 분량 든다

### 3. 마감 뒤 남는 호출 정리

예산이 끝나 응답이 이미 나갔는데도 LLM 호출이 뒤에서 계속 돌며 슬롯을 쥐고 있다(Planner·Curator 모두 `future.get(remainingMs)`로 기다리기만 하고 `cancel`하지 않는다).

- **재시도 전 남은 예산 확인** — 재시도 루프(`LlmRetryExecutor`·의미 재시도)가 `CourseDeadline`을 모른다. 예산이 없으면 재시도·백오프를 하지 않게 한다
- **진행 중인 호출 취소** — 단, `cancel`이 reactor-netty의 실제 HTTP 요청까지 끊는지 **조사가 먼저다**(체크리스트 첫 항목)
- ~~**4단계보다 먼저인 이유**: 버려진 호출이 슬롯을 쥔 상태에서 동시 호출 수를 조정하면 측정값에 그 점유가 섞여 해석할 수 없다~~
- **순서를 4단계 뒤로 바꿨다(2026-10-03).** 위 근거는 측정 구조상 약했다 — 단일 요청 측정에서는 남는 호출이 0건이었고, 동시 측정은 라운드 간격 90초라 남는 호출이 다음 라운드로 넘어가지 않는다. 라운드 안에서 생기는 남는 호출은 오염이 아니라 운영에서도 일어나는 현상의 일부다
- **구현 여부는 4단계 측정으로 정한다.** 남는 호출의 해악은 과부하 구간(슬롯 시간 수요 > 공급)에서만 크다. 슬롯을 늘려 그 구간이 동시 5명 밖으로 밀려나면 이 단계의 가치가 작아진다. 동시 5명에서 폴백이 크게 남으면 구현하고, 작으면 #176 을 보류한다
- **보류로 판단했다(2026-10-05).** 4단계 재확정(슬롯 5) 측정에서 동시 5명 폴백이 11.1% 로 작다. 동시 8명은 슬롯 4·5·6 모두 폴백 54% 이상이라 남는 호출 정리만으로 풀리지 않고, 요청을 받아들이는 수 자체를 제한하는 쪽(AI 동시 입장 제한)과 함께 봐야 한다
- **6단계에서 보탠 근거** — 남는 호출의 크기를 처음 쟀다(`scripts/loadtest/late-calls.py`). 동시 8명에서 Curator 호출의 약 절반(30초 30 / 56회, 35초 23 / 55회)이 마감 뒤에 끝났고, 마감 후 최대 20~30초까지(1초 해상도의 50~60초 구간) 돌며 슬롯을 쥐었다. 같은 측정에서 "버려진 호출도 결과만 버려질 뿐 끝까지 돈다"는 전제로 예산별 효과를 역산할 수 있었다([STEP-6](steps/STEP-6-budget.md) 2절)
- 조사 결과(인터럽트로 슬롯 대기·HTTP·백오프를 모두 멈출 수 있다, 인터럽트가 재시도 대상으로 오분류된다)는 [STEP-3](steps/STEP-3-late-calls.md)에 있다

### 4. `max-concurrent-calls` 조정 (#108)

- 0단계 상한(서버당 보수적 4 · 실사용 8) 안에서 올리며 2단계와 같은 세트로 잰다. **4 를 먼저 쟀다**(3 은 생략 — STEP-4 한계 참고)
- **4 결과**: 단일 요청 Curator 대기 0, p95 24.1 → 18.6초. 동시 3명 폴백 42 → 7%, 동시 5명 74 → 38%(풀 4 — 4-1 풀 정렬 전). 동시 5명에서 슬롯 대기는 0인데 `aiAgentExecutor`(core 4) 큐가 최대 11 — **실질 상한이 스레드 풀 4라 세마포어가 더 이상 병목이 아니다**([STEP-4](steps/STEP-4-concurrent-calls.md))
- **스레드 풀 정렬([#177](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/177)).** 실제 동시 호출 수는 `min(스레드 수, 세마포어)`인데, 풀이 큐 50칸이 차기 전에는 core 4 를 넘지 않아 세마포어 4 와 같아졌다. 의도(`AsyncConfig` 주석)는 "스레드 > 세마포어"로 줄이 항상 세마포어 앞(20초 상한·지표 있음)에서만 서게 하는 것이다. 세마포어는 어느 경로로 부르든 OpenAI 로 나가는 호출을 모두 세는 한도 보호 장치라 없앨 수 없으므로, 풀을 넉넉히 하고 상한 손잡이를 `max-concurrent-calls` 하나로 만든다
- **4-1 결과**: 풀을 `max-concurrent-calls` × 4(core = max)로 묶었다. 동시 5명에서 풀 큐 11 → 0, 세마포어 `waiting` 0 → 11, 대기 상한 포기 0 → 3회(마감 뒤 호출이 될 작업이 시작 전에 끝남). 폴백은 38 → 33% 로 표본 편차 안이다 — 자리만 옮겼지 처리 능력은 같다([STEP-4-1](steps/STEP-4-1-executor-sizing.md))
- **8 결과(로컬 1대, 풀 정렬 뒤)**: 동시 5명 폴백 33 → 0%, p95 30.1 → 25.5초. 새 한계는 동시 5~8명 사이. 슬롯을 넓히는 이득은 크다 — 운영에 쓰려면 아래 조건 ①이 필요하다. 측정 중 **네이버 지역 검색 초당 호출 제한(429)** 과 `placeGroundingExecutor`가 #177 이전과 같은 구조라는 점이 드러났다([STEP-4](steps/STEP-4-concurrent-calls.md) 4절)
- **5 이상은 조건부다.** ① 한도 여유 확보 — TPM 이 `max_completion_tokens`를 세는지 확인하거나 Curator 출력 상한을 낮춘다(~~실측 최대 876 에 맞춰 4,096 → 약 1,500~~ — 876 은 표본 3건이라 1,500 은 실측 최대 1,540 에 잘린다) ② ~~스레드 풀이 슬롯 수만큼 실제로 동시에 돌게 조정한다~~ — 4-1 에서 해결(풀이 슬롯을 따라간다). 이제 남은 조건은 ① 하나다. 없이 올리면 운영 2대에서 429 위험이 생긴다. **4-3에서 ① 해소**: 상한 2,048 로 보수적 서버당 약 6.1 — 5는 넉넉하고 6은 빠듯하다. 슬롯을 올린 뒤 같은 날 전후 측정으로 폴백과 `ai.llm.truncated`를 함께 본다
- 볼 것: Curator 단계 지연, 슬롯 대기, 429 빈도, 요청 전체 p95
- 정한 값과 근거(티어 ÷ 인스턴스 수)를 `application.yml` 주석에 남긴다
- **확정(2026-10-03): 4.** 공식 문서상 출력 상한도 TPM 에 잡혀 보수적 기준(서버당 4.8)을 따른다. 운영은 2대로 요청이 나뉘어 동시 5~6명까지 폴백 없이 버틸 것으로 본다(운영 실측은 아님). 6으로 올리는 순서: 네이버 429 대응(4-2 ✅) → Curator 출력 상한 조정·잘림 측정(4-3 ✅) → 6 재측정 *(4-4: 재측정에서 슬롯을 넓히면 네이버 순간 몰림이 되살아나 식사·카페가 빈다는 것이 드러났다. 네이버 버스트 제어(#185)를 끼워 넣는다)*
- **재확정(2026-10-05): 5.** 네이버 429 대응(4-2) → Curator 출력 상한 2,048(4-3) → 네이버 속도 제한기 초당 25(4-5) 순서로 전제를 갖춘 뒤 같은 날 4·5·6을 비교했다. 5가 동시 5명 폴백 32.8 → 11.1% 로 가장 좋았고, 6은 13.0% 로 이득이 없으면서 계정 전체 동시 12 / 보수적 상한 12.2 로 빠듯했다. 운영 2대 기준 계정 전체 10 / 12.2 다 *([STEP-4-4](steps/STEP-4-4-slot-raise.md) 6절)*
- **동시 8명은 슬롯으로 풀리지 않는다** — 4·5·6 모두 폴백 54% 이상이다. 3단계(#176)와 AI 동시 입장 제한의 판단 근거로 넘긴다
- 1단계 E2E 기준 기대 효과: Curator 단계 약 5초 단축(요청 전체의 약 1/4) — 2단계 분포로 확정한다

### 5. Planner 단계 상한 (조건부)

- Planner는 파이프라인 첫 단계라 30초 전체를 쓸 수 있다. 슬롯 대기·재시도로 예산을 다 쓰면 후속 단계가 전부 진입 즉시 만료돼 504가 된다

- **판정(2026-10-05): 보류.** 2~4단계에서 쌓인 측정을 다시 집계했다(LLM 비용 없음). 이 경로로 끝난 요청은 **0건**이다

### 6. 30초 예산 재조정 + 시간 제한 관계 문서화

- 개선 후 분포로 "p95 + 여유" 기준을 다시 적용한다. 개선이 잘 되면 오히려 줄일 수도 있다
- `llm.timeout-ms`의 실제 의미(HTTP 시도 1회 + 슬롯 대기의 상한)를 주석에 바로잡는다
- "서버 예산 < 클라이언트 60초 = ALB 60초" 불변식을 `budget-ms` 주석과 운영 문서에 명시한다

**결과(2026-10-05, [#189](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/189) · [STEP-6](steps/STEP-6-budget.md))**

- **`timeout-ms`** — 슬롯 대기 · HTTP 연결 · HTTP 응답 읽기 공백(reactor-netty `responseTimeout`, spring-web 6.2.12 바이트코드로 확인) 세 곳에 각각 걸린다. 재시도가 곱해져 호출 1건은 타임아웃만 나면 약 82초, 이론상 최악 약 144초다. 주석 6곳을 정정했다
- **예산을 p95 가 아니라 폴백으로 봤다** — 예산을 넘기면 실패가 아니라 폴백 200 이 나가므로 "p95 + 여유"로는 교환 관계가 보이지 않는다. 버려진 Curator 호출이 마감을 몇 초 넘겨 끝났는지로 예산별 효과를 기존 데이터에서 역산했다(`scripts/loadtest/late-calls.py`)
- **역산 예측이 빗나갔다** — 오전 데이터로 "35초면 동시 5명 폴백 거의 0%"를 예측했으나, 오후에 Curator 호출이 7.05 → 8.66초로 느려져 35초에서도 11.1% 였다. 같은 오후에 30초 대조군을 다시 재 **30 → 35초 = 24.4 → 11.1%** 를 확인했다. 같은 30초에서 오전 11.1% · 오후 24.4% — 폴백은 예산보다 하루 안 LLM 지연 흔들림에 더 민감하다
- **35초 확정** — 효과가 실측된 값 가운데 대가가 가장 작은 값이다(마감에 걸린 요청만 +5초). 40초 이상의 이득은 과부하 구간에 쏠려 입장 제한의 몫으로 남긴다. `PIPELINE_LATENCY_MAX`와 벤치마크 운영값도 35초로 맞췄다
- **불변식** — 위 "시간 제한 불변식" 절에 정본으로 정리했다. 예산 + 후처리(0.3초 미만) < 클라이언트 = ALB 60초는 지켜진다. 배포 연결 정리(`deregistration_delay` 30초)는 예산보다 짧아져 [#190](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/190)으로 넘겼다

### 별도. AI 동시 입장 제한

- 서비스 입구에 **서버당 AI 동시 처리 상한**(예: 4~6)을 둔다. 넘으면 짧게(3~5초) 기다린 뒤 `429` + `Retry-After`로 거절한다
- 효과: AI 요청이 쓰는 Tomcat 워커를 최대 N개로 묶어 나머지를 빠른 API 몫으로 보장한다(벌크헤드). 받은 요청은 슬롯을 실제로 쓸 수 있어 품질이 유지된다
- **동기·비동기 어느 구조에서도 필요하다** — 202로 가도 큐 길이 제한이 같은 역할을 하므로 먼저 만들어도 버려지지 않는다
- **UX**: 제한이 없어도 넘친 사용자는 "30초 대기 + 품질이 떨어진 결과"를 받는다. 제한은 그것을 "짧은 대기 또는 재시도 안내"로 바꾸는 장치다. FE와 429 자동 재시도("요청이 많아 잠시 기다리는 중") 합의가 필요하다. 사용자당 동시 1건 제한도 함께 검토한다
- 4단계로 용량을 늘려 **평소에는 거의 작동하지 않는 안전밸브**로 두는 것이 목표다
- **6단계에서 보탠 근거** — 동시 8명은 예산 35초에서도 폴백 54.1%(30초 59.9%)다. 대기는 거의 전부 LLM 슬롯 앞에서 생긴다(요청당 Curator 슬롯 대기 합 40.1초, 대기 포기 16회. Tomcat busy 최대 9 / 32). 30초 동안 필요한 LLM 작업(추정: 호출 약 32회 × 9초 ≈ 290 슬롯·초)이 공급(슬롯 5 × 30초 = 150)의 두 배라 예산·슬롯·스레드 풀로는 풀리지 않는다. 또 `aiAgentExecutor` 큐가 차면(`CallerRunsPolicy`) 요청 스레드가 LLM 을 직접 불러 **예산이 걸리지 않고** 82~144초까지 갈 수 있다(STEP-6 발견 ③, 동시 약 18명 이상) — 입장 수를 묶으면 이 경로도 막힌다
- 다음 단계 후보(필요할 때): 컨트롤러를 `CompletableFuture`/`DeferredResult` 반환으로 바꾸는 **서블릿 비동기** — API 계약과 FE는 그대로 두고 Tomcat 워커만 풀어 준다

### 7. 202 Accepted 전환 판단

- 1~6단계를 거쳐도 p95가 동기로 감당하기 어렵거나, 품질을 위해 예산을 60초 가까이 늘려야 하거나, AI 부하가 다른 API 지연을 끌어올리면 전환한다
- **비동기는 빠르게 만드는 기술이 아니다** — 생성 시간은 그대로이고, 누가 어디서 기다리느냐만 바뀐다. 병목을 먼저 줄이지 않으면 대기 장소만 옮겨진다
- 설계 요지: 작업 상태는 **Redis**(서버 2대라 메모리 불가), 워커는 처음엔 **같은 서버 안의 전용 스레드 풀**(디스패처 인터페이스로 분리해 나중에 큐로 교체 가능), **큐 길이 제한 필수**, 소유자 확인·멈춘 작업 정리·중복 접수 방지, 폴링 + 선택적 진행 단계(`stage`) 표시
- API 계약이 바뀌므로 FE 합의가 먼저이고, 전환 기간에는 새 엔드포인트를 따로 둔다

## 열린 질문

- TPM 계산의 `max_completion_tokens` 반영 여부(공식 문서 기준 반영으로 보고 4-3을 진행했다. 계정에서 직접 확인하지는 않았다), 캐시 적중 토큰의 TPM 할인 여부 (0단계 미확인 항목)
- FE `BASE_URL`(`yourtrip.site`)과 Swagger 안내 도메인(`yourtrip.cloud`)이 다르다 — 구 도메인 잔존 여부 미확인
- 배포 중 instance refresh(`deregistration_delay` 30초)가 진행 중인 AI 요청을 자르는 빈도 — 202 전환 시 워커 유실 문제와 직결된다. 예산 35초로 요청 최대 시간이 연결 정리 시간을 넘어섰다 → [#190](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/190)
