# 별도 단계 보강 — 도착률 기반 AI 코스 생성 측정 (#193)

> 선행: [STEP-admission-limit](STEP-admission-limit.md)(#192, 서버당 입장 상한 4)
> 같은 브랜치에서 진행한다 — 이 측정 결과로 입장 상한이 다시 바뀔 수 있기 때문이다.

## 왜 필요한가

#192는 입장 상한을 **"8명이 1초 안에 동시에 출발"하는 최악의 몰림**으로만 쟀다(`scripts/k6/ai-course-concurrent.js`). 그 측정으로는 받아들인 요청의 품질은 비교할 수 있지만, **평소 트래픽에서 상한이 얼마나 자주 사람을 돌려보내는지**는 알 수 없다.

그 공백을 #192에서는 리틀의 법칙 추정으로 메웠다 — "하루 활성 사용자 1,000명이면 평균 동시 약 1.8건이라 상한 4에 닿지 않는다, 평소에는 작동하지 않는 안전밸브다". **이 추정은 평균만 봤다.** 요청은 무작위로 도착하므로 평균이 1.8이어도 순간적으로 4를 넘는다. 측정 설계 중 이 점을 발견했고(1-2), 이 단계에서 실측으로 확인한다.

## 1. 조사 (2026-10-05)

### 1-1. 지금 측정 도구의 한계

| | `ai-course-concurrent.js` |
|---|---|
| 도착 | 90초마다 N명이 같은 순간에 출발(라운드 안 출발 편차 1초 이내) |
| 잴 수 있는 것 | 포화 상태에서 받아들인 요청의 품질, 거절 응답 속도 |
| 잴 수 없는 것 | 흩어진 도착에서의 거절률, 상한에 붙어 있는 시간 비율 |

### 1-2. 거절률 예측 — 얼랑 B

자리 c개, 넘치면 기다리지 않고 거절하는 시스템의 거절 확률은 **얼랑 B 공식**이 정확히 다룬다. 입장 제한(즉시 거절)이 바로 이 구조다. 제공 부하 a = 도착률 × 평균 처리 시간이고, 처리 시간 분포와 무관하게 평균만으로 성립한다(얼랑 B의 무감응성).

요청 처리 시간 W ≈ 22초(#192 측정의 받아들인 요청 p50 근처)로 계산한 예측:

| 분당 도착 | 평균 간격 | 평균 동시(a) | 거절 확률 상한 4 | 상한 5 |
|---|---|---|---|---|
| 2건 | 30초 | 0.7 | 0.6% | 0.1% |
| 3건 | 20초 | 1.1 | 2.0% | 0.4% |
| **5건** | 12초 | **1.8** | **7.8%** | 2.8% |
| 8건 | 7.5초 | 2.9 | 19.9% | 10.4% |
| 11건 | 5.5초 | 4.0 | 31.4% | 20.2% |

**#192의 "평소에는 작동하지 않는다"는 틀렸다.** 하루 활성 사용자 1,000명 가정(1인 2회, 피크 1시간에 15%)은 피크 분당 5건이고, 이때 상한 4는 약 13명 중 1명을 거절한다고 예측된다.

공식의 가정 두 가지는 실제와 다르다. 그래서 이 표는 결론이 아니라 **측정으로 검증할 가설**이다.

- **처리 시간이 부하와 무관하다** — 실제로는 동시 처리가 많을수록 LLM 슬롯 경합으로 느려진다(#192: 동시 4건 p50 25초, 8건 몰림 35초)
- **거절된 사람은 재시도하지 않는다** — 1-5 참고

### 1-3. 도착 모델 — 시드 고정 포아송 일정 + 도착마다 시나리오

| 방식 | 판단 |
|---|---|
| k6 `constant-arrival-rate` | ✗ 도착을 **등간격**으로 낸다(분당 5건이면 정확히 12초마다). 몰림이 없어 분당 도착 수의 분산이 0이다. 위 표의 거절이 거의 재현되지 않아 현실을 과소평가한다 |
| `ramping-arrival-rate` | ✗ 등간격 문제가 같고, 부하가 계속 바뀌어 수준별 해석이 어렵다 |
| 1초마다 확률 λ/60으로 보낼지 결정(베르누이 솎아내기) | △ 포아송에 가깝지만 1초 단위로 뭉개지고, 보내지 않은 반복까지 k6 지표에 섞인다 |
| VU 하나가 지수분포만큼 `sleep` 후 요청 | ✗ 응답을 기다린 뒤 다음 간격을 재는 **닫힌 모델**이 된다. 응답이 느릴수록 도착이 줄어 결과가 왜곡된다(`detail-arrival-rate.js` 머리말이 지적한 함정) |
| **시드 고정 포아송 일정 → 도착마다 시나리오(`startTime`)** | ✓ 정확한 도착 시각, 열린 모델, 같은 시드면 같은 일정 |

구현 원리:

- **포아송 과정의 도착 간격은 지수분포다.** 균등 난수 U를 역변환하면 간격 = −ln(1 − U) / λ가 되고, 이를 누적하면 도착 시각이다
- k6의 `Math.random()`은 시드를 정할 수 없어 **mulberry32**(32비트 상태 PRNG)를 둔다. init 코드는 VU마다 다시 실행되지만 시드가 같아 모든 VU가 같은 일정을 얻는다
- 도착마다 `per-vu-iterations`(VU 1, 반복 1) 시나리오를 만들고 `startTime`을 도착 시각으로 준다. 각 도착이 자기 VU를 가져 앞사람 응답을 기다리지 않는다. 기존 스크립트가 라운드마다 시나리오를 만드는 방식을 도착 단위로 확장한 것이다
- **같은 시드를 상한 4와 5에 쓴다(공통 난수).** 두 결과는 도착 시각과 입력 순서가 완전히 같아, 차이가 상한 차이만 반영한다. 표본이 작을 때 비교 편차를 크게 줄인다

### 1-4. 측정 비용의 제약

- **TourAPI 일일 한도 1,000건** — 요청 1건이 TourAPI를 약 7.6회 부른다(#192 측정: 15건 → 107~114회). 하루 약 130건이 상한이다
- 거절률 8%를 ±3%p로 재려면 수준당 약 300건이 필요하다. TourAPI를 켠 채로는 불가능하다
- 네이버 지역검색은 요청 1건당 약 28회다(일 25,000건 한도 안)

### 1-5. 거절된 사람은 재시도하는가 — 지금은 아니다

FE(`YOURTRIP_FE` `CreateAICourseLoadingActivity.submitAICourse`)는 2xx가 아니면 상태 코드를 구분하지 않고 "AI 코스 생성에 실패했습니다" 토스트를 띄운 뒤 로딩 화면을 닫는다. `Retry-After`는 읽지 않고, OkHttp 기본 설정은 429를 재시도하지 않는다. 다시 보낼지, 언제 보낼지는 사용자가 정한다.

- 측정에서 "재시도 없음"은 지금 FE와 맞고, 얼랑 B 가정과도 같다. 수동 재시도는 언제 올지 모르는 새 도착에 가까워 도착률에 섞여 들어간다고 본다
- **#192의 상한 4 판단 근거 중 "거절된 사람은 재시도로 회복할 수 있다"는 FE가 429를 재시도 가능한 상태로 안내할 때 성립한다.** 지금은 429가 다른 실패와 같은 문구로 보인다. FE 변경(429 문구 분리)은 보류됐다(2026-10-05)
