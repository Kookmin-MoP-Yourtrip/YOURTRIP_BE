# STEP-4-3 — Curator 출력 상한 낮추기 (#182)

> **결론**: Curator 출력 상한(`max-output-tokens`)을 4,096 → **2,048**로 낮췄다. 근거였던 "실측 최대 876"은 표본 3건짜리였고, 동시 측정 누적 596건으로 다시 재 보니 최대 **1,490**(이번 측정 1,540)이었다 — 로드맵이 제안한 1,500 이면 잘렸을 것이다. 같은 날 전후 측정에서 2,048 의 절단은 **0건**이었다. 보수적 TPM 기준 서버당 동시 호출 상한이 4.7 → 약 6.1 이 되어 슬롯 상향(5~6)의 전제가 섰다. 슬롯 자체는 이 단계에서 바꾸지 않았다.

## 1. 출발점 — 왜 출력 상한인가

[STEP-0](STEP-0-token-usage.md)은 TPM 을 동시 호출 수로 환산하면서 두 기준을 뒀다. OpenAI 가 TPM 에 **실제 출력이 아니라 요청의 `max_completion_tokens`를 미리 잡는다면** 상한을 크게 둔 만큼 동시 호출 여유를 버린다. 공식 문서상 잡히므로 보수적 기준(서버당 4.8)을 따라 슬롯을 4로 확정했고([STEP-4](STEP-4-concurrent-calls.md)), 로드맵은 "6으로 올리는 순서"를 **네이버 429 대응(4-2) → Curator 출력 상한 → 6 재측정**으로 정해 뒀다.

Curator 상한 4,096 은 실측 근거 없이 2-6 스모크(nano 가 추론에 상한을 다 쓰고 0바이트를 돌려준 사건) 이후 넉넉하게 둔 값이다.

## 2. 잘림을 볼 수 있는가 — 측정 수단부터

상한을 낮춘 대가는 **잘림**(`finish_reason=length`)으로 나타난다. 어댑터는 이미 파싱 전에 절단을 판정하고(`LlmTruncatedResponseException`) 호출 결말에 `truncated`를 따로 센다. 그런데 **절단은 의미 재시도 대상**이다.

| 상황 | `ai.llm.call` outcome | 흔적 |
|---|---|---|
| 1차 잘림 → 2차도 잘림 | `truncated` | 지표 |
| **1차 잘림 → 2차 성공** | `success` | **WARN 로그 한 줄** |

상한을 낮췄을 때 생길 잘림은 대부분 두 번째 모양이라, 그대로는 "잘림 0건"과 "재시도가 가린 잘림"을 지표로 가를 수 없다. 게다가 보정 재시도도 **같은 상한**으로 나가 토큰과 시간(약 8초)이 두 배가 된다 — 숨어 있어도 비용은 실재한다.

그래서 상한을 바꾸기 **전에** `ai.llm.truncated{agent, reason}`을 추가했다(`94683ca`).

- **HTTP 응답 단위로 센다.** 예외를 만드는 자리(`OpenAiLlmClient.truncated`)에서 세므로 재시도가 예외를 삼켜도 남는다. `ai.llm.tokens`가 재시도 응답을 따로 세는 것과 같은 이유다
- `reason`은 `length`·`content_filter`·`no_choice`·`other`로 닫는다. 벤더 원문을 태그에 실으면 새 값마다 시계열이 늘고, `length`(상한 탓)와 `content_filter`(상한 무관)는 대응이 다르다
- 설정된 agent 마다 0으로 미리 등록한다

## 3. 출력 분포 — 새 측정 없이

지금까지의 동시 측정 poll 파일 17개(`results/ai-concurrent*/c*-poll.txt`, 1초 간격 스크레이프)에 `ai.llm.tokens` 히스토그램이 이미 남아 있었다. 파일마다 첫·끝 스냅샷 차이로 집계했다(LLM 비용 0).

| Curator (596건) | 평균 | 분포 | 최대 |
|---|---|---|---|
| 출력 (추론 포함) | 872 | p50 ≤ 851 · p99 ≤ 1,365 | **1,490** |
| 그중 추론 | 368 | p99 ≤ 851 | 980 |
| 입력 | 4,045 | – | 5,142 |

- 4,096 에서 절단은 0건이었다. Planner(210건)는 출력 평균 538 · 최대 826 이다(상한 2,048)
- **꼬리는 추론 토큰이 만든다.** 본문 길이는 슬롯 수·후보 3개로 거의 고정인데, `reasoning-effort: low`여도 추론이 최대 980 까지 흔들린다
- 최대값은 Micrometer `max`(2분 창)를 1초마다 읽은 값이라 사실상 모든 기록을 본다. 버킷으로도 상한 1,706 아래가 확인된다

### 상한별 TPM 환산

STEP-0과 같은 식(코스 1건 = Planner 1 + Curator 3, 호출 시간 8초, 계정 500K TPM ÷ 운영 2대)에 입력만 위 실측 평균으로 바꿨다.

| Curator 상한 | 호출당 예약 토큰 | 서버당 동시 호출 상한 | 관측 최대 대비 여유 |
|---|---|---|---|
| 4,096 (이전) | 7,033 | 4.7 | 2.7배 |
| **2,048** | 5,497 | **6.1** | **1.37배** |
| 1,500 | 5,086 | 6.6 | 1.01배 |

**2,048 을 골랐다.** 1,500 은 최대에 붙어 잘림이 나고, 잘림은 같은 상한으로 재시도되므로 여유를 아낄 이유가 없다. Planner 와 같은 값이라 설명하기도 쉽다. 6.1 은 슬롯 6에 겨우 닿는 값이고 같은 조직 한도를 로컬·벤치마크도 나눠 쓰므로, **슬롯 5는 넉넉하고 6은 빠듯하다.** 그 판단은 다음 단계 몫이다.

## 4. 같은 날 전후 측정

### 조건

- 로컬 bootRun, 슬롯 4, Tomcat 32, k6 `ai-course-concurrent.js` 동시 3·5명 × 3라운드(이전 측정과 같은 스크립트·입력)
- **전**: 커밋은 그대로 두고 `SPRING_APPLICATION_JSON`으로 Curator 상한만 4,096 으로 덮어 기동 / **후**: 현재 설정(2,048)
- 2026-10-04 같은 날 연속 측정. 날짜가 다르면 LLM 응답 속도가 13~18% 달라 지표가 흔들린다([STEP-4-2](STEP-4-2-naver-queries.md) 6절)

### 결과

| | 4,096 (전) | 2,048 (후) |
|---|---|---|
| Curator 응답 | 66 | 61 |
| **절단 `ai.llm.truncated`** | **0** | **0** |
| 의미 재시도 (서버 로그 WARN) | 0 | 0 |
| Curator 출력 최대 (추론) | 1,534 (1,024) | 1,540 (926) |
| Curator 출력 평균 N=3 / N=5 | 835 / 855 | 898 / 996 |
| Curator 성공 호출 평균 N=3 / N=5 | 8.71 / 8.59초 | 9.30 / 9.93초 |
| Curator 입력 평균 N=3 / N=5 | 4,138 / 4,126 | 3,582 / 2,412 |
| TourAPI | 정상 (hit 67 / 110) | **일일 한도 소진** (N=3 failed 22 · N=5 hit 0 · failed 112) |
| 폴백 N=3 / N=5 | 11.1% / 42.2% | 6.1% / 40.6% |
| unfilled N=3 / N=5 | 0 / 0 | 2 / 24 (+504 1건) |

**판정**

- **2,048 에서 절단 0건.** 최대 1,540 으로 상한까지 1.33배 남았다. 이번 측정에서도 출력 최대가 누적 관측치 1,490 을 두 번 넘었다 — 1,500 이었다면 잘렸다
- **폴백·unfilled·호출 시간의 차이는 이 변경 탓이 아니다.** 후 조건 도중 TourAPI 개발계정 일 1,000건이 소진돼(같은 날 앞선 측정·감사가 약 980건을 썼다) 관광 후보가 빠졌고, Curator 입력이 줄었으며 빈 슬롯이 생겼다. 상한은 **잘림을 통해서만** 결과에 닿는데 잘림이 0이었다. 출력이 다소 길어진 것도 입력 구성이 바뀐 탓으로 본다 — 상한은 모델의 출력 길이를 바꾸지 않는다
- TPM 여유는 지표로 드러나지 않는다. 그 효과는 슬롯을 올리는 다음 단계에서 보인다

## 한계

- **폴백 비교는 무효다.** TourAPI 결손으로 후 조건의 입력이 달라졌다. 이 단계의 질문("낮춰도 잘리지 않는가")에는 영향이 없어 재측정하지 않았다
- **TPM 이 `max_completion_tokens`를 미리 잡는다는 전제는 공식 문서 기준이다.** 계정에서 직접 확인한 것은 아니다. 잡지 않는다면 이 변경의 한도 이득은 없고 잃는 것도 없다(절단 0)
- **출력 분포는 3일 코스 · 기준선 10지역 입력이다.** 일수가 늘어도 Curator 는 day 마다 따로 불려 호출당 출력은 크게 변하지 않는다. 다만 슬롯 수가 많은 day 나 프롬프트 변경은 분포를 옮길 수 있다 — `ai.llm.truncated{reason=length}`가 0을 넘으면 상한을 다시 본다
- **동시 측정 poll 의 "응답 − 호출"은 의미 재시도 수가 아니다.** 측정 구간 경계에 걸쳐 늦게 끝나는 호출(#176) 때문에 1~2건 어긋났다. 재시도 수는 서버 로그로 셌다
