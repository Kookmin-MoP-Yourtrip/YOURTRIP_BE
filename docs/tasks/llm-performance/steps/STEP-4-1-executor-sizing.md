# `aiAgentExecutor`를 세마포어보다 넉넉하게 — 줄을 세마포어 앞으로 되돌린다

> [LLM 호출 경로 성능·안정성 로드맵](../README.md)의 4-1단계이며, [#177](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/177)의 설계·진행 기록이다. 발견 계기는 [STEP-4](STEP-4-concurrent-calls.md) 3절이다.

## 왜 필요한가

LLM 동시 호출의 상한은 `llm.max-concurrent-calls` 세마포어가 정하도록 설계됐다. OpenAI 한도를 지키는 장치이고, 대기에 20초 상한(`llm.timeout-ms`)과 지표(`ai.llm.permit.wait`, `waiting` 게이지)가 붙어 있다. 그런데 STEP-4 에서 세마포어를 4로 올리자 동시 5명에서 **세마포어 대기는 0인데 풀 큐가 11까지 쌓였다.** 작업이 세마포어에 닿기도 전에 스레드 풀에서 막혔다는 뜻이다. 큐 대기에는 상한도 지표도 없다.

## 1. 조사 — 줄은 실제로 어디에 서는가

학습 테스트: `AgentExecutorSizingLearningTest`

- 상황: STEP-4 의 동시 5명(3일 코스 5건 → Curator 15개, 슬롯 4)
- 작업: `OpenAiLlmClient.generate`의 슬롯 처리만 흉내 냈다(`tryAcquire(상한)` → 점유 → `finally` 반납). 질문이 "어디서 기다리는가"라 HTTP 는 넣지 않았다
- 시간: 호출 200ms, 대기 상한 300ms로 줄였다. 셋째 줄부터 상한을 넘는 구조는 운영(호출 약 9초, 상한 20초)과 같다

| 질문 | 결과 |
|---|---|
| Q1. 운영 설정(core 4 / max 8 / 큐 50) | 스레드 **4개**, 큐 **11**, 세마포어 대기 **0**. 아무도 포기하지 않고 마지막 작업은 상한(300ms)을 훌쩍 넘긴 약 800ms에 끝난다 — STEP-4 의 실측과 같은 모양 |
| Q2. 스레드를 작업 수 이상(16)으로 | 스레드 15, 큐 0, **세마포어 대기 11**. 상한을 넘긴 작업은 포기한다 |
| Q3. core 4 그대로, max 만 64 로 | Q1 과 같다. **max 는 큐가 꽉 차야 쓰인다** |
| Q4. `CallerRunsPolicy` | 스레드와 큐가 **모두** 찼을 때만 발동한다. 넘친 작업은 제출한 스레드(=Tomcat 요청 스레드)에서 끝까지 돌고, 그동안 제출 자체가 막힌다 |

### 판정

- **max 8 은 지금 아무 일도 하지 않는다.** `ThreadPoolExecutor`는 core → 큐 → max 순으로 채운다. 큐 50칸이 먼저 차야 하는데, 그 전에 요청은 30초 마감에 걸린다. `AsyncConfig`의 "풀은 세마포어보다 넉넉해야 한다"는 주석이 의도한 상태는 **core 기준으로만** 성립한다
- **큐 대기와 세마포어 대기는 같은 기다림이 아니다.** 세마포어 대기는 20초에서 끊기고 `permit.wait`와 `waiting`에 잡힌다. 큐 대기는 상한이 없어 마감이 지난 뒤에도 스레드를 얻으면 호출을 끝까지 실행한다. 3단계(#176)가 문제 삼은 "버려질 결과를 위한 호출"을 큐가 오히려 늘린다
- **풀에 들어오는 작업 수에는 상한이 없다.** `AICourseCreateRequest`는 시작일 ≤ 종료일만 검사한다. Curator 작업 수 = 여행 일수이므로 30일짜리 요청 1건이 작업 30개를 넘긴다. 어떤 고정 크기도 "언제나 충분"할 수는 없다 → 넘쳤을 때의 동작도 함께 정해야 한다

## 2. 크기를 정하는 기준

스레드가 많을수록 좋은 것도 아니다. 세마포어 앞에서 기다리는 작업은 20초 안에 출입증을 받아야 의미가 있다. 출입증 하나가 Curator 호출 1건(STEP-4 p50 약 8.7초)만큼 묶이므로, 20초 동안 출입증 P장으로 소화할 수 있는 작업은 대략

> P(지금 호출 중) + P × 20 / 8.7(기다리다 차례가 오는 몫) ≈ **3.3 P**

다. 이보다 많은 작업은 스레드를 줘도 세마포어 앞에서 20초를 채우고 포기한다. 그래서 **스레드 수를 P의 배수로 잡으면 "쓸모 있게 기다릴 수 있는 만큼"이 손잡이 하나(P)를 따라 움직인다.**

## 3. 후보

| 방식 | 내용 | 장점 | 걸리는 점 |
|---|---|---|---|
| A. 고정 크기 상향 | core = max = 16 같은 고정값 | 변경이 가장 작다 | P를 바꿀 때마다 풀도 손으로 맞춰야 한다 — 지금의 어긋남이 생긴 원인 그대로 |
| **B. P에서 유도** | core = max = P × 4, 큐·`CallerRunsPolicy` 유지 | **손잡이가 `max-concurrent-calls` 하나가 된다.** P=4 → 16 | `AsyncConfig`가 LLM 설정을 읽게 된다(의존 추가). 넘침(16 초과)은 여전히 큐로 간다 |
| C. 가상 스레드 | 작업마다 가상 스레드, 세마포어가 유일한 상한 | 크기 고민 자체가 사라진다 | 스레드 풀 지표가 없어진다. Java 21 의 pinning 이 이 HTTP 스택에서 없는지 따로 검증해야 한다. 변경 폭이 크다 |
| D. 넘침을 거절 | B + 큐 0 + `AbortPolicy` | 넘친 작업이 즉시 실패 → 그 day 는 바로 폴백. 마감 뒤 호출이 생기지 않는다 | Planner 가 거절되면 코스 전체가 기본 플랜으로 떨어진다. 과부하 시 동작 정책을 바꾸는 결정이라 별개로 재야 한다 |

## 4. 결정

**B를 택했다** — core = max = `max-concurrent-calls` × 4 (`AsyncConfig.THREADS_PER_PERMIT`)

- 이슈 목표("상한을 바꾸는 손잡이를 하나로")를 정확히 겨냥하면서 변경 폭이 작다
- 넘침 동작(큐 + `CallerRunsPolicy`)은 그대로 둔다. 바꾸면 이번 측정의 전후 차이를 어느 쪽 효과로 볼지 가를 수 없다. D 는 별개 후보로 남기고, 일수 상한은 [#178](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/178)로 뗐다
- **배수는 설정값에서 계산하지 않고 4로 고정했다.** `1 + timeout-ms / 예상 호출 시간`으로 계산하면 대기 상한을 바꿔도 따라오지만, "예상 호출 시간"이라는 설정이 하나 더 생긴다. 대기 상한을 바꿀 일은 드물고, 이 값은 정밀할 필요가 없다 — 많으면 스레드 몇 개를 더 쓸 뿐이고, 적으면 줄이 큐로 넘어가는 것이 진짜 문제다

### 바꾼 것

- `AsyncConfig.aiAgentExecutor(AiLlmProperties)` — 슬롯 수를 받아 `agentExecutorFor(int)`로 만든다. 벤치마크 하네스는 스프링 컨텍스트 없이 `agentExecutorFor(하네스 슬롯 수)`를 불러, 슬롯을 바꿔 재도 풀이 운영과 같은 규칙으로 따라온다
- 운영 슬롯은 아직 2 그대로라 풀은 core 4 / max 8 → **8 / 8** 이 된다. 슬롯 4 측정 조건에서는 16 / 16
- 회귀 테스트 `AsyncConfigTest` — 스레드 수 = 슬롯 × 4, core = max, 슬롯 × 4 개가 동시에 와도 큐가 비어 있다(이전 설정이면 작업 4개만 시작해 실패한다)
- 환각률 하네스(`AiPipelineHallucinationBenchmarkTest`, 슬롯 2)의 풀도 4 → 8 이 된다. 품질을 재는 하네스라 결과에 영향은 없을 것으로 보지만, 재실행 시 지연 수치를 이전과 비교하지 않는다

### 함께 확인할 것

- **세마포어 공정성.** `new Semaphore(P)`는 비공정이라, 출입증이 반납되는 순간 새로 온 작업이 오래 기다린 작업을 앞지를 수 있다. 큐는 FIFO 였으므로, 줄을 세마포어로 옮기면 순서 보장이 약해진다. 전후 측정에서 오래 기다린 요청의 마감 초과가 늘었는지 본다
