# STEP-4-2 — 네이버 지역검색 호출 줄이기 (#179)

> **결론**: 429 를 재시도로 덮기 전에 호출 자체를 감사했다. 요청 1건의 네이버 HTTP 52.2회 중 30회가 스타일 수식어 질의였고, 그 **84%가 쓸 후보 0건**이었다. 수식어를 맞는 슬롯에만 붙이자(C 규칙) 시더 호출이 요청당 약 45 → 28회로 줄고 네이버 실패율이 동시 3·5명 **23~29% → 4.0%·3.3%**, 동시 8명 51.6 → 10.9%가 됐다. 기본 질의가 5건을 꽉 채운 칸에만 수식어를 보내는 조건을 더하자 시더 호출은 약 25회가 됐고, 실패율은 동시 3명 8.6%·5명 0.5%로 잡음 범위에서 오르내렸다. 잃는 새 후보는 감사 기준 5%다.

## 1. 출발점 — 왜 재시도부터 하지 않았나

[STEP-4](STEP-4-concurrent-calls.md) 4절에서 네이버 429 의 정체를 확인했다. API 키당 50 RPS 인데 요청 1건이 약 45회(시더 호출 기준)를 1초 안에 보내, 동시 3명 이상이면 조회의 18~29%가 실패했다. 첫 대응으로 "초당 제한 429 만 1초 뒤 1회 재시도"를 만들다가 멈췄다 — **45번이 다 필요한지 묻지 않은 채 증상만 덮는 순서**였다. 재시도를 먼저 넣으면 쓸모없는 호출에도 재시도가 붙어 한도 경쟁이 오히려 심해진다. 재시도 코드는 stash 로 보관했다.

다만 **429 분류는 먼저 바로잡았다**(`e952bcc`). 본문 `errorCode`로 초당 제한(`410`·`420` → `RATE_LIMITED`)과 월 한도 소진(`400` → `QUOTA_EXCEEDED`)을 가른다([NCP 공통 오류 코드](https://api.ncloud-docs.com/docs/common-ncpapi)). 어떤 대응을 고르든 맞는 변경이다.

## 2. 왜 45번인가

`CandidateRetrievalStage.seedSpecs`가 시더 호출을 이렇게 만든다.

```
시더 호출 = Σ(day) [ 슬롯 종류 수 × (기본 1 + 스타일 수식어 최대 2) ]  ≈ 3일 × 5종 × 3 = 45
HTTP     = 시더 호출 + 재질의(anchor·location, 기본 질의가 3건 미만일 때)  ≈ 52
```

- **질의를 여러 개로 나누는 것 자체는 API 제약 때문이다** — 지역검색은 1회 최대 5건이고 `start`를 무시해 페이징이 안 된다
- **설계 추정(18~30회)과 어긋났다** — 수식어를 **슬롯 종류와 무관하게 전부 곱해서** `"경주 루프탑 산책로"`, `"경주 역세권 전망대"` 같은 질의가 나간다

## 3. 질의 감사

### 방법

`NaverQueryAuditProbeTest`(`@Tag("benchmark")`). 기준선 30요청(10지역 × 키워드 3세트, 3일)의 **Planner 계획을 실제로 받아 운영 `CandidateRetrievalStage`를 그대로** 돌리고, 네이버 클라이언트·시더를 상속해 지나가는 호출만 기록했다. 질의를 프로브가 재구성하지 않으므로 운영과 같은 질의다.

- 실행기는 동기(`Runnable::run`) — 429 가 섞이지 않고, 시더 호출마다 탈락 지표 증분을 귀속할 수 있다. 재는 것이 지연이 아니라 질의별 결과라 운영과 달라도 된다
- TourAPI·카카오도 실호출(풀 구성과 거리 필터가 운영과 같아야 한다)
- 순기여 = 같은 day·슬롯의 기본 질의에 없던 새 후보 수. 풀 반영 = 그중 최종 풀(Curator 목록)에 오른 수
- 호출 규모: Planner 30 · 네이버 1,567 · 카카오·TourAPI 수백. 실패 0

## 4. 결정 — 수식어별 적용 슬롯 선언 (`cfb8456`)

`StyleTag.appliesTo(SlotType)`가 세 갈래로 가르고, `seedSpecs`는 맞는 슬롯에만 수식어 질의를 만든다.

| 갈래 | 태그 | 적용 슬롯 |
|---|---|---|
| 가게 속성 (기본값) | 분위기·편의·가격·영업시간 | MEAL · CAFE · SHOPPING |
| 장소 종류 | 자연·역사·문화·액티비티·실내 (`cat3` 유래 어휘) | 위 + ATTRACTION · STROLL |
| 붙이지 않음 | 역세권 | 없음 |

- **근거는 30표본의 숫자가 아니라 의미다** — 가게 속성은 업소를 수식하고 `cat3` 유래 어휘는 장소의 종류를 말한다. 감사가 그 구분을 확인했다
- **역세권은 선정에서 빼지 않는다** — `modifiersFor`는 검색 가능한 상위 2개를 고르므로, 빼면 다음 순위가 자리를 채워 감사로 잰 규칙과 다른 질의가 나간다. 검색어를 고칠지는 별도 판단
- **실측으로 확인한 태그는 6개**(조용한·루프탑·주차·프리미엄·자연·역세권)다. 나머지는 의미로 분류했다 — 야경·한옥은 관광 슬롯에서 통할 여지가 있지만 근거가 없어 가게 속성으로 뒀다

## 5. 동시 요청 재측정 (2026-10-04)

STEP-4 와 같은 k6 시나리오(로컬 1대, 슬롯 4, Tomcat 32, 라운드 3회). 비교 대상은 4-1 풀 정렬 뒤 측정(`ai-concurrent-pool16`, 10-03)이고, **동시 8명은 슬롯 4 의 이전 측정이 없어 슬롯 8 측정(`ai-concurrent-slot8`)과 나란히 둔다** — 네이버 지표는 LLM 슬롯과 무관해 비교가 성립하지만 폴백 칸은 비교하지 않는다.

| 측정 | 시더 호출/요청 | 네이버 실패율 | 1초 최대 조회 | 1초 최대 실패 | unfilled |
|---|---|---|---|---|---|
| 전 N=3 | 45.7 | 28.5% (117/411) | 135 | 49 | 0 |
| **후 N=3** | **28.0** | **4.0%** (10/252) | **57** | 7 | 0 |
| 전 N=5 | 44.8 | 22.9% (154/672) | 135 | 90 | 18 |
| **후 N=5** | **28.5** | **3.3%** (14/427) | **56** | 6 | 1 |
| 전 N=8 (슬롯 8) | 45.5 | 51.6% (564/1,092) | 228 | 130 | 51 |
| **후 N=8** | **27.5** | **10.9%** (72/660) | **90** | 28 | 28 |

- 시더 호출이 요청당 약 45 → 28회(−38%)로 줄었다. 감사 시뮬레이션(HTTP 기준 −33%)과 방향이 같다
- 1초 최대 조회가 135 → 57로 내려와 동시 3·5명의 실패율이 **23~29% → 3~4%** 가 됐다
- 동시 8명은 여전히 10.9% — 1초 최대 90회로 한도를 넘는 구간이 남는다
- TourAPI 실패 0(오염 없음)

### Curator 폴백이 늘어난 것은 이 변경 때문이 아니다

동시 3명 폴백 0 → 14.5%, 동시 5명 33 → 46%로 늘었다. 원인은 **측정일의 모델 응답 시간**이다.

| Curator | 전 N=3 | 후 N=3 | 전 N=5 | 후 N=5 |
|---|---|---|---|---|
| 호출당 토큰(입력 / 출력) | 4,076 / 894 | 4,163 / 826 | 4,004 / 889 | 4,077 / 834 |
| **호출당 응답 시간** | **8.04초** | **9.08초** | **7.86초** | **9.28초** |
| 후보 공급 단계 | 1.32초 | 1.11초 | 1.06초 | 1.08초 |

일의 양(토큰)은 같은데 응답이 13~18% 느렸다. 슬롯 4 에서 Curator 가 약 3순배 줄을 서므로 호출당 1초가 마감 30초에 그대로 누적된다. 후보 공급은 오히려 짧아졌다. **LLM 경로 지표는 날짜가 다른 측정끼리 비교하면 안 된다** — STEP-4 한계에 적은 "날짜가 다르다"가 이번에는 결과를 뒤집을 만큼 컸다.

## 6. 남은 호출 재점검 — 기본 질의가 꽉 찼을 때만 수식어 (`1953a70`)

C 규칙 뒤에도 요청당 HTTP 34.8회가 남아, 감사 CSV 로 갈래마다 다시 봤다.

| 갈래 | 요청당 | 판정 | 근거 |
|---|---|---|---|
| 기본 질의 | 약 15 | 유지 | 관광 슬롯 채택에서도 네이버 단독이 TourAPI 보다 많다(관광명소 44 대 25, 산책로 43 대 38, 08-27 최종 코스) |
| 재질의 | 7 | 유지 | 빈손 8~31%, 재질의를 탄 시더가 0건으로 끝난 적이 없다 |
| 같은 요청 안 중복 질의 | 0.5 | 두고 봄 | `경주 맛집` 같은 도시 단위 재질의가 day 끼리 겹친다. 1.4% |
| **기본 질의 첫 응답이 5건 미만인 칸의 수식어** | **3.3** | **제거** | **100회 중 새 후보 0건** |
| 나머지 수식어 | 9.4 | 유지 | 순기여 0.90 |

기본 질의가 5건을 꽉 못 채우는 권역은 데이터가 얇아, 수식어를 붙여도 이미 찾은 곳만 다시 나온다. 그래서 슬롯마다 기본 질의를 먼저 던지고 **첫 응답이 꽉 찼을 때만** 수식어 질의를 이어 던진다. 판단은 필터 전 건수로 한다 — 필터 뒤 수에는 "우리가 버린 것"이 섞여 권역의 데이터 두께를 말하지 못한다. 보내지 않은 수식어는 `ai.candidate.retrieval{result=skipped}`로 센다.

조건부 약한 조합(자연×카페 0.10, 조용한×쇼핑 0.11 등)은 표본이 9~21회로 얇고 태그별 예외가 의미 기반 규칙을 깨서 건드리지 않았다(요청당 약 1.3회).

### 같은 날 전후 측정 (동시 3·5명)

C 규칙 측정(`ai-concurrent-naver42`)과 **같은 날**이다. TourAPI 일일 한도 때문에 동시 8명은 재지 않았다.

| 측정 | 실제 시더 호출/요청 | 건너뜀/요청 | 네이버 실패 | 1초 최대 조회 | 후보 공급 | unfilled |
|---|---|---|---|---|---|---|
| C 규칙 N=3 | 28.0 | – | 4.0% (10/252) | 57 | 1.11초 | 0 |
| **+ 5건 조건 N=3** | **24.7** | 3.4 | 8.6% (19/222) | 60 | 1.11초 | 0 |
| C 규칙 N=5 | 28.5 | – | 3.3% (14/427) | 56 | 1.08초 | 1 |
| **+ 5건 조건 N=5** | **25.4** | 2.7 | 0.5% (2/381) | 82 | 1.28초 | 0 |

- 실제 호출이 요청당 약 3회(−11%) 줄었다. 감사 예측(3.3회)과 맞는다. unfilled 는 늘지 않았다
- **네이버 실패와 1초 최대 조회는 방향이 엇갈린다**(N=3 은 늘고 N=5 는 줄었다). 건수가 한 자릿수~십여 건이라 잡음 범위다 — "두 물결로 나뉘어 1초 최대가 낮아진다"는 기대는 **확인되지 않았다**
- 후보 공급은 N=5 에서 0.2초 늘었다(왕복 한 번 대기의 대가)
- Curator 폴백(N=3 24 → 6, N=5 126 → 96)은 오후의 모델 응답이 빨라서다(Curator 호출 9.08 → 8.54초, 9.28 → 8.33초). 이 변경에 귀속하지 않는다

## 7. 남은 429 — 재시도는 보류

| 판단 근거 | 내용 |
|---|---|
| 동시 5명 이하에서 남은 실패가 품질에 거의 닿지 않는다 | 네이버 실패 3~4% 안팎, unfilled 0~1 |
| 재시도는 마감에 붙은 경로에 시간을 더한다 | 429 를 맞은 요청의 후보 공급이 1~2초 늘어난다. LLM 경로는 이미 30초 경계에 있다(측정일 모델 속도 차이만으로 폴백이 0 ↔ 14% 를 오갔다) |
| 동시 8명의 병목은 네이버가 아니다 | 같은 측정에서 Curator 폴백 70% — LLM 처리 능력이 먼저 막힌다 |

**재검토 조건**: 운영에서 네이버 실패가 10% 안팎으로 지속될 때. 운영 서버 여러 대가 키 하나를 같이 써서 초당 한도가 합산이므로, 로컬 동시 6~8명에 해당하는 부하가 서버당 3~4명에서 생길 수 있다. 운영에서 보는 지표는 `ai.candidate.retrieval{source=naver_local,result=failed}`와 WARN 로그의 `RATE_LIMITED`다.

**서버당 호출 속도 제한은 더 싸졌다** — 호출이 줄어 단일 요청이 잃는 시간이 약 0.8초에서 약 0.1초로 줄었다. 다만 부하가 높을 때 호출을 몇 초에 걸쳐 흩어 보내게 되므로 지금 단계에서는 재시도와 같은 이유로 넣지 않는다.

**한도 단위는 확인됐다** — [STEP-4](STEP-4-concurrent-calls.md) 4절에서 "콘솔에서 확인할 거리"로 남겼던 일 25,000 / 월 775,000 은 NAVER API HUB 개요 기준 **월 775,000건(월 단위 관리, 일 한도 없음)** 이다. 일 25,000건은 이관 전 개발자센터 한도였다. 설계 문서를 그에 맞춰 바로잡았다(`65fd2fc`).
