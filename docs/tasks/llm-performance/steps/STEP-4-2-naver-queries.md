# STEP-4-2 — 네이버 지역검색 호출 줄이기 (#179)

> **결론**: 429 를 재시도로 덮기 전에 호출 자체를 감사했다. 요청 1건의 네이버 HTTP 52.2회 중 30회가 스타일 수식어 질의였고, 그 **84%가 쓸 후보 0건**이었다. 수식어를 맞는 슬롯에만 붙이는 규칙으로 요청당 약 **34.8회(−33%)**, 잃는 새 후보는 5%다. 동시 요청 재측정과 재시도 필요성 판단은 아래 4절.

## 1. 출발점 — 왜 재시도부터 하지 않았나

[STEP-4](STEP-4-concurrent-calls.md) 4절에서 네이버 429 의 정체를 확인했다. API 키당 50 RPS 인데 요청 1건이 약 45회(시더 호출 기준)를 1초 안에 보내, 동시 3명 이상이면 조회의 18~29%가 실패했다. 첫 대응으로 "초당 제한 429 만 1초 뒤 1회 재시도"를 만들다가 멈췄다 — **45번이 다 필요한지 묻지 않은 채 증상만 덮는 순서**였다. 재시도를 먼저 넣으면 쓸모없는 호출에도 재시도가 붙어 한도 경쟁이 오히려 심해진다. 재시도 코드는 stash 로 보관했다.

다만 **429 분류는 먼저 바로잡았다**(`e952bcc`). 본문 `errorCode`로 초당 제한(`410`·`420` → `RATE_LIMITED`)과 월 한도 소진(`400` → `QUOTA_EXCEEDED`)을 가른다([NCP 공통 오류 코드](https://api.ncloud-docs.com/docs/common-ncpapi)). 어떤 대응을 고르든 맞는 변경이다.

## 2. 왜 45번인가

`CandidateRetrievalStage.seedSpecs`가 시더 호출을 이렇게 만든다.

```
시더 호출 = Σ(day) [ 슬롯 종류 수 × (기본 1 + 스타일 수식어 최대 2) ]  ≈ 3일 × 5종 × 3 = 45
HTTP     = 시더 호출 + 재질의(anchor·location, 기본 질의가 3건 미만일 때)  ≈ 52
```

- **질의를 여러 개로 나누는 것 자체는 API 제약 때문이다** — 지역검색은 1회 최대 5건이고 `start`를 무시해 페이징이 안 된다
- **설계 추정(18~30회)과 어긋났다** — 수식어를 **슬롯 종류와 무관하게 전부 곱해서** `"경주 루프탑 산책로"`, `"경주 역세권 전망대"` 같은 질의가 나간다

## 3. 질의 감사

### 방법

`NaverQueryAuditProbeTest`(`@Tag("benchmark")`). 기준선 30요청(10지역 × 키워드 3세트, 3일)의 **Planner 계획을 실제로 받아 운영 `CandidateRetrievalStage`를 그대로** 돌리고, 네이버 클라이언트·시더를 상속해 지나가는 호출만 기록했다. 질의를 프로브가 재구성하지 않으므로 운영과 같은 질의다.

- 실행기는 동기(`Runnable::run`) — 429 가 섞이지 않고, 시더 호출마다 탈락 지표 증분을 귀속할 수 있다. 재는 것이 지연이 아니라 질의별 결과라 운영과 달라도 된다
- TourAPI·카카오도 실호출(풀 구성과 거리 필터가 운영과 같아야 한다)
- 순기여 = 같은 day·슬롯의 기본 질의에 없던 새 후보 수. 풀 반영 = 그중 최종 풀(Curator 목록)에 오른 수
- 호출 규모: Planner 30 · 네이버 1,567 · 카카오·TourAPI 수백. 실패 0

### 결과 (2026-10-04)

| 질의 종류 | 질의 | 남은 후보 0건 | 남은 후보 평균 | 순기여 |
|---|---|---|---|---|
| 기본 | 452 | **0%** | 3.58 | – |
| 수식어 | 904 | **84%** | 0.35 | **0.29** |

새 후보 1건에 기본 질의는 약 0.4회, **수식어 질의는 약 3.4회**가 든다.

**슬롯별 (수식어 질의)**

| 슬롯 | 0건 | 순기여 |
|---|---|---|
| CAFE | 68% | 0.72 |
| MEAL | 72% | 0.58 |
| SHOPPING | 85% | 0.27 |
| ATTRACTION | 88% | 0.12 |
| EXPERIENCE · STROLL · VIEWPOINT | 93~95% | 0.03~0.06 |

**수식어별로 갈리는 지점**

- **역세권**(`NEAR_STATION`) — 전 슬롯 0건 97~100%. 검색어 자체가 통하지 않는다
- **자연**(`NATURE`) — 관광 슬롯에서 유일하게 통한다. 관광명소 순기여 0.59
- **무인지 지역** — 수식어 질의 0건 92%(유명 지역 77%)

**채택과 교차 확인** — 2026-08-27 파이프라인 벤치마크 최종 코스(30요청, 525곳)에서 수식어 질의 유래 채택 84곳 중 **식사·카페·쇼핑이 66곳(79%)**, 관광 슬롯 18곳 중 **16곳이 자연**이었다. 공급 쪽과 품질 쪽이 같은 방향이다.

## 4. 결정 — 수식어별 적용 슬롯 선언 (`cfb8456`)

`StyleTag.appliesTo(SlotType)`가 세 갈래로 가르고, `seedSpecs`는 맞는 슬롯에만 수식어 질의를 만든다.

| 갈래 | 태그 | 적용 슬롯 |
|---|---|---|
| 가게 속성 (기본값) | 분위기·편의·가격·영업시간 | MEAL · CAFE · SHOPPING |
| 장소 종류 | 자연·역사·문화·액티비티·실내 (`cat3` 유래 어휘) | 위 + ATTRACTION · STROLL |
| 붙이지 않음 | 역세권 | 없음 |

- **근거는 30표본의 숫자가 아니라 의미다** — 가게 속성은 업소를 수식하고 `cat3` 유래 어휘는 장소의 종류를 말한다. 감사가 그 구분을 확인했다
- **역세권은 선정에서 빼지 않는다** — `modifiersFor`는 검색 가능한 상위 2개를 고르므로, 빼면 다음 순위가 자리를 채워 감사로 잰 규칙과 다른 질의가 나간다. 검색어를 고칠지는 별도 판단
- **실측으로 확인한 태그는 6개**(조용한·루프탑·주차·프리미엄·자연·역세권)다. 나머지는 의미로 분류했다 — 야경·한옥은 관광 슬롯에서 통할 여지가 있지만 근거가 없어 가게 속성으로 뒀다

## 5. 동시 요청 재측정

⬜ 진행 전. 규칙을 넣어도 요청 1건이 약 35회를 1초 안에 보내 **동시 2건이면 여전히 50 RPS 를 넘을 수 있다.** 동시 3·5·8명으로 네이버 실패율·unfilled 를 재고, 남은 429 를 보고 재시도(stash)를 되살릴지 정한다.
