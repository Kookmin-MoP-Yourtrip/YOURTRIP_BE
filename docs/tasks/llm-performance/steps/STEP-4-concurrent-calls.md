# `max-concurrent-calls` 조정 — 슬롯을 넓히자 병목이 스레드 풀로 옮겨갔다

> [LLM 호출 경로 성능·안정성 로드맵](../README.md)의 4단계이며, [#108](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/108)의 설계·진행 기록이다. 비교 기준은 [STEP-2](STEP-2-baseline.md)(동시 호출 2)다.
>
> **결론** — 동시 호출을 2 → 4로 올리자 단일 요청의 Curator 슬롯 대기가 사라져 **p50 20.3 → 15.7초, p95 24.1 → 18.6초**가 됐고, 동시 3명의 폴백이 **42% → 7%** 로 줄었다. 하지만 동시 5명에서는 여전히 **38%** 가 폴백이다. 이때 슬롯 대기는 0인데, **`aiAgentExecutor`(core 4)의 작업 큐가 최대 11개까지 쌓였다** — 병목이 세마포어에서 스레드 풀로 옮겨갔고, 그 대기는 지금 어떤 지연 지표에도 잡히지 않는다.

## 측정 조건 (2026-10-03)

STEP-2 와 같다. 바꾼 것은 동시 호출 수 하나다.

- 단일 요청: `LATENCY_BASELINE_MAX_CONCURRENT_CALLS=4` (하네스가 이 값만 환경변수로 받게 했다 — 기준선과 같은 커밋의 같은 하네스)
- 동시 요청: 서버를 `LLM_MAXCONCURRENTCALLS=4`로 띄움(기동 로그 `maxConcurrentCalls=4` 확인), 나머지는 STEP-2 와 같음
- `application.yml`은 바꾸지 않았다

## 1. 단일 요청 30건

| 지표 | 동시 호출 2 (STEP-2) | 동시 호출 4 |
|---|---|---|
| 요청 전체 | p50 20,309 · p95 24,097 · max 24,387 | p50 **15,744** · p95 **18,571** · max 18,888 |
| Planner | p50 5,263 · p95 6,782 | p50 5,699 · p95 7,785 |
| **Curator** | p50 13,851 · p95 17,772 | p50 **8,706** · p95 **11,853** |
| Curator 슬롯 대기 (요청별 합) | 30 / 30건, p50 6,393 | **0 / 30건** |
| 폴백 · LLM 실패 · 슬롯 포기 | 0 · 0 · 0 | 0 · 0 · 0 |
| 코스당 토큰 | p50 16,940 | p50 16,878 |

(단위 ms)

- Curator 3개가 한 번에 나가면서 세 번째 호출의 대기가 사라졌다. **Curator 단계 p50 이 5.1초 줄었다** — 1단계 E2E 로 예상한 "약 5초"와 맞는다
- 토큰은 그대로다. 비용은 늘지 않고 시간만 줄었다
- Planner 가 0.4~1초 느려진 것은 슬롯과 무관하다(Planner 대기는 양쪽 모두 0). 모델 응답 시간의 날짜 간 차이로 본다

|   | Curator 폴백 | 10.2% | **0%** |

- **동시 호출 4 에서 슬롯 대기(`permit.wait`)·`waiting` 게이지가 모든 N에서 0이다.** 그런데 N=3·5 에서 라운드 안의 소요가 약 15 → 23 → 30초로 **계단식**이다 — 어딘가에서 줄을 서고 있다

## 3. 병목이 옮겨간 곳 — `aiAgentExecutor`

같은 폴링 스냅샷의 `executor_*` 지표(`name="aiAgentExecutor"`):

| 측정 | active 최대 | 풀 크기 | **큐 최대** |
|---|---|---|---|
| 동시 호출 2, N=3 | 4 | 4 | 5 |
| 동시 호출 2, N=5 | 4 | 4 | 11 |
| 동시 호출 4, N=3 | 4 | 4 | 5 |
| 동시 호출 4, N=5 | 4 | 4 | **11** |

- 풀이 **core 4 / max 8 / 큐 50** 이라, 큐 50칸이 다 차기 전에는 스레드가 4개에서 늘지 않는다. Planner·Curator 호출이 전부 이 풀에서 돌므로 **실질 동시 LLM 호출 상한은 세마포어가 아니라 이 4다.** 슬롯을 4로 올린 순간 둘이 같아져 세마포어는 사실상 하는 일이 없어졌다
- **기준선(동시 호출 2)에도 같은 큐 대기가 있었다.** STEP-2 의 "Curator 슬롯 대기"는 세마포어 대기만 셌으므로, 동시 요청에서의 실제 대기를 **과소평가**했다
- **이 대기는 어떤 지연 지표에도 없다.** `ai.llm.permit.wait`는 작업이 스레드를 얻은 뒤 세마포어 앞에서의 대기만 재고, `ai.llm.call`은 그 뒤만 잰다. 큐에 들어가 스레드를 기다린 시간은 비어 있다

### 다음 결정에 주는 함의

- **동시 호출 수를 5 이상으로 올리는 것은 이 상태로는 무의미하다.** 스레드가 4개라 5번째 호출은 어차피 큐에서 기다린다. 풀 크기를 함께 바꿔야 하고, 그건 별개 변경이라 따로 재야 한다
- **3단계의 성격이 바뀐다.** 큐에서 기다리던 작업은 마감이 지난 뒤에 스레드를 얻어도 호출 전체를 실행한다. JDK 구현상 `CompletableFuture.supplyAsync`의 작업은 **시작 전에 future 가 취소돼 있으면 실행하지 않는다** — 즉 큐에 있는 작업은 인터럽트 없이 `cancel`만 불러도 버릴 수 있다(학습 테스트로 확인 필요). 지금은 에이전트가 마감 때 `cancel`을 아예 부르지 않는다
- **측정 공백을 먼저 메운다.** 큐 대기를 재지 않으면 풀 크기 조정이든 취소든 효과를 볼 수 없다
