# `max-concurrent-calls` 조정 — 슬롯을 넓히자 병목이 스레드 풀로 옮겨갔다

> [LLM 호출 경로 성능·안정성 로드맵](../README.md)의 4단계이며, [#108](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/108)의 설계·진행 기록이다. 비교 기준은 [STEP-2](STEP-2-baseline.md)(동시 호출 2)다.
>
> **결론** — 동시 호출을 2 → 4로 올리자 단일 요청의 Curator 슬롯 대기가 사라져 **p50 20.3 → 15.7초, p95 24.1 → 18.6초**가 됐고, 동시 3명의 폴백이 **42% → 7%** 로 줄었다. 하지만 동시 5명에서는 여전히 **38%** 가 폴백이다. 이때 슬롯 대기는 0인데, **`aiAgentExecutor`(core 4)의 작업 큐가 최대 11개까지 쌓였다** — 병목이 세마포어에서 스레드 풀로 옮겨갔고, 그 대기는 지금 어떤 지연 지표에도 잡히지 않는다.
>
> **8 (풀 정렬 #177 뒤)** — 동시 5명의 폴백이 **33 → 0%**, p95 30.1 → 25.5초가 됐다. 새 한계는 동시 5명과 8명 사이(8명 폴백 10%)다. 측정 중 **네이버 지역 검색의 초당 호출 제한(429)** 이 드러났다 — 동시 8명에서 조회의 52%가 실패했고, 이전 측정에도 18~29% 섞여 있었다(4절).

## 측정 조건 (2026-10-03)

STEP-2 와 같다. 바꾼 것은 동시 호출 수 하나다.

- 단일 요청: `LATENCY_BASELINE_MAX_CONCURRENT_CALLS=4` (하네스가 이 값만 환경변수로 받게 했다 — 기준선과 같은 커밋의 같은 하네스)
- 동시 요청: 서버를 `LLM_MAXCONCURRENTCALLS=4`로 띄움(기동 로그 `maxConcurrentCalls=4` 확인), 나머지는 STEP-2 와 같음
- `application.yml`은 바꾸지 않았다

## 3. 병목이 옮겨간 곳 — `aiAgentExecutor`

같은 폴링 스냅샷의 `executor_*` 지표(`name="aiAgentExecutor"`):

| 측정 | active 최대 | 풀 크기 | **큐 최대** |
|---|---|---|---|
| 동시 호출 2, N=3 | 4 | 4 | 5 |
| 동시 호출 2, N=5 | 4 | 4 | 11 |
| 동시 호출 4, N=3 | 4 | 4 | 5 |
| 동시 호출 4, N=5 | 4 | 4 | **11** |

- 풀이 **core 4 / max 8 / 큐 50** 이라, 큐 50칸이 다 차기 전에는 스레드가 4개에서 늘지 않는다. Planner·Curator 호출이 전부 이 풀에서 돌므로 **실질 동시 LLM 호출 상한은 세마포어가 아니라 이 4다.** 슬롯을 4로 올린 순간 둘이 같아져 세마포어는 사실상 하는 일이 없어졌다
- **기준선(동시 호출 2)에도 같은 큐 대기가 있었다.** STEP-2 의 "Curator 슬롯 대기"는 세마포어 대기만 셌으므로, 동시 요청에서의 실제 대기를 **과소평가**했다
- **이 대기는 어떤 지연 지표에도 없다.** `ai.llm.permit.wait`는 작업이 스레드를 얻은 뒤 세마포어 앞에서의 대기만 재고, `ai.llm.call`은 그 뒤만 잰다. 큐에 들어가 스레드를 기다린 시간은 비어 있다

### 다음 결정에 주는 함의

- **동시 호출 수를 5 이상으로 올리는 것은 이 상태로는 무의미하다.** 스레드가 4개라 5번째 호출은 어차피 큐에서 기다린다. 풀 크기를 함께 바꿔야 하고, 그건 별개 변경이라 따로 재야 한다
- **3단계의 성격이 바뀐다.** 큐에서 기다리던 작업은 마감이 지난 뒤에 스레드를 얻어도 호출 전체를 실행한다. JDK 구현상 `CompletableFuture.supplyAsync`의 작업은 **시작 전에 future 가 취소돼 있으면 실행하지 않는다** — 즉 큐에 있는 작업은 인터럽트 없이 `cancel`만 불러도 버릴 수 있다(학습 테스트로 확인 필요). 지금은 에이전트가 마감 때 `cancel`을 아예 부르지 않는다
- **측정 공백을 먼저 메운다.** 큐 대기를 재지 않으면 풀 크기 조정이든 취소든 효과를 볼 수 없다

## 4. 동시 호출 8 — 풀 정렬(#177) 뒤 (2026-10-03)

[#177](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/177)로 풀이 슬롯 × 4 를 따라가게 된 뒤라, `LLM_MAXCONCURRENTCALLS=8` 하나만 바꿔 쟀다(기동 지표 `aiAgentExecutor` 32 / 32 확인). 비교 기준은 같은 날 같은 코드의 슬롯 4 측정([STEP-4-1](STEP-4-1-executor-sizing.md) 5절)이다. **로컬 서버 1대라 8은 보수적 기준 계정 전체 상한(9.6) 안이다 — 운영값 후보가 아니라 "슬롯을 넓히면 얼마나 얻는가"를 본 측정이다.**

- 공통: 201 전부, LLM 실패 0, 빠른 API p95 2.5~4.2ms, `aiAgentExecutor` 큐 0
- **동시 5명의 폴백이 사라졌다(33 → 0%).** 코스 1건이 슬롯을 약 32초(Planner 5 + Curator 3 × 9) 쓰므로 5명이 30초 안에 끝나려면 슬롯 6~7개가 필요하다는 계산과 맞는다. 4-1 과 달리 이번에는 **처리 능력이 늘었으므로** 이 개선은 변경의 효과다
- **새 한계는 동시 5명과 8명 사이다.** 8명에서는 라운드마다 뒤쪽 2~3건이 다시 마감에 걸린다
- 동시 2명은 재지 않았다 — 아래 TourAPI 한도 때문에 멈췄다. 슬롯 4 에서도 폴백 0%라 결론에 영향이 없다

### 측정 중 드러난 다른 병목

- **네이버 지역 검색이 초당 호출 제한에 걸린다.** 서버 로그에 `429 TOO_MANY_REQUESTS` · `{"errorCode":"420","message":"Rate Limited"}`가 찍힌다. 동시 8명에서 네이버 조회의 **52%**(564 / 1,092)가 실패했고, 그 결과 폴백할 후보가 없는 슬롯(unfilled 51, 주로 식사·카페)이 크게 늘었다. **이 실패는 이전 측정에도 섞여 있었다** — 동시 3명 이상에서 18~29%(STEP-2·STEP-4·STEP-4-1 공통). 측정마다 비슷한 수준이고 LLM 경로의 폴백·대기 비교에는 직접 영향이 없지만, unfilled 와 코스 품질 수치는 이 실패에 오염돼 있다
- **`placeGroundingExecutor`가 #177 이전의 `aiAgentExecutor`와 같은 모양이다.** core 8 / max 16 / 큐 200 이라 큐가 다 차기 전에는 스레드가 8개에서 늘지 않는다. 큐 최대는 동시 5명 55(슬롯 4) → 100(슬롯 8), 동시 8명 142 였고, 동시 8명에서는 풀이 16으로 늘었다 — 큐가 순간적으로 200 에 닿았다는 뜻이다(1초 폴링이라 최대값이 덜 찍혔다). 장소 API 는 0.15~0.3초짜리라 아직 지연을 망가뜨리지는 않았지만, LLM 쪽이 넓어질수록 다음 병목이 된다

## 한계

- 로컬 단일 인스턴스, 동시 N별 6~15건 — STEP-2 와 같다

- 동시 호출 3은 재지 않았다 — 4가 0단계 보수적 상한 안이고, 스레드 풀이 4라 3 과 4 사이의 선택이 결과를 크게 바꾸지 않을 것으로 봤다
