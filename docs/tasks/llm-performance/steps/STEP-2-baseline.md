# 기준선 측정 — 운영값에서 LLM 슬롯이 품질을 깎는 지점

> [LLM 호출 경로 성능·안정성 로드맵](../README.md)의 2단계이며, [#175](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/175)의 기록이다. [#108](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/108)의 "개선 전" 측정을 겸한다.
>
> **결론** — 단일 요청은 30건 전부 예산 안(p95 24.1초)이지만, **Curator 슬롯 대기가 매 요청 5.2~8.4초 발생한다.** 동시 사용자가 2명만 돼도 요청이 30초 마감에 걸리기 시작하고, **3명이면 Curator 슬롯의 42%, 5명이면 74%가 폴백으로 채워진다.** 응답은 전부 201이라 에러율로는 보이지 않는다.

## 측정 조건 (2026-10-02)

- **운영값**: 예산 30초, `llm.timeout-ms` 20초, `max-concurrent-calls` 2, 재시도 3·2
- 입력: `BaselineInputSet` (지역 10 × 키워드 3, 3일). 웜업 1건 제외
- 단일 요청: `AiCourseLatencyBaselineTest` (in-process, 운영 실행기 풀, 요청 간 5초, 슬롯이 빈 뒤 증분 수집)
- 동시 요청: `scripts/k6/ai-course-concurrent.js`, 로컬 bootRun (`SERVER_TOMCAT_THREADS_MAX=32`), N명 × 3라운드, 라운드 간격 90초, 빠른 API(`GET /api/upload-courses/popular`) 초당 2건 병행. 집계는 `scripts/loadtest/aggregate-ai.py`

| 후보 공급 | 0.5~0.9s | 878 | 1,332 | 2,035 |
| **Curator** | 3.0~6.0s | **13,851** | **17,772** | 18,121 |

| URL 보강 | 0.2~0.4s | 172 | 415 | 443 |

- **Curator 슬롯 대기 (요청별 합)**: 30 / 30건에서 발생, p50 6.4초 · p95 8.0초 · min 5.2초. 유명·무인지 지역 차이 없음. 1단계 표본 1건(8.1초)은 우연이 아니라 **구조적**이다 — Curator 3개가 슬롯 2개에 두 라운드로 나뉜다
- Curator 단계(p50 13.9초)는 설계 상단(6초)의 2배를 넘는다. 이 중 약 6.4초가 대기이고, 나머지가 두 번째 라운드 호출 시간이다
- Planner도 설계보다 1.3~3초 느리다(대기 0, 순수 모델 시간)
- 폴백 0 / 545 슬롯, Planner 기본 플랜 0, 슬롯 대기 포기 0, LLM 실패 0, 마감 근접 0
- 토큰: 코스당 p50 16,940 (max 18,244), 응답당 평균 p50 4,235 (max 4,561). STEP-0 표본 1건(4,105)을 확인했다 — **0단계 상한(서버당 4~8)이 그대로 유효**하다
- STEP-8(예산 180초 조건, p50 22.3 · p95 29.4초)보다 빠른 것은 이후 개선(#164 등)과 조건 차이가 섞인 결과라 직접 비교하지 않는다

## 2. 동시 요청 — N별 (각 3라운드)

| N | AI 요청 | 클라이언트 p50 / p95 (ms) | 30초 마감 도달 | Curator 대기 (요청당) | **Curator 폴백** | unfilled | Tomcat busy 최대 | 빠른 API p95 |
|---|---|---|---|---|---|---|---|---|
| 2 | 6 (201 ×6) | 20,491 / 30,110 | 3 / 6 | 14.4s | **11 / 108 (10.2%)** | 7 | 4 | 3.5ms |
| 3 | 9 (201 ×9) | 30,053 / 30,092 | 6 / 9 | 19.4s | **68 / 162 (42.0%)** | 10 | 5 | 3.0ms |
| 5 | 15 (201 ×15) | 30,067 / 30,093 | 12 / 15 | 21.3s | **201 / 271 (74.2%)** | 4 | 7 | 3.0ms |

- **N=3부터 "라운드당 1명만 정상, 나머지는 30초 + 폴백"** 패턴이 고정된다. 각 라운드에서 가장 빨리 끝난 1건(19~22초)만 예산 안이다
- **슬롯 대기 포기(`timeout`)는 한 번도 없다.** 20초 상한보다 30초 마감이 먼저 대기를 끊기 때문이다 — 사용자에게 가는 저하는 전부 "마감 → 폴백" 경로다
- LLM 비성공 결말 0: 폴백으로 버려진 day의 호출도 **마감 뒤에 끝까지 돌아 성공했다** — 결과는 버려지고 슬롯·토큰만 썼다(3단계 근거)
- Tomcat busy 최대 7, 빠른 API p95 3ms대로 영향 없음 — 이 규모에서는 워커 고갈이 아니라 **LLM 슬롯이 유일한 병목**이다
- 응답은 전부 201이라 HTTP 에러율로는 저하가 보이지 않는다. `ai_curation_slot_total{result="fallback"}`이 유일한 신호다

## 판정 — 다음 단계에 주는 함의

- **4단계(#108)를 먼저 한다.** 단일 요청에서도 대기 6.4초(요청의 약 30%)가 매번 생기고, 동시 3명에서 폴백 42%다. 코스 1건이 슬롯을 약 24초(호출 4회 × 약 6초) 쓰므로 슬롯 2개로는 동시 3명에 약 36초, 5명에 약 60초가 필요하다 — 슬롯 4개면 5명도 약 30초 안이다. 0단계 상한(서버당 4) 안에서 2 → 3 → 4로 올리며 이 문서의 두 표를 다시 잰다
- **3단계(마감 뒤 남는 호출 정리, [#176](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/176))는 4단계 측정 뒤 판단한다.** 동시 3·5명에서 폴백이 42%·74%인데 LLM 호출 실패는 0건이다 — 폴백으로 버려진 day 의 호출도 마감 뒤 끝까지 돌아 성공했다. 처음에는 이 점유가 4단계 측정을 오염시킨다고 보고 3단계를 앞에 뒀으나, 라운드 간격(90초) 덕분에 다음 라운드로 넘어가지 않아 근거가 약했다. 남는 호출이 폴백을 얼마나 키웠는지는 이번 측정으로 재지 못했다
- **5단계(Planner 상한)는 근거 없음** — Planner 대기 0, 기본 플랜 0. 착수하지 않는다
- **별도(AI 동시 입장 제한)**: 로컬 5명까지 Tomcat 영향이 없어 시급하지 않다. 4단계 뒤 재평가한다

## 한계

- 로컬 개발 머신 단일 인스턴스다. 운영(t3.small vCPU 2, ASG 최대 2대, 계정 단위 TPM 공유)의 CPU·인스턴스 간 경합은 재현하지 않았다
- 동시 시나리오의 "응답 뒤 남은 호출"은 HTTP 경로라 요청별로 귀속하지 못했다(하네스의 `drainMs`는 단일 요청에서 전부 0)
- 표본: 동시 N별 6~15건. 폴백 비율의 경향은 뚜렷하지만 소수점 정밀도는 없다
