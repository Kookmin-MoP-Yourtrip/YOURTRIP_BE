# 호출당 토큰 실측 — TPM 한도를 동시 호출 상한으로 바꾼다

> [LLM 호출 경로 성능·안정성 로드맵](../README.md)의 0단계 보완이며, [#174](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/174)의 설계·진행 기록이다.
>
> **결론** — 3일 코스 1건이 실제로 쓰는 토큰은 **16,418개**(호출 평균 약 4,100개)다. Tier 1 한도(500K TPM)를 동시 호출로 환산하면 서버 한 대당 **약 4.8개(보수적) ~ 8.1개(실사용 기준)**다. 지금의 `max-concurrent-calls: 2`는 한도의 절반 이하만 쓰고 있고, **#108에서 2 → 3 → 4로 올려 보는 범위는 보수적 기준으로도 한도 안이다.**

## 왜 필요했나

0단계에서 조직 한도(Tier 1, `gpt-5.6-luna` 500,000 TPM / 500 RPM)를 확인했다. RPM 기준 동시 호출은 약 66개라 걸림돌이 아니고, **실제로 먼저 걸리는 쪽은 TPM**이다. 그런데 TPM을 동시 호출 수로 바꾸려면 호출당 토큰 수가 필요했고, 어댑터가 응답의 `usage`를 읽지 않아 **그 값이 어디에도 남지 않았다.** 그래서 0단계 환산표는 5k·10k·20k를 가정한 범위로만 남아 있었다.

## 추가한 지표

| 이름 | 종류 | 태그 |
|---|---|---|
| `ai.llm.tokens` | DistributionSummary (히스토그램, 1 ~ 100,000) | `agent`, `type`=`input`·`output`·`reasoning`·`cached` |

- **호출이 아니라 HTTP 응답 단위로 센다.** 의미 재시도는 한 호출 안에서 응답을 두 번 받고, 응답이 잘려도 토큰은 다 쓴다. 둘 다 TPM을 소모하므로 빠뜨리면 한도 계산이 낙관적이 된다. 그래서 응답을 판정(절단·스키마 검사)하기 **전에** 기록한다. 이 값의 `count`가 `ai.llm.call`의 `count`보다 클 수 있다
- **`type` 사이의 포함 관계**: `input`은 `cached`를 포함하고, `output`은 `reasoning`을 포함한다(OpenAI `usage` 정의 그대로). 더하면 이중 계산이다
- 지연 지표와 마찬가지로 **기동 시점에 0으로 등록**한다(agent × type 12개 시계열)

### 테스트가 잡은 결함 — "모름"이 "0 토큰"으로 기록됐다

처음 구현은 Spring AI의 벤더 중립 `Usage` 인터페이스에서 입력·출력 토큰을 읽었다. 그런데 "`usage`가 없는 응답이면 아무것도 기록하지 않는다" 테스트가 실패했다. **Spring AI는 응답에 `usage`가 없어도 0으로 채운 객체를 대신 넘겨 준다.** 그대로 쓰면 "모른다"가 "0 토큰 썼다"로 기록되고 호출당 평균이 내려간다. 한도 계산이 낙관적으로 틀어지는 방향이다.

그래서 **벤더 원본 `OpenAiApi.Usage`가 있을 때만** 기록하도록 바꿨다. 원본이 있다는 것 자체가 응답에 `usage`가 실려 왔다는 뜻이고, 추론·캐시 토큰도 원본에만 있다. 벤더 타입을 읽는 위치는 Spring AI가 등장하는 유일한 파일인 `OpenAiLlmClient` 안이라 포트 경계는 유지된다.

같은 테스트 작업에서 "응답이 잘리면 의미 재시도 대상이라 응답을 두 번 받는다"는 사실도 확인했다. 성공 응답이 하나도 없어도 TPM은 두 번 소모된다.

## 로컬 E2E 실측

[STEP-1](STEP-1-permit-wait.md)과 같은 조건(로컬, 실제 OpenAI, `경주` 3일, `WALK`·`FRIENDS`·`FOOD`)으로 1회 생성했다 → **201**, 24.2초.

| agent | 호출 | 입력 (캐시 적중) | 출력 (추론) | 합계 |
|---|---|---|---|---|
| Planner | 1 | 1,655 (0) | 590 (307) | 2,245 |
| Curator | 3 | 평균 3,894 · 최대 4,154 (평균 1,120) | 평균 830 · 최대 876 (평균 339) | 평균 4,724 |
| **코스 1건** | **4** | 13,337 | 3,081 | **16,418** |

- **Curator의 입력이 가장 크다.** 후보 목록을 프롬프트에 싣기 때문이다. 0단계에서 예상한 그대로다
- **캐시 적중이 실제로 일어난다.** Curator 3건 중 적중분이 평균 1,120토큰(입력의 약 29%)이다. 고정 규칙을 system 프롬프트로 분리한 효과가 숫자로 보인다(`PlannerAgent.buildCall` 주석의 "향후 컨텍스트 캐싱" 의도)
- **추론 토큰이 출력의 약 40~50%다.** Curator를 `reasoning-effort: low`로 둬도 추론은 0이 아니다
- 슬롯 대기도 다시 관측됐다 — 세 번째 Curator가 **6.7초** 기다렸다(STEP-1에서는 8.1초)

## TPM을 동시 호출 수로 환산

동시 호출 ≈ (TPM ÷ 호출당 토큰) × 호출 시간 8초 ÷ 60 (리틀의 법칙, 호출 시간은 STEP-1 실측).

두 기준으로 계산했다. OpenAI가 TPM을 셀 때 요청의 `max_completion_tokens`(출력 상한)를 미리 잡아 두는지 확인하지 못했기 때문이다. 미리 잡는다면 실제 출력이 아니라 상한을 기준으로 한도를 소모한다.

| 기준 | 호출당 토큰 | 분당 호출 | 동시 호출 | **서버 1대 (÷2)** | 분당 코스 |
|---|---|---|---|---|---|
| 실사용 (입력 + 실제 출력) | 4,105 | 121.8 | 16.2 | **8.1** | 30.5 |
| 보수적 (입력 + 출력 상한) | 6,918 | 72.3 | 9.6 | **4.8** | 18.1 |

출력 상한은 `application.yml` 설정값이다: Planner 2,048, Curator 4,096. 보수적 기준은 코스 1건을 `(1,655 + 2,048) + (11,682 + 3 × 4,096)` = 27,673토큰으로 계산했다.

**판정**

- 서버 한 대당 동시 호출 상한은 **보수적으로 4, 실사용 기준으로 8**이다
- #108에서 **2 → 3 → 4**로 올려 보는 범위는 보수적 기준으로도 한도 안이다. 3이면 3일 코스의 Curator 3개가 한 번에 나가 이번에 관측한 6.7~8.1초 대기가 사라진다
- 5 이상으로 올리려면 `max_completion_tokens`의 TPM 반영 여부를 먼저 확인해야 한다. 반영된다면 출력 상한(특히 Curator 4,096)을 실제 출력(최대 876)에 맞게 낮추는 것만으로 한도 여유가 커진다

## 한계

- **표본 1건, 단일 지역**이다. Curator 입력은 후보 목록 길이에 따라 달라진다. 후보가 많은 대도시는 더 클 수 있다. 2단계 기준선 측정(30요청)에서 분포로 보완한다
- **일수가 늘면 코스당 토큰은 늘지만 호출당 토큰은 크게 변하지 않는다.** Curator가 day마다 따로 불리기 때문이다. 상한 계산은 호출당 값을 쓰므로 일수에 덜 민감하다
- 캐시 적중 토큰이 TPM에서 할인되는지는 확인하지 않았다. 위 계산은 할인하지 않은 보수적 값이다
- ~~프로젝트 한도는 아직 확인하지 않았다~~ → 확인했다. 프로젝트 한도는 조직 한도와 같다(`gpt-5.6-luna` 500,000 TPM / 500 RPM, 오버라이드 없음). 위 환산은 그대로 유효하다
