# 30초 예산 재조정 + 시간 제한 관계 문서화

> [LLM 호출 경로 성능·안정성 로드맵](../README.md)의 6단계이며, [#189](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/189)의 설계·진행 기록이다. 이슈 범위는 1절 조사로 정했다.

## 왜 필요한가

`ai.course.budget-ms: 30000`은 설계 추정(p95 17~24초) 위에 여유를 두고 정한 값이고, 주석은 "8단계 E2E 실측 뒤 조정한다"에 머물러 있다. 그 뒤 4단계에서 슬롯·스레드 풀·네이버 호출을 손봐 지연 분포가 바뀌었으므로 "p95 + 여유" 기준을 다시 적용할 때다.

예산을 다시 정하려면 먼저 **시간이 실제로 어디서 끊기는지**를 알아야 한다. ROADMAP은 `llm.timeout-ms`가 "호출 1건의 상한"이 아니라고 지적했지만(이론상 약 144초), 코드로 확인한 적은 없었다. 확인 없이 주석을 고치면 틀린 서술을 다른 틀린 서술로 바꿀 수 있어, 조사를 첫 단계로 뒀다.

## 1. 조사 — 시간 제한은 실제로 어떻게 걸려 있나

코드만 읽었다(변경 없음). 라이브러리 문서가 아니라 **이 저장소의 실제 배선과 실제 의존성 버전**으로 확인했다.

### 층위

밖(클라이언트)에서 안(외부 API) 순서다.

| 층 | 값 | 무엇을 자르나 | 근거 |
|---|---|---|---|
| Android OkHttp `readTimeout` | 60초 | **읽기와 읽기 사이의 공백**. 전체 시간이 아니다. `callTimeout`은 설정하지 않아 기본값(무제한)이다 | FE `RetrofitClient.java:22` |
| ALB `idle_timeout` | 60초 | 연결에서 아무 바이트도 오가지 않는 시간 | `terraform/prod/variables.tf` 기본값, `terraform.tfvars`에서 덮어쓰지 않음 |
| 서버 예산 `ai.course.budget-ms` | 30초 | 각 스테이지가 **기다리는 시간**. 하던 일은 멈추지 않는다 | `AiCoursePipeline.doGenerate` |
| `llm.timeout-ms` | 20초 | 슬롯 대기 · HTTP 연결 · HTTP 응답 읽기 공백, 세 곳에 같은 값이 들어간다(아래) | `OpenAiLlmClient` |
| 네이버·TourAPI·카카오 WebClient | 연결 2초 · 응답 3초 · 커넥션 풀 대기 5초 | 외부 API 호출 1회 | `NaverConfig`·`TourApiConfig`·`KakaoConfig` |
| 네이버 속도 제한기 | 최대 대기 2초 | 토큰을 받을 때까지의 대기 | `naver.rate-limit.max-wait-ms` |

예산이 걸리는 방식은 모든 스테이지가 같다. 요청당 한 번 만든 `CourseDeadline`을 나눠 쓰고, Planner·후보 공급·Curator·그라운딩·URL 보강이 모두 `future.get(deadline.remainingMs())`로 기다린다. 시간이 다 되면 그때까지 끝난 결과만 쓰고, 그라운딩과 URL 보강은 들어가기 전에 이미 만료됐으면 단계를 통째로 건너뛴다.

### `llm.timeout-ms`는 호출 1건의 상한이 아니다

같은 20초가 서로 다른 세 곳에 들어간다.

1. **슬롯(세마포어) 대기**: `concurrencyGate.tryAcquire(timeoutMs)` (`acquirePermit`)
2. **HTTP 연결**: `ClientHttpRequestFactorySettings.withConnectTimeout` (`buildChatModel`)
3. **HTTP 응답 읽기 공백**: `withReadTimeout` (`buildChatModel`)

3번은 바이트코드로 확인했다. 런타임의 spring-web **6.2.12**에서 `ReactorClientHttpRequestFactory.setReadTimeout`은 reactor-netty `HttpClient.responseTimeout`을 호출한다. 이 값은 "응답을 다 받기까지"가 아니라 **요청을 보낸 뒤 읽기와 읽기 사이에 허용되는 최대 공백**이다. 응답 전체에 상한을 거는 `exchangeTimeout`은 Boot의 `ClientHttpRequestFactoryBuilder.reactor()`가 설정하지 않아 비어 있다(`Mono.block()`을 시간 제한 없이 호출).

OpenAI 비스트리밍 응답은 생성이 끝날 때까지 바이트를 보내지 않으므로, 실제로는 **"첫 바이트가 올 때까지 20초"** 로 동작한다.

### 최악의 경우 — 144초는 맞지만 특정 경로에서만 나온다

재시도는 두 계층이고, 각각 잡는 예외가 다르다.

- **전송 계층**(`LlmRetryExecutor`, 3회): 429·408·5xx와 `IOException`(연결 실패·읽기 타임아웃)을 재시도한다. 백오프는 0.5초 → 1.0초(지터 ±30%)이다
- **의미 계층**(`generateWithSemanticRetry`, 2회): `LlmResponseException`(200이 왔는데 쓸 수 없는 응답)**만** 잡는다. 전송 재시도를 다 쓴 `LlmTransportException`은 의미 재시도 없이 바로 올라간다

그래서 두 계층이 곱해지는 것은 "전송 시도 1·2회는 타임아웃이고, 3회째에 깨진 200이 오는 일이 두 번 반복되는" 경로뿐이다.

| 경로 | 계산 | 합계 |
|---|---|---|
| 이론상 최악(ROADMAP의 144초) | 슬롯 대기 20 + 2 × (20 × 3 + 백오프 최대 1.95) | **143.9초** |
| 타임아웃만 계속 나는 경우 | 슬롯 대기 20 + 20 × 3 + 1.95 | **82초** |
| 슬롯을 얻은 뒤의 점유 상한 | 2 × (20 × 3 + 1.95) | 약 124초 |

- 슬롯은 의미 재시도 두 번에 걸쳐 **계속 쥔 채로** 있다. `acquirePermit`이 `generate` 입구에서 한 번만 불리기 때문이다
- 위 계산은 커넥션 풀의 연결을 재사용한다고 가정했다. 새로 연결하면 시도마다 연결 시간 20초가 더해질 수 있고, 바이트가 조금씩 들어오면 읽기 공백 제한에 걸리지 않으므로 엄밀한 상한은 없다

**정리하면 요청의 응답 시간은 예산(30초)이 막지만, 버려진 호출이 슬롯과 스레드를 쥐는 시간은 82~144초까지 갈 수 있다.** 이것은 [STEP-3](STEP-3-late-calls.md)의 "마감 뒤 남는 호출"과 같은 현상이고, 예산 값과는 따로 움직인다. 예산을 줄여도 뒤에서 도는 호출은 줄지 않는다.

### 문서에 없던 발견

**① 예산과 같은 값이 지표 코드에 하드코딩돼 있다.** `AiCourseMetrics.PIPELINE_LATENCY_MAX = 30초`가 요청 전체·스테이지 히스토그램의 `maximumExpectedValue`다. 주석도 "요청 예산과 같은 값이다"라고 적고 있다. 예산을 바꾸면 이 상수도 따라 바꿔야 한다. 그대로 두고 예산만 늘리면 30초를 넘는 값이 전부 `+Inf` 버킷에 뭉쳐 분포를 읽을 수 없다.

**② 요청 전체 시간은 예산보다 조금 길다.** 예산이 끝난 뒤에도 RouteOptimizer(CPU), 응답 조립, `AiCoursePersister.save`(짧은 DB 트랜잭션)가 실행된다. [STEP-8](../../ai-course-create/steps/STEP-8-switch.md)의 max 30.1초가 이것으로 설명된다. 그래서 불변식은 "예산 < 60초"가 아니라 **"예산 + 후처리 < 클라이언트 60초 = ALB 60초"** 로 적어야 정확하다.

**③ `CallerRunsPolicy` 경로에서는 예산이 걸리지 않는다.** `aiAgentExecutor`(스레드 = 슬롯 × 4 = 20, 큐 50)가 가득 차면 요청 스레드가 LLM 호출을 직접 실행한다. 그러면 `future.get(remainingMs)`에 닿기 전에 호출이 동기로 끝나야 하므로, 이 경로의 응답 시간은 예산이 아니라 위 82~144초가 정한다. ALB 60초를 넘을 수 있다. 동시 작업이 70개(대략 동시 18명 이상)를 넘어야 발동해 지금까지의 측정 범위(최대 동시 8명)에서는 일어나지 않았다. 6단계의 대상이 아니라, 받아들이는 요청 수 자체를 묶는 **AI 동시 입장 제한**이 막아야 할 영역이다.

**④ `timeout-ms`를 "호출 1건의 상한"으로 적은 주석이 여러 곳이다.**

| 위치 | 현재 서술 | 판단 |
|---|---|---|
| `application.yml` `llm.timeout-ms` | "호출 1건의 상한" | 정정 — 세 가지 의미로 |
| `application.yml` `ai.course.budget-ms` | "설계 p95 17~24초", "8단계 E2E 실측 뒤 조정한다" | 정정 — 실측 근거와 불변식으로 |
| `application.yml` `llm:` 블록 머리 | "8단계 스위치 전까지 프로덕션 경로에서 호출되지 않는다" | 정정 — 스위치는 끝났다 |
| `AiLlmProperties` `@param timeoutMs` | "호출 1건의 상한" | 정정 |
| `PlannerAgent.await` javadoc | "`llm.timeout-ms`(호출 1건의 상한)" | 정정 |
| `AiCourseProperties` 클래스 javadoc | "그쪽은 호출 1건의 상한" | 정정 |
| `AiCourseMetrics.LLM_LATENCY_MAX` | "HTTP 시도 1회의 상한" | 정확하다 — 그대로 둔다 |

과거 단계 기록(ai-course-create의 STEP-7 등)에 있는 같은 서술은 당시 판단을 남긴 기록이라 고치지 않는다.

### 이 조사로 정해진 6단계 범위

1. 위 표의 주석 6곳 정정
2. 개선 후 지연 분포로 예산 재판단 (2절)
3. 불변식 "예산 + 후처리 < 클라이언트 60초 = ALB 60초"를 `budget-ms` 주석과 운영 문서에 명시
4. 예산 값을 바꾸면 `PIPELINE_LATENCY_MAX`도 함께 맞춤

③(`CallerRunsPolicy` 경로)은 범위에서 뺀다. ROADMAP "별도. AI 동시 입장 제한"의 근거로 넘긴다.

## 2. 개선 후 지연 분포 재집계

진행 예정. 아래는 무엇을 볼지 미리 정해 둔 것이다.

### 예산은 지연이 아니라 품질의 손잡이다

예산을 넘긴 요청은 실패하지 않는다. 스테이지마다 그때까지 끝난 것만 들고 다음으로 넘기고, 빈 곳은 LLM 없이 코드가 채운다.

| 스테이지 | 예산이 끝나면 |
|---|---|
| Planner | 결정론적 기본 플랜(날마다 관광·식사·카페·관광·식사, 권역 = 입력 지역)으로 간다 |
| 후보 공급 | 응답이 온 소스·슬롯만 풀에 담는다. 진입 전에 만료됐으면 빈 풀 |
| Curator | 끝난 날의 응답만 쓰고, 못 끝난 날은 자리만 있는 빈칸으로 넘긴다 |
| 빈칸 채우기 | Curator가 비운 자리를 후보 목록 상위 3개로 채운다(`DeterministicCuration`) — **지표의 "폴백"이 이것이다** |
| 그라운딩 | 진입 전에 만료됐으면 카카오 검증을 건너뛴다. 목록 밖 제안(SUGGESTED)은 탈락한다 |
| URL 보강 | 만료됐으면 통째로 건너뛴다 |

에러는 전 day 장소가 0개일 때만 난다(만료면 504, 아니면 503). 그래서 **예산을 줄이면 응답은 빨라지지만 폴백이 늘고, 늘리면 폴백은 줄지만 사용자가 오래 기다린다.** p95만 보고 "p95 + 여유"를 적용하면 이 교환 관계가 보이지 않는다 — 폴백은 200 으로 나가 에러율에도 지연에도 잡히지 않기 때문이다. 4단계 측정에서 보고한 폴백 비율(동시 5명 11.1% 등)은 거의 전부 Curator 빈칸 채우기다.

### 볼 것

1. **지연 분포** — 요청 전체 p50·p95·max를 조건별(단일 요청 · 동시 3·5·8명)로. 슬롯 5 · 네이버 제한기 25(4단계 재확정 조건) 데이터만 쓴다
2. **폴백 비율** — `ai.curation.slot{result}` 기준 fallback·unfilled 비율을 같은 조건별로
3. **폴백이 예산 몇 초 지점에서 생기는가** — 예산이 지금보다 Δ초 길었다면 살아났을 폴백이 얼마인가. 마감 뒤에 끝나 버려진 Curator 호출은 실패 없이 끝까지 돌아 `success`로 기록된다([STEP-3](STEP-3-late-calls.md)). 그 호출이 **마감을 몇 초 넘겨 끝났는지**를 알면 "예산 35초면 폴백 몇 %"를 추가 비용 없이 역산할 수 있다
4. **후처리 시간** — 예산이 끝난 뒤의 경로 계산 + 저장이 몇 초인가. 불변식 "예산 + 후처리 < 60초"의 후처리 항이다

**3·4는 기존 데이터로 가능한지 먼저 확인한다.** 요청별로 마감 시각과 Curator 호출 종료 시각을 이어 붙일 수 있는 로그·지표가 남아 있어야 한다. 남아 있지 않으면 계측을 추가하고 다시 측정할지, 예산을 몇 가지로 바꿔 직접 재볼지를 그때 정한다(후자는 LLM 비용이 든다).
