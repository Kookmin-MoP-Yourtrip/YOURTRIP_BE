# 별도 단계 — AI 동시 입장 제한 (#192)

> 로드맵: [README.md](../README.md) "별도. AI 동시 입장 제한"
> 선행 근거: [STEP-6](STEP-6-budget.md)(예산 35초 · 동시 8명 폴백 54.1%)

## 왜 필요한가

6단계까지 예산·슬롯·스레드 풀을 차례로 조정했지만 **동시 8명은 어느 조합에서도 풀리지 않았다.** 30초 동안 필요한 LLM 작업(호출 약 32회 × 9초 ≈ 290 슬롯·초)이 공급(슬롯 5 × 30초 = 150)의 두 배라서, 남은 처방은 **받아들이는 요청 수 자체를 묶는 것**이다. 넘친 요청을 35초 기다리게 한 뒤 품질이 떨어진 코스를 주는 대신, 바로 `429` + `Retry-After`로 돌려보낸다.

## 1. 조사 (2026-10-05)

### 1-1. 지금 요청이 지나가는 경로

```
Tomcat 워커 (운영 max 32)
 └ JwtAuthenticationFilter → MyCourseController.createAICourse (@Valid)
    └ MyCourseServiceImpl.createAICourse       ← 트랜잭션 없음
       ├ userService.getCurrentUserId()
       ├ aiCoursePipeline.generate(brief)      ← CourseDeadline(35초)이 여기서 시작
       │   Planner 1회 + Curator days회 → aiAgentExecutor(20스레드·큐 50) → 슬롯 세마포어(5)
       └ aiCoursePersister.save()              ← 짧은 트랜잭션
```

- 요청 하나는 끝날 때까지 Tomcat 워커 하나를 쥔다. **AI 요청 수를 묶는 장치는 없다.** 유일한 제한은 LLM 호출 단위의 슬롯(`OpenAiLlmClient.concurrencyGate`)인데, 그 앞에서는 최대 20초를 기다릴 뿐 요청을 거절하지 않는다
- 운영 ASG는 평소 1대다(`asg_desired_capacity` 1, 최대 2). 슬롯이 서버마다 따로 있으므로 상한도 **서버별 메모리 세마포어**가 맞다. 서버 간 공유 상태(Redis)는 필요 없다

### 1-2. 지금 예산을 다 쓰는 요청의 비율

같은 날 오후 측정 로그(`results/ai-concurrent-budget35`, `control30`)에서 k6 요청 시간이 예산 이상인 요청을 셌다. 예산을 넘긴 요청은 에러가 아니라 **35초 시점에 Curator 빈칸을 폴백으로 채운 201**로 나간다.

| 동시 사용자 | 예산 35초 (현재) | 30초 대조군 | Curator 칸 폴백 (35초) | 요청 p50 / 최대 (35초) |
|---|---|---|---|---|
| 1명 | 0% (0/10)\* | 0% | 0% | 19.8 / 24.7초 |
| 5명 | **20%** (3/15) | 40% (6/15) | 11.1% | 28.1 / 35.1초 |
| 8명 | **50%** (12/24) | 67% (16/24) | 54.1% | 35.0 / 35.1초 |

\* 동시 1명은 30초 예산의 [STEP-4-5](STEP-4-5-naver-rate-limiter.md) 측정(`ai-single-185-on`)이다. 최대 24.7초라 35초에서도 0%다.

- 마감에 걸리지 않은 요청은 모두 정상으로 끝났다(동시 5명의 가장 느린 정상 요청 34.8초). 503·504는 0건이다
- 동시 8명은 **p50이 곧 예산**이다 — 절반이 35초를 꽉 채워 기다린 뒤 품질이 떨어진 결과를 받는다. 예산을 30 → 35초로 늘려도 67 → 50%로만 줄었다
- 표본이 작다(15건·24건). 한두 건 차이로 5~7%p 움직인다

### 1-3. 제한을 걸 위치

| 위치 | 판단 |
|---|---|
| 필터·인터셉터 | ✗ 이 시점에도 Tomcat 워커는 이미 배정돼 있어 벌크헤드 효과는 서비스와 같다. 인증·입력 검증에 실패할 요청까지 자리를 차지하고, 해제(`afterCompletion`)를 따로 관리해야 한다 |
| `AiCoursePipeline` 안 | ✗ 벤치마크 3종과 프로브 테스트가 파이프라인을 직접 조립한다(`PipelineBenchmarkWiring` 등). 측정 도구까지 제한을 받게 된다. 파이프라인은 "코스 하나 만들기"만 맡는 지금 구조가 맞다 |
| **`MyCourseServiceImpl.createAICourse`의 `generate` 둘레** | ✓ 검증·인증을 통과한 요청만 자리를 받고, 이 API의 사용자 대면 진입점이다 |

구현은 `java.util.concurrent.Semaphore` 하나면 된다. 슬롯 세마포어와 같은 방식이고, Resilience4j를 들이지 않기로 한 기존 판단(`AiLlmProperties.Retry` javadoc)과도 맞는다.

### 1-4. 응답 형식

- **`AiCourseErrorCode`는 `AI_COURSE_BUSY`를 일부러 만들지 않았다.** 슬롯 포화는 다른 전송 실패와 같은 `LlmTransportException`으로 나와 구분되지 않고, 결국 degrade에 흡수돼 이 코드를 낼 경로가 없었기 때문이다. 입장 제한은 **이 코드를 실제로 내는 첫 경로**다. "발화하지 않는 상수를 두지 않는다"는 원칙을 그대로 지키면서 상수를 추가한다
- `GlobalExceptionHandler`는 `ErrorCode`에서 상태와 본문만 만들고 **헤더를 붙일 방법이 없다.** `Retry-After`를 실으려면 경로가 하나 더 필요하다
- 서버가 429를 내보내는 곳은 지금 한 곳도 없다(외부 API의 429를 받는 코드만 있다). API 계약에 새 응답이 추가된다

### 1-5. 상한 값

- k6 측정 요청은 3일 일정이라 요청당 LLM 호출이 4회(Planner 1 + Curator 3)다
- 슬롯 공급은 35초 × 5 = 175 슬롯·초, 요청 하나는 약 4회 × 9초 = 36 슬롯·초를 쓴다. **동시 4~5건이 이론상 한계**이고, 측정(동시 5명 마감 20%, 8명 50%)과도 맞는다

### 1-6. 발견 ① 입장 대기는 예산 밖에 있다

`CourseDeadline`은 `generate` 안에서 시작한다. 입장 대기를 그 앞에 두면 응답 최대 시간은 **대기 + 35초 + 후처리**가 된다.

| 대기 처리 | 응답 최대 | 불변식 ① (< 60초) | 불변식 ② (#190, 30초) | 대가 |
|---|---|---|---|---|
| **즉시 거절** (대기 0) | 35.3초 | ✓ | 지금과 같음 | 순간적인 몰림에도 바로 429 |
| 3초 대기, 예산과 별도 | 38.3초 | ✓ | 더 나빠짐 | 받아들인 요청 품질은 그대로 |
| 3초 대기, 예산에 포함 | 35.3초 | ✓ | 지금과 같음 | 기다린 요청은 예산 32초로 시작해 폴백이 는다 |

포화 상태에서는 요청 하나가 자리를 20~35초 쥐므로, 몇 초 대기로 자리를 얻을 가능성이 크지 않다. 대기는 시간 제한 불변식만 건드리고 이득은 불확실하다.

### 1-7. 발견 ② 요청 수만 묶어서는 `CallerRunsPolicy`가 막히지 않는다

- `AICourseCreateRequest`에는 **여행 일수 상한이 없다**(시작일 ≤ 종료일만 검사한다). Curator가 day마다 병렬이므로 **30일 요청 하나가 LLM 작업 31개**를 만든다. 이런 요청 셋만 겹쳐도 `aiAgentExecutor` 용량(20 + 큐 50)을 넘어, 요청 스레드가 LLM을 직접 부르는 경로(예산이 걸리지 않는 82~144초, STEP-6 발견 ③)로 빠진다
- 로드맵의 "입장 수를 묶으면 이 경로도 막힌다"는 **일수가 짧다는 전제에서만 맞다.** 막으려면 (a) LLM 호출 수(1 + days)로 가중한 입장 제한이나 (b) 일수 상한 검증이 필요하다

## 2. 결정 (2026-10-05)

- **즉시 거절** — 대기 없이 `tryAcquire()` 한 번으로 판정한다. 시간 제한 불변식을 그대로 두고, 재시도 간격은 `Retry-After`로 클라이언트에 맡긴다. 대기가 필요하다는 근거가 측정으로 나오면 그때 추가한다
- **위치는 서비스 진입부**, 단위는 **요청 수** — `generate` 호출만 감싼다. 저장(짧은 트랜잭션)은 LLM을 쓰지 않으므로 자리를 쥐지 않는다
- **일수 상한은 [#178](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/178)에서 다룬다** — 입력 검증과 API 계약의 문제라 대상 파일·검증 방법이 다르다. 그 전까지 이 제한은 "일수가 짧은 요청" 기준이라는 전제를 문서와 주석에 남긴다
- **FE 합의(429 자동 재시도·안내 문구)는 이후에 진행한다** — 이번 범위는 BE 응답과 Swagger 명시까지다

## 3. 재측정 (2026-10-05 저녁)

### 3-1. 조건과 설계

6단계와 같은 조건이다 — 로컬 1대, 예산 35초, 슬롯 5, 네이버 제한기 25, TourAPI 켬, `scripts/k6/ai-course-concurrent.js` 3라운드(라운드 안 N명 동시 출발). 6단계에서 같은 예산이라도 오전·오후의 LLM 지연이 약 20% 달라 예측이 빗나갔으므로, **비교할 조건을 모두 같은 시간대(17:00~17:33)에 연달아 쟀다.** 입장 상한만 실행 인자(`--ai.course.admission.max-concurrent-requests`)로 바꿨다.

| 측정 | 입장 상한 | 동시 | 결과 디렉터리 | 목적 |
|---|---|---|---|---|
| A | 5 | 8명 | `results/ai-admission-limit5` | 상한 5 적용 효과 |
| A' | 4 | 8명 | `results/ai-admission-limit4`, `-r2` | 상한 4 적용 효과(2회) |
| B | 없음(100) | 8명 | `results/ai-admission-off/c8` | 같은 시간대 적용 전 |
| C | 없음(100) | 5명 | `results/ai-admission-off/c5` | 동시 5건 품질 기준선 |

**측정 중 사고 — TourAPI 일일 한도 소진.** 처음 A·A'를 잰 직후(16:49) TourAPI가 `QUOTA_EXCEEDED`(429)를 내기 시작했다. 6단계부터 같은 키로 측정을 이어 온 탓이다. 후보 공급은 fail-open이라 에러는 나지 않지만 TourAPI 후보가 빠져 Curator 입력이 달라지므로 A와 A'를 같은 조건으로 비교할 수 없게 됐다. 새 키(일 1,000건)로 바꿔 네 측정을 처음부터 다시 쟀다. 그때까지의 결과는 `results/_tourapi-quota-exhausted/`로 분리했다 — 무효는 A'(`limit4`)뿐이고, 첫 A(`limit5-oldkey`, 16:41)는 TourAPI가 정상(성공 114 · 실패 0)이라 아래 합산에 넣었다. 이후 실행 스크립트는 6단계처럼 **TourAPI 실패가 늘거나 성공이 0이면 측정을 멈추도록** 했다.

- **제한은 설계대로 동작한다.** 라운드마다 정확히 3명(상한 5)·4명(상한 4)이 0.2초 안에 429를 받았고, 거절된 요청은 LLM을 한 번도 부르지 않았다(LLM 호출 B 80회 → A 59회 → A' 48회). 슬롯 대기 포기 16 → 0~1회, 버려진 호출 32 → 1~12회로 줄었다
- **제한이 없으면 모두가 늦고 대부분이 폴백을 받는다** — B는 p50이 35.1초로 예산과 같고, 67%가 예산을 다 썼다. 6단계(54.1%)보다 나쁜 것은 같은 동시 8명이라도 시간대 흔들림이 크다는 뜻이다
- **A(26.7%)가 C(9.2%)보다 나쁜 것은 표본 편차다.** 둘 다 파이프라인에 동시에 든 요청은 5건이라 구조적 차이가 없다. 차이는 15건 중 예산 소진 5건이냐 3건이냐에서 오는데(표준편차 약 1.7건), 소진된 요청 하나가 폴백 칸을 8~14개씩 만들어 칸 비율이 크게 흔들린다

### 3-3. 상한 4와 5의 합산 비교

동시 5건이 처리된 측정을 모두 모았다(오늘 A 2회 · C · 6단계 오후 `ai-concurrent-budget35` c5). 첫 A(16:41, `_tourapi-quota-exhausted/limit5-oldkey`)는 TourAPI가 아직 정상이던 때라 포함했다.

| | 상한 5 (4회, 60건) | 상한 4 (2회, 24건) |
|---|---|---|
| 받아들인 요청의 예산 소진 | 15/60 (**25%**) | 4/24 (**17%**) |
| Curator 칸 폴백 | 169/1,084 (**15.6%**), 회차별 9~27% | 19/435 (**4.4%**), 회차별 0~9% |

- A' 1회차의 0%는 운이 좋은 쪽이었다. 2회차에 8.7%가 나와 "상한 4면 폴백이 없다"는 결론은 성립하지 않는다
- 그래도 **방향은 일관된다** — 상한 4의 두 회차 모두 상한 5의 평균보다 낫다
- **대가도 있다** — 몰릴 때 서비스가 내놓는 온전한 코스가 라운드당 약 11% 줄어든다. 상한을 하나 올려 더 받는 1명은 대체로 폴백이 섞인 코스를 받지만, 0개는 아니다

## 4. 판단 — 상한 4 (2026-10-05)

**4로 정한다.** 받아들인 사람의 품질을 몰릴 때의 처리량보다 우선했다.

- **품질** — 받아들인 요청의 폴백이 15.6% → 4.4%로 약 3분의 1 이하가 된다. 상한 5는 회차에 따라 27%까지 흔들려, 운이 나쁜 시간대에는 받아들인 사람 셋 중 하나가 예산을 다 쓴다
- **거절이 폴백보다 회복 가능하다** — 거절된 사람은 `Retry-After` 뒤 재시도해 온전한 코스를 받을 수 있지만, 폴백 코스를 받은 사람은 그 결과가 그대로 남는다
- **여유** — 상한 5는 공급 한계(175 ÷ 36 ≈ 4.9건)에 붙어 있어 LLM이 조금만 느려져도 넘친다. 상한 4는 약 20% 여유로 하루 안의 지연 흔들림(6단계에서 잰 약 20%)을 흡수한다
- **처리량 감소는 평소에 보이지 않는다** — 서버 1대 처리량은 약 분당 10~11건(상한 4 ÷ 요청 약 22초)이다. 하루 활성 사용자 1,000명, 1인 2회, 피크 시간 15% 몰림을 가정해도 평균 동시 처리는 약 1.8건이라 상한에 닿지 않는다. 상한은 로드맵이 의도한 대로 **평소에는 작동하지 않는 안전밸브**다

**한계**

- **표본이 작다** — 상한 4는 2회 24건이다. 회차별 폴백이 0~9%로 흔들리므로 4.4%는 점추정이 아니라 "상한 5보다 확실히 낮다"는 방향의 근거로 읽는다
- **k6는 최악의 몰림이다** — 8명이 1초 안에 동시에 출발한다. 실제 도착은 흩어져 있어 같은 상한에서 거절과 폴백이 모두 이보다 적을 것이다
- **3일 일정 기준이다** — 일수가 긴 요청은 하나가 슬롯을 더 쓴다. 일수 상한(#178)이 들어가기 전까지 상한 4는 짧은 일정 기준의 값이다
- **로컬 1대 측정이다** — 운영(t3.small, ALB 뒤)에서는 재지 않았다. 병목이 LLM 슬롯이라 서버 성능의 영향은 작을 것으로 본다

**다시 볼 조건**

- OpenAI 티어를 올리거나 `llm.max-concurrent-calls`를 바꿀 때 — 상한은 슬롯 공급에 묶여 있다
- 운영에서 `ai_course_admission_total{result="rejected"}`가 평소에도 0이 아닐 때 — 안전밸브가 상시 병목이 됐다는 뜻이고, 상한이 아니라 공급(티어·요청당 LLM 작업량)을 늘릴 신호다
- #178(일수 상한)이 들어가 요청 크기 분포가 바뀔 때
