# STEP-4-5 — 네이버 호출 속도를 서버에서 고르게 제한 (#185, 진행 중)

> **결론(중간)**: 네이버 지역검색 호출 앞에 서버 단위 속도 제한기(초당 25 · 버스트 15 · 최대 대기 2초)를 뒀다. 슬롯 5 · TourAPI 차단 조건의 같은 날 전후 측정에서 **네이버 실패율 33.7 → 0%**(동시 5명), 11.9 → 0%(동시 8명), "후보 없음" 빈 슬롯 55 → 0, 504 4 → 0건이 됐다. 대가는 시간이다 — 후보 공급 단계가 평균 0.73 → 3.26초로 늘어 Curator 몫을 먹었고 동시 5명 폴백이 10.9 → 28.9% 가 됐다. 최대 대기가 0.29초라 속도 25는 보수적이었다. 실제 조건(TourAPI 켬)에서 속도 25·40 과 슬롯 4·5 를 함께 재서 확정한다.

## 1. 출발점

[STEP-4-4](STEP-4-4-slot-raise.md)에서 LLM 슬롯을 4 → 5로 넓히자 네이버 실패가 동시 5명 1.0 → 14.4% 로 뛰고 식사·카페가 비었다. 좁은 슬롯이 요청들을 시간차로 흩어 네이버 초당 제한(API 키당 50)을 우연히 막고 있었다. 평균은 한도의 1/6(동시 8명도 초당 약 8건)이고 **순간 몰림만** 넘는다 — 요청 하나가 약 31건을 후보 공급 단계(1~2초) 안에 몰아 보낸다.

## 2. 방식 선택

| 후보 | 고르지 않은 이유 |
|---|---|
| LLM 슬롯 4 유지 | 우연한 시간차에 기댄다. 슬롯 4에서도 동시 8명 4~11% 실패, LLM 이 빨라지기만 해도 깨진다 |
| 429 뒤 1회 재시도(#179 stash) | 거절을 맞은 **뒤** 수습한다. 거절된 호출이 1초 뒤 다시 몰리고, 거절마다 1~2초가 고정으로 붙는다 |
| 세마포어(동시 개수) | 한도의 단위가 "초당"이다. 응답이 0.1 → 0.05초로 빨라지면 같은 설정에서 초당 개수가 두 배가 된다 |
| grounding 풀 축소 | 세마포어와 같은 문제에 카카오·TourAPI 까지 함께 느려진다 |
| 질의 더 줄이기 | #179 에서 쓸모없는 질의는 이미 걷었다(45 → 25). 더 줄이면 후보가 준다 |
| 분산 제한기(Redis) | 두 서버 합을 정확히 세지만 호출마다 Redis 왕복이 붙는다. 두 서버 버스트가 같은 1초에 겹치는 일은 드물다 |
| **서버 안 속도 제한기** | **채택** — 보내기 전에 간격을 둬 거절 자체를 막고, 한도와 단위가 같고, 앞 단계 속도와 무관하다 |

- **위치는 `NaverLocalClient.search()` 앞이다.** 시더 기본·수식어·재질의가 모두 지나가므로 새 경로가 생겨도 빠져나가지 못한다
- **알고리즘은 GCRA**(토큰 버킷과 동치)다. "다음 호출이 나가도 되는 시각" 하나를 CAS 로 예약하고 그 차례까지만 잔다. 쉬던 뒤 버스트만큼은 바로 보낸다. 고정 창 카운터("1초마다 0으로")는 창 경계에서 두 배가 몰리는 구멍이 있어 택하지 않았다
- **직접 구현했다(약 20줄).** Guava `RateLimiter`는 이 저장소에서 버전 경합이 기록돼 있고(`build.gradle`), 한 곳에서만 쓰는데 새 의존성을 들일 이유가 작다. 가짜 시계로 검증할 수 있다
- **대기 상한을 넘으면 예약하지 않고 포기한다.** 호출이 grounding 풀(카카오·TourAPI 공유) 스레드에서 돌기 때문이다. 포기는 HTTP 를 보내지 않고 `RATE_LIMITED`로 돌려 429 와 같은 fail-open 을 탄다
- 지표 `naver.local.throttle.wait{result=acquired|rejected}`

| 설정 | 값 | 근거 |
|---|---|---|
| `permits-per-second` | 25 | 키 한도 50 ÷ 운영 2대 |
| `burst` | 15 | 단일 요청의 기본 질의(3일 × 5종)가 기다리지 않는 크기. 1초 창 상한은 서버당 40 |
| `max-wait-ms` | 2000 | 공유 풀 스레드를 오래 쥐지 않는다 |

## 3. 전후 측정

### 조건

- 같은 날, 로컬, **슬롯 5**, Tomcat 32, k6 동시 5·8명 × 3라운드
- **TourAPI 를 껐다**(`tour.base-url`을 닫힌 로컬 포트로). 두 키의 일일 한도를 #184 측정이 거의 다 써서다. 식사·카페·쇼핑은 원래 TourAPI 를 쓰지 않고 네이버 질의 수도 TourAPI 와 무관해, 네이버 지표의 전후 비교에는 영향이 없다. 시작 전 AI 요청 1건으로 TourAPI 성공 0건을 확인했다
- 끔 조건은 `naver.rate-limit`을 초당 100,000 · 버스트 100,000 으로 덮었다

### 결과

| | 제한기 끔 | 제한기 켬 |
|---|---|---|
| **동시 5명** 네이버 실패율 | 33.7% (120건) | **0.0%** |
| "후보 없음" 빈 슬롯 | 55 | **0** |
| 504 | 4 | **0** |
| Curator 폴백 | 10.9% | 28.9% |
| 후보 공급 단계 평균 | 0.73초 | 3.26초 |
| **동시 8명** 네이버 실패율 | 11.9% | **0.0%** |
| "후보 없음" 빈 슬롯 / 실패 응답 | 24 / 503 1건 | **0 / 0** |

### 판정

- **거절이 사라졌다.** 그 결과였던 식사·카페 결손과 504 도 함께 사라졌다
- **대가는 후보 공급 시간이다.** 호출당 대기는 짧지만, 동시 5명의 약 155건을 초당 25로 흘리면 마지막 호출은 5~6초 뒤에 나간다 — 속도가 정한 하한이다. 늘어난 2.5~3초가 Curator 몫을 먹어 동시 5명 폴백이 늘었다
- **사용자 결과로는 이득이다.** 나쁜 순서가 504(코스 없음) > 빈 슬롯(장소 없음) > 폴백(코드가 고른 장소)인데, 앞의 둘을 없애고 가장 가벼운 쪽이 늘었다
- **속도 25는 보수적이었다.** 최대 대기 0.29초로 포기 상한에 한 번도 닿지 않았다. 40이면 단계 지연이 약 40% 줄 것으로 본다. 대신 두 서버가 같은 1초에 몰리면 이론상 한도를 넘는다 → 실제 조건에서 25·40 을 재서 정한다

## 한계

- **TourAPI 를 꺼서 기준 조건이 실제보다 빨랐다**(후보 공급 0.73초, 평소 약 1.4초). 몰림이 더 촘촘해 끔 조건 실패율(33.7%)이 #184(14.4%)보다 높다. 폴백 절대값은 실제 조건과 다르다
- 조건마다 1회 측정이다
- Curator 출력 최대가 **1,854**(추론 1,326)까지 나왔다 — #182 상한 2,048 까지 1.1배다. 절단은 0건이지만 `ai.llm.truncated{reason=length}`를 계속 본다
- 로컬 1대라 두 서버가 키를 나눠 쓰는 상황은 재현하지 않았다
