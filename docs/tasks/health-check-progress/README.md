# 과부하를 고장으로 오판하지 않는 헬스체크 — 관리 포트 + 진행 여부 판정

> [#216](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/216)의 설계·판정 기준 기록이다. 아래 판정 기준은 **구현 전에 못 박은 것**이고, 실제 측정 결과는 구현 뒤 `verification.md`에 남긴다.
>
> **상태**: 측정 완료(2026-11-22). 예측 9칸이 모두 맞았고 채택안은 틀린 칸이 없다 — 결과는 [verification.md](verification.md). P5는 부분 통과, P6은 미측정이다.

## 1. 무엇이 문제인가

빠른 API 고부하 측정(s-T1·s-T2·s-W1·s-V1, [measurement.md](../ai-bulkhead-loadtest/measurement.md) 8-10·8-11절)에서 **워커 32·200·가상 스레드 네 회차 모두 `UnHealthyHostCount`가 1이 됐다.** 측정 중에는 ASG `ReplaceUnhealthy`를 멈춰 교체가 없었지만, 운영이었다면 네 구성 모두 인스턴스가 교체됐다.

그런데 s-T 회차의 서버는 **죽지 않았다.**
- ALB 5xx 0건, 앱 5xx 0건, 거절 연결 0건. 오류는 전부 k6 쪽 2초 타임아웃이었다
- 처리 중 요청은 32에 묶였고 나머지는 커넥션 큐(상한 8,192)에서 기다렸다
- 부하가 빠지자 2분 안에 p99 15ms로 돌아왔다

즉 헬스체크가 **"느리지만 일하는 서버"를 "멈춘 서버"로 오판했다.** 과부하로 교체하면 해결되는 것이 없다. 새 인스턴스도 같은 부하를 받고, 교체되는 동안 용량만 줄어 남은 인스턴스로 부하가 몰린다.

### 원인: 헬스체크가 재는 것은 "줄 대기 시간"이다

현재 헬스체크([alb.tf](../../../terraform/prod/alb.tf))는 `/actuator/health/liveness`를 **본 트래픽과 같은 8080, 같은 Tomcat 워커 풀**로 보낸다. liveness 엔드포인트 자체는 `LivenessState`만 돌려줘 사실상 항상 200이므로, 이 검사가 실제로 판정하는 것은 **"헬스체크 요청이 줄을 통과해 5초 안에 돌아왔는가"** 하나다. 과부하에서는 줄이 길어 실패한다.

그리고 이 판정 하나를 ALB(라우팅)와 ASG(`health_check_type = "ELB"`, 교체)가 **함께 쓴다.** 라우팅 판정과 재시작 판정이 하나로 묶여 있어서, 라우팅에서 빼야 할 상황(과부하)이 재시작 사유가 된다.

## 2. 검토한 대안

| 대안 | 판단 |
|---|---|
| **A. 타임아웃·실패 횟수 상향** | ❌ 줄 대기 시간은 부하가 정하므로 어떤 값도 "어디까지 봐줄지"의 추측이다. 과부하를 봐주는 만큼 진짜 고장도 늦게 잡는다(예: timeout 30 / interval 40 / 3회면 고장 감지 최대 약 2분). 검사가 둘을 구분하지 못해 공통 창을 늘릴 수밖에 없다 |
| **B. 관리 포트로 헬스체크만 이동** | ❌ 과부하 오판은 사라지지만, **JVM은 멀쩡한데 8080만 멈춘** 경우(워커 데드락, 커넥션 풀 영구 대기, 8080 커넥터 정지)에 관리 포트가 계속 200을 낸다. 같은 함정의 실제 장애 회고가 있다(분리된 포트가 메인 포트 스레드 고갈 동안 초록불) |
| **C. B + 주기적 하트비트로 진행 여부 판정** | △ 구분은 되지만 10초마다 도는 트래픽이 지표를 오염시키고 스케줄러가 필요하다 |
| **D. B + 진행 여부 판정 + 필요할 때만 8080 직접 확인** | ✅ 채택. 아래 3절 |

A는 구현이 가장 싸고, OOM을 재시작으로 처리하면 대가도 작아진다는 점에서 유력했다. 그래도 D를 택한 이유는 **과부하 허용 범위에 상한이 없고(완료가 이어지는 한 UP), 진짜 고장 감지는 지금 속도를 유지**하기 때문이다. A는 두 성질을 맞바꾼다.

## 3. 설계

### 3-1. 핵심 아이디어: 과부하와 고장은 "완료가 이어지는가"로 갈린다

바깥에서 보면 과부하와 고장은 똑같이 "응답이 늦다"다. 안에서 보면 다르다.

| | 과부하 | 고장(멈춤) |
|---|---|---|
| 응답 시간 | 길다 | 무한대 |
| **완료되는 요청** | **줄지만 계속 생긴다** | **없다** |

ALB의 8080 직접 검사는 **자기 요청 하나**가 통과했는지에 판정이 걸려 있다. 진행 여부 판정은 **누구의 요청이든** 끝났는지를 본다. 과부하에서는 헬스체크 요청이 줄 뒤에 밀려도, 줄 앞에서 다른 요청들이 계속 끝나므로 UP이다.

진행 여부 판정의 유일한 빈칸은 **요청이 없을 때**다. 완료 기록이 없으니 판단할 근거가 없다. 이때는 줄도 없으므로 8080을 직접 찔러 보면 정확하다. 두 방식의 약점이 반대 상황에서 나타나므로, 각각을 정확한 상황에서만 쓴다.

### 3-2. 구성

```
[메인 포트 8080]                                    [관리 포트 8081]
 사용자 요청 ──▶ RequestProgressFilter                ALB 헬스체크 (30초 간격)
                 워커가 요청을 마치면 기록 갱신              │
                        │                                    ▼
                        ▼                          /actuator/health/liveness
                 ProgressTracker (같은 JVM 싱글톤) ◀── RequestProgressHealthIndicator
                  lastCompletedAt                         │
                                                          ├─ 판정 규칙(3-3)
 /internal/ping ◀──────── 기록이 끊겼을 때만 직접 확인 ───┘
```

| 구성 요소 | 역할 |
|---|---|
| `management.server.port` | actuator를 별도 커넥터·스레드 풀로 분리한다. 헬스체크가 8080의 줄에 서지 않는다. **prod 프로필에만** 둔다(로컬 Prometheus는 8080에서 수집한다) |
| `ProgressTracker` | 메인 포트에서 마지막으로 워커가 요청을 마친 시각(`System.nanoTime()`)을 담는다 |
| `RequestProgressFilter` | **메인 포트 요청만** 기록한다(`/actuator` 경로 제외). 관리 포트 요청이 기록되면 8080이 멈춰도 UP이 나와 판정 전체가 무력화된다 |
| `RequestProgressHealthIndicator` | liveness 그룹에 넣어 3-3의 규칙으로 UP/DOWN을 낸다. DOWN이면 503 → ALB 실패 |
| `/internal/ping` | DB·Redis를 건드리지 않는 8080 엔드포인트. 외부 차단, `http.server.requests` 지표 제외 |

**비동기 요청은 워커를 반납하는 순간을 "완료"로 센다.** 이 판정이 지키려는 것은 "8080의 워커가 일을 끝내고 있는가"이고, 비동기 대기(LLM 응답 등)는 워커를 쓰지 않기 때문이다. 비동기 작업 자체의 멈춤은 이 판정의 대상이 아니다 — AI 쪽은 예산(35초)을 넘기면 응답을 끝내므로 멈춤이 아니라 504로 드러난다.

### 3-3. 판정 규칙 (D1 확정)

```
마지막 완료가 임계값(10초) 이내  → UP                  (8080에 요청을 보내지 않는다)
그렇지 않으면 → 127.0.0.1:8080/internal/ping (타임아웃 2초)
                  성공 → UP
                  실패 → 그사이 완료 기록이 갱신됐으면 UP(경합 보정), 아니면 DOWN
```

처리 중 요청 수(`inFlight`)는 판정에 쓰지 않는다. 이유는 5절 D1.

### 3-4. 상황별 기대 동작

| 상황 | 판정 경로 | 결과 |
|---|---|---|
| 한가함 | 8080 확인 성공 | UP |
| 과부하 (s-T) | 완료 기록이 계속 갱신 | **UP — 교체 없음** |
| 워커 데드락, 커넥션 풀 영구 대기 | 완료 기록 끊김 | DOWN → 교체 |
| 8080 커넥터 정지 | 8080 확인 실패 | DOWN → 교체 |
| JVM 정지, GC thrashing | 8081도 응답 없음 | ALB 타임아웃 → 교체 |
| 프로세스 종료 | 연결 거부 | 교체 |
| OOM | JVM이 즉시 종료 → systemd 재시작 | **교체 없이 같은 인스턴스에서 복구** |

### 3-5. OOM 시 종료·재시작

s-V1에서는 `OutOfMemoryError` 뒤 앱이 **프로세스만 살아 있는 상태**로 26분 넘게 남았고 systemd 재시작은 0회였다. OOM은 던져진 스레드만 죽이고 JVM은 계속 돌기 때문이다. 그래서:

- `-XX:+ExitOnOutOfMemoryError`를 [jvm-opts.env](../../../deploy/prod/jvm-opts.env)에 추가해 첫 OOM에서 JVM을 종료시킨다. 종료 코드가 0이 아니므로 기존 `Restart=on-failure`가 다시 띄운다
- **프로세스 재시작에는 `health_check_grace_period`가 적용되지 않는다.** 재기동(RestartSec 5초 + Spring 기동)이 ALB 판정 창(30초 × 3회, 약 60~90초)보다 길면 systemd 재시작이 끝나기 전에 ASG가 인스턴스를 교체한다. 그래서 재기동 시간을 재서 판정 창 안에 드는지 확인한다(P8)
- 힙 덤프(`-XX:+HeapDumpOnOutOfMemoryError`)는 넣지 않는다. 768MB를 디스크에 쓰는 동안 재기동이 늦어져 위 판정 창을 넘길 수 있고, 루트 볼륨 여유도 확인되지 않았다

## 4. 범위 밖

- **과부하 대응(스케일아웃 지표 보강)**: 고장 판정과 관심사가 다르다. 워커 비동기 반납 이후에는 워커 사용률이 요청 수 지표와 중복되므로, 풀별 점유율 기반 정책을 따로 검토한다
- **타임아웃 상향(대안 A)**: 적용하지 않는다
- **커넥션 풀 누수**: Hikari 대기 타임아웃(기본 30초) 때문에 풀이 고갈되면 요청이 멈추지 않고 에러로 끝난다. 완료가 이어지므로 UP이다. 에러율 알람으로 다룰 문제다
- **8080 네트워크 경로 장애**: 보안그룹·라우팅 오류로 ALB에서 8080에만 닿지 않으면, `127.0.0.1` 확인과 8081 헬스체크가 모두 통과해 감지하지 못한다. 런타임 고장이 아니라 설정 오류라 배포 후 확인 절차의 영역이다

| D1 | 판정 규칙 | **"최근 완료 있음 → UP, 없음 → 8080 직접 확인"**. `inFlight`를 판정에 쓰지 않는다 |
| D2 | #198과의 범위 | **한 PR에서 #198·#216을 함께 닫는다.** 커밋은 관심사별로 나눈다 |
| D3 | 값 | 완료 기록 임계값 **10초**, 8080 확인 타임아웃 **2초**로 시작한다. s-T 계단에서 완료 간격 최대값을 재서 확정한다 |
| D4 | 결함 주입 | 측정 전용 프로퍼티(`fault-injection.enabled`, 기본 false)로만 빈이 생기는 장치. 워커 점유는 8080에서 **응답하지 않는 소켓을 타임아웃 없이 읽게** 해 만들고(스레드 덤프로 증명할 수 있게 `Thread.sleep`에서 바꿨다), 8080 커넥터 정지는 **관리 포트 엔드포인트**에서 `pause()`(JMX를 열지 않는다), JVM 정지는 `kill -STOP`, OOM은 초당 N MB씩 쌓는 누수. 시나리오·비교 구성·측정 범위는 [fault-scenarios.md](fault-scenarios.md) |
| D5 | 관리 포트 노출 | **8081**(부하테스트와 동일). 보안그룹은 ALB SG에서만 허용. ALB `/actuator` 차단 규칙은 방어적으로 유지하고 `/internal` 차단을 추가한다 |
| D6 | OOM 재시작 | 이번 범위에 포함한다(3-5절) |

### D1 — 왜 `inFlight` 분기를 없앴는가

처음 검토한 규칙은 `inFlight > 0`이면 완료 기록만 보고, 0이면 8080을 직접 확인했다. 그런데 **긴 정상 요청 하나만 처리 중인 한가한 서버**가 오판된다. 예를 들어 다른 트래픽 없이 느린 모바일 회선의 대용량 업로드 하나가 1분 넘게 워커를 쥐고 있으면, `inFlight = 1`이고 완료가 없으니 DOWN이 이어져 교체된다. 임계값을 그 요청보다 길게 잡으면 데드락 감지가 그만큼 늦어진다.

확정한 규칙은 **완료 기록이 끊겼을 때 바로 DOWN하지 않고 8080을 직접 확인**한다.
- 긴 요청 하나만 있는 경우: 나머지 워커가 비어 있어 확인이 성공 → UP
- 워커 데드락: 워커가 전부 묶여 확인 요청이 처리되지 못함 → DOWN
- 과부하: 완료가 계속 생기므로 확인 자체를 하지 않음 → UP(줄에 밀릴 일이 없다)

이렇게 하면 `inFlight`가 판정에서 빠진다. 비동기 반납 요청을 언제 "처리 중"으로 셀지(`AsyncListener` 처리) 같은 문제도 함께 사라지고, 임계값은 "언제 직접 확인할지"만 정하는 값이 되어 짧게 잡아도 된다.

### D2 — 왜 #198과 한 PR로 묶는가

`management.server.port`를 켜면 actuator 전체가 8081로 옮겨가 **8080의 `/actuator/health/liveness`가 사라진다.** 그래서 #198만 먼저 하려면 ALB 헬스체크를 (a) 8081로 같이 옮기거나(대안 B의 사각지대가 #216 전까지 운영에 남는다) (b) 8080에 임시 엔드포인트를 만들어야 한다(#216에서 버릴 작업이다). 두 이슈가 같은 설정 한 줄로 묶여 있으므로, 커밋은 관심사별로 나누되 PR 하나에서 함께 닫는 편이 낫다.

## 6. 판정 기준

교체를 켠 채(`ReplaceUnhealthy` 활성) 운영 인프라(t3.small 1대)에서 잰다.

| # | 기준 | 방법 | 통과 조건 |
|---|---|---|---|
| P1 | 과부하로 교체되지 않는다 | s-T2와 같은 계단 부하 | `UnHealthyHostCount` 0, 교체 0회 |
| P2 | 워커가 멈추면 잡는다 | 무응답 소켓 대기로 워커 32개를 모두 묶는다 | 임계값 + ALB 판정 창 안에 DOWN → 교체 |
| P3 | 8080만 멈춰도 잡는다 | 8080 커넥터 `pause()` | 위와 같음 |
| P4 | JVM 정지를 잡는다 | `kill -STOP` | ALB 타임아웃으로 교체 |
| P5 | 한가할 때 오판하지 않는다 | 트래픽 없이 30분 + 긴 요청 하나만 처리 중인 상태 | DOWN 0회 |
| P6 | 관리 포트 분리가 지표 수집을 지킨다 (#198) | P1 중 Alloy 수집 | 수집 공백 3초 미만 |
| P7 | 외부에서 내부 경로가 보이지 않는다 | ALB 경유로 `/internal/ping`, `/actuator/*`, 8081 접근 | 모두 차단 |
| P8 | OOM이 같은 인스턴스에서 복구된다 | 측정 전용 누수로 OOM | JVM 종료 → systemd 재시작, **ASG 교체 0회**, 재기동 소요 시간 기록 |

P1~P3은 채택안(C2)과 관리 포트 단독(C1)에 같은 결함을 넣어 비교한다(P4 이후는 C2만 잰다) — C1이 P2·P3에서 미탐을 내는 것이 진행 여부 판정을 둔 근거다. 기준선(현재 운영 구성)은 측정하지 않고 기록과 구조로 둔다. 시나리오별 구성·예측·측정 범위(9회)는 [fault-scenarios.md](fault-scenarios.md)에 있다.

P2·P3·P5의 판정 로직은 운영 측정 전에 통합 테스트(워커 상한을 작게 둔 `RANDOM_PORT` 컨텍스트)로 먼저 확인한다. 운영 측정에서는 포트·보안그룹·ALB·ASG 연결과 실제 소요 시간만 확인한다.
