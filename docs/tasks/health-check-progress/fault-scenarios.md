# 결함 주입 시나리오 — 같은 JAR, 설정만 바꿔 세 설계를 같은 결함으로 비교한다

> [README.md](README.md)의 판정 기준 P1~P8을 **무엇으로, 어떤 순서로, 무엇과 비교해** 확인할지 정한 측정 설계다. 예측과 통과 조건은 **측정 전에 못 박은 것**이고, 결과는 `verification.md`에 남긴다.

## 1. 무엇을 증명하려는가

헬스체크 설계의 품질은 두 가지 오류로 잰다.

| | 실제로 고장 | 실제로 정상(과부하·한가함) |
|---|---|---|
| **교체함** | ✅ 정탐 | ❌ **오탐** — 멀쩡한 서버를 죽여 용량을 줄인다 (#216의 문제) |
| **교체 안 함** | ❌ **미탐** — 죽은 서버가 트래픽을 계속 받는다 | ✅ 정상 |

두 오류는 서로 맞바꾸기 쉽다. 오탐을 없애려고 판정을 느슨하게 하면 미탐이 생기고, 미탐을 없애려고 조이면 오탐이 생긴다. 그래서 "과부하에서 교체되지 않았다" 하나만 보여 주면 설득력이 없다 — **판정을 아예 끄면 누구나 얻는 결과**이기 때문이다. 이 측정은 채택안이 **오탐을 없애면서 미탐을 만들지 않았다**는 것을 보이는 것이 목표다.

그래서 각 결함을 채택안 하나에만 넣지 않고, **검토했다가 기각한 설계에도 똑같이 넣는다.** 각 대안이 어느 결함에서 틀리는지가 곧 기각 사유의 실측 근거가 된다.

## 2. 비교하는 세 설계 — 같은 JAR, 설정만 다르다

| 구성 | 헬스체크 경로 | liveness 그룹 | 무엇을 대표하나 |
|---|---|---|---|
| **C0 기준선** | 8080 `/actuator/health/liveness` | `livenessState` | 지금 운영 구성 |
| **C1 대안 B** | 8081 `/actuator/health/liveness` | `livenessState` | 관리 포트만 분리한 설계 |
| **C2 채택안** | 8081 `/actuator/health/liveness` | `livenessState, requestProgress` | 이번 구현 |

**같은 JAR을 쓰는 것이 이 설계의 핵심이다.** 버전이 다르면 결과 차이가 헬스체크 때문인지 다른 코드 변경 때문인지 가를 수 없다. 구성은 환경변수(SSM)와 타깃 그룹 헬스체크 포트로만 바꾼다.

| 구성 | `MANAGEMENT_SERVER_PORT` | `MANAGEMENT_ENDPOINT_HEALTH_GROUP_LIVENESS_INCLUDE` | 타깃 그룹 헬스체크 포트 |
|---|---|---|---|
| C0 | `8080` (관리 포트를 메인과 합친다) | `livenessState` | 8080 |
| C1 | (prod 기본 8081) | `livenessState` | 8081 |
| C2 | (prod 기본 8081) | (기본 — 두 기여자) | 8081 |

## 3. 시나리오

각 시나리오는 **실제로 일어나는 장애 유형**을 하나씩 대표한다. 같은 신호("완료가 끊긴다")로 잡히는 결함이라도 원인이 다르면 따로 둔다 — 판정이 특정 주입 방식에만 맞춰진 것이 아니라 **원인과 무관하게 증상으로 잡는다**는 것을 보이기 위해서다.

| # | 시나리오 | 대표하는 실제 장애 | 주입 방법 | 정답 |
|---|---|---|---|---|
| **S1** | 빠른 API 과부하 | 트래픽 급증 | s-T2와 같은 계단 부하(초당 200 → 1,800, 계단 90초) | **교체 안 함** |
| **S2** | 외부 API 무응답 | 타임아웃을 안 건 외부 호출이 응답하지 않아 워커가 전부 대기 | 응답하지 않는 로컬 소켓(tarpit)에 타임아웃 없이 읽기를 거는 요청 32개 | **교체** |
| **S3** | 락 순서 역전 데드락 | 두 락을 서로 반대 순서로 잡는 코드 | 락 A→B, B→A 요청 한 쌍 + 같은 락을 기다리는 요청 30개 | **교체** |
| **S4** | 8080 커넥터 정지 | 커넥터가 요청 처리를 멈춤(종료 절차가 중간에 멈춘 경우 등) | 관리 포트에서 8080 커넥터 `pause()` | **교체** |
| **S5** | JVM 정지 | GC thrashing, 프로세스 전체 정지 | `kill -STOP <pid>` | **교체** |
| **S6** | 메모리 누수 → OOM | 해제되지 않는 캐시·컬렉션이 서서히 쌓임 | 초당 N MB씩 붙잡아 두는 누수 스레드 | **교체 없이 같은 인스턴스에서 재시작** |
| **S7** | 긴 요청 하나 | 느린 회선의 대용량 업로드 하나만 처리 중인 한가한 서버 | 워커 1개를 3분간 묶음(S2 장치로 1개만) | **교체 안 함** |

**S2·S3를 `Thread.sleep`이 아니라 실제 블로킹으로 만드는 이유**: 측정이 끝난 뒤 스레드 덤프를 증거로 남길 수 있다. S2의 워커 32개는 `SocketInputStream.read`에서 RUNNABLE, S3는 `jstack`이 `Found one Java-level deadlock`을 출력한다 — "워커를 묶었다"는 주장을 덤프 한 장으로 보일 수 있다. S3는 `ReentrantLock.lockInterruptibly()`로 만든다. `synchronized`와 같은 데드락이지만 인터럽트로 풀 수 있어, 같은 장치를 통합 테스트에서도 안전하게 쓸 수 있다.

## 4. 예측 — 측정 전에 고정

| | C0 기준선 | C1 대안 B | C2 채택안 |
|---|---|---|---|
| S1 과부하 (정답: 유지) | ❌ **교체** (오탐) | ✅ 유지 | ✅ 유지 |
| S2 외부 API 무응답 (정답: 교체) | ✅ 교체 | ❌ **유지** (미탐) | ✅ 교체 |
| S3 데드락 (정답: 교체) | ✅ 교체 | ❌ **유지** (미탐) | ✅ 교체 |
| S4 8080 커넥터 정지 (정답: 교체) | ✅ 교체 | ❌ **유지** (미탐) | ✅ 교체 |
| S5 JVM 정지 (정답: 교체) | ✅ 교체 | ✅ 교체 | ✅ 교체 |
| S7 긴 요청 하나 (정답: 유지) | ✅ 유지 | ✅ 유지 | ✅ 유지 |
| **틀린 칸** | 1 | 3 | **0** |

- **C0와 C2의 고장 감지 속도는 비슷할 것으로 예측한다.** 채택안은 고장을 더 빨리 잡는 설계가 아니다 — 같은 속도로 잡으면서 오탐을 없애는 설계다. 정확한 예측은 C0가 ALB 3회(약 60~90초), C2가 임계값 10초 + 직접 확인 2초 + ALB 3회(약 70~100초)다. **C2가 C0보다 최대 약 12초 늦는 것을 이 설계의 대가로 미리 적어 둔다.**
- S7은 세 구성 모두 맞힐 것으로 예측한다. 이 시나리오가 실제로 가르는 것은 구성이 아니라 **기각한 판정 규칙(D1 ①, "처리 중이면 완료 기록만 본다")** 이고, 그 규칙은 운영에 올리지 않았으므로 통합 테스트로 대신 보인다.

### S6만 비교 대상이 다르다

S6는 헬스체크 구성이 아니라 **OOM 처리 방식**을 비교한다. 비교 대상은 새로 재지 않고 **s-V1 기록을 쓴다** — OOM 뒤 프로세스만 살아 있는 상태로 26분 넘게 남았고 systemd 재시작은 0회였다([measurement.md](../ai-bulkhead-loadtest/measurement.md) 8-10절). 이번에는 `-XX:+ExitOnOutOfMemoryError`를 넣은 C2에서 한 번 잰다.

| | s-V1 (기록) | S6 (이번) |
|---|---|---|
| OOM 뒤 상태 | 프로세스만 살아 응답 없음 26분+ | JVM 종료 → systemd 재시작 |
| 회복 | 없음(교체를 멈춘 조건) | 재기동 소요 시간을 잰다 |
| ASG 교체 | — | **0회여야 한다** — 재기동이 ALB 판정 창 안에 끝나야 한다 |

## 5. 비용을 줄이는 순서

모든 칸을 다 재면 19회다(구성 3 × 헬스체크 시나리오 6 + S6 1). 이미 있는 기록으로 대신할 수 있는 칸과, 결과가 자명한 칸을 뺀다.

| 칸 | 처리 | 이유 |
|---|---|---|
| C0 × S1 | **기록 재사용** | s-T1·s-T2가 이미 같은 부하에서 `UnHealthyHostCount` 1을 기록했다. 단 그때는 `ReplaceUnhealthy`를 멈춰 **교체 자체는 관측하지 않았다** — 한계로 적는다 |
| C0·C1 × S5 | 생략 | JVM이 멈추면 어느 포트도 응답하지 못한다. 구성과 무관하게 같은 경로(ALB 타임아웃)다 |
| C0·C1 × S7 | 생략 | 세 구성 모두 같은 결과로 예측했고, 가르는 대상은 통합 테스트로 보인다 |
| C0 × S3 | 생략 | S2와 같은 경로(8080 워커 고갈 → 헬스체크도 줄에 막힘)다. S3는 C1·C2에서 원인 일반성만 보인다 |

**남는 측정은 13회다** — C2 × 7(S1~S7), C1 × 4(S1~S4), C0 × 2(S2, S4). C2를 먼저 다 재고, 그다음 C1, C0 순으로 간다. 채택안의 정답 여부가 가장 중요하고, 대안 비교는 그 위에 얹는 근거이기 때문이다.

## 6. 회차마다 남기는 것

| 기록 | 어디서 | 왜 |
|---|---|---|
| 주입 시각 t0 | 주입 스크립트 | 모든 시간의 기준점 |
| 첫 503·타임아웃 시각, `check` 값 | 앱 로그(`HttpMainPortProbe` 경고), 1초 간격 liveness 폴링 | 판정이 어느 분기로 내려졌는지 |
| `UnHealthyHostCount` = 1 시각 | CloudWatch (1분) | ALB 판정까지의 시간 |
| 인스턴스 종료·신규 InService 시각 | ASG 활동 기록 | 교체 여부와 회복까지의 시간 |
| 사용자 영향 | 배경 k6 트래픽(초당 20건, 2초 타임아웃)의 오류율 구간 | **"죽은 서버가 트래픽을 받은 시간"** — 미탐의 비용을 사용자 관점으로 보인다 |
| 스레드 덤프 | S2·S3에서 `jstack` 1회 | 주입한 결함이 의도한 상태였다는 증거 |
| `journalctl` | S6 | 종료 코드, systemd 재시작 시각 |

C1의 미탐 회차는 **10분이 지나도 교체되지 않으면 미탐으로 판정하고 끝낸다.** 그 뒤에는 수동으로 인스턴스를 교체한다.

## 7. 안전장치

결함 주입 장치가 운영에 남으면 그 자체가 장애 경로다.

1. **기본값으로는 빈이 생기지 않는다.** `fault-injection.enabled=true`일 때만 장치가 만들어진다(`@ConditionalOnProperty`, 기본 false). 꺼져 있으면 경로 자체가 없다.
2. **측정 때만 켜고 끝나면 끈다.** SSM 환경변수로 넣고, 켜기·끄기를 측정 스크립트의 사전·사후 점검에 넣는다 — 측정용 설정을 원복 때 다시 넣지 않아 지표가 비었던 일이 이미 있었다(measurement.md 8-10절).
3. **외부에서 닿지 않는다.** 모든 호출은 인스턴스 안의 `localhost`에서 한다. ALB 리스너가 `/internal`과 `/actuator`를 차단하고, 8081로는 트래픽을 보내지 않는다.
4. **인증 예외는 장치와 함께 생긴다.** `/internal/fault/**`의 인증 면제는 장치 설정 안의 별도 보안 체인에 두어, 장치가 꺼지면 면제도 함께 사라진다. 공통 `SecurityConfig`에는 넣지 않는다.

## 8. 주입 장치

| 장치 | 포트 | 호출 | 시나리오 |
|---|---|---|---|
| 무응답 소켓 대기 | 8080 | `GET /internal/fault/hang` | S2, S7 |
| 락 순서 역전 | 8080 | `GET /internal/fault/deadlock?side=a\|b` | S3 |
| 무응답 소켓 해제 | 관리 | `POST /actuator/fault/release-hang` | S2·S7 정리, 테스트 |
| 8080 커넥터 정지·재개 | 관리 | `POST /actuator/fault/pause-connector`, `resume-connector` | S4 |
| 메모리 누수 시작 | 관리 | `POST /actuator/fault/leak` 본문 `{"mbPerSecond":N}` | S6 |
| 주입 상태 조회 | 관리 | `POST /actuator/fault/status` | 전 시나리오의 사전 점검 |
| JVM 정지 | OS | `kill -STOP <pid>` | S5 |

**관리 포트 장치는 본문이 비어 있어도 JSON `Content-Type`이 필요하다.** actuator 쓰기 동작의 규칙이라 빠뜨리면 415가 난다(통합 테스트에서 실제로 겪었다). 스크립트는 `curl -X POST -H 'Content-Type: application/json' -d '{}' localhost:8081/actuator/fault/<동작>` 형태로 부른다.

워커를 묶는 장치는 **8080**에, 상태를 조작하는 장치는 **관리 포트**에 둔다. 8080을 멈추거나 워커를 다 묶은 뒤에도 조작할 수 있어야 하기 때문이다.

## 9. 이 설계의 한계

- **회차당 1회다.** 판정은 "교체됐는가"라는 이진 결과라 반복의 이득이 작지만, 감지 시간은 ALB 헬스체크 주기(30초)에 따라 ±30초 흔들린다. 감지 시간은 범위로만 말한다
- **S2·S3는 실제 장애의 재현이 아니라 증상의 재현이다.** 외부 API 무응답과 데드락이 바깥에서 보이는 모습(워커가 묶이고 완료가 없다)을 만든 것이고, 실제 장애의 원인 경로(특정 외부 API, 특정 코드)를 재현한 것은 아니다
- **C0 × S1은 교체를 관측하지 않은 기록이다.** 이 칸의 "교체"는 `UnHealthyHostCount` 1과 ASG 설정(`health_check_type = "ELB"`)에서 추론한 것이다
