# 결함 주입 시나리오 — 같은 JAR, 설정만 바꿔 관리 포트 단독(C1)과 채택안(C2)을 같은 결함으로 비교한다

> [README.md](README.md)의 판정 기준 P1~P8을 **무엇으로, 어떤 순서로, 무엇과 비교해** 확인할지 정한 측정 설계다. 예측과 통과 조건은 **측정 전에 못 박은 것**이고, 결과는 `verification.md`에 남긴다.
>
> **범위 조정(측정 전)**: 처음 설계는 기준선(C0)까지 세 구성 × 7개 시나리오, 13회였다. 측정 전에 **C0 측정 전부와 S3를 뺐다.** 남은 측정은 C1·C2 대상 **9회**다. 뺀 칸과 그 이유는 [5절](#5-측정하는-칸과-빼는-칸)에 있다.

## 1. 무엇을 증명하려는가

헬스체크 설계의 품질은 두 가지 오류로 잰다.

| | 실제로 고장 | 실제로 정상(과부하·한가함) |
|---|---|---|
| **교체함** | ✅ 정탐 | ❌ **오탐** — 멀쩡한 서버를 죽여 용량을 줄인다 (#216의 문제) |
| **교체 안 함** | ❌ **미탐** — 죽은 서버가 트래픽을 계속 받는다 | ✅ 정상 |

두 오류는 서로 맞바꾸기 쉽다. 오탐을 없애려고 판정을 느슨하게 하면 미탐이 생기고, 미탐을 없애려고 조이면 오탐이 생긴다. 그래서 "과부하에서 교체되지 않았다" 하나만 보여 주면 설득력이 없다 — **판정을 아예 끄면 누구나 얻는 결과**이기 때문이다. 이 측정은 채택안이 **오탐을 없애면서 미탐을 만들지 않았다**는 것을 보이는 것이 목표다.

그래서 각 결함을 채택안 하나에만 넣지 않고, **검토했다가 기각한 설계(관리 포트 단독)에도 똑같이 넣는다.** 그 대안이 어느 결함에서 틀리는지가 곧 기각 사유의 실측 근거가 되고, 동시에 **오탐을 없앤 것은 관리 포트 분리이고 미탐을 막는 것은 진행 여부 판정**이라는 기여가 갈린다.

## 2. 비교하는 설계 — 같은 JAR, 설정만 다르다

| 구성 | 헬스체크 경로 | liveness 그룹 | 무엇을 대표하나 | 측정 |
|---|---|---|---|---|
| C0 기준선 | 8080 `/actuator/health/liveness` | `livenessState` | 지금 운영 구성 | **하지 않는다** — 기록과 정의로 둔다(5절) |
| **C1 대안 B** | 8081 `/actuator/health/liveness` | `livenessState` | 관리 포트만 분리한 설계 | 한다 |
| **C2 채택안** | 8081 `/actuator/health/liveness` | `livenessState, requestProgress` | 이번 구현 | 한다 |

**같은 JAR을 쓰는 것이 이 설계의 핵심이다.** 버전이 다르면 결과 차이가 헬스체크 때문인지 다른 코드 변경 때문인지 가를 수 없다. C1과 C2는 타깃 그룹 헬스체크 포트(8081)까지 같고, **환경변수 하나만 다르다.** 그래서 구성을 바꿀 때 terraform은 건드리지 않는다. SSM 값을 바꾼 뒤 **instance refresh로 새 인스턴스를 띄운다** — `/opt/app/.env`는 user-data가 부팅 때만 SSM에서 받아 쓰므로, 앱 재기동만으로는 새 값이 반영되지 않는다(`scripts/loadtest/health-config.sh`).

| 구성 | `MANAGEMENT_ENDPOINT_HEALTH_GROUP_LIVENESS_INCLUDE` |
|---|---|
| C1 | `livenessState` |
| C2 | (설정하지 않음 — `application.yml`의 기본값 `livenessState, requestProgress`) |

## 3. 시나리오

각 시나리오는 **실제로 일어나는 장애 유형**을 하나씩 대표한다.

| # | 시나리오 | 대표하는 실제 장애 | 주입 방법 | 정답 |
|---|---|---|---|---|
| **S1** | 빠른 API 과부하 | 트래픽 급증 | s-T2와 같은 계단 부하(`fast-api-ramp.js` 기본값 — 초당 200 → 2,800 8계단, 계단 90초 + 회복 2분) | **교체 안 함** |
| **S2** | 외부 API 무응답 | 타임아웃을 안 건 외부 호출이 응답하지 않아 워커가 전부 대기 | 응답하지 않는 로컬 소켓(tarpit)에 타임아웃 없이 읽기를 거는 요청 32개 | **교체** |
| ~~S3~~ | ~~락 순서 역전 데드락~~ | 두 락을 서로 반대 순서로 잡는 코드 | — | **측정 제외** — 통합 테스트로만 확인(5절) |
| **S4** | 8080 커넥터 정지 | 커넥터가 요청 처리를 멈춤(종료 절차가 중간에 멈춘 경우 등) | 관리 포트에서 8080 커넥터 `pause()` | **교체** |
| **S5** | JVM 정지 | GC thrashing, 프로세스 전체 정지 | `kill -STOP <pid>` | **교체** |
| **S6** | 메모리 누수 → OOM | 해제되지 않는 캐시·컬렉션이 서서히 쌓임 | 초당 N MB씩 붙잡아 두는 누수 스레드 | **교체 없이 같은 인스턴스에서 재시작** |
| **S7** | 긴 요청 하나 | 느린 회선의 대용량 업로드 하나만 처리 중인 한가한 서버 | 워커 1개를 3분간 묶음(S2 장치로 1개만) | **교체 안 함** |

**S2를 `Thread.sleep`이 아니라 실제 블로킹으로 만드는 이유**: 측정이 끝난 뒤 스레드 덤프를 증거로 남길 수 있다. 워커 32개가 `SocketInputStream.read`에서 RUNNABLE로 찍힌다 — "외부 호출 대기로 워커가 묶였다"는 주장을 덤프 한 장으로 보일 수 있다. `Thread.sleep`이면 TIMED_WAITING이 찍혀 그 주장을 증거로 남길 수 없다.

## 4. 예측 — 측정 전에 고정

| | C0 기준선 (측정 안 함) | C1 대안 B | C2 채택안 |
|---|---|---|---|
| S1 과부하 (정답: 유지) | ❌ 교체 — **기록** | ✅ 유지 | ✅ 유지 |
| S2 외부 API 무응답 (정답: 교체) | ✅ 교체 — 정의 | ❌ **유지** (미탐) | ✅ 교체 |
| S4 8080 커넥터 정지 (정답: 교체) | ✅ 교체 — 정의 | ❌ **유지** (미탐) | ✅ 교체 |
| S5 JVM 정지 (정답: 교체) | ✅ 교체 — 정의 | ✅ 교체 (측정 안 함) | ✅ 교체 |
| S7 긴 요청 하나 (정답: 유지) | ✅ 유지 — 정의 | ✅ 유지 (측정 안 함) | ✅ 유지 |
| **틀린 칸** | 1 | 2 | **0** |

- **C0 칸은 측정값이 아니다.** S1은 s-T1·s-T2의 기록(`UnHealthyHostCount` 1)이고, 나머지는 정의에서 나온다 — C0는 8080을 직접 찌르므로, 8080이 응답하지 못하는 결함(S2·S4·S5)에서는 구조상 반드시 실패하고, 워커가 남아 있는 S7에서는 반드시 통과한다
- **감지 시간은 C2의 절대값만 잰다.** 채택안은 고장을 더 빨리 잡는 설계가 아니라 같은 속도로 잡으면서 오탐을 없애는 설계다. 계산상 C0는 ALB 3회(약 60~90초), C2는 임계값 10초 + 직접 확인 2초 + ALB 3회(약 70~100초)라 **C2가 최대 약 12초 늦다.** C0를 재지 않으므로 이 차이는 계산값으로만 남는다(9절)
- S7이 실제로 가르는 것은 구성이 아니라 **기각한 판정 규칙(D1 ①, "처리 중이면 완료 기록만 본다")** 이고, 그 규칙은 운영에 올리지 않았으므로 통합 테스트로 대신 보인다

### S6만 비교 대상이 다르다

S6는 헬스체크 구성이 아니라 **OOM 처리 방식**을 비교한다. 비교 대상은 새로 재지 않고 **s-V1 기록을 쓴다** — OOM 뒤 프로세스만 살아 있는 상태로 26분 넘게 남았고 systemd 재시작은 0회였다([measurement.md](../ai-bulkhead-loadtest/measurement.md) 8-10절). 이번에는 `-XX:+ExitOnOutOfMemoryError`를 넣은 C2에서 한 번 잰다.

| | s-V1 (기록) | S6 (이번) |
|---|---|---|
| OOM 뒤 상태 | 프로세스만 살아 응답 없음 26분+ | JVM 종료 → systemd 재시작 |
| 회복 | 없음(교체를 멈춘 조건) | 재기동 소요 시간을 잰다 |
| ASG 교체 | — | **0회여야 한다** — 재기동이 ALB 판정 창 안에 끝나야 한다 |

## 5. 측정하는 칸과 빼는 칸

| 칸 | 처리 | 이유 |
|---|---|---|
| **C0 전부** | 측정하지 않음 | S1의 오탐은 s-T1·s-T2에서 이미 발견된 사실이다. 나머지 칸은 C0의 구조(8080 직접 검사)에서 결과가 정해진다. 대가: C0 대비 감지 시간 차이가 실측 없이 계산값으로 남는다 |
| **S3 전부** | 측정하지 않음 | S2와 증상과 판정 경로가 같다(8080 워커가 전부 묶여 완료가 끊긴다). 더하는 것은 "원인이 달라도 같은 증상으로 잡는다"는 일반성뿐이고, 그것은 통합 테스트가 이미 보인다(데드락 → 503, `FaultInjectionIntegrationTest`). 장치는 테스트용으로 남긴다 |
| C1 × S5 | 측정하지 않음 | JVM이 멈추면 관리 포트도 응답하지 못한다. 진행 여부 판정과 무관한 같은 경로(ALB 타임아웃)다 |
| C1 × S7 | 측정하지 않음 | 워커가 남아 있어 C1·C2 모두 통과로 예측했다. 가르는 대상(기각한 규칙)은 통합 테스트가 보인다 |
| S6 | C2만 | 헬스체크 구성과 무관한 OOM 처리 비교다 |

**남는 측정은 9회다.**

| 순서 | 구성 | 시나리오 | 예상 소요 |
|---|---|---|---|
| 1 | C2 | S1 과부하 | 약 20분 (계단 14분 + 준비) |
| 2~4 | C2 | S2 무응답, S4 커넥터 정지, S5 JVM 정지 | 회차당 약 11분 (점검 2 + 감지 약 2 + 교체 약 6 + 확인 1) |
| 5 | C2 | S6 OOM | 약 10분 |
| 6 | C2 | S7 긴 요청 하나 | 약 6분 |
| — | C2 → C1 전환 | SSM 값 변경 + 앱 재기동 | 약 5분 |
| 7 | C1 | S1 과부하 | 약 20분 |
| 8~9 | C1 | S2 무응답, S4 커넥터 정지 | 회차당 약 16분 (점검 2 + 미탐 판정 대기 10 + 복구 4) |

순수 측정은 **약 2시간**이다. 인프라 준비(약 40~60분)와 정리(약 15분), 재시도 여유를 더하면 **약 3시간 반~4시간**이다. 회차 소요는 계단 부하 14분(s-T2·s-W1)과 인스턴스 교체 5~6분(cd-pipeline verification C6·C8)의 실측에서 잡았다.

C2를 먼저 다 재고 C1으로 간다. 채택안의 정답 여부가 가장 중요하고, 대안 비교는 그 위에 얹는 근거이기 때문이다. C1 → C2로 되돌릴 필요가 없도록 순서를 잡았다.

## 6. 회차마다 남기는 것

| 기록 | 어디서 | 왜 |
|---|---|---|
| 주입 시각 t0 | 주입 스크립트 | 모든 시간의 기준점 |
| 첫 503·타임아웃 시각, `check` 값 | 앱 로그(`HttpMainPortProbe` 경고), 1초 간격 liveness 폴링 | 판정이 어느 분기로 내려졌는지 |
| `UnHealthyHostCount` = 1 시각 | CloudWatch (1분) | ALB 판정까지의 시간 |
| 인스턴스 종료·신규 InService 시각 | ASG 활동 기록 | 교체 여부와 회복까지의 시간 |
| 사용자 영향 | 배경 k6 트래픽(초당 20건, 2초 타임아웃)의 오류율 구간 | **"죽은 서버가 트래픽을 받은 시간"** — 미탐의 비용을 사용자 관점으로 보인다 |
| 스레드 덤프 | S2에서 `jstack` 1회 | 주입한 결함이 의도한 상태였다는 증거 |
| `journalctl` | S6 | 종료 코드, systemd 재시작 시각 |

C1의 미탐 회차는 **10분이 지나도 교체되지 않으면 미탐으로 판정하고 끝낸다.** 그 뒤에는 `systemctl restart`로 복구한다 — 주입한 결함이 모두 프로세스 안의 상태라 재시작으로 풀리고, 인스턴스 교체(약 6분)보다 짧다.

## 7. 안전장치

결함 주입 장치가 운영에 남으면 그 자체가 장애 경로다.

1. **기본값으로는 빈이 생기지 않는다.** `fault-injection.enabled=true`일 때만 장치가 만들어진다(`@ConditionalOnFaultInjection`, 기본 false). 꺼져 있으면 경로 자체가 없다.
2. **측정 때만 켜고 끝나면 끈다.** SSM 환경변수로 넣고, 켜기·끄기를 측정 스크립트의 사전·사후 점검에 넣는다 — 측정용 설정을 원복 때 다시 넣지 않아 지표가 비었던 일이 이미 있었다(measurement.md 8-10절). C1용 `MANAGEMENT_ENDPOINT_HEALTH_GROUP_LIVENESS_INCLUDE`도 같은 원복 대상이다 — 남으면 운영이 대안 B로 돈다.
3. **외부에서 닿지 않는다.** 모든 호출은 인스턴스 안의 `localhost`에서 한다. ALB 리스너가 `/internal`과 `/actuator`를 차단하고, 8081로는 트래픽을 보내지 않는다.
4. **인증 예외는 장치와 함께 생긴다.** `/internal/fault/**`의 인증 면제는 장치 설정 안의 별도 보안 체인에 두어, 장치가 꺼지면 면제도 함께 사라진다. 공통 `SecurityConfig`에는 넣지 않는다.

## 8. 주입 장치

| 장치 | 포트 | 호출 | 시나리오 |
|---|---|---|---|
| 무응답 소켓 대기 | 8080 | `GET /internal/fault/hang` | S2, S7 |
| 락 순서 역전 | 8080 | `GET /internal/fault/deadlock?side=a\|b` | 측정 제외 — 통합 테스트 전용 |
| 무응답 소켓 해제 | 관리 | `POST /actuator/fault/release-hang` | S2·S7 정리, 테스트 |
| 8080 커넥터 정지·재개 | 관리 | `POST /actuator/fault/pause-connector`, `resume-connector` | S4 |
| 메모리 누수 시작 | 관리 | `POST /actuator/fault/leak` 본문 `{"mbPerSecond":N}` | S6 |
| 주입 상태 조회 | 관리 | `POST /actuator/fault/status` | 전 시나리오의 사전 점검 |
| JVM 정지 | OS | `kill -STOP <pid>` | S5 |

**관리 포트 장치는 본문이 비어 있어도 JSON `Content-Type`이 필요하다.** actuator 쓰기 동작의 규칙이라 빠뜨리면 415가 난다(통합 테스트에서 실제로 겪었다). 스크립트는 `curl -X POST -H 'Content-Type: application/json' -d '{}' localhost:8081/actuator/fault/<동작>` 형태로 부른다.

워커를 묶는 장치는 **8080**에, 상태를 조작하는 장치는 **관리 포트**에 둔다. 8080을 멈추거나 워커를 다 묶은 뒤에도 조작할 수 있어야 하기 때문이다.

## 9. 이 설계의 한계

- **회차당 1회다.** 판정은 "교체됐는가"라는 이진 결과라 반복의 이득이 작지만, 감지 시간은 ALB 헬스체크 주기(30초)에 따라 ±30초 흔들린다. 감지 시간은 범위로만 말한다
- **기준선(C0) 대비 비교는 실측이 아니다.** S1 오탐은 기록이고, 고장 칸은 구조에서 나온 결론이다. 특히 "C2의 감지가 C0보다 최대 약 12초 늦다"는 계산값이며 측정으로 확인하지 않는다
- **C0 × S1 기록은 교체를 관측한 것이 아니다.** s-T 회차는 `ReplaceUnhealthy`를 멈춘 조건이라, "교체됐을 것"은 `UnHealthyHostCount` 1과 ASG 설정(`health_check_type = "ELB"`)에서 추론한 것이다
- **S2는 실제 장애의 재현이 아니라 증상의 재현이다.** 외부 API 무응답이 바깥에서 보이는 모습(워커가 묶이고 완료가 없다)을 만든 것이고, 특정 외부 API의 실제 장애 경로를 재현한 것은 아니다
- **원인이 다른 고장(데드락)은 운영 인프라에서 재지 않는다.** 같은 증상이라는 근거로 S2에 대표시켰고, 실제 Tomcat에서 503이 되는 것은 통합 테스트로만 확인했다
