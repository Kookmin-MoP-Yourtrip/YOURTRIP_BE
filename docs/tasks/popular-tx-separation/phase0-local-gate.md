# Phase 0 — 로컬 사전 확인 (EC2 측정 전 게이트)

> 인기 코스 조회의 트랜잭션 분리(커밋 `6637534`) 효과를 EC2에서 측정하기 전에, **가설 H1이 성립하는지 로컬에서 먼저 확인**한 기록이다. H1이 기각되면 EC2 인프라를 띄울 이유가 없어지므로 비용을 쓰기 전의 게이트로 실행했다.
>
> 결론만 먼저 밝히면: **H1은 성립한다.** before는 캐시가 전부 히트해 DB 쿼리가 0건인데도 요청마다 정확히 1회씩 커넥션을 대여했고(70,468요청 : 70,468대여), after는 73,932요청 동안 **단 한 번도 대여하지 않았다(0회)**. 다만 같은 측정에서 **처리량 개선은 +4.9%에 그쳤다** — 그 이유와 그로 인한 시나리오 조정 필요성이 이 문서의 후반부다.

## 검증하려던 가설

**H1 — before는 캐시가 전부 히트해도 DB 커넥션을 획득한다.**

Hibernate는 지연 커넥션 획득(`DELAYED_ACQUISITION_AND_RELEASE_AFTER_TRANSACTION`)을 하므로 "쿼리가 없으면 커넥션도 안 잡는 것 아닌가"라는 반론이 가능하다. 그러나 `hibernate.connection.provider_disables_autocommit`이 설정돼 있지 않으면(현재 `application.yml`에 없음) 트랜잭션 begin 시점에 물리 커넥션을 잡아 autocommit을 끄고, `readOnly = true`면 `Connection.setReadOnly(true)` 호출도 커넥션을 요구한다.

이게 사실이 아니라면 before/after의 차이가 없어지므로, 본 측정 전체가 무의미해진다.

## 측정 방법

| | 값 |
|---|---|
| 환경 | 로컬 개발 머신 1대 (앱 + PostgreSQL:5434 + Redis:6479 + k6 전부 동일 머신) |
| 코드 기준점 | before `98ef39b`(dev 머지 지점) / after `6637534`(리팩터링 커밋) |
| 부하 | k6 `constant-vus`, VU 20 × 25초, `GET /api/upload-courses/popular` 반복 |
| 캐시 | 부하 전 `curl` 3회로 워밍 (랭킹 캐시 `ALL` 히트 상태) |
| 데이터 | **없음** (`DB_DDL_AUTO=create`로 스키마만 생성) — 랭킹 응답은 `{"uploadCourses":[]}` |
| 판정 지표 | `hikaricp.connections.usage`의 **COUNT 증분** vs `http.server.requests` COUNT 증분 |

**순간값(`active`) 폴링이 아니라 누적 대여 횟수를 쓴 이유**: 캐시 히트 경로는 커넥션을 빌렸다 즉시 반납하므로 `active`를 초 단위로 찍으면 잡히다 말다 한다(실제로 첫 시도에서 `active`가 10과 0을 오갔다). "요청당 몇 번 빌렸는가"는 누적 COUNT 증분으로만 정확히 셀 수 있다.

**데이터가 없어도 되는 이유**: H1은 "트랜잭션 begin이 커넥션을 요구하는가"에 대한 가설이라 데이터와 무관하다. 오히려 쿼리가 0건이라 "쿼리 때문에 잡은 것"이라는 교란 요인이 원천 배제돼 더 순수한 검증이 된다.

**JIT 워밍업 통제**: 첫 run은 JIT 컴파일이 덜 된 상태라 처리량이 낮게 나온다(after 첫 run 1,896 req/s → 2번째 run 2,956 req/s, **+56%**). 두 arm 모두 **워밍업된 2번째 run**의 수치를 채택했다.

## 결과

| | TPS | avg | p95 | 실패율 | **커넥션 대여 횟수** | 요청 수 |
|---|---|---|---|---|---|---|
| before (`98ef39b`) | 2,818.2/s | 6.86ms | 11.81ms | 0% | **70,468회** | 70,468 |
| after (`6637534`) | 2,956.3/s | 6.51ms | 11.48ms | 0% | **0회** | 73,932 |
| 증감 | **+4.9%** | -5.1% | -2.8% | 동일 | **-100%** | — |

**판정 1 — H1은 성립한다. before는 DB 쿼리를 한 건도 하지 않으면서 요청마다 정확히 1회씩 커넥션을 대여했다.** 대여 횟수와 요청 수가 70,468 : 70,468으로 완전히 1:1이다. 데이터가 없어 실행된 SQL이 0건이라는 점을 감안하면, 이건 "일은 하나도 안 하면서 커넥션만 점유"의 직접 증거다 — `PRESIGN-BOTTLENECK.md`의 직접 증거 3(SQL 0건인데 pending 급증)과 같은 논증 구조다.

**판정 2 — after는 커넥션을 전혀 대여하지 않는다.** 73,932요청 동안 증분 0회. 리팩터링이 의도한 "캐시 히트 경로가 DB 커넥션을 아예 획득하지 않는다"가 런타임에서 확인됐다.

**판정 3 — 그럼에도 이 환경에서 처리량 개선은 +4.9%에 그쳤다.** 이게 이번 Phase 0에서 가장 중요한 발견이며, 아래에서 따로 다룬다.

## 왜 커넥션을 100% 없앴는데 처리량은 4.9%만 올랐는가

**캐시 히트 경로는 커넥션을 빌렸다 즉시 반납하기 때문이다.** 점유 시간이 마이크로초 수준이면 풀 크기가 10이어도 초당 수천 번 회전할 수 있다. 즉 이 시나리오에서 커넥션 풀은 **애초에 병목이 아니었다.** 상세조회(mycourse)가 풀에 막혔던 건 그 경로가 커넥션을 쥔 채 실제 쿼리·서명을 했기 때문이지, 커넥션을 잡는다는 사실 자체 때문이 아니다.

따라서 이번 리팩터링의 실질 가치는 "워밍 캐시에서의 처리량"이 아니라 다음 두 곳에 있고, **본 측정의 시나리오를 그쪽에 맞춰야 한다**:

1. **콜드 캐시 + 락 대기 (계획의 S3).** 랭킹 캐시 미스 시 락을 못 잡은 요청은 최대 1초(`10 × 100ms`) `Thread.sleep`한다. before는 이 구간 내내 커넥션을 쥐고 있다 — 여기서는 점유 시간이 짧지 않다. 실제로 이번 측정의 **첫 run(캐시가 아직 안 데워진 상태)에서 `active=10`, `pending=5`가 3초간 관측**됐고, 캐시가 채워진 뒤 곧바로 0으로 떨어졌다. H3의 예고편이 우연히 잡힌 셈이다.

2. **커넥션 풀을 공유하는 다른 API에 대한 간접 효과.** 인기 코스 조회가 커넥션을 전혀 쓰지 않으면, 같은 풀(10개)을 쓰는 상세조회·마이코스가 그만큼 여유를 얻는다. 단일 엔드포인트만 때리는 시나리오로는 이 효과가 원리적으로 드러나지 않는다.

## 한계

- 로컬 단일 머신 측정이라 앱·DB·Redis·k6가 CPU를 공유한다. 기존 문서(`stage0/local/index.md` Phase C)가 이미 "이 환경에서는 결론을 못 낸다"고 결론 낸 조건이므로, **처리량·지연의 절대값은 신뢰하지 않는다.** 이 측정에서 신뢰하는 건 커넥션 대여 횟수(0 vs 요청당 1회)라는 이산적 사실뿐이다.
- 데이터가 없어 랭킹 쿼리가 즉시 끝난다. 실제 3,000건 데이터에서는 랭킹 쿼리(`ORDER BY view_count DESC`, 전용 인덱스 없음)가 느려져 콜드 구간의 락 대기가 훨씬 길어진다.
- 각 arm 1회 측정이다.

## 시사점 — 본 측정 시나리오 조정

Phase 0 게이트는 통과했으므로 EC2 측정으로 진행한다. 다만 계획의 시나리오 우선순위를 아래와 같이 바꾼다.

- **S3(콜드 캐시)를 핵심 시나리오로 승격.** 워밍 캐시(S1/S2)에서는 커넥션 점유 시간이 짧아 차이가 작게 나온다는 것이 로컬에서 확인됐다.
- **혼합 부하 시나리오(S5) 신설 검토.** `/popular`과 상세조회를 동시에 걸어, 인기 코스가 커넥션을 반납함으로써 상세조회 쪽 `pending`/`acquire_seconds`가 개선되는지 본다. 이게 실제 운영에서 이 리팩터링이 갖는 의미에 가장 가깝다.
- S1/S2는 유지하되, **"커넥션 대여 0"을 입증하는 시나리오**로 성격을 재정의한다(처리량 개선을 주장하는 근거로 쓰지 않는다).
