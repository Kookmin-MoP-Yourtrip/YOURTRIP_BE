## 0. 요약

- 입장 제한(#192)은 요청 1건을 자리 1개로 셌다. 그런데 요청 하나가 만드는 LLM 호출은 `1 + 일수`개(Planner 1 + day 마다 Curator 1)라, **같은 상한 4가 1일 요청에는 호출 8개, 5일 요청에는 24개**를 뜻했다. 상한 4를 정한 측정은 전부 3일 일정(호출 16개)이었다
- **기준선 측정으로 문제를 확인했다**(1절). 같은 시간대에 일수만 바꿔 동시 4명을 보내자, 5일은 받아들인 요청의 **25%가 예산을 다 쓰고** Curator 칸 13%가 폴백이었다. 1일은 LLM 슬롯 5개가 **다 찬 순간이 한 번도 없었다** — 슬롯이 남는데 5번째 요청은 429를 받는다
- 요청 하나가 쓰는 슬롯 시간은 **호출 하나당 약 6초**로 일수와 무관하게 거의 일정했다(2절). 그래서 입장을 **요청마다 자리 `1 + 일수`개**로 세고, 총량은 상한 4의 품질 기준선(3일 × 4건 = 16)을 그대로 옮긴 **16**으로 정했다
- 긴 일정이 굶는지 Kaufman–Roberts 재귀로 계산했다(3절). **굶주림은 없다**(대기가 없어 도착마다 독립 판정). 자리 수에 비례해 더 자주 거절될 뿐이고, 자리 예약으로 이를 고르게 하면 전체 거절이 크게 늘어 넣지 않았다
- 자리는 요청이 끝날 때가 아니라 **그 자리를 묶은 LLM 호출이 끝날 때** 돌려준다(4절). 예산이 지나 버려진 호출도 끝까지 슬롯을 쓰기 때문이다. 이로써 "총량 16 ≤ 실행기 스레드 20"이 버려진 호출까지 포함해 성립한다
- **로컬 전후 측정(5절)**: 5일 × 동시 4 에서 폴백 **11.5% → 1.7%**, 요청당 Curator 슬롯 대기 31~34초 → 4~8초. 3일은 그대로(회귀 없음), 1일은 동시 8건을 받아 **처리량이 2배**가 되면서 폴백 0%. 대가로 5일 요청이 몰릴 때 라운드마다 2건이 429를 받는다
- **운영 구성 측정(6절)**: #197 장애 격리 실험과 같은 조건(t3.small · 배경 API 초당 20건 · 포아송 도착)에 일수를 1~5일 균등으로 섞었다. C 실험이 서비스 전체 장애를 낸 분당 70건에서도 **배경 API 정상**(p99 12ms, Tomcat 11/32, CallerRuns 0)이고, 같은 도착에서 **온전한 코스가 56 → 89건(+59%)**, 예산 소진 2 → 0건, 폴백 2.5 → 0.0%. 대가로 5일 코스는 9 → 2건

## 2. 총량 산정 — 16

### 2-1. 단위: 호출 하나

| 일수 | 요청 1건의 슬롯 시간 | 자리(1 + 일수) | 자리당 슬롯 시간 |
|---|---|---|---|
| 1 | 10.8 ~ 11.7초 | 2 | 5.4 ~ 5.9초 |
| 3 | 24.8 ~ 25.4초 | 4 | 6.2 ~ 6.4초 |
| 5 | 39.8 ~ 41.5초 | 6 | 6.6 ~ 6.9초 |

- 자리당 비용이 일수에 따라 조금 오르는 것은 일정이 길수록 Planner 출력이 길어서다. 5일을 약간 싸게 세는 쪽으로 기우는 오차다

동시 도착(최악)에서 슬롯을 다 비우는 시간은 대략 `자리 수 × 자리당 시간 ÷ 슬롯 5`다.

## 3. 긴 일정은 굶는가

### 3-1. 방법

입장 제한은 대기 없이 즉시 429를 내는 **손실 시스템**이고, 요청마다 쥐는 자리 수가 다르다. 이때 종류별 거절 확률은 **Kaufman–Roberts 재귀**가 준다. 얼랑 B를 여러 크기의 손님으로 넓힌 공식이라 같은 무감응성(처리 시간 분포와 무관하게 평균만으로 성립)을 가지며, #193에서 얼랑 B가 실측과 1 ~ 4%p로 맞은 근거가 그대로 이어진다. 상태에 따라 판정을 바꾸는 자리 예약은 재귀가 성립하지 않아 이벤트 시뮬레이션으로 쟀다. 예약이 없는 칸에서 두 방법은 0.3%p 안으로 일치했는데, 이는 **계산이 맞다는 확인일 뿐** 아래 근사가 실제 정책과 같다는 근거는 아니다.

**모델의 한계 — 일괄 점유 근사.** 이 계산은 요청이 자리 `1 + 일수`개를 입장부터 끝까지 한꺼번에 쥔다고 본다. 실제 구현(4절)은 호출마다 반납해 Planner 자리가 요청 시간의 약 3분의 1 지점에 먼저 돌아온다. 실제 점유가 더 짧으므로 아래 거절률은 **실제보다 높은 쪽의 추정**이고, 일수 사이의 상대적 차이(긴 일정이 더 자주 거절된다)를 보는 용도로 읽는다. 실제 거절률은 운영의 `ai.course.admission{days}`로 확인한다.

- 처리 시간: 1일 11초에서 일당 4초씩 늘려 5일 27초(기준선 동시 4의 p50과 맞춘 보수적 가정). 1.3배 민감도도 계산했다
- 일수 분포는 실제 트래픽이 없어 셋을 가정했다 — 국내 여행형(2·3일 70%, 5일 5%) · 균등 · 긴 일정형(5일 40%)
- 재현: `python scripts/loadtest/admission-blocking.py [--scale 1.3]` → `results/admission-200/blocking/`

### 3-3. 판단

- **굶주림은 없다.** 대기열이 없으니 도착마다 그 순간의 빈자리로 독립적으로 판정된다. 국내 여행형에서 5일 요청이 재시도까지 두 번 연속 거절될 확률은 약 1.5%(12%²)다. "자리 6개가 모이길 기다리다 영영 못 들어간다"는 대기가 있을 때만 생기는 현상이다
- **대신 자리 수에 비례해 더 자주 거절된다** — 5일은 1일보다 낮은 부하에서 4 ~ 6배, 높은 부하에서 2.5 ~ 3배
- **자리 예약(trunk reservation)은 넣지 않았다.** 짧은 요청이 마지막 자리 r개를 못 쓰게 하는 방식인데, 예약 2는 5일 거절을 1.7%p 줄이는 대신 3일 거절을 4.2%p 올리고 전체를 5.3 → 8.8%로 만든다. 짧은 요청을 일부러 막아 자리를 비워 두는 만큼 처리량도 준다
- **입장 대기도 넣지 않았다.** 대기는 `CourseDeadline` 앞이라 응답 최대 시간을 늘리고, 기다리는 동안 요청 스레드를 쥔다 — 비교 실험 C의 워커 점유와 같은 함정이다
- 그래서 **쓰는 만큼 막힌다**를 의도된 비용으로 받는다. 상한 4는 긴 요청의 비용을 받아들인 모두의 폴백으로 떠넘겼고, 총량 16은 그 비용을 긴 요청 자신의 거절률로 돌려준다. 긴 일정형 분포에서 전체 거절이 7.5 → 19.4%로 오르는 것도 같은 비용이다 — 상한 4가 더 받던 요청은 대부분 5일이고, 그 4분의 1이 예산을 다 썼다(1절)
- 일수별 거절률은 `ai.course.admission{days}`로 운영에서 본다. 5일 거절이 목표를 넘으면 손잡이는 예약이 아니라 공급(슬롯·OpenAI 티어)이다

## 4. 구현

### 4-1. 자리를 떼고 돌려주는 경로

```
MyCourseServiceImpl.createAICourse
 └ AiCourseAdmission.admit(days, lease -> ...)   tryAcquire(1 + days), 모자라면 즉시 429
    └ AiCoursePipeline.generate(brief, lease)
       ├ PlannerAgent.plan(..., lease)            lease.track(호출) — 호출이 끝나면 1자리 반납
       └ CuratorAgent.curate(..., lease)          day 호출마다 lease.track(호출)
 ← admit 종료 시 lease.close()                     호출에 묶이지 않은 자리만 반납
```

- `LlmWorkLease`가 요청 하나가 뗀 자리를 담아 에이전트까지 내려간다. `track(future)`는 실행기에 올린 호출의 future 에 `whenComplete`로 반납을 건다
- **호출이 끝날 때 돌려주는 이유** — 예산이 지나면 파이프라인은 기다림을 끊고 폴백으로 응답하지만, 이미 떠난 LLM 호출은 취소되지 않고 끝까지 슬롯을 쓴다(STEP-3). 요청 종료 시 돌려주면 그 호출이 슬롯을 쥔 채 새 요청이 들어와, 입구가 보는 자리 수가 실제 LLM 작업량보다 작아진다. 비교 실험 C의 좀비 작업과 같은 어긋남이다. 덤으로 Planner 자리는 Curator 가 도는 동안 먼저 돌아온다
- **올리지 않은 호출의 몫** — Planner 실패(기본 플랜), 진입 전 예산 소진으로 건너뛴 Curator 의 자리는 `close()`가 요청 종료 시 돌려준다
- **예약보다 많은 호출** — Planner 가 일수를 다르게 돌려주면 넘친 호출은 자리 없이 돈다. 막으면 이미 받아들인 요청의 품질이 깨지고, 자리가 총량을 넘겨 부풀지 않는다는 점은 테스트로 고정했다

### 4-2. 시그니처를 어떻게 넓혔나

자리를 `CourseDeadline`에 끼우면 모든 단계에 이미 넘어가므로 시그니처가 그대로지만, 시간 예산과 작업 자리라는 다른 관심사가 한 타입에 섞인다. 그래서 Planner·Curator·파이프라인에 **임대를 받는 오버로드**를 더하고, 기존 시그니처는 `LlmWorkLease.untracked()`로 위임했다. 에이전트를 단독으로 부르는 테스트·벤치마크 약 30곳은 그대로이고, 바뀐 것은 파이프라인 테스트의 목 설정뿐이다.

|---|---|---|
| 설정 | `ai.course.admission.max-concurrent-requests: 4` | `ai.course.admission.max-work-units: 16` + `max-requests: 8` |
| 거절 지표 | `ai.course.admission{result}` | `ai.course.admission{result, days}` (시계열 10개, 0으로 사전 등록) |
| 점유 게이지 | 요청 수 | **자리 수**(버려졌지만 아직 도는 호출 포함) + 처리 중 요청 수(`ai.course.admission.requests.in_use`) |

**요청 수 상한(8)을 따로 두는 이유** — 작업 자리는 LLM 호출이 끝나면 돌아오지만, 요청은 그 뒤 그라운딩(장소 API)·경로·URL 보강 동안에도 Tomcat 워커를 쥔다. 자리만 세면 후속 단계가 느려질 때 자리가 빈 틈으로 새 요청이 계속 들어와 워커가 쌓인다 — 비교 실험 C r70 에서 장소 API 대기로 워커 32개가 모두 찬 것과 같은 경로다(PR 리뷰에서 지적받았다. 처음에는 "동시 요청 ≤ 16 ÷ 2 = 8"을 자리에서 유도했는데, 자리는 요청 수명 전체를 덮지 않아 그 유도가 틀렸다). 그래서 요청이 끝날 때까지 쥐는 요청 자리를 함께 둔다. 8은 자리만으로 받을 수 있는 최대 요청 수와 같아 평소에는 자리보다 먼저 걸리지 않고, 후속 단계가 멈출 때만 막는다. 그라운딩은 평소 0.1초 안이라 6절의 측정 결과는 이 상한과 무관하게 같다고 본다.

`AiExecutorCapacityInvariantTest`가 네 부등식을 운영 설정 파일에서 읽어 고정한다.

1. **총량 16 ≤ `aiAgentExecutor` 스레드 20** — 자리가 호출 종료 시 돌아오므로 버려진 호출까지 합쳐도 실행기 작업이 스레드를 넘지 않는다. 큐가 쌓이지 않으니 `CallerRunsPolicy`(요청 스레드가 LLM 을 직접 실행 — #197 서비스 전체 장애의 원인)가 발동할 수 없다. #178 때는 "입장 4 × 5일 = 20"으로 따졌고 버려진 호출은 이 부등식 밖이었다
2. **가장 긴 요청 6자리 ≤ 16** — 넘으면 그 요청은 영원히 입장하지 못하는데 응답은 재시도하라는 429 다. 일수 상한이 400으로 먼저 막아야 한다
3. **요청 수 상한 8 < prod Tomcat 워커 32** — 후속 단계가 멈춰도 AI 요청이 워커를 모두 쥐지 못한다
4. **요청 수 상한 8 ≥ 총량 16 ÷ 1일 요청 2자리** — 요청 수 상한이 먼저 걸리면 슬롯이 남아도 1일 요청을 돌려보내 이 변경의 목적이 무너진다

5일 요청이 동시에 몰리면 **예산 안에 끝난 5일 코스**가 라운드당 3.3건(이전, 24건 중 20건) → 1.8건(새, 12건 중 11건)으로 줄었다. 받아들인 요청은 폴백이 거의 없고 나머지는 즉시 429로 재시도할 수 있다. #192에서 정한 "받아들인 사람의 품질을 처리량보다 우선한다"를 긴 일정에도 똑같이 적용한 결과다.

새 코드 2회차가 소진 0 · 폴백 0%로 여유 있게 끝난 것은, LLM 이 빠른 시간대에는 16이 5일 요청에 보수적일 수 있다는 신호다. 16은 느린 날 기준이라 유지하고, 운영의 `days` 거절률과 함께 다시 본다.

## 6. 운영 구성 측정 (AWS)

### 6-1. 왜 따로 쟀나

5절은 품질과 처리량을 보여 주지만 **격리**는 보여 주지 못한다. 로컬에는 배경 부하가 초당 2건뿐이고 코어도 넉넉하다. 이번 변경으로 동시 AI 요청의 최대치가 4건에서 8건(1일 요청만 몰릴 때)으로 늘었는데, #197 의 장애는 바로 vCPU 2개 위에서 Tomcat 워커가 AI 요청에 붙잡혀 생겼다. 그래서 그 실험과 같은 구성에서 다시 쟀다.

### 6-2. 조건

- [#197 설계](../ai-bulkhead-loadtest/README.md) 10절과 같다 — `terraform/prod`(t3.small 1대, ALB, RDS, ElastiCache), k6 EC2 `m7i-flex.large`, 배경 API(`/popular` + 코스 상세) 초당 20건, 웜업 2분 → 기준선 2분 → AI 포아송 도착 5분 → 회복 3분, TourAPI 생략, ASG 교체·확장 일시 중지, 관리 포트 8081 분리
- **새로 더한 것** — `ai-bulkhead.js`의 `DAYS_MIX`로 본 도착의 일수를 1~5일 균등으로 섞었다. 일수는 도착 순번마다 시드로 정해 **B와 D가 정확히 같은 "도착 시각 + 일수" 순서**를 받는다. 웜업은 3일 고정
- arm: B = 요청 수 상한 4(`47c0425`, dev 와의 앱 코드 차이는 #178 일수 검증뿐이라 5일 이하 입력에서는 같다) · D = 자리 16(`6476ccc`). 순서 B40 → D40 → D70 → B70
- **측정 중 사고** — 첫날 r70-D 도중(AI 도착 약 1분 30초째) **네이버 지역검색 일일 한도**가 소진됐다(QUOTA_EXCEEDED 406줄). 후보 공급이 전면 실패해 504 21건이 났고, 이어질 r70-B 는 k6 시작 전에 멈췄다. 두 회차를 무효로 분리하고(`r70-*m1.naver-quota-exhausted`·`.aborted`), 인프라를 유지한 채 한도가 초기화된 다음 날 r70 두 회차를 다시 쟀다. 같은 날 로컬 측정과 같은 키를 쓴 탓이다 — 10-05 의 TourAPI 사고와 같은 유형이다

### 6-4. 해석

- **격리는 운영 조건에서도 유지된다.** C 실험(#201)이 Tomcat 32/32 포화로 서비스 전체 장애를 낸 분당 70건에서, 동시 요청이 늘 수 있는 D 도 배경 API p99 12ms · Tomcat 11/32 였다. 측정 당시 코드에는 요청 수 상한이 없었지만 그라운딩이 막히지 않아 워커 점유가 11에 그쳤다 — 후속 단계가 막히는 경우는 4-3절의 요청 수 상한이 맡는다
- **같은 슬롯으로 더 많이, 더 온전하게.** 같은 도착에서 온전한 코스가 r40 +40%, r70 +59%다. 요청 수로 세던 B 는 1일 요청에도 자리를 1개씩 줘 슬롯이 남는 동안 짧은 요청을 돌려보냈다. 동시에 예산 소진과 폴백은 0으로 내려갔다 — B 는 몰리면 5일 요청이 예산을 다 썼다
- **대가는 3절의 예측대로 긴 일정이 진다.** r70 에서 5일 코스 9 → 2건, 4일 13 → 7건. "쓰는 만큼 막힌다"가 운영에서도 그대로 나타났다. 운영의 `days` 태그로 이 비율을 계속 본다
- **흩어진 도착에서는 B 의 품질 문제도 작다**(폴백 0.7 ~ 2.5%). 5절의 큰 차이(11.5 → 1.7%)는 5일 요청 4건이 동시에 몰리는 최악의 경우다. 이 변경의 이득은 평소에는 **처리량**, 몰릴 때는 **품질**로 나타난다
- **실행기 큐가 순간 1** — r40-D 에서 한 번. 자리는 호출의 future 가 완료되는 순간 돌아오는데, 그때 실행기 스레드는 아직 작업을 정리하는 중이라 새 작업이 잠깐 큐를 거칠 수 있다. 큐 50이 받고 CallerRuns 는 0이라 무해하다. 불변식 ①은 "스레드 수 안"이 아니라 "큐가 쌓이지 않는다"의 근사로 읽는다

## 7. 한계

- **서버 1대다** — 운영 ASG 는 최대 2대이고 총량 16은 서버당 값이다. OpenAI 계정 한도(TPM)는 서버들이 나눠 쓰므로, 2대가 동시에 자리를 다 쓰는 경우는 재지 않았다
- **일수 분포는 균등 하나만 쟀다** — 3절의 국내 여행형·긴 일정형 분포는 계산뿐이다. 회차당 표본도 1회다(#197 에서 같은 arm 의 반복이 판정을 바꾸지 않았다는 근거에 기댄다)
- **일수 분포는 가정이다** — 실제 트래픽이 생기면 `days` 태그로 분포와 일수별 거절률을 함께 얻는다
- **표본이 작다** — 5일은 조건마다 2회, 다른 일수는 새 코드 1회다. 폴백 비율은 소진된 요청 하나가 칸을 몇 개 비우느냐로 크게 흔들린다(이전 코드 회차별 8 ~ 18%)
- `scripts/loadtest/aggregate-arrival.py`는 입장 게이지를 요청 수 상한(`--limit`)과 견주고 얼랑 B로 예측한다. 자리 단위가 된 뒤의 도착률 측정에는 맞지 않는다
