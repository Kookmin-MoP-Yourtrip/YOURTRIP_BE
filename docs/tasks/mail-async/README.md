# 인증 메일 발송의 Tomcat 워커 분리 — 설계

> **상태: 설계 확정 (구현 전)** · 이슈 #221
>
> 이 문서는 구현 전에 내린 설계 결정과 그 근거를 남긴다. 기준선·개선 후 측정의 예측과 판정 기준은 측정 전에 별도 문서(`measurement-design.md`)로 고정한다.

## 0. 요약

- **문제**: 인증번호 발송 API가 SMTP 왕복 내내 Tomcat 워커(prod 32개)와 Hikari 커넥션(10개)을 함께 쥔다. SMTP 타임아웃이 없어 이론상 무한히 쥘 수 있다.
- **결정**: 발송을 메일 전용 풀로 넘기고 바로 응답한다(A안). 성공 응답의 의미는 "발송 완료"에서 "**발송 접수**"로 바뀐다.
- **감수하는 것**: 프로세스가 비정상 종료될 때 큐에 남아 있던 메일의 유실. 사용자는 재발송으로 복구한다.
- **함께 고치는 것**: `MailService`의 `@Transactional` 때문에 SMTP 대기 중 커넥션을 쥐고, 최종 실패 시 MailLog까지 롤백되는 문제.

## 1. 현재 구조와 문제

대상 API는 둘이고 같은 경로를 탄다.

| API | 진입점 |
|---|---|
| `POST /api/users/email/send` | `UserServiceImpl.sendVerificationCode` |
| `POST /api/users/password/find/email` | `UserServiceImpl.findPasswordSendEmail` |

```
[Tomcat 워커] DB findByEmail → Redis saveCode → MailService.sendVerificationMail (@Transactional → 커넥션 확보)
                                                  ├ SMTP 발송 (타임아웃 없음)
                                                  ├ 실패 시 대기 없이 재귀 재시도 ×3
                                                  └ 시도마다 MailLog save
                                                → 커밋 / 최종 실패면 롤백 → 응답
```

| # | 문제 | 근거 |
|---|---|---|
| P1 | SMTP를 기다리는 동안 Tomcat 워커와 Hikari 커넥션을 함께 쥔다 | `JpaTransactionManager`는 트랜잭션 시작 시점에 커넥션을 확보한다. 지연 획득 설정(`provider_disables_autocommit` + `LazyConnectionDataSourceProxy`)이 없다 |
| P2 | SMTP 타임아웃이 없다 | `spring.mail.properties.mail.smtp.*timeout` 미설정 → JavaMail 기본값은 무한 대기 |
| P3 | 재시도에 간격이 없다 | 순간 장애에도 4번 모두 같은 장애에 부딪힌다. 인증 오류처럼 재시도해도 소용없는 실패까지 재시도한다 |
| P4 | 최종 실패 시 MailLog가 사라진다 | 마지막 `BusinessException`이 트랜잭션을 롤백해, 앞서 저장한 FAILED 로그까지 지운다 |

### 1-1. 트랜잭션은 왜 걸려 있었나

`@Transactional`은 메일 인증 기능을 처음 넣은 커밋(`2108f7bc`)에 기능과 함께 들어왔고, 이유가 기록된 곳은 없다. 이 메서드에서 DB를 쓰는 작업은 MailLog `save()`뿐이다. 그런데 `SimpleJpaRepository.save()`는 그 자체로 트랜잭션이라 바깥 트랜잭션이 없어도 저장된다. 바깥 트랜잭션이 더하는 것은 "시도별 로그를 한 번에 커밋한다"는 원자성뿐인데, 시도별 로그는 서로 독립된 기록이라 묶을 이유가 없다. 오히려 그 원자성 때문에 P4가 생긴다. 메일 발송은 롤백할 수 없으므로 트랜잭션으로 보호되는 것도 없다. 결국 **이득은 없고 P1·P4라는 손해만 있다.**

## 2. 설계안 비교

| | **A. 즉시 응답 + 전용 풀** | B. 서블릿 비동기 (`CompletableFuture`) | C. Outbox / 영속 큐 |
|---|---|---|---|
| Tomcat 워커 | 제출 직후 응답까지 끝남 | 제출 직후 반납, 응답은 재디스패치 | 즉시 반납 |
| 클라이언트 대기 | Redis 저장까지 | SMTP와 재시도 전체 | Redis 저장까지 |
| 발송 실패를 응답으로 알리나 | 아니요 (MailLog·지표로 봄) | 예 (500) | 아니요 |
| 재시도 백오프 | 자유 | 55초 `request-timeout` 안 | 자유 |
| 프로세스 비정상 종료 시 | 큐에 남은 메일 유실 | 해당 없음 | 보존 |
| 변경 범위 | `MailService` 내부 | 컨트롤러·서비스 시그니처 + 테스트 | 테이블·폴링 워커·중복 방지 |

### 2-1. A를 고른 이유

- **B가 응답으로 알려주는 "실패"는 좁다.** SMTP 접수 성공은 도착을 뜻하지 않는다. 스팸함이나 바운스는 B로도 알 수 없고, 실제로 "메일이 안 와요"를 겪게 하는 가장 흔한 원인이 이쪽이다. B로만 잡히는 실패는 인증 정보 오류나 발송 한도 초과 같은 **시스템 장애**인데, 이런 장애는 사용자 한 명에게 500을 보여줄 일이 아니라 지표와 알림으로 운영자가 잡을 일이다.
- **복구 경로가 이미 있다.** 인증번호 화면에는 재발송이 있다. 인증번호는 5분짜리 일회용 값이라, 유실돼도 데이터가 깨지거나 가입이 반쯤 된 상태로 남지 않는다. 유실 비용은 "재발송 한 번"이다.
- **C는 이 규모에서 과하다.** "재발송 한 번"을 막기 위해 테이블·워커·중복 방지를 들이는 비용이 더 크다. 게다가 재기동 후 다시 보낼 시점에는 코드가 이미 만료됐을 수 있다.

### 2-2. 유실의 범위와 감수하는 것

| 유실 지점 | 처리 |
|---|---|
| ⓐ 배포·정상 종료 중 큐에 남은 메일 | **막는다** — 종료 시 큐를 비우고 내려간다 |
| ⓑ SMTP 일시 장애 | **막는다** — 백오프 재시도 |
| ⓒ 프로세스 비정상 종료 (OOM·강제 종료) | **감수한다** — 메모리 큐라 사라진다. 막으려면 C가 필요하다 |
| ⓓ SMTP 장기 장애로 재시도 전부 실패 | 발송은 못 한다. **감지한다** — MailLog·지표 |
| ⓔ 접수 후 스팸·바운스 | 어떤 방식으로도 못 막는다 — 재발송 |

ⓒ를 막는 더 가벼운 길로, 인증번호와 같은 Redis에 작업을 넣는 신뢰 큐(`LMOVE`)도 검토했다. 다중 인스턴스에서 중복을 막는 처리가 필요해 이번 범위에서는 채택하지 않았다.

## 3. A안 상세

### 3-1. 비동기 경계 — executor를 직접 호출한다

`MailService.sendVerificationMail(to, code)`의 시그니처는 그대로 두고, 내부에서 `mailExecutor`에 제출만 한다. 풀이 가득 차 거절되면 Tomcat 워커에서 바로 `RetryLaterException`(503 + `Retry-After`)을 던진다.

- AI의 `AiCourseAdmission.admitAsync`와 같은 구조다. 거절 판정은 Tomcat 워커에서, 받아들인 작업만 풀에서 처리한다.
- `@Async`를 쓰지 않는 이유: 거절 처리가 프록시 뒤에 숨어 코드에 드러나지 않고, 같은 클래스 안에서 호출하면 적용되지 않으며, 단위 테스트에서 동기 실행으로 바꾸기도 번거롭다.
- `UserServiceImpl`은 바꾸지 않는다. "Redis 저장 성공 후에만 발송한다"는 순서 불변식이 그대로 유지된다.

### 3-2. 전용 풀 `mailExecutor`

- **거부 정책은 `AbortPolicy`다.** `CallerRunsPolicy`면 넘친 작업을 Tomcat 워커가 직접 처리해 격리 목적이 사라진다(`AsyncConfig.aiRequestExecutor`와 같은 원칙).
- **스레드는 적게, 큐는 유한하게 둔다.** SMTP 장애 시 작업 하나가 "타임아웃 × 시도 횟수 + 백오프"만큼 스레드를 쥐므로, 큐가 무한이면 장애가 소리 없이 쌓이기만 한다. 구체적인 값은 기준선 실측 뒤에 정한다.
- **종료 시 큐를 비운다** — `waitForTasksToCompleteOnShutdown`. 기다리는 시간의 상한은 한 작업의 최악 소요 시간에서 정한다.

### 3-3. SMTP 타임아웃

`mail.smtp.connectiontimeout`, `timeout`, `writetimeout`을 명시한다. **비동기화보다 먼저 넣는다.** 타임아웃 없이 비동기로만 바꾸면 무한 대기가 메일 풀로 옮겨가 그 풀이 소리 없이 바닥난다. 값은 기준선에서 잰 정상 발송 지연을 보고 정한다.

### 3-4. 재시도

한 작업이 메일 스레드 하나를 쥐고, 그 스레드 안의 반복문에서 재시도한다.

```
시도 → 실패 → 재시도할 실패인가? (인증 오류·잘못된 주소면 즉시 포기)
     → 백오프 대기 → Redis의 현재 코드가 내 코드인가? (재발송으로 바뀌었으면 폐기)
     → 다음 시도 … → 상한에 닿으면 포기
```

**대기 중에도 스레드를 쥐는 방식을 택했다.** 대안은 실패할 때마다 `TaskScheduler`에 다음 시도를 예약하고 스레드를 반납하는 것이다. 하지만 그렇게 하면 예약된 재시도가 풀의 큐 상한을 우회해, 장애 시 작업이 상한 없이 쌓일 수 있다. 쥐고 있는 스레드는 메일 전용이라 다른 API에 주는 피해가 없다. 벌크헤드의 목적은 메일 스레드를 효율적으로 쓰는 것이 아니라 메일 지연을 메일 풀 안에 가두는 것이다. 또 장애 시 스레드를 실제로 오래 쥐는 것은 백오프보다 타임아웃 대기다.

**재발송으로 바뀐 코드는 폐기한다.** 백오프 대기 중에 사용자가 재발송하면 Redis의 코드가 새 값으로 바뀐다. 이때 옛 코드의 재시도가 나중에 성공하면, 늦게 도착한 옛 메일 속 코드는 검증에서 `INVALID_VERIFICATION_CODE`가 된다. 동기 구조에서도 이론상 있던 창이지만, 백오프가 그 창을 수 초로 넓히므로 이번에 함께 막는다.

### 3-5. MailLog

- 발송 경로의 `@Transactional`을 걷는다. 시도마다 `save()` 자체의 짧은 트랜잭션으로 커밋된다. 이것으로 P1(이 메서드 몫)과 P4가 해결된다.
- `retryCount`는 이름과 달리 **"몇 번째 시도인가"(0부터)**를 뜻하고, 시도마다 행이 하나씩 생긴다. 쓰는 곳은 `MailService` 하나, 읽는 곳은 없다. **의미는 바꾸지 않고** 메일 스레드의 반복문에서 같은 값을 쓴다.
- `status`에 `GAVE_UP`(재시도 상한 도달), `STALE`(재발송으로 폐기)을 더한다. 컬럼 길이 10 안에 들어간다.
- 같은 메일의 시도 행들을 묶는 식별자는 없다. 컬럼을 추가해야 하는 스키마 변경이라 이번 범위에서 제외한다.

### 3-6. 관측

A안에서는 실패가 응답으로 드러나지 않으므로, **지표가 실패를 보는 유일한 창이다.**

| 지표 | 내용 |
|---|---|
| `mail.send.attempt` (Timer) | SMTP 시도 한 번의 지연. 결말(`success`/`failure`)별 히스토그램 |
| `mail.send` (Counter) | 메일 한 통의 최종 결말(`sent`, `gave_up`, 이후 `stale`·`rejected`) |
| `mail.executor` | 활성 스레드·큐 크기 (풀 도입 후) |

## 4. 작업 순서

| 단계 | 내용 | 커밋 |
|---|---|---|
| 1 | `mail.send` 지표 추가 (동작 변화 없음) | `feat` |
| 2 | 측정 설계 고정 → 가짜 SMTP 지연 주입으로 기준선 실측 | `docs` |
| 3 | SMTP 타임아웃 명시 | `fix` |
| 4 | MailLog 트랜잭션 분리 | `fix` |
| 5 | `mailExecutor` 제출 + 포화 시 503 | `perf` |
| 6 | 재시도 예외 분류·백오프·낡은 코드 폐기 | `feat` |
| 7 | 같은 조건으로 재측정, 결과 기록 | `docs` |

측정은 실제 Gmail로 하지 않는다. 발송 한도와 스팸 판정 위험이 있기 때문이다. 가짜 SMTP 서버를 띄우고 지연을 주입한다. 핵심 지표는 메일 요청 자체의 속도가 아니라, **SMTP가 느릴 때 메일 요청과 함께 들어오는 다른 API의 응답 시간**이다.

## 5. 범위 밖

| 항목 | 이유 |
|---|---|
| 비밀번호 찾기에서 회원가입 템플릿이 나가는 문제 | `findPasswordSendEmail`이 `sendVerificationMail`을 호출한다(`sendPasswordResetMail`은 미사용). 관심사가 달라 별도로 다룬다 |
| 메일 단위 식별자 컬럼 | 스키마 변경. 필요해지면 별도 이슈 |
| 성공 응답을 202로 바꾸기 | FE 영향을 확인하지 않았다. 200 유지 |
| ⓒ 유실 방지 (Outbox·Redis 신뢰 큐) | 2-1절 |
