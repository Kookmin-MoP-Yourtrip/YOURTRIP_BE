# AI 코스 생성 여행 일수 상한 — 5일

> 이슈 [#178](https://github.com/Kookmin-MoP-Yourtrip/YOURTRIP_BE/issues/178). 측정일 2026-10-08, 로컬, 실제 OpenAI·네이버·TourAPI·카카오 호출.

## 0. 요약

- `AICourseCreateRequest`는 시작일 ≤ 종료일만 검사해 **여행 일수에 상한이 없었다.** FE 날짜 선택기에도 범위 제한이 없다
- Curator 는 day 마다 LLM 호출 1개를 병렬로 낸다. 그래서 일수가 곧 요청 하나의 LLM 작업 수이고, 30일 요청 하나가 작업 31개를 만든다
- 입장 제한(#192)은 요청 **수**만 센다. 긴 일정 요청 몇 건이 입장을 통과하면 `aiAgentExecutor`(스레드 20 + 큐 50)가 넘치고, 아직 남아 있는 `CallerRunsPolicy`가 Tomcat 워커에 LLM 작업을 떠넘긴다. 이 경로가 #197 장애 격리 실험에서 서비스 전체 장애를 만든 원인이다 — **개선 후 구조에도 긴 일정이라는 우회로가 남아 있었다**
- **일수 상한 5일**을 두고 넘으면 400으로 거절한다. 근거는 둘이다
  1. **LLM 슬롯 5개와 맞는다** — 5일까지는 Curator 가 한 번에 다 나가 슬롯 대기가 0이고, 6일부터 두 바퀴째가 생겨 대기가 붙는다(1절)
  2. **실행기 불변식이 성립한다** — 입장 상한 4 × 최대 5일 = Curator 작업 20 ≤ 실행기 스레드 20. 받아들인 요청만으로는 큐가 쌓이지 않아 CallerRuns 가 발동할 수 없다(2절)
- 단일 요청의 **35초 예산은 근거가 아니었다.** 7일도 최대 27.9초로 예산 안에 끝났다. 상한을 예산에서 유도했다고 쓰면 사실과 다르다

## 1. 일수별 단일 요청 지연

`AiCourseLatencyBaselineTest`에 일수 손잡이(`LATENCY_BASELINE_TRIP_DAYS`)를 더해 같은 입력 10건(공유 입력 세트 13~22번: 강릉·순천·영주·공주, 유명 1곳과 무명 3곳)을 일수만 바꿔 순차로 돌렸다. 운영값(예산 35초, LLM 상한 20초, 동시 호출 5, 실행기 20)이고, 요청 사이 5초를 쉬어 요청끼리 경합하지 않는다. 같은 날 14:35~14:55 연속 측정.

| 일수 | Curator 호출 | 요청 p50 | 요청 max | Curator 단계 p50 | Curator 슬롯 대기(요청별 합) p50 | 폴백 칸 |
|---|---|---|---|---|---|---|
| 3 | 3 | 15.2초 | 19.4초 | 8.2초 | 0 | 0 / 180 |
| **5** | **5** | **17.5초** | **22.5초** | **7.7초** | **0** | 2 / 300 |
| 6 | 6 | 22.7초 | 26.5초 | 11.3초 | **4.6초** (10건 모두) | 0 / 360 |
| 7 | 7 | 25.3초 | 27.9초 | 13.1초 | **11.3초** (10건 모두) | 1 / 420 |

- **5 → 6 에서 꺾인다.** 5일까지는 Curator 단계 시간이 3일과 같다(8.2 → 7.7초) — day 가 늘어도 슬롯 5개에 한 번에 들어가 병렬로 끝나기 때문이다. 6일부터는 6번째 Curator 가 앞의 호출이 끝나길 기다려 단계 시간이 +3.6초, 7일은 +5.4초 늘었다
- 3 → 5 의 요청 지연 증가(+2.3초)는 Curator 가 아니라 Planner(5.1 → 7.5초, 일정이 길어 출력이 늘었다)와 후보 수집(0.8 → 1.8초)에서 왔다
- 폴백은 일수와 무관하게 0~2칸이다. 혼자 들어온 요청에는 품질 문제가 없다
- **이 표는 경합이 없는 조건이다.** 동시 요청이 슬롯 5개를 나눠 쓰면 6일 이상의 두 바퀴째는 더 길어진다. 경합 아래의 지연은 #200(일수를 섞은 부하 측정)에서 다룬다

## 2. 실행기 불변식 — 받아들인 요청만으로 CallerRuns 가 발동하지 않는다

```
입장 상한 4 × 최대 일수 5 = Curator 작업 20  ≤  aiAgentExecutor 스레드 20 (슬롯 5 × 4)
```

- 요청 하나가 실행기에 **동시에** 올리는 작업은 Curator 의 day 수가 최대다. Planner 는 Curator 보다 먼저 끝난다
- `ThreadPoolExecutor`는 스레드가 모두 바쁠 때 큐에 쌓고, 큐가 다 차야 거절 정책(CallerRuns)을 부른다. 받아들인 요청의 작업이 스레드 수 안에 들어가면 큐조차 쌓이지 않는다
- 상한이 없던 때와 비교: 30일 요청 4건이면 작업 120개 > 스레드 20 + 큐 50 = 70 → CallerRuns. 6일만 돼도 4 × 6 = 24 > 20 으로 큐가 쓰이기 시작한다
- 예외: 예산이 지나 포기된 요청의 작업(좀비)은 입장 자리를 돌려준 뒤에도 실행기에 남을 수 있다. 이 몫은 큐(50)가 받는다
- `AiExecutorCapacityInvariantTest`가 `application.yml`의 두 값과 `MAX_TRIP_DAYS`로 이 부등식을 고정한다. 슬롯·입장 상한·일수 상한 중 하나만 바꾸면 깨져 나머지를 함께 보게 한다
- **후속(#200)**: 입장이 LLM 작업 자리 단위(총량 16, 요청마다 `1 + 일수`)로 바뀌어 이 부등식은 "총량 16 ≤ 스레드 20"이 됐다. 자리가 호출 종료 시 돌아오므로 위의 예외(좀비 작업)도 부등식 안에 든다 — [ai-admission-day-weight](../ai-admission-day-weight/README.md) 4-3절

## 3. 상한 값의 선택

| 후보 | 단일 요청 | 실행기 불변식 (입장 4 기준) | 판단 |
|---|---|---|---|
| 3 | 15초, 대기 0 | 12 ≤ 20 | 너무 짧다 — 2박 3일이 끝이라 서비스 용도(국내 여행)를 많이 자른다 |
| **5** | **18초, 대기 0** | **20 ≤ 20** | **채택** — 슬롯이 한 바퀴에 끝나는 가장 긴 일정 |
| 6 | 23초, 대기 4.6초 | 24 > 20 | 입장 상한을 3으로 내려야 불변식이 선다 |
| 7 | 25초, 대기 11초 | 28 > 20 | 같은 이유 + 두 바퀴째 대기가 예산 여유를 먹는다 |

- 국내 여행 코스 앱이라 4박 5일이면 대부분의 일정을 덮는다고 봤다. 6일 이상이 필요하면 슬롯을 늘리거나 입장 상한을 낮추는 결정과 함께 바꾼다
- 비용: 5일 코스는 LLM 호출 6회로 3일(4회)의 1.5배다. 토큰은 일수에 비례한다
